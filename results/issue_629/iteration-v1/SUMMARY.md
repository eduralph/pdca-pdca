# Advisory code review — issue 629 (hold `Conflicts with` partner of an unpushed bundle)

Lens: bugs the patch adds, and reuse / simpler / cheaper options. Advisory only.

The core change is correct. `_runnable` reuses `waves.conflict_map` as the brief asked; it does not re-read the briefs itself. `bundles` really is the live drive set: it is a local list that adoption grows and shrinks in place (`template/src/pdca_harness/flow.py:1702`, `:1721`). So rebuilding the map each wave (`flow.py:2186`) does pick up adopted split children. The C4 red leg fails on the right assertion (`issue_702` was built), and the T3 suite is green (2371 tests).

- NEEDS-HUMAN [impl] — The held line's advice leads straight back to the bug. `template/src/pdca_harness/flow.py:778-781` tells the operator to "publish them (`pdca publish <id>` …), then re-run." After CA is published by hand, a re-run does not put CA on the line for CJ. If CA is not named again, `waves.conflict_map` drops the edge because CA is outside the batch (`waves.py:136-153`). If CA is named again, the pre-wave carry only acts for a plain `Depends on` (`flow.py:892-893`, `:910-914`), never a `Conflicts with`. Either way CJ is built on a base without CA: the same collision this fix prevents. The brief keeps finished-id partners out of scope, so the honest advice is to wait until CA's PR merges into the base, then re-run. That is the "wait … until their PR merges" shape of the unmerged-prerequisite line at `flow.py:766-772`. This is a one-string fix, and a test assertion on the advice text would pin it.
- Minor, not blocking: a bundle that declares both `Depends on: X` and `Conflicts with: X` against the same unpushed X now gets two stderr lines for one cause. One is the old "skipped — prerequisite(s) not ready (X)" line (`flow.py:773-775`, through the `held` branch at `:762-765`). The other is the new "held — it `Conflicts with` …" line (`flow.py:776-781`). It is only noise, and the bundle is still held exactly once. Skipping the partner line when `p` is already in `unmet` would remove it.
- Minor, not blocking: the guard is done twice. The caller passes `conflicts=None` when `held_unpushed` is empty (`flow.py:2186-2187`), and `_runnable` checks `if conflicts and unpushed_set` again (`flow.py:727-728`). This is harmless and cheap (`conflict_map` reads each brief once per wave, and only after a hold). Either check alone would do.
- Test gap, not blocking: `template/tests/test_flow_conflict_partner_hold.py` does not test the "live `bundles`" requirement from the brief's Scope: an adopted split child whose `Conflicts with` edge points at an unpushed bundle. The code handles it (see above), but nothing pins it if someone later hoists the `conflict_map` call out of the wave loop.

No resource leaks, concurrency problems or API misuse found in the diff. The two docs edits (`docs/07-crosscutting.md:672-675`, `template/PCDA/quality-cycle/09-parallel-lanes.md:69`) match the code's behaviour.
