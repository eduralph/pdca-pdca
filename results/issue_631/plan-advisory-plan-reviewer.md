# Plan review — issue 631 / fold-starts-from-a-clean-integration-tree

I tried to fault the root cause, the line citations, the targets and the scope. They hold up. On the target source, `_prepare_worktree` reuses an existing tree as it is (`template/src/pdca_harness/integrate.py:625-628`). `fold` goes straight to `checkout -B` (`integrate.py:431`) and then `_merge` (`integrate.py:588`). `merge --abort`'s return code is thrown away (`integrate.py:594`). The re-gate runs in that same tree (`flow.py:816-819`, `gates.py:261`). The docs claim a reset that does not happen (`template/pdca.toml.jinja:216-217`, `sweep.py:18-19`). The brief also matches the issue's "Done when" ("resets and cleans the integration worktree … before `checkout -B` … A test runs a re-gate that writes an untracked file, then a continuing fold, and the fold succeeds"). The fixture the brief names exists, and its `_publish(..., cut_from=...)` (`template/tests/test_integrate_stack_bases.py:142`) supports criterion (2)'s "B cut from the line at t1". The findings:

- NEEDS-HUMAN — **Criterion (3) cannot go red in the default mode.** The brief says: "the fold raises `IntegrationError` instead of going on to merge another bundle into that tree, in the default mode and in the carry's `skipped` mode … Pre-fix … (3) continues." That is true only for `skipped` mode. In the default mode (`skipped is None`), any non-zero `_merge` makes `_merge_published` raise. It raises at `integrate.py:477-485`, and `fold` re-raises at `integrate.py:437-438`, whether or not the abort worked. So in the default mode the fold already raises `IntegrationError` before the patch. The default-mode leg is green before the patch and proves nothing, and the C4 revert-the-fix gate cannot show RED for it. The planner should do one of two things. Option A: limit the RED claim for (3) to `skipped` mode. Option B: state the real default-mode effect of a failed abort and test that. That effect is a mid-merge tree (`MERGE_HEAD` left in place) that the *next* fold inherits, and the reset-before-fold half of the fix is what covers it.

- NEEDS-HUMAN — **Raising on a failed abort in `skipped` mode changes what the carry does, and the brief does not say so.** `skipped` exists so the #646 carry keeps going past a bundle that fails (`integrate.py:436-439`: "this bundle only; the merge was aborted"). Criterion (3) makes a failed abort stop the whole carry, so every later bundle in that carry is lost too. A `reset --hard HEAD` after a failed abort would also undo the half-done merge and keep the carry going. The brief picks "raise" and does not weigh the other option or say who decided it. That is a design decision for a human to make at sign-off, not something to settle in the test.

- NEEDS-HUMAN — **The scope does not say which clean is required, and that affects the tests and other behaviour.** The scope says "start from a tree that holds exactly its start ref". The issue suggests "`git reset --hard` + `git clean -fdx`, or equivalent" or "the re-gate runs in a separate tree", but the brief does not pick one. Criterion (1) uses an untracked file that is *not* gitignored. A `git clean -fd` without `-x` would therefore pass (1) yet still leave ignored build output behind. That output can also block a merge when a later branch commits a path the base ignores, and then the brief's invariant ("Nothing left … can change what a fold does") is not met. If the invariant is meant to include ignored files, the brief should name `-x` or add a test case with a `.gitignore`d leftover. If it is not, the invariant should say ignored files are excluded.

- NEEDS-HUMAN — **"crashed fold or carry" is in the invariant but no criterion tests it.** The invariant lists "an aborted or failed merge, a crashed fold or carry". Criteria (1)-(3) only cover leftovers from the re-gate and a failed abort inside a single fold. The case the invariant's self-test leans on ("an aborted merge or a crashed carry leaves the same state") has no red→green test: a fold that starts in a tree left mid-merge (`MERGE_HEAD` present) by an earlier fold. A cheap fix is to add a test that starts a fold in a tree with a merge left in progress. Without one, Check can only accept the "every user" claim on trust.
