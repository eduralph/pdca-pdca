- **Slug:** fold-starts-from-a-clean-integration-tree
- **Defect:** One integration worktree per target is reused by every fold of a run, by the #646 pre-wave carry, and by the optional between-waves re-gate (`[driver].regate_between_waves`). `integrate._prepare_worktree` (`template/src/pdca_harness/integrate.py:618-628`) only creates the tree when it is missing and otherwise reuses it as it is. `fold` then runs `git checkout -B <line> <start_ref>` (`integrate.py:431`) and `git merge` of each published branch (`_merge`, `integrate.py:583-595`). Nothing resets or cleans the tree in between. The re-gate runs the repo-scoped gates with that tree as cwd (`gates.run_integration`, `template/src/pdca_harness/gates.py:235-261`, called from `flow._fold_lines`, `template/src/pdca_harness/flow.py:816-819`). Build output it leaves (an untracked file a later branch adds, a modified tracked file) makes the next fold's `checkout -B` or `git merge` refuse, and the run stops with "did not integrate". Round 4 of #593 fixed only the message (`integrate.py:477-485`), not the cause. `_merge` also ignores the return code of `git merge --abort` (`integrate.py:594`), so a failed abort leaves a mid-merge tree that the carry's per-bundle `skipped` mode (`integrate.py:433-439`) merges the next bundle into. The template's own docs already claim the reset happens: "each fold resets its tree to a freshly fetched ref" (`template/pdca.toml.jinja:216`, `template/src/pdca_harness/sweep.py:18`).
- **Success criterion:** With the patch, on a real-git fixture (bare `origin`, published bundle branches, as in `template/tests/test_integrate_stack_bases.py`'s `StackFoldGit`):
  (1) **Leftover untracked output.** Fold [A] at `folded_this_run={}`. Then run `gates.run_integration(cfg, wt)` on the fold's worktree, with a repo-scoped gate whose command writes `out/build.txt` (untracked). Then fold [A, B] at `folded_this_run={TARGET: t1}`, where B's published branch adds `out/build.txt`. The second fold succeeds, and the line tip's `out/build.txt` holds B's content (not the gate's).
  (2) **Leftover modified tracked file.** The same, with the gate overwriting a tracked file that the next branch changes: A adds `a.txt`, the gate rewrites `a.txt` in the tree, and B's branch is cut from the line at `t1` and changes `a.txt`. The next fold succeeds, and the line tip's `a.txt` is B's committed content. (A dirty file the next merge does not touch does not make git refuse, so it would not show the defect.)
  (3) **A failed abort is not ignored (carry's `skipped` mode).** Fold [X, B] with `skipped={}`, where X's merge conflicts with the line and `git merge --abort` fails (`integrate._git` patched to fail only for `merge --abort`, so the tree is really left mid-merge). The fold puts the tree back to the line tip it had before X's merge (e.g. `git reset --hard` to it, which also drops `MERGE_HEAD`), records X in `skipped`, and then merges B: B is on the pushed line and not in `skipped`. Only if that reset also fails does the fold raise `IntegrationError`. This keeps the carry's contract, "this bundle only; the merge was aborted" (`integrate.py:436-439`), true.
  (4) **A fold starts clean from a tree left mid-merge.** Leave the worktree mid-merge (`MERGE_HEAD` present: start a conflicting `git merge` in it and do not abort), as a crashed fold or carry, or the default mode's failed abort, would leave it. The next fold [A, B] at `folded_this_run={TARGET: t1}` succeeds and the line holds B.
  Pre-fix, (1), (2) and (4) raise `IntegrationError` ("could not merge … `git merge` exited …" or "could not start …"), and in (3) B lands in `skipped` because git refuses to merge into a tree with `MERGE_HEAD`. That is the RED. In the default mode (no `skipped`) a failed merge already raises before and after the patch (`integrate.py:437-438`, `:477-485`), so there is no default-mode leg for (3); the default mode's real exposure is the mid-merge tree it leaves for the NEXT fold, which (4) covers.
- **Falsifiability:** RED is reachable offline with real git and no host: `gates.run_integration` runs a shell command from the given tree (`template/tests/test_regate.py:55-62` shows a gate running in a given worktree), and git refuses a merge that would overwrite an untracked file. The C4 gate reverts the production hunks and keeps the test, so the red leg runs on the same fixture.
- **Invariant to restore:** A fold's result depends only on the ref it starts from and the branches it merges. Nothing left in the shared integration worktree by an earlier user of it (a re-gate's build output, an aborted or failed merge, a crashed fold or carry) can change what a fold does or make it refuse. Ignored files (per the tree's `.gitignore`) are outside this: git overwrites an ignored file on checkout and merge without refusing (checked with git on 2026-10-10: a merge bringing a committed `out/x` over an ignored leftover `out/x` succeeds and takes the branch's content), so they cannot change a fold's result, and keeping them lets the re-gate reuse its build caches. Source: the harness's own stated contract for that tree, `template/pdca.toml.jinja:216` / `sweep.py:18` ("each fold resets its tree to a freshly fetched ref"), and the fold's append-only contract, `integrate.py:30-34`. Self-test: guarding only the re-gate would not satisfy it (an aborted merge or a crashed carry leaves the same state), so the property is stated over the tree's every user.
