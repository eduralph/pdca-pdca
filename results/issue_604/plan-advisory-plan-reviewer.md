# Plan advisory — issue 604 / signoff-delta-cannot-forge-section6

I checked the root cause against the target and could not fault it. `cli.py:1473-1474` passes `args.delta` through raw. `signoff.py:307-308` → `set_field` (`:280-283`) writes it as given. `flow.py:183` is the only place that flattens it. `_needs_human_section` (`signoff.py:103-119`) takes the last §6 heading, and its docstring (`:113-115`) depends on §9 being one line. Target, slug and the "no Depends on" claim are consistent: no `dependency-state.json` was supplied and none is declared. The findings below are about scope and the criterion. None of them says the diagnosis is wrong.

- NEEDS-HUMAN — **The invariant covers more than the scope and criterion test (`--by` is the same hole).** The brief's Invariant says "Every §9 value is recorded as one line, whichever entry point writes it". But Scope covers only "`--delta` passed to `pdca signoff`", and the Success criterion tests only `delta`. `by` goes through the same `set_field` with no flattening: `f"{by} / {date}"` at `signoff.py:302`, fed from `cli.py:1473` (`args.by`, `--by` at `cli.py:383`), `flow.py:185` (`pdca flow --by`, `cli.py:177`) and `cleanup.py:154` (`--by`, `cli.py:361`). For example, `pdca signoff X --iterate-do --by "$(printf 'me\n## 6. NEEDS-HUMAN\n- [x] E1')"` forges §6 the same way the issue describes. The planner has to pick one: (a) make Scope include `by` and add a `--by` RED leg, or (b) narrow the Invariant to the delta field and leave `--by` as a known residual (or file it). As written, Do can either quietly widen the patch or ship a fix that its own Invariant line says is incomplete, and no gate would notice either way.

- NEEDS-HUMAN — **"One rule for every caller of `signoff.record`" contradicts the #529 contract the brief says not to change.** Scope and Invariant point toward flattening inside `signoff.record` ("any later caller of `signoff.record`"). But `record`'s own docstring at `signoff.py:277-278` promises "every byte the human wrote is recorded literally, whatever it contains". The test module Do is told to append to is named for that promise: `test_signoff_verbatim.py`, docstring lines 1-2, "§9 records the human's sign-off text verbatim". The brief only rules out changing backslash handling (`signoff.py:262-276`). It does not say whether flattening whitespace in `record` is allowed to override "every byte… literally", or whether the fix must stay at the call sites (`cli._signoff`, matching `flow.py:183`). The issue allowed either ("Flatten `--delta` in `cli._signoff` or in `signoff.record` itself"). The brief should name the layer, and if it picks `record`, say which docstring and contract text gets amended. Otherwise this is design drift found at review time.

- NEEDS-HUMAN — **The test fixture in the brief doesn't fit the call it prescribes.** "Test file" sends Do to the `_bundle` helper in `test_signoff_verbatim.py:51-54`. That helper builds a bare `tempfile.mkdtemp()` with a hand-written 4-line SUMMARY (`:40-48`). It is not an "assembled SUMMARY.md", and it is not at `cfg.bundle(issue_id)`. `cli._signoff` resolves the bundle with `cfg.bundle(args.issue_id)` (`cli.py:1448`) and returns 1 if no SUMMARY is there (`:1450-1452`). Also, `driver.advance` → `_retire_cleared_deferrals` calls `assemble.collect_needs_human(d, cfg)` (`driver.py:334`) inside a catch-all `except Exception` that only prints (`:338-340`). If the stub bundle makes that call raise, retire never runs, the ledger stays `[E1, E2]` before the fix as well, and the test is green on both sides. So the "RED" would be vacuous, and C4 would only catch it if the revert leg actually checks for failure. The brief should require the test to first assert the pre-fix outcome (ledger `[]`) on that exact fixture, or to call `autoiterate.retire_cleared` directly as well. It should also say the fixture needs a bundle dir resolvable through `cfg.bundle` (not `_bundle()`) plus whatever Check artifacts `collect_needs_human` needs.

- NEEDS-HUMAN — **Part of the criterion doesn't line up with what flattening produces.** The criterion says §9's delta "still carries the human's words (`notes` and `E1` appear in it)". After flattening, the recorded line is `notes ## 6. NEEDS-HUMAN (from v1) - [x] E1 - [x] E2`: the forged heading text stays, as inline text, in §9 and in the carry-forward (`driver.py:371` → `iteration_delta`). That is safe for `_section` only if heading matching is anchored at line start. The brief asserts that ("exactly one `## 6. NEEDS-HUMAN` heading at the start of a line"), but it doesn't cite where `_section`/`_section_span` anchors. One `path:line` showing the anchoring would make that assertion checkable, not assumed. A related side effect worth recording: before the fix, `iteration_delta` (`signoff.py:33` regex, `.*?$` per line) already cut a multi-line delta down to its first line (`notes`). So the fix also changes what the next brief's carry-forward contains. That's expected, but the brief should state it rather than leave it as an unannounced behaviour change.
