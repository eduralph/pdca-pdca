# Plan review — issue 652 / carry-not-clean-cascades-across-finished-ids

The root cause holds up against the target source. `_finished_head` (`flow.py:836-857`) judges one id at a time. `dependents` is built only from drive-set bundles (`flow.py:892-897`). The carry folds every clean id of the target (`flow.py:927-933`), and nothing looks at the edges between finished ids. The thread's proposed fix matches the brief's Scope. Criteria (1)–(3) can be checked offline with real git, and the cited fixture helpers exist (`test_flow_resume_stack_prereqs.py:61,80,123,151-162,176,226`; `test_integrate_stack_bases.py:142-159`). These are the faults I found:

- NEEDS-HUMAN — **The invariant is wider than the criterion, and a fold-time "not clean" is not covered.** The brief's invariant says "The pre-wave carry never puts onto the line work it has judged not clean, directly or through another finished bundle's branch". The criterion only spreads "not clean" from the PR-state judgment that runs before the fold (`_finished_head`, `flow.py:913-920`). An id can also become not clean *during* the fold. `integrate.fold` with `skipped` records a merge failure for one bundle "and the next bundle is merged" (`integrate.py:334-336`, `:433-439`). The carry then adds it to `why` after the fold (`flow.py:937-938`). So a finished `P` that is state-clean but skipped at fold time (a conflict, as in `test_of_two_conflicting_prerequisites…`, `:246`), followed in the same fold by a finished `Q` with `Depends on: P` whose branch contains `P`, still puts `P`'s commits on the line. A fix that only spreads the pre-fold `why` before line 927 meets criteria (1)–(3) and still breaks the stated invariant. The planner should either narrow the invariant to "judged not clean before the fold" and list the fold-time case as out of scope, or add a criterion: a `P` skipped at fold time means `Q` is not folded. Doing that means pruning dependents during the fold or re-folding without them, which is a larger change.
- NEEDS-HUMAN — **The fix contradicts the documented contract the brief cites, and no doc update is in scope.** The brief draws its invariant from `docs/07-crosscutting.md:686-691`. The second sentence there says "A finished prerequisite that is not clean holds **only** the bundles whose plain `Depends on` names it". The `_carry_finished` docstring says the same: "Any other finished id goes into `held`, so only its plain `Depends on` dependents wait" (`flow.py:883-885`). After the fix, a closed `P` also holds `Q`'s dependents, so both texts become wrong. Yet the brief cites both as the source of the invariant. Scope and Citations do not list updating either one. Either add the doc and docstring edits to Scope as one clause, or a reviewer will flag them as drift (or as an unplanned change) during Check.
- NEEDS-HUMAN — **#624 is closed as a duplicate while its literal shape is explicitly left out.** The thread describes #624 as "the hold of an **unpublished** bundle doesn't cascade through a pre-run COMPLETE dependent". Criterion (2) swaps in "`U` finished with its PR CLOSED". The brief's Scope then excludes "a drive-set bundle whose own push fails mid-run … the rare residual of #624, not briefed". There is no `sources/` directory in this bundle, so I could not check #624's own thread or the human's Plan decision against the brief. If #624 is closed as a duplicate of this bundle, that residual has no tracker item left. Before #624 closes, the human should confirm the residual is acceptable or file a follow-up for it.
- NEEDS-HUMAN — **The 652 → 653 ordering is stated in prose but not declared.** The Ordering note says "Separate waves: 652 first, and 653 builds on it". The brief declares only `Conflicts with: 653`, which separates the two into different waves but does not set their order. There is no `dependency-state.json` here, so I could not check whether 653's brief declares `Depends on: 652` / `Stacks on: 652`. If it doesn't, the "652 first" order is not enforced by anything.
- NEEDS-HUMAN — **The hint for a cascaded hold is not specified.** Criterion (1) requires that the held line "names `issue_P` as the cause", but the brief does not say which `_CARRY_HINTS` entry (`flow.py:860-866`) `Q`'s line uses. The existing hints are worded for the id itself. For example, `"open"` says "get {name}'s PR open", which would tell the operator to reopen `Q`'s PR, but `Q`'s PR is already OPEN. The useful action is to fix `P`, or to remove `Q`'s `Depends on: P` edge. The brief should state the expected advice, or a hint key, so that the line's wording can be checked rather than left to Do.
