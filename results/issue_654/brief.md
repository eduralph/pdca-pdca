## Motivation

A re-issued stack run continues the line an earlier run left on origin (#646). The line keeps the base it was cut from (docs/07-crosscutting.md:843-846: "the line does not follow the base"). After a long gap, dependents build on an old `main`. Since #655 it is worse: a dependent whose prerequisite merged into the base after the line was cut is *held*, and the only way out is "delete {branch} on origin, then re-run" (flow.py:850). That throws away the line's fold history and asks the operator to delete a remote branch by hand. The owner's comment asks for "a built-in way to restart a stale line from the current base, or a `pdca` command that deletes it". This brief reads "restart from the current base" as a merge-refresh, which keeps the line's fold history, and defers the delete command (B), which the owner also named as acceptable. That reading is the planner's, not the owner's: the maintainer confirms A over B (or both) at sign-off.

## Design

**Recommended (option A — refresh by merge).** When the pre-wave carry continues a line found on origin, merge the current `<base_remote>/<base>` into the line before wave 0 builds on it:

- Append-only: one merge commit on top of the line tip, pushed without force, under the same lock the carry and the first fold already hold. The line's previous tip stays an ancestor. Open PRs cut from the line are untouched; their branches simply lack the newest base until "Update branch", as today.
- A line that already contains the base tip needs nothing (no empty merge).
- Same safety checks the gone-branch path uses: a textual conflict, or a base merge that would remove work a bundle put on the line (`_undone_paths`, #623), resets the line to the tip it had and holds the dependents that would build on it, each named with the line, the base and the files. The run goes on; it does not stop.
- After a successful refresh the #655 check (`_line_lacks_merge`) finds the prerequisite's merge on the line, so the dependent builds.

## Alternatives considered

- **B — a `pdca` command that deletes a stale line** (`pdca line reset <base>` or similar). Removes the hand-typed `git push --delete`, but still throws away fold history and still needs an operator step. Could be added later as an escape hatch; not needed if A lands.
- **C — keep the behaviour, document it as a known limit** (the issue's second option). Cheapest, but #655 turned a stale base into a hold, so the cost is now a stopped dependent, not just an older base.
- **Rebase the line onto the new base.** Rewrites history every open stack PR was cut from; violates the append-only rule (#593). Rejected.

## Impact & compatibility

- Re-issued stack runs whose line is behind the base now push one extra merge commit to the line before wave 0. Runs whose line is current see no change.
- The "Update branch" advice for open stack PRs (docs/07-crosscutting.md:658-661) is unchanged.
- No config or brief-field change; no `copier.yml` change.

## Open questions

- Should the refresh happen whenever a line is continued, or only when a dependent would otherwise be held by #655? Recommended: whenever it is continued (simpler, and a dependent built on a stale base is the original complaint even without a hold). Because a failed refresh falls back to today's behaviour, it adds no new holds. Maintainer to confirm at sign-off, along with A vs B.
