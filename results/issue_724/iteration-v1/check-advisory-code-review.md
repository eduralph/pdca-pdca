# Advisory code review — issue_724 (dependency-scoped stack bases)

Lens: bugs the patch introduces, plus reuse/simplification. Advisory only. Line numbers are on the patched tree at `$PDCA_TARGET`.

Overall: the production change is small and reads correctly. `_bundle_bases` reuses `integrate._fold_candidates` and #723's `build_bundle_base` and does not copy their logic. Members are filtered out of `excluded` inside `build_bundle_base` (`integrate.py:797-799`), so passing `heads` as both `carried` and `excluded` is safe. Gone branches (head `None`) are dropped from `carry_heads` and handled by `_gone_branch`. An empty `carried` map makes `fold` record heads without checking any (`integrate.py:515`, `:705`), as the new docstring says. Member order (carried first, then accepted in wave order) is kept, because `_fold_candidates` keeps input order (`integrate.py:237`). I found no blocking bug. Three smaller points:

- NEEDS-HUMAN [impl] — `template/src/pdca_harness/flow.py:879-884`: `_closure` keeps walking through a bundle that is in the closure but was never built. Example: E `Conflicts with` A, A (earlier wave) `Depends on` Q, and A then fails or is DISCONTINUED. A is not accepted, so it is not a member. Its own prerequisite Q is still reached, so E's base gets Q's work even though E declared no edge to Q. `_runnable` does not hold E for this, because a `Conflicts with` partner that never completed is not an unmet prerequisite. The docstring's reason for walking transitively ("a member's branch was cut from a base holding ITS closure") only holds for members that have a branch. The brief's Invariant limits the base to bundles "that this run built or carried". Possible fix: only walk on from a node that is a candidate member, or from a plain `Depends on` / `Stacks on` edge, which `_runnable` would already have held. No test covers this case.
- NEEDS-HUMAN [impl] — `template/tests/test_integrate_carried_rewrite_late.py:267` and `:297`: the tests changed their input, not just how they restate the base. The rewrite and fetch-failure trigger moved from the line's push to B's own base push (`args[-1] != line`). The new premise is sound: B's base is now the last thing that reads `fix/A`. But brief criterion (10) allows input changes only where an "X is built on Y" premise needs a declared edge. Also, the original case (a rewrite racing the line fold's own push) is no longer covered in this file. Check that `build-notes.md` names this change. If it doesn't, either name it there or add a case that keeps the line-push race.
- `template/src/pdca_harness/flow.py:2599` with `:2742`: a base-build failure sets `line_stopped = True`, so the end-of-run late-rewrite check (`_report_late_rewrites`) is skipped. That skip was written for a stopped line *fold*, which has already reported its refused rewrite. A base-build stop for another reason (for example the foreign-ancestry refusal in case (7)) now also hides a late rewrite of some other branch an earlier fold carried. The run still exits non-zero (wave k stays PLANNED), so the impact is limited to a missing diagnostic line. This is minor and I'm not escalating it. A separate flag, or not setting `line_stopped` here, would keep the report.

Reuse / efficiency: nothing to file. `waves.conflict_map` and the `waves_of` / `paths` maps are rebuilt once per wave (`_bundle_bases`), which costs little next to the git work. One worktree fetch and push per dependent that has a non-empty closure is what the design requires (one base branch per bundle). Removing `_line_lacks_merge` and `merged.merge_and_head` leaves no dangling callers.
