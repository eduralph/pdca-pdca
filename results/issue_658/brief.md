- **Slug:** merge-mode-never-merges-an-onto-branch-pr
- **Defect:** Under `[driver].wave_mode = "merge"`, merge mode readies and merges a pull request the run did not open. A bundle whose brief has an `Onto branch` field is published by `publish._publish_stacked`, which adds one commit to an EXISTING open PR (possibly someone else's, with any base) and records that PR in `publish.json` with `"mode": "stacked"` (`template/src/pdca_harness/publish.py:549`). `publish.publish` dispatches to `_publish_stacked` at `publish.py:225-228`, before the merge-mode base guard from #411 (`_merge_base_refusal`, called at `publish.py:294`, defined at `:761`), so that guard never sees it. Then, for a non-final wave, `flow` calls `merge.merge_wave` (`template/src/pdca_harness/flow.py:2317-2318`), and `merge._merge_one` (`template/src/pdca_harness/merge.py:453`) reads `pr_url` from the record (`merge.py:463`), runs `gh pr ready` on it (`merge.py:493-494`), and then `gh pr merge` into whatever base that PR has. `merge.py` never looks at the record's `mode`. An unattended run can therefore merge a pre-existing PR, with everything else on it, without anyone approving that. The rest of the harness already refuses to trust such a record: the fold treats an `Onto branch` record as possibly merged into another base (`template/src/pdca_harness/integrate.py:555-556`, `_gone_branch`), and `merged.merged_into` never counts one as merged (`template/src/pdca_harness/merged.py:104-110`).
- **Success criterion:** With the patch, merge mode never readies or merges the PR behind a `"stacked"` publish record, and says why. Concretely, driving `merge.merge_wave(cfg, [b], dry_run=False, method="merge")` (the call `flow.py:2318` makes for a non-final merge-mode wave) on a bundle `b` that is COMPLETE, has a non-empty `patch.diff`, and has `publish.json` = `{"mode": "stacked", "branch": "feat", "base": "other/feat", "pr_url": "<url>", "repo": "org/repo"}`, with `subprocess.run` in `merge` recorded by a stub:
  (1) no `gh pr ready <url>`, no `gh pr ready <url> --undo`, no `gh pr update-branch`, and no `gh pr merge` call is made, and `merge_wave` returns non-zero (the wave stops, so `flow` prints its existing "wave k did not merge; STOPPING" line);
  (2) stderr names the bundle (`issue_<id>`), the PR URL, and says the bundle is an `Onto branch` commit on an existing PR that merge mode does not ready or merge, and what the operator can do instead: run the batch in the default `wave_mode = "stack"`, or take the bundle out of this merge-mode batch. The message must NOT suggest merging that PR by hand as a way to unblock the run: by criterion (3) a hand-merged `"stacked"` PR is still refused, so a re-run would stop the same way. (It may say the PR itself is the human's to ready or merge, as long as it says that does not let this merge-mode run continue.);
  (3) the same holds when the PR already reads `MERGED` (`merged.is_merged` patched to return `True`): the record is still refused, not skipped as "already merged" (consistent with `merged.merged_into`, `merged.py:104-110`);
  (4) with `dry_run=True` the plan prints no `gh pr merge … <url>` line for that bundle and `merge_wave` returns non-zero. Why this matters, stated accurately: a dry-run publish of an `Onto branch` bundle writes no `publish.json` (`_publish_stacked`'s dry-run branch, `publish.py:496-509`, returns before the write at `:556`; the stub publisher records none either, `integrate.py:340`), so a fresh offline rehearse of an `Onto branch` bundle already stops at the "no recorded PR" check (`merge.py:465-468`). This branch is reached by a dry run over a `"stacked"` record left on disk by an earlier real publish; such a dry run must not print a merge plan for it;
  (5) a bundle whose record is `"new-pr"` (or has no `mode`) is merged exactly as today: the existing `template/tests/test_merge.py` cases and the `new-pr` cases of `template/tests/test_merge_third_remote.py` pass unchanged.
  Pre-fix, (1) fails (`gh pr ready <url>` is called), and (3) returns 0 without a refusal. That is the RED.
- **Falsifiability:** RED is reachable offline in-process: `test_merge.py`'s `MergeWave` cases already stub `pdca_harness.merge.subprocess.run` and `merge.state.state`, and today a `"stacked"` record goes straight to `gh pr ready` (`merge.py:493-494`). No host, no network, no `gh` needed. The C4 gate (`engine/scripts/run-verify.sh`) reverts the production hunks and keeps the tests, so the red leg runs the new test against today's `merge.py`. The new test must import only modules (e.g. `from pdca_harness import merge, state`), never a symbol the fix adds, so with the fix reverted the file still loads and fails on its assertions (a load failure is reported as UNVERIFIABLE, not red).
- **Invariant to restore:** The driver only readies or merges a pull request this run opened for the bundle (a `"new-pr"` / `"stacked-pr"` record), never a PR the bundle only added a commit to. Merge mode must make the same judgement about an `Onto branch` record that the fold (`integrate._gone_branch`, `integrate.py:555-556`) and `merged.merged_into` (`merged.py:104-110`) already make. Source: the harness's STOP discipline (CLAUDE.md: a PR is marked ready or merged only on the human's say-so; merge mode is the one opt-in exception, for the run's own PRs, `merge.py:1-16`) and the #411 guard's stated purpose (`publish.py:283-292`). Self-test: refusing only at publish would not satisfy it, because a `"stacked"` record already on disk (from a stack-mode run, or an earlier publish) still reaches `_merge_one`.
