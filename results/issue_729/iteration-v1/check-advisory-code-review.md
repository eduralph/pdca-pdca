# Advisory code review — issue #729

I found no correctness bugs. The patch does what the brief asks: `_runnable` reads the line only for a bundle that a seam keeps on it. That answer comes from #727's own `_closure_members`, through the new shared `_base_plans`, so the predicate is called, not copied. The gates agree. C4 (red before the fix, green after) shows both new own-base tests failing pre-fix with the #655 "does not have that merge" hold, and T3 runs 2593 tests OK. Below are two cleanups and one small test gap. None of them blocks.

- `template/src/pdca_harness/flow.py:2693-2696` and `template/src/pdca_harness/flow.py:1006-1007`: `_base_plans` now runs twice per wave with the same inputs. It runs once on the whole wave to get `on_line`, then again inside `_bundle_bases` on `runnable`. Nothing between the two calls changes `built`, `finished`, `bundles` or `line_cut`, and a bundle's plan depends only on that bundle (`_closure_members`, `flow.py:920-965`). So the two answers are the same today. Each call repeats `waves.conflict_map` (reads every brief), `integrate._fold_candidates` and the closure walk. A simpler shape: compute `plans` once per wave and pass it into `_bundle_bases` (which would read `plans[d.name]` for each runnable `d`). That removes the repeated work. It also guarantees the bundles `_runnable` judges on the line are exactly the ones `_bundle_bases` points at the line, which today depends on the two calls staying in step. The cost is small (it does not touch git or the host), so this is a cleanup, not a bug.
- NEEDS-HUMAN [impl] — `template/tests/test_flow_merged_prereq_dependency_base.py:59-65`: the own-base test calls `h._built_on_line()` (`template/tests/test_flow_merged_prereq_on_line.py:200`) and then asserts the same things again by hand: `base == f"{h.line}-bD"` and W's tip is an ancestor. Because the helper is called "built on line", the line `tip = h._built_on_line()   # D built; on its own base` reads as the opposite of what is checked. Either use the helper's return value and drop the repeated asserts, or skip the helper and keep the explicit asserts. The assertions themselves are correct and not weaker.
- `template/src/pdca_harness/flow.py:793-794`: the new branch has two "not on the line" cases. One is a base of its own (covered by the new tests). The other is the real base, `_closure_members` returning `[]`: a `D` with no in-batch edge, only an out-of-batch merged `P`, on a target that already has a line. No test drives the second case. It uses the same `on_line` membership test, so the risk is low. I'm noting it as a gap, not a defect.
- Checked with no problem found: `_base_plans` is now called on the whole wave before `_runnable` and outside the `IntegrationError` try (`flow.py:2756-2768`). That is safe: `_closure_members` and `publish._resolve_target` (`publish.py:594`) only read briefs and raise nothing that the old `runnable`-only call could not. When `own_bases` is false, `on_line=None` keeps the old behaviour, and the merged check is off there anyway (`hold_unmerged` is the same flag, `flow.py:2675-2679`). The 9 direct `_runnable(` callers in tests omit `on_line` and keep the old line rule. The new test file loads the on-line suite by path as a module attribute, so unittest discovery does not run `MergedPrereqOnTheLine` twice.
