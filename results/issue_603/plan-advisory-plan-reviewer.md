# Plan review — issue 603 / plan-advisory-tick-survives-iterate-do

I checked the root cause against the target source and it holds. Every cited `path:line` resolves on the target: `assemble.py:446-448` re-globs `plan-advisory-*.md`; `driver.py:460-464` archives `plan-advisory-*` only when `include_brief`; `driver.py:332-333` returns early when the ledger is empty; `autoiterate.py:366-370` says a tick on a fresh row "retires nothing"; `RetireAtTheIterate` is at `test_autoiterate.py:1486`, `_section6` at `:95`, `_Base` at `:125`. Both iterate entry points go through `driver.advance` (`flow.py:201-209` defers the iterate-do; `flow.py:516` runs `driver.advance`), so the "both entry points" claim is sound. My findings are about the success criterion and the design it leaves open:

- NEEDS-HUMAN — **The success criterion only tests round N → N+1, but the reported defect spans 3–4 rounds.** The thread's evidence is "issue_409: 5 plan findings … re-entered §6 at every one of 4 rounds". The brief's criterion only checks that a tick at round N is not open at round N+1. Suppose a fix only reads round N's SUMMARY ticks at the next iterate and does not persist them. Or suppose it drops the row from §6 at N+1, so there is nothing to re-tick at the N+1 → N+2 iterate. Either fix passes the RED→GREEN test, and the row is back open at N+2. Add a second `iterate-do` (N+1 → N+2, with no new tick) to the criterion so that persistence across rounds is what gets tested.

- NEEDS-HUMAN — **"File unchanged" in the criterion contradicts clause (ii) when a re-plan writes a byte-identical file.** The criterion and invariant tie the carried tick to "as long as the `plan-advisory-*.md` file that raised it is unchanged" / "the evidence that raised it is unchanged". Clause (ii) says a re-plan "raising the same text shows it as an open row again". A deterministic advisory gives exactly that case. The stub leaf always writes the same text (`leaves.py:4243-4248`), and that is the stub-config fixture the brief's own repro uses. A fix keyed on content hash or finding text would therefore carry the tick across iterate-plan and fail (ii), or meet (ii) only by accident. The brief should say that what resets the tick is an *event*: the iterate-plan archive (`driver.py:460-464`) and/or the plan-advisory re-run that unlinks stale artifacts (`leaves.py:4341-4342`). It should not be file identity. It should also say where the carried-tick record lives. A name matching `plan-advisory-*` is archived and unlinked at the right moments, but if it ends in `.md` it also lands in assemble's `plan-advisory-*.md` glob (`assemble.py:446-447`) and `_plan_advisory_outcomes` (`leaves.py:3917`). A name in `DOWNSTREAM_OF_BRIEF` would be archived on every iterate-do and defeat the fix.

- NEEDS-HUMAN — **The brief doesn't say how a carried row is rendered, and one plausible choice silently retires deferred-ledger entries.** The criterion only says the row must not be an open `- [ ]`. That allows either dropping the row or having assembly pre-render it as `- [x]`. The second choice is unsafe:
  - Ticks are read positively from `- [x]` rows in the assembled §6 (`signoff.cleared_needs_human`, used by `autoiterate.retire_cleared`, `autoiterate.py:355-362`).
  - A row that assembly pre-ticks then counts as a human tick at the next iterate.
  - If the same text is also a ledger entry, it retires that entry with no human action, since "a tick EQUAL to a rendered row is … a ledger entry's, which retires it" (`autoiterate.py:368-369`).
  - It also contradicts the auto-iterate contract "It never clears a §6 box" (`autoiterate.py:46`).

  The brief should pick a rendering (drop the row, or show it in a read-only non-checkbox line outside the §6 checkbox list) and rule out assembly-written `[x]`.

- NEEDS-HUMAN — **The scope covers runs with a deferred-findings ledger, but the test doesn't.** The Scope says "with or without a deferred-findings ledger present". The Repro and Falsifiability fixture has only a `plan-advisory-x.md` and no ledger. The case with a ledger is reachable: plan findings are HUMAN-kind (`assemble.py:442-445`), and `autoiterate.deferrable` excludes only IMPL and `no_verdict` items (`autoiterate.py:318-325`). So an auto-iterate round writes plan findings into the ledger. From then on, `_deferred_needs_human` (`assemble.py:571-598`) renders such a finding as an open row from the ledger whenever it is missing from this Check's fresh items. A fix that removes the ticked plan finding from `collect_needs_human` therefore brings it back through the ledger as an open `- [ ]` row unless the ledger entry is retired too. Add a ledger-present case to the criterion: the plan finding was deferred in an earlier auto round, the human ticks it, and it is not open after the next iterate-do.

- NEEDS-HUMAN — **I could not check that issue 605 exists.** `Conflicts with: 605` is a conflict, not a `Depends on`, so it can't block the run. But there is no `dependency-state.json` and the thread never mentions 605, so the ordering note ("605 builds on it") is the planner's claim alone. Confirm 605 exists and touches `assemble.collect_needs_human` before relying on the wave order.
