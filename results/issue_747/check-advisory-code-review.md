## Correctness

- `template/src/pdca_harness/integrate.py:1794-1857` (`_held_by_line`): the rule follows (a)-(e) with no second classifier. It reuses `_clash`, `_partners`, `_built_on` and `_trial`. Rule (d) comes free from `_partners` (`integrate.py:1933-1935`): a partner is only named when its trial `[its, head]` fails at index 1, so its own head has already merged cleanly onto the base. The "a line bundle left on the line is built on a partner taken off" stop (`:1840-1842`) checks `under` for every bundle in `left`, the kept prerequisite partners included. The tests at `template/tests/test_flow_cross_wave_fold_holds.py:422`, `:448` and `:555` cover those three paths. The error handling matches `_clash`: `IntegrationTreeError` and `_LineBroken` are re-raised, and any other `IntegrationError` gives None, which means a stop. That is the safe direction. No bug found.
- `template/src/pdca_harness/integrate.py:659`: dropping `kept` from the guard and moving it into a conditional `_held_by` call is right. An empty `kept` used to skip the classifier entirely; now it goes straight to `_held_by_line`. When `_held_by` returns None for the "merges onto pre + kept" case (a base taken in mid-wave), `_held_by_line` still ends in `"line"`/`"moved"` → None. The existing stop test `test_a_conflict_only_with_a_base_taken_in_mid_wave_still_stops_the_run` is unchanged and passes (T3 log).
- `template/src/pdca_harness/flow.py:1471-1476`, `:1501`: the carry now passes `carried=put` to get the heads it folded. This is safe. `put` is a fresh empty dict for each target, so `fold`'s rewrite check (`integrate.py:546`, `if carried and not dry_run`) is still skipped for the carry, and `fold` only writes into it at `integrate.py:744-745` after a successful push. It does reuse a parameter whose documented meaning is "the run's #633 record" as a plain output slot. The `_fold_lines` docstring now says so (`flow.py:1169-1172`). That is fine, but if a later change makes `fold` read `carried` before the push, the carry would start checking its own folds. A comment at the call site would help.
- `template/src/pdca_harness/integrate.py:1830-1831`: finished heads go in `on` before `took` and are filtered by `_carries` against the line HEAD as it stands now. That is the right merge order, because the carry always runs before wave 0. It also keeps a finished id out of the partner set on a target that started fresh. No issue.

## Reuse / simplification

- `template/src/pdca_harness/flow.py:1548-1553` (`_own_prereqs`): the flow reads each held bundle's brief again to split its partners into prerequisites and others. The fold already made that split (`integrate.py:1837`, `own`). The two agree as long as the brief does not change during the run. A long `pdca flow` can outlive brief edits, though, and then the fold-time line, the end-of-run line and the hold decision could disagree on which partner is "its own prerequisite". A simpler, drift-free option is to have `_held_by_line` return the prerequisite subset with the hold (or record it next to `held_out`), so the flow only formats it. This is minor and does not block.
- `template/src/pdca_harness/integrate.py:1980-2015` (`_trial(..., made=)`): an out-list parameter to get the final trial commit back works, but changing the return value would be simpler. It is small and local, and the out-list does keep every existing caller's tuple shape, so it is fine either way.
- Efficiency: on the conflict path only, each in-run fold conflict now runs `_built_on` over every bundle on the line, plus up to two `_partners` trials per bundle and up to two more for rule (e). Each trial checks out and resets the integration worktree. Before this patch the same path stopped the run, so nothing that used to pass is slower. On a large repo with a long line, one conflict could take a while. Not a defect.
