# Advisory code review — issue_747 (cross-wave fold hold)

Lens: bugs the patch introduces, plus reuse and simplification. Line numbers are on the patched tree at `$PDCA_TARGET`. The gates are green: C4 shows the new tests red before the fix and green after, and T3 ran 2616 tests OK. I found no crash, leak or ordering bug in the new code paths. `_held_by_line` keeps `IntegrationTreeError` / `_LineBroken` fatal and turns other git failures into "stop as before". The trials go through `_trial`, so the line never moves. `finished_heads` is used only to name partners: it is never merged, never put in `took`, never put in `carried`. Passing `carried=put` into the carry's fold is safe: an empty mapping skips `_carried_tips` (`integrate.py:546`) and is only filled at push (`integrate.py:744-745`).

- NEEDS-HUMAN [human] — `template/src/pdca_harness/integrate.py:1834-1844`: rule (e) is relaxed for a partner that is the held bundle's own prerequisite, and the brief does not allow this. The brief says that if any bundle left on the line was built on a partner, rule (e) fails and the run stops. The patch applies that check only to partners in `theirs` (non-prerequisites). Prerequisite partners (`pre`) are instead merged first, and then the head is merged with `wins=len(pre)` (`-X theirs`), so any clash the head has with its prerequisite counts as explained. The flip test needs this exemption: in `template/tests/test_flow_same_wave_conflict.py:368-371`, bundle 20 was built on 10 and is still on the line, and under the brief's literal rule (e) that run would stop. So case (4) of the brief and its rule (e) contradict each other, and the builder picked a resolution. A human should confirm it. It is a real widening: for a prerequisite partner, the check becomes "does the rest of the line merge on top of base + prereq + head-winning", not "does the line without the partner merge the head cleanly". child-2 (#748) refines rule (e) and should know this exemption exists.
- NEEDS-HUMAN [impl] — `template/src/pdca_harness/integrate.py:1835-1840`: only one test covers the prerequisite branch (the flip test), and it has a single prerequisite partner and no non-prerequisite partner. Two cases are untested. (i) Mixed partners, where `pre` and `theirs` are both non-empty. Then the "rest built on a partner" check sees only `theirs`, and the end-of-run line prints both a rebuild step and a `Conflicts with` proposal (`flow.py:1594-1600`). (ii) A rest bundle built on the prerequisite whose own change also clashes with the head. That case should stop, because the rest merge after head-winning fails. Add a small test for (ii) at least, so the `wins` trial is pinned.
- `template/src/pdca_harness/flow.py:1547-1552` (reuse, not blocking): `_own_prereqs` finds the bundle again with `cfg.find_bundle` and reaches into the private `integrate._prerequisites` to work out again what the fold already knew (`own` at `integrate.py:1834`). It is called once per held bundle at fold time (`flow.py:1580`) and again at the end of the run (`flow.py:1594`). The result is right, because both sides call the same function. A simpler shape: have `_held_by_line` return which partners are prerequisites as part of the hold record, so the flow does not read the brief a second time and the advice cannot drift from the fold's decision.
- `template/src/pdca_harness/integrate.py:1828-1829` (efficiency, minor): on every cross-wave `_Conflict`, `_built_on` walks the own commits of every head the fold has read (`tips` = all of `read`), even though `under` is only used for the `on` bundles. This runs only on a conflict, so the cost is small. Narrowing `tips` to the `on` bundles plus `d` is not safe without checking, because `_built_on` subtracts the commits of other bundles whose heads a tip holds. Leave it as is unless profiling says otherwise.

Nothing else found on either lens.
