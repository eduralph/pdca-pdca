# Adversarial review: issue 674 (same-wave conflict holds one bundle, not the run)

I re-ran the red→green myself on a scratch copy of the patched `template/` (git 2.53, Python 3.14), so this verdict is not provisional. Green: 5/5 pass. Red (production `flow.py` and `integrate.py` restored from `HEAD`, test kept): 2 failures and 1 error, matching `gate-logs/C4-verify.log`. The fix meets the brief's four criteria. I found one real missed case and one question about what the run should report.

## Findings

- NEEDS-HUMAN [impl] — `template/src/pdca_harness/flow.py:2293-2295`: a `Conflicts with` partner of a bundle held for a conflict is **not** held. `_runnable` is given `unpushed=held_unpushed`, and `conflicts=` is only built `if held_unpushed`, so `held_conflict` never reaches the #629 partner check at `flow.py:731`. I ran this case. Wave 0 is `10` (changes `shared.txt` line 2), `11` (lines 2 and 8) and `12`. `25` declares `Conflicts with: 11` and changes line 8, so `waves.compute_waves` puts it in wave 1 so that it builds on 11's work. Result: 11 is held, and 25 is built on the line **without** 11 (11's head is not an ancestor of 25's recorded base). 25 ends COMPLETE and no stderr line names it. I ran the same batch with 11's publish failing instead (the #629 `held_unpushed` path), and the run prints "issue_25 held — it `Conflicts with` issue_11 … no line of this run holds that work" and does not build 25. The cause is the same in both cases (no line holds 11's work), but the outcome is the opposite. The declared order is silently broken, and 25's PR will clash with 11's rebuild. Fix: pass `held_conflict` into the partner hold, with its own wording (the current `flow.py:783-787` text says "pushed no branch … publish them", which is wrong for this case). Add the case to `test_flow_same_wave_conflict.py`, and update `docs/07-crosscutting.md:700` and `template/PCDA/quality-cycle/09-parallel-lanes.md:69`, which say only dependents are held. If the human decides partners should *not* be held here, that is a scope call, and the docs should say so.

- NEEDS-HUMAN [human] — `template/src/pdca_harness/cli.py:690` (`_results_rc`) with `flow.py:2441`: when the held bundle has no in-batch dependents, the run now exits 0. I ran `10`/`11` (conflicting on `shared.txt`), `12`, and `22` (`Depends on: 12`). Every result is COMPLETE and `_results_rc` returns 0. Before the fix the same batch stopped and exited 1. Now the only signal that 11's work is on no line, and that its draft PR conflicts with 10's, is two stderr lines. This matches the #593 `held_unpushed` precedent (also COMPLETE, so also rc 0), and the brief does not ask for a non-zero exit. So this is a fitness-to-purpose question, not a defect: should a run that held a bundle for a conflict the human must resolve exit non-zero (or mark the bundle) so that a script or CI caller notices?

- Info, no action needed: `template/tests/test_flow_same_wave_conflict.py:286`. `test_a_hold_leaves_the_integration_tree_clean_on_the_line` calls `integrate.fold(..., held_out=…, wave=…)`, which are keywords the fix adds. So its red leg is `TypeError: fold() got an unexpected keyword argument 'held_out'`, not an assertion. It proves nothing about the defect before the fix, and it goes against the spirit of the brief's "never a symbol the fix adds" rule (brief.md, Falsifiability). C4's red still holds up: the two flow-level cases fail on their assertions ("wave 0 did not integrate … STOPPING") in both the gate log and my re-run.

## Tried to break, could not

- **Earlier-wave conflict mistaken for a same-wave one:** `_held_by` first trial-merges the head onto `pre` alone and returns `[]` if that fails (`integrate.py:895-896`), so the fold still raises. `test_a_conflict_with_earlier_wave_work_still_stops_the_run` pins this: without the guard, `issue_20` would be named as the partner and `21` held.
- **Hold that lasts only one fold:** `flow.py:2430-2431` filters `held_conflict` out of every later fold. Criterion (1)'s wave-1 fold plus `30` would go red otherwise.
- **Judged against an already-held bundle:** a held bundle is never added to `kept` (`integrate.py:536-546`). The chain case (4) passes, and 42 is kept.
- **`pre` taken before an earlier-wave merge:** `accepted` grows one wave at a time (`flow.py:2394`) and `fold` keeps that order inside each target group, so the wave's bundles come last. `pre`/`kept` are reset per group (`integrate.py:518-519`).
- **Trial merges leaving the shared tree dirty or detached:** the `finally` in `_trial` resets the tree, checks the branch back out, and checks the tip (`integrate.py:925-929`). It runs inside the fold's lock. The tree test asserts the symbolic ref, the tip and a clean `status`.
- **Carry, dry-run and direct callers:** `held_out` is `None` there (`flow.py:2433`), so behaviour is unchanged.
- **Test runs a copy instead of production:** no. It drives `flow._drive_and_act` → `_fold_lines` → the real `integrate.fold` with real git. Only the build/sign-off leaves, `_publish_bundle` and `gh` are stubbed, as the brief prescribes.
- **Fallback that names every kept bundle** (`integrate.py:898`): I could not build a line-based case that reaches it, because git treats changes on adjacent lines as a conflict, so a pairwise trial always finds the partner. Not a finding.

## On the verdict

The statement itself is true, but it leaves out that `Conflicts with` partners, which the harness's #629 rule holds for the same reason, are built anyway (first finding).
