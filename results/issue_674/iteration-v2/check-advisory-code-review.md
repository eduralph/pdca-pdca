# Advisory code review — issue 674 (same-wave conflict holds one bundle, not the run)

Lens: bugs the patch introduces, plus reuse / simplification / efficiency. Line numbers are on the patched target at `$PDCA_TARGET`.

Overall: the core logic is sound. `fold` records `pre` (the line before the wave's first merge) and a `kept` list. It holds a bundle only on a `_Conflict` (a textual conflict) whose head merges cleanly onto `pre`. So a conflict with earlier-wave work still raises, a bundle is judged only against bundles actually kept (the three-way chain case is right), and nothing is held in a dry-run. `_trial` puts the tree back on the branch at the same tip, or raises `_LineBroken`. The #629 partner hold now covers `held_conflict` (the iteration-1 finding is fixed). No blocking defects found. A few small points:

- NEEDS-HUMAN [impl] — `template/src/pdca_harness/integrate.py:895-898`: when no single kept bundle conflicts with `head` on its own, `_held_by` falls back to naming **every** kept bundle. That is meant for "conflicts only with several of them together", but it also fires when the line changed after `pre` for a reason other than a kept bundle. A same-wave bundle whose branch is gone (its PR merged right after publish) has `head is None`. It goes through `_gone_branch` → `_take_in_base` (`integrate.py:621-622`, `:689`), which merges the base into the line but is never added to `kept` (`integrate.py:543-546`). A later wave bundle that conflicts only with that new base content then merges cleanly onto `pre` and is held. The report blames innocent same-wave partners and proposes a wrong `Conflicts with:` line, where the old behaviour was to stop. This is rare (it needs a PR merged between publish and fold), but a cheap guard exists: before using the fallback, check that `head` conflicts with `pre` + all kept heads (`_trial(wt, branch, pre, [*kept_heads, head]) == len(kept)`), and raise as before if it doesn't.
- `template/src/pdca_harness/integrate.py:925-929`: `_trial`'s `finally` can raise `_LineBroken`, and if it does it replaces any exception already raised in the `try` (for example the "git step failed" `IntegrationError` at `:919-921`). The run still stops, but the first cause is lost from the message. Low impact. Chaining it (`raise ... from`) or checking `sys.exc_info()` would keep both.
- `template/src/pdca_harness/flow.py:2456-2461`: on the stop path, holds recorded by a fold that then raised (for example target A held a bundle, then target B failed) are still announced. `_report_conflict_holds` (`flow.py:2489`) then repeats them at the end with "was held out of this run's integration line" and the rebuild step, even though that fold never pushed anything. The advice is still true, so this is only wording, but the end-of-run line reads as if the run went on. No test covers this path.
- Efficiency, `template/src/pdca_harness/integrate.py:895-929`: each held bundle costs 1 + len(kept) trial merges. Each trial does a full `checkout --detach`, merge, `reset --hard`, `clean -ffd` and `checkout` in the shared integration worktree. This only runs on a real conflict, so it is fine. `git merge-tree --write-tree` would avoid touching the worktree but needs git ≥ 2.38, which the brief flags as a sign-off question. Keeping the worktree approach is a reasonable choice, not a defect. Reusing #646's `skipped=` mode as-is wouldn't work, because it can't tell a same-wave conflict from an earlier-wave one, so the separate `held_out` path is justified.
- Test, `template/tests/test_flow_same_wave_conflict.py:330`: `test_a_hold_leaves_the_integration_tree_clean_on_the_line` passes `held_out=`/`wave=` to `integrate.fold`, so with the fix reverted it fails with a `TypeError` (an ERROR, not a FAIL; see `gate-logs/C4-verify.log`). The brief asked for assertion failures, not load failures. The module still imports, and the other cases go red on their assertions, so C4's verdict holds. Only this one case's red is "wrong signature" rather than "wrong behaviour". Cosmetic.

Nothing else found: no resource leaks (all trials run under the fold's lock, `integrate.py:477-479`), and nothing duplicates an existing helper (`_merge`, `_reset_tree` and `_rev` are reused). The `_Conflict` subclass keeps every existing `except IntegrationError` caller working.
