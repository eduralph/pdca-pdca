# Result — issue 672 / carry-keeps-a-fold-time-skip-off-the-line

## 1. Spec (from brief.md)              ← Check verifies against THIS
- Defect / goal: The pre-wave carry (`flow._carry_finished`, `template/src/pdca_harness/flow.py:1032-1130`) spreads "not clean" along `Depends on` edges only for ids judged not clean **before** the fold (`_cascade_not_clean`, `flow.py:1002-1029`, called at `:1093`). An id can also fail **during** the fold: `integrate.fold` with `skipped=` records a merge failure for that one bundle and goes on to the next (`template/src/pdca_harness/integrate.py:532-539`). The carry learns of it only after the fold has merged and pushed (`flow.py:1104-1113`). So a finished `Q` merged in the same fold whose branch holds commits of `P` puts them on the line, although `P` itself was skipped. The docs and docstring state this as a known residual (`docs/07-crosscutting.md:728-730`; `flow.py:1052-1054`).
  A textual conflict of `P` alone usually does not leak: a `Q` that contains `P`'s conflicting change conflicts the same way and is skipped too. It leaks when `Q` holds `P` commits but not the conflicting one, or resolved it. Shapes reproduced with plain git at Plan, each leaking on main: (a) `Q` cut from `fix/P`, then `fix/Q` updated from a base that conflicts with `P` and resolved, `P` not updated; (b) `Q` cut from `P`'s first commit `p1`, then `P` adds `p2` that conflicts with the base, folded in the order `Q, P` (Q merges with `p1`, then `P` fails); (c) an earlier integration line `L` holds `p1`, `P` is rebuilt on `L` with a conflicting `p2`, `Q` is built on `L`, `L` is gone, the fold starts fresh: `P` fails, `Q` merges with `p1`.

# Advisory code review — issue 672 (carry keeps a fold-time skip off the line)

Scope: correctness bugs this diff adds, plus reuse/simplification. Grounded on `$PDCA_TARGET` (the patched tree). The loop ends because each extra pass drops at least one more bundle (`integrate.py:591-593`). In-run folds (`skipped=None`) re-raise before `new` is filled, so they break after one pass and compute no work (`integrate.py:569-581`, `:597`). The findings below are about over-holds, messages and small cleanups.

- NEEDS-HUMAN [human] — The transitive hold also reaches *backwards* into a held id's own prerequisites, and the message then reads the wrong way round. `_hold_work` sets a held id's work to everything its head reaches past the base (`template/src/pdca_harness/integrate.py:1044`), and that includes the commits of any finished, clean bundle it was cut from. Example: `Q` is cut from finished `Y` and also has `P`'s commit, and `P` is skipped. `Q` is held for `P`, then `work[Q]` contains `Y`'s commits. On the next round of the fixed-point loop (`integrate.py:1039`), `Y` is held with cause `Q`, and the carry prints "issue_Y was built on issue_Q, which is not carried" (`flow.py:1003`). In fact `Q` was built on `Y`. `Y` has no link to `P`, and its plain dependents are held too. This is the same graph tie the brief accepts as over-hold (i), one step removed. But the doc's known-limits sentence names only "a commit its branch shares with the failed one" (`docs/07-crosscutting.md:753`), not one shared with a bundle held in turn, and (iv) excuses wording only for (ii)–(iii). Decide whether this wider hold is accepted. If it is, the known-limits sentence should name it (an [impl] doc fix). No test pins it either way.

- NEEDS-HUMAN [impl] — The restart pass calls `_merge_published` again for every kept bundle (`integrate.py:542-560`). For a bundle whose branch is gone and whose PR merged, that means a second `gh` lookup (`merged.merged_head`, `integrate.py:716`) and a second copy of the stderr line "…is gone and its PR merged at … skipped." (`integrate.py:722-724`, or `:800-802`). The result is correct, because the line is rebuilt from `start_ref`, but the log shows the message twice and the host is asked twice. Cheap fix: remember the `merged_head` answer per bundle, like `read` already does for branch tips (`integrate.py:547-549`), or print only on the last pass.

- `_work` fails open when neither head is in the clone: it returns `[]` (`integrate.py:1008`), so a skipped id with no readable head has empty work and holds nothing. The pre-fold `_finished_head` check normally catches a head that does not resolve, and the docstring says this (`integrate.py:1004-1005`). So this is a note, not a defect. A one-line comment at `:1008` pointing to that guard would make the reliance explicit.

- `_built_on_skipped` reads each failed bundle at one tip (`read[n] or pr.get(n)`, `integrate.py:599`; used at `:1067`). `_hold_work` and the failed id's own `work` use both the branch tip and the PR head (`integrate.py:588`, `:1044`). If a failed bundle's branch tip and PR head differ, the cause relabel can miss a shared commit that only the PR head reaches. This only changes which message the bundle gets: it is already off the line, so nothing leaks. Using `_work(wt, (read[n], pr.get(n)), …)` at `:1067` would match the brief's two-head definition.

- Simplification: inside the fixed-point loop, `hit` scans every `work[c]` list for every candidate on every round (`integrate.py:1039-1040`, and `:1068`). That is fine at batch sizes. Keeping `work` as sets, or one `{commit: first cause}` map filled in fold order, would make the lookup direct and turn the tie-break ("earliest in fold order") into a single rule in one place.

- Reuse (test): `_update_ours` (`template/tests/test_flow_resume_stack_prereqs.py:483`) repeats the fixture's existing `_update_branch` (`template/tests/test_integrate_stack_bases.py:199`) and only adds `-X ours`. A strategy argument on the shared helper would avoid the copy. Minor.

Adding the same `assertIn` to (5) would make it as strict.

No other correctness bugs found in the diff. `holds.clear()` on a fold exception (`flow.py:1124`) correctly falls back to the "open" hint for every id. `causes.update(holds)` feeds the existing `built_on` formatting unchanged.
