# Advisory code review — issue 672

Two lenses: bugs the patch adds, and reuse / simplification / efficiency. Gates: C4 is red before the fix and green after (`gate-logs/C4-verify.log`, 5 failures pre-fix). T3 is green (2469 tests). The round-1 finding about base history the two branches share is handled: `_commits` now subtracts `origin/<base>` (`target/template/src/pdca_harness/integrate.py:928`), and `test_base_history_two_branches_share_is_no_skipped_ids_work` covers it. The partial-containment finding is handled by the re-fold before the push (`integrate.py:598-604`) and its test.

Findings:

- NEEDS-HUMAN [impl] — The docs understate one known limit on a continued line. `target/docs/07-crosscutting.md:744-747` says "a finished prerequisite whose branch moved on after another was cut from it … (both are held)". Here is the case on a line the carry continues from origin (`start == "continue"`). The line holds X's old head x1. X's branch has since moved to x2. P was cut from the line, does not name X in `Depends on`, and conflicts, so it is skipped. `_own_work` (`integrate.py:944-951`) does not exclude X, because x2 is not in P's history and P's brief does not name X. So x1 counts as P's work. The line holds x1, so the check at `integrate.py:592-597` raises `SkippedWorkOnLine`. The carry then holds **every** bundle of the target with the "delete the line" hint (`flow.py:1121-1126`), not just the two. This is my reading of the code; I did not run it. No test covers it. Either fix the doc sentence to say the whole target is held on a continued line, or keep commits the line already held from a `clean` id's earlier head out of the skipped id's work. The new tests only pin the declared-edge form (`test_a_declared_prerequisite_that_moved_on_since_is_still_carried`) and the fresh-line form.
- `target/template/src/pdca_harness/integrate.py:579-580,604` — A bundle skipped in pass 1 stays skipped in pass 2, even when the bundle it conflicted with is the one pass 2 drops. Example: Q merges first, holds P's first commit, and changes a file P's later commit also changes. P conflicts and is skipped. Q holds P's work, so pass 2 drops Q. P would now merge cleanly but is not retried. This is safe (no leak) and close to the documented "two finished prerequisites that conflict" limit. It just holds more than it needs to. Advisory only.
- `target/template/src/pdca_harness/integrate.py:559,592` — The new local `held` (a `(name, commit)` tuple) reuses the name of the lock flag from `integrate.py:498` (`held = holder.enter_context(...)`). That is harmless today because the lock flag is only read at `:499`. A distinct name such as `holds` would avoid confusion if someone later reads the lock flag again. Nit.
- `target/template/src/pdca_harness/integrate.py:544-604` — The re-fold loop resets `took`/`pre`/`kept` each pass but keeps `held_out` entries in `left`. Pass-1 `held_out` decisions were made against a `kept` list that pass 2 may shrink. Today this cannot happen: the loop only repeats when `skipped` is passed, and only the carry passes `skipped`, with `held_out=None` (`flow.py:1118-1120`). Nothing enforces that, though. A one-line assert or a docstring line saying `skipped` and `held_out` are never both given would guard it. Nit.

Reuse / efficiency: no problems. `_in_line` is reused for the ancestry tests, `_reset_tree` for the restart, and `adds` caches one `rev-list` per tip. The extra git calls only run once something has been skipped (`own` is non-empty), so the normal fold path costs nothing extra.
