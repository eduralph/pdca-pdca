# Result — issue 623 / fold-refuses-base-that-reverts-line-work

## 1. Spec (from brief.md)              ← Check verifies against THIS
- Defect / goal: When a folded bundle's published branch is gone and its PR merged at a head the line does not have (e.g. a fixup pushed after the fold), `integrate._gone_branch` (`template/src/pdca_harness/integrate.py:488-536`) checks only that the base has that head by commit ancestry (`_carries(…, of=base_ref)` → `git merge-base --is-ancestor`, `integrate.py:528`, `:539-545`, `:569-580`), then `_take_in_base` merges the whole base into the line (`integrate.py:548-566`). Ancestry stays true after the merge is reverted on the base, so the fold merges the base in and the revert with it. Reproduced on real git by the #593 final adversary review: fold [A] → T1; push a fixup to `fix/A`; merge `fix/A` into `main`; delete `fix/A`; `git revert -m 1` that merge on `main`; fold [A, B] with `{TARGET: T1}`. The fold passes and the line ends with only `['b.txt', 'base.txt']`: A's change is gone, not only the fixup. B, which depends on A, builds without A, and stderr says "the merged work reaches pdca-integration/main through origin/main" (`integrate.py:564-566`), which is false. The same happens when the base merge brings in a revert of any OTHER bundle already on the line.
- Success criterion: With the patch, on the real-git fixture of `template/tests/test_integrate_stack_bases.py` (`StackFoldGit`):
  (1) **Revert of the gone bundle.** The repro above: the second `integrate.fold(cfg, [a, b], folded_this_run={TARGET: t1})` raises `integrate.IntegrationError`. The message names A and says that taking in `origin/main` would remove A's work from the line. Origin's line is still at `t1` (nothing pushed). Stderr has no "reaches … through" line.
  (2) **Revert of another bundle on the line.** Bundles Z and A are on the line (folded at `t1`). Z's change is reverted on `main` (a revert commit on `main` of the commit that added Z's file). A's branch is then gone with its PR merged at a head the line lacks, so the fold would take `main` in. The fold raises `IntegrationError` naming Z, and origin's line is still at `t1`.
  In (2) both folds pass the same `batch=["Z", "A", "B"]` (the first `integrate.fold(cfg, [z, a], folded_this_run={}, batch=…)`, the second `integrate.fold(cfg, [a, b], folded_this_run={TARGET: t1}, batch=…)`), as the flow does (`flow.py:2298-2301` passes `batch=run_batch`). Z is not in the second fold's `bundles`; it is found through `batch` (see Scope). With a batch the line is `integrate.integration_branch(cfg, "main", batch)` (`integrate.py:70`), not the fixture's unscoped `LINE` (`test_integrate_stack_bases.py:48`), so the test reads that name. (1) and (4) keep `batch=None` and `LINE`, and there the message names A because A is in `bundles`.
  (3) **Unchanged.** `test_a_merged_branch_the_line_never_carried_comes_in_through_the_base` (`test_integrate_stack_bases.py:426-447`) and the rest of the file still pass: a base merge that removes no folded bundle's work still happens, unforced, with the "reaches … through" line.
  (4) **Carry mode.** The repro of (1), but the second fold is called with `skipped={}` (as the #646 pre-wave carry calls it, `flow.py:931-933`). `skipped` names `issue_A` with the revert reason, and origin's line, if pushed at all, still has `a.txt` and does not contain the revert commit. The worktree was reset to the line as it was before the base merge before the error was raised, so B's merge (and the push) happen on a line without the revert.
  (5) **No false stop.** The base EDITS a file A added (a commit on `main` changing `a.txt` to `a2`, not a revert), then A's branch is gone with its PR merged at a head the line lacks. The fold takes `main` in, unforced, prints "reaches … through", and the line has `a.txt` = `a2`.
  Pre-fix, (1), (2) and (4) pass the fold and push a line without A's (Z's) file, and (1) prints "reaches … through". That is the RED. (5) is green before and after; it guards against an over-broad fix.
- Repo + branch target: eduralph/pdca-harness @ main
- Scope (one logical fix) / out of scope: Make a fold that would take the base in stop, before pushing, when doing so would remove from the line any change a bundle on the line (or being folded) carries, and make the "reaches … through" message true whenever it is printed. Detection rule (what "remove a bundle's work" means): let C be the line's cut point, the first commit on the line's first-parent chain that the base already has (an ancestor of `base_ref`); decided by commit, never by message. For each path that differs between C and the line before the base merge, the base merge removes work if, after it, that path's content is back to its content at C (absent, where C did not have it). An edit that leaves the path with NEW content is not a removal (criterion (5)). "A's work" therefore means everything the line has from A, not only A's merged head (`a.txt` as well as the fixup). The message names each such path and the bundle that brought it: a bundle in the fold's `bundles` or in the run's `batch` (already passed to `fold`, `integrate.py:274`, `:303-305`) whose commits in `C..<its head>` touched the path; where none matches, it names the path and the line commit that last changed it. Before raising, the fold resets the worktree to the line as it was before the base merge, so that under `skipped` (the #646 carry, `integrate.py:436-439`, then the push at `:447-448`) the remaining bundles merge and push on a line without the revert (criterion (4)). Put that reset in the gone-branch path (`_take_in_base`, `integrate.py:548-566`), not in `_merge` (`integrate.py:583-595`): 631 changes `_merge`'s abort handling in the same wave. Update the stack-mode paragraph that describes taking the base in, `docs/07-crosscutting.md:665-677` (the sentence ending "the run stops rather than build the next wave without that work"), to say the run also stops when the base would undo a folded bundle's work. / out of scope: detecting reverts the fold never takes in (a revert on the base that this run never merges does not touch the line); squash/rebase merges (already refused, `integrate.py:528-535`); a revert on a bundle's own PR branch (#633's territory); #655 (a mid-run merge of an out-of-batch prerequisite); a known false stop: a base that reverts its OWN change that an earlier base take-in brought onto the line also stops (named by path); rare, and fail-closed.

# Advisory code review — issue_623 (fold refuses a base that reverts line work)

I found no correctness bug that breaks the brief's criteria. The detection rule (a path back to its content at the cut point), the reset before raising, the `_LineBroken` escape from the carry, and the batch lookup through `find_bundle` with de-duplication by name all match the brief. The gates agree: C4 is red without the fix (7 of the 8 new tests fail; criterion (5) is green on both sides, as intended) and green with it, and T3 passes. Both points raised in round 1 are fixed: `find_bundle` plus `setdefault(o.name, …)` at `template/src/pdca_harness/integrate.py:446-448`, and topic merges now count through `_own_commits` at `integrate.py:651`. What remains are minor, non-blocking notes:

- `template/src/pdca_harness/integrate.py:696` — Efficiency. For the gone bundle `d` itself, `_undone_paths` calls `merged.merged_head(...)` again, which is a second `gh pr view` network call. `_gone_branch` already has that answer as `head` (`integrate.py:527`) and passes it to `_take_in_base`. Passing `{d.name: head}` down would save the call. It only runs on the refusal path, so the cost is small. It is not a correctness issue.
- `template/src/pdca_harness/integrate.py:446-448` — Efficiency, and possible noise. `owners` is built from the whole run `batch`, which covers every target, not only this group's `(repo, base)`. On the refusal path, each owner from another target whose branch does not resolve in this worktree costs one `gh pr view` (`integrate.py:696`) before the `cat-file` check drops it. The result is still correct. Filtering `owners` to bundles of the same target would avoid the calls.
- `template/src/pdca_harness/integrate.py:702-705` — Message precision. "last changed by <sha>" uses `touched[0]` from a plain `git rev-list`, which sorts by commit date, not by graph order. It also uses default history simplification, so it can name a bundle's own commit inside a merged branch rather than the line's merge commit. This text only shows up in the fallback case (no owner matched), and the fold still stops. It is cosmetic.
- `template/src/pdca_harness/integrate.py:651-670` — Edge case in attribution only, not detection. `_own_commits` skips only the current line's first-parent chain and the base's chain since the cut. A batch bundle cut from an older line tip that a fresh fold has since replaced (force-pushed) would count those old line commits as its own work. It could then be named for a path it did not bring. The fold still stops correctly, and this needs a re-run that replaced the line mid-batch, so it is unlikely.
- `docs/07-crosscutting.md:671-675` — Style nit. The reflow leaves "An" alone at the end of the line ("…is merged in as usual. An"). It renders fine and T2 passes.

No NEEDS-HUMAN findings: none of the above needs a scope decision or blocks the brief's success criteria.
