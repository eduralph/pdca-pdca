- **Slug:** fold-refuses-base-that-reverts-line-work
- **Defect:** When a folded bundle's published branch is gone and its PR merged at a head the line does not have (e.g. a fixup pushed after the fold), `integrate._gone_branch` (`template/src/pdca_harness/integrate.py:488-536`) checks only that the base has that head by commit ancestry (`_carries(…, of=base_ref)` → `git merge-base --is-ancestor`, `integrate.py:528`, `:539-545`, `:569-580`), then `_take_in_base` merges the whole base into the line (`integrate.py:548-566`). Ancestry stays true after the merge is reverted on the base, so the fold merges the base in and the revert with it. Reproduced on real git by the #593 final adversary review: fold [A] → T1; push a fixup to `fix/A`; merge `fix/A` into `main`; delete `fix/A`; `git revert -m 1` that merge on `main`; fold [A, B] with `{TARGET: T1}`. The fold passes and the line ends with only `['b.txt', 'base.txt']`: A's change is gone, not only the fixup. B, which depends on A, builds without A, and stderr says "the merged work reaches pdca-integration/main through origin/main" (`integrate.py:564-566`), which is false. The same happens when the base merge brings in a revert of any OTHER bundle already on the line.
