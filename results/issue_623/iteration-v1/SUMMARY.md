- Defect / goal: When a folded bundle's published branch is gone and its PR merged at a head the line does not have (e.g. a fixup pushed after the fold), `integrate._gone_branch` (`template/src/pdca_harness/integrate.py:488-536`) checks only that the base has that head by commit ancestry (`_carries(…, of=base_ref)` → `git merge-base --is-ancestor`, `integrate.py:528`, `:539-545`, `:569-580`), then `_take_in_base` merges the whole base into the line (`integrate.py:548-566`). Ancestry stays true after the merge is reverted on the base, so the fold merges the base in and the revert with it. Reproduced on real git by the #593 final adversary review: fold [A] → T1; push a fixup to `fix/A`; merge `fix/A` into `main`; delete `fix/A`; `git revert -m 1` that merge on `main`; fold [A, B] with `{TARGET: T1}`. The fold passes and the line ends with only `['b.txt', 'base.txt']`: A's change is gone, not only the fixup. B, which depends on A, builds without A, and stderr says "the merged work reaches pdca-integration/main through origin/main" (`integrate.py:564-566`), which is false. The same happens when the base merge brings in a revert of any OTHER bundle already on the line.

- Scope (one logical fix) / out of scope: Make a fold that would take the base in stop, before pushing, when doing so would remove from the line any change a bundle on the line (or being folded) carries, and make the "reaches … through" message true whenever it is printed. Detection rule (what "remove a bundle's work" means): let C be the line's cut point, the first commit on the line's first-parent chain that the base already has (an ancestor of `base_ref`); decided by commit, never by message. An edit that leaves the path with NEW content is not a removal (criterion (5)). "A's work" therefore means everything the line has from A, not only A's merged head (`a.txt` as well as the fixup). The message names each such path and the bundle that brought it: a bundle in the fold's `bundles` or in the run's `batch` (already passed to `fold`, `integrate.py:274`, `:303-305`) whose commits in `C..<its head>` touched the path; where none matches, it names the path and the line commit that last changed it. ### Advisory — code-review

# Advisory code review — issue 623 (fold-refuses-base-that-reverts-line-work)

Overall: no blocking correctness bug found. The detection rule matches the brief: it compares each path at the cut point (the first line commit the base already has), on the line before the base merge, and after it. The worktree reset sits in `_take_in_base`, not in `_merge`. `_LineBroken` keeps a failed reset from being swallowed by `skipped`. All five criteria have a test (criterion (3) is covered by the existing test). C4 is red without the fix and green with it, and T3 is green. The findings below are small.

- NEEDS-HUMAN [impl] — `template/src/pdca_harness/integrate.py:443-444`: batch owners are built with `cfg.bundle(...)`, which is always the active `results/issue_<id>` path. `merged.merged_head` (`merged.py:123`) and the flow (`flow.py:729`) use `cfg.find_bundle`, which also finds archived `results/completed/issue_<id>` bundles. If a batch bundle has been archived, `_published_ref` (`integrate.py:155`) finds no `publish.json` there, so the bundle is silently not named. The fold still stops (fail-closed), but the message falls back to "last changed by <sha>". There is a second effect: if `accepted` paths come from `find_bundle` and point at the archive, `dict.fromkeys` will not dedupe them against the `cfg.bundle` path for the same id. The same bundle then shows up twice in a path's owner list, e.g. `a.txt (issue_A, issue_A)` (`integrate.py:670`). Fix: use `cfg.find_bundle` here and dedupe by `Path.name`.
- `template/src/pdca_harness/integrate.py:624-630`: the `_cut_point` docstring says it returns None when "the chain never meets the base". The code does something different. It returns `tip` when the chain is empty (the line is already inside the base). It returns None only when the oldest commit on the chain has no parent, i.e. `chain[-1]^1` does not resolve. Both cases behave correctly, because None falls back to the empty tree at `:651-652`. Only the docstring is wrong.
- `template/src/pdca_harness/integrate.py:660-665`: an owner is matched when its first-parent chain since the cut shares a commit with the commits that touched the path. A later-wave bundle cut from the line (as in criterion (4), `test_integrate_stack_bases.py:338`) has the line's own merge commits on its first-parent chain. So if a path entered the line through a merge commit that is not TREESAME (its tree content for that path matches neither parent, e.g. a hand-resolved conflict), that later bundle is also named as an owner. The error only gets a wrong extra name; the stop itself is still right. Minor. A clean `--no-ff` merge is TREESAME to one parent, so git's history simplification follows that parent and this does not happen.
- `template/src/pdca_harness/integrate.py:662`: when an owner's branch is gone, `_undone_paths` calls `merged.merged_head` for it, which runs `gh pr view` once per gone owner in `accepted` plus `batch`. This only runs on the refusal path, after `undone` is non-empty (`:654`), so cost is not a concern. On a `gh` failure that bundle is not named (fail-closed, stderr says why). No change needed.
- `template/src/pdca_harness/integrate.py:613-621`: `_out` is a new "run git, capture stdout, raise on failure" helper next to `_git`/`_rev` (`:122-133`), which only return a code or a SHA. No existing helper returns raw output with a raising error, so this does not duplicate anything. No reuse issue.
- Tests (`template/tests/test_integrate_stack_bases.py:449-554`): they test the real `integrate.fold` against real git, not a copy. Criterion (5) (`test_a_base_that_edits_a_bundles_file_is_still_taken_in`) guards against an over-broad fix. One gap: criterion (4) checks `skipped` and the pushed tip, but no test makes the reset fail to check the `_LineBroken` path (`integrate.py:675-680`, `:450`). That path is hard to reach offline. Leaving it untested is acceptable, but the reviewer should know it has no test.
