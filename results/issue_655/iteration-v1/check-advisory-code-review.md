# Advisory code review — issue 655 (merged-prereq-gate-checks-the-line)

Two lenses: bugs the patch adds, and reuse / simplification / efficiency. Grounded on `$PDCA_TARGET` (the patched tree). The gate logs agree with the diff: C4 shows 4 of 7 new tests red without the fix (cases 1, 2 and both case-5 holds) and all green with it. Cases 3, 4 and "no line" are green both ways, as the brief expects.

The core logic is sound. The check only runs when `merged_into` already said yes, a line exists, and a tip was recorded (`template/src/pdca_harness/flow.py:773-775`). It fails closed on every error path (`flow.py:839-856`). It reuses `integrate._carries`, so a commit missing from the clone reads as "not on the line" rather than an error (`integrate.py:648-654`). The dry-run case (tip `None`) is skipped, as the docstring says. No resource leaks or ordering problems found.

## Findings

- NEEDS-HUMAN [impl] — False hold when this run's carry already put P's work on the line. `template/src/pdca_harness/flow.py:776` accepts P only if its PR's `mergeCommit` is an ancestor of the line tip. But the #646 carry folds a finished named prerequisite's PR **head** onto the line, and it treats a MERGED PR as clean when its head is on the base (`flow.py:949-952`, folded at `flow.py:1070`). On a resumed run whose origin line was continued (not cut fresh), a D with `Depends on (merged): P`, where P is named and carried, has P's work on the line but not main's merge commit. So D is now held with "does not have that merge", while before the patch it was built correctly. This is safe (it holds, it does not build on a bad base), but it wrongly blocks a valid case. Suggested fix: count P as on the line if **either** `mergeCommit` **or** the PR head is an ancestor of the tip. The head being on the line is enough proof that P's work is there. Criterion (4) still holds, because squash/rebase are covered by the `mergeCommit` check. No test covers a carried-plus-merged prerequisite.
- Reuse: `merge_commit` (`template/src/pdca_harness/merged.py:148-178`) is nearly a line-for-line copy of `merged_head` (`merged.py:115-145`) and `pr_state` (`merged.py:181-201`). Only the `--json` fields and the field it returns differ. A small private helper such as `_pr_view(pr_url, fields) -> dict | None` would remove a third copy of the subprocess call, the OSError guard and the JSON parsing.
- Efficiency: each held-or-checked prerequisite now costs two `gh pr view` calls on the same PR: `pr_state` inside `merged_into` (`merged.py:99`), then `merge_commit` (`flow.py:847`). `_runnable` runs once per wave, so a run with several later-wave dependents of the same P repeats both calls each wave. That's minor for small batches. Asking for `state,headRefOid,mergeCommit` in one call, or caching by `pr_url` within a `_runnable` call (as `views` already caches the checkout, `flow.py:738`), would halve the host calls. The `views` cache is keyed by `(repo, base)`, but `carry_view` only fetches the repo, so two targets in the same repo with different bases fetch twice. That's negligible.
- Message wording nit: when the fetch fails, the "why" text is the raw `_fetch` error, which says "the fold cannot see the branches it merges" (`integrate.py:874-875`). In the held line at `flow.py:802-807` this reads as if a fold failed, when it was the gate's read-only fetch. Cosmetic. A short prefix already exists ("its checkout could not be fetched:", `flow.py:843`), so this is low priority.

No other correctness problems found in this diff. The docs hunk (`docs/07-crosscutting.md:744-754`) matches the code's behaviour.
