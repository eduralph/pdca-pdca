- **Slug:** merge-mode-retarget-wrong-based-pr
- **Kind:** enhancement (design proposal)
- **Goal:** Under `[driver].wave_mode = "merge"`, before the driver readies and merges a wave's PR, it checks the PR's base on the host against the bundle's resolved target base, and checks that the target base is not itself a branch another bundle of this batch produced (#411 route 2). A batch-produced target refuses with no `gh pr edit` call. When the host base differs from a good target, it retargets the PR (`gh pr edit <pr> --base <target>`), reads the base again, and goes on only if the host now reports the target base. If the retarget fails or does not take, it refuses with a message that names both branches, and the run stops as merge mode does for any refusal.
- **Success criterion:** With `wave_mode = "merge"` and a COMPLETE bundle whose PR the host reports with `baseRefName` ≠ the bundle's resolved target base: (a) when `gh pr edit --base` succeeds and the next read reports the target base, the PR is merged with the normal gates and no `gh pr merge` call is made before the retarget; (b) when `gh pr edit --base` fails, or the re-read still reports the wrong base, `merge.merge_wave` returns non-zero, no `gh pr merge` is called for that PR, the PR is not left marked ready (no `gh pr ready` without a matching `--undo`), and stderr names both the PR's base and the target base; (c) both hold under `merge_requires = "all"` AND `merge_requires = "required"` (the second path skips the base read today: the read sits inside `if cfg.merge_requires != "required":`, merge.py:536-618); (d) a PR whose base already equals the target makes no `gh pr edit` call; (e) when the bundle's resolved target base is a branch a sibling bundle of the batch published (#411 route 2, `publish._batch_branch_producer`), `_merge_one` refuses whether or not the host base equals it — no `gh pr edit`, no `gh pr ready`, no `gh pr merge` call, stderr names the producing bundle; (f) the check runs after the `expected_checks_error` refusal (merge.py:507-511): with a malformed `expected_checks` and a wrong-based PR, no `gh pr edit` is called. In (b) and (e) **no `gh pr ready` call is made at all** for that PR (the check runs before the ready-mark), and no `gh pr ready --undo` either: the refusal leaves the PR's draft/ready state as it found it.
- **Falsifiability:** RED offline in the `gh`-stubbed unit tests of `merge._merge_one` (the pattern `template/tests/test_merge.py` uses, a stub in front of `subprocess.run`). Today `_merge_one` (merge.py:463-638) never compares the PR's base with the target: `_pr_head` reads `baseRefName` (merge.py:278-294) only so `_base_read` can compare the head against THAT base (merge.py:366-396), so a wrong-based PR is readied and `gh pr merge` is called. ## Motivation

#411 made merge mode refuse, at publish, a PR whose base is not the bundle's own target. But a PR opened by an earlier run (before #411, or in stack mode before #593 opened every PR against the real base), or one whose base was edited on the host afterwards, never passes through that guard again. At merge time nothing checks: `_merge_one` readies and merges the PR into whatever base it carries. The issue asks to heal those PRs mechanically instead of making each a manual stop. Its premise is partly wrong: it assumes a merge-time check that refuses today, but reading the code shows there is no merge-time stop at all, so a wrong-based PR merges silently. This change therefore does two things: adds the missing fail-closed merge-time check (a safety fix — triage's sev:minor/P3 rested on "current fail-closed behaviour is safe", which is not true at merge time), and adds the retarget the issue asked for.

It also **reverses a recorded decision**: #411 chose to refuse at publish "rather than at merge time: the publisher is an interactive step with a human present" (publish.py:288-290), and the user docs promise "the harness never retargets a PR for you" (docs/07-crosscutting.md:897). The maintainer must confirm that reversal at sign-off. If they do not want an unattended retarget, the refuse-only half (criteria b, c, e, f, without a) is the fallback, and they may also ask to split it into a refuse-only bundle with the retarget stacked on it.

## Design

1. In `_merge_one`, after the `"stacked"` refusal, the `is_merged` skip and the `expected_checks_error` refusal (merge.py:511), and before `gh pr ready`, refuse if the target base is a batch-produced branch (route 2); otherwise read the PR's host base (`_pr_head`) and the bundle's resolved target base.
2. Equal → continue exactly as today.
3. Different → `gh pr edit <pr> --base <target>`, then read the base again. Equal now → print one line saying the PR was retargeted from X to Y, and continue (the #531 behind-base update and the rollup gate then run against the new base under `merge_requires = "all"`). Still different, or the edit failed → refuse naming both branches. The ready-mark has not been set by this run, so nothing is undone; a PR an earlier run or a human readied is left as it is.
4. Under `merge_requires = "required"` the same check runs; only the rollup/base-update gate is skipped, as today.

Retargeting is within merge mode's existing authority: it already readies and merges PRs unattended (merge.py:1-17).

## Alternatives considered

- **Refuse only (no retarget).** The safe floor, and what the issue says #411 provides. But it leaves every such PR as manual work, which is what the issue asks to remove.
- **Retarget at publish/re-publish.** Does not reach a PR from an earlier run that is never re-published.

## Impact & compatibility

- Merge-mode runs gain one `gh pr view` per PR (already done once by `_base_read` under `"all"`; Do may reuse it) and, only for a wrong base, one `gh pr edit`.
- A wrong-based PR that used to merge into the wrong branch now merges into the target or stops. Stack mode unchanged.

## Open questions

- If retargeting changes the PR's diff a lot (its old base held work the target lacks), should the driver refuse instead? Recommended: no special case, with a stated residual risk the maintainer accepts at sign-off. After a retarget, `_base_read` only updates a head that is BEHIND the new base (merge.py:384, :393, :556-572). In the usual stack→merge case the head already contains the target tip, so no update happens and `_wait_for_green` reads the existing rollup for that head SHA. A merge into the target then gives the head's own tree, which push-triggered checks on that SHA ran on. The remaining risk is `pull_request`-triggered checks that ran on a merge with the old base. Those results stand without a re-run, because a base edit alone usually does not re-trigger CI. Under `"required"` the operator chose to trust the host.
