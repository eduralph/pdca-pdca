# Result — issue 500 / merge-mode-retarget-wrong-based-pr

## 1. Spec (from brief.md)              ← Check verifies against THIS
- Defect / goal: Under `[driver].wave_mode = "merge"`, before the driver readies and merges a wave's PR, it checks the PR's base on the host against the bundle's resolved target base, and checks that the target base is not itself a branch another bundle of this batch produced (#411 route 2). A batch-produced target refuses with no `gh pr edit` call. When the host base differs from a good target, it retargets the PR (`gh pr edit <pr> --base <target>`), reads the base again, and goes on only if the host now reports the target base. If the retarget fails or does not take, it refuses with a message that names both branches, and the run stops as merge mode does for any refusal.
- Success criterion: With `wave_mode = "merge"` and a COMPLETE bundle whose PR the host reports with `baseRefName` ≠ the bundle's resolved target base: (a) when `gh pr edit --base` succeeds and the next read reports the target base, the PR is merged with the normal gates and no `gh pr merge` call is made before the retarget; (b) when `gh pr edit --base` fails, or the re-read still reports the wrong base, `merge.merge_wave` returns non-zero, no `gh pr merge` is called for that PR, the PR is not left marked ready (no `gh pr ready` without a matching `--undo`), and stderr names both the PR's base and the target base; (c) both hold under `merge_requires = "all"` AND `merge_requires = "required"` (the second path skips the base read today: the read sits inside `if cfg.merge_requires != "required":`, merge.py:536-618); (d) a PR whose base already equals the target makes no `gh pr edit` call; (e) when the bundle's resolved target base is a branch a sibling bundle of the batch published (#411 route 2, `publish._batch_branch_producer`), `_merge_one` refuses whether or not the host base equals it — no `gh pr edit`, no `gh pr ready`, no `gh pr merge` call, stderr names the producing bundle; (f) the check runs after the `expected_checks_error` refusal (merge.py:507-511): with a malformed `expected_checks` and a wrong-based PR, no `gh pr edit` is called. In (b) and (e) **no `gh pr ready` call is made at all** for that PR (the check runs before the ready-mark), and no `gh pr ready --undo` either: the refusal leaves the PR's draft/ready state as it found it.
- Repo + branch target: eduralph/pdca-harness @ main
- Scope (one logical fix) / out of scope: A merge-time check of the PR's host-side base against the bundle's resolved target base in `merge._merge_one`, with a retarget attempt before refusing; covers both `merge_requires` values; updates the merge-mode bullet of `docs/07-crosscutting.md` (:858 onward) AND the #411 paragraph at :888-897, whose "the harness never retargets a PR for you" becomes false; updates the #411 comment at publish.py:288-290 ("Refuse here rather than at merge time") so it no longer says no merge-time check exists. / out of scope: the publish-time #411 guard (`publish._merge_base_refusal`, publish.py:770) — unchanged, it stays the first line of defence; stack mode; retargeting a `"stacked"` (`Onto branch`) record — merge mode already refuses those first (merge.py:483-494, #658), keep that order; resolving the target any way other than the one parser publish uses.

# Advisory code review — issue #500 (merge-mode retarget of a wrong-based PR)

Lens: correctness bugs the patch adds, plus reuse / simplification / efficiency. Grounded on `$PDCA_TARGET`. I found no correctness bug that blocks. The new check sits where the brief asks: after the `"stacked"` refusal, the `is_merged` skip and the `expected_checks_error` refusal, and before `gh pr ready` (merge.py:589). It refuses with a plain `return 1`, not `_refuse`, so no stray `gh pr ready --undo` is sent. Both round-1 implementation findings are fixed. The hint text now lives once, in `publish.MERGE_BASE_FIX` (publish.py:775, used at publish.py:803 and merge.py:509). The edit-failed and edit-ignored refusals now give a host-side hint instead of the brief-side one (merge.py:515-532). The base race from the round-1 C5 finding is closed under `"all"`, because `_base_read` now refuses when the base differs from the target (merge.py:399). The new tests exercise each of legs a–f under both `merge_requires` values, through the production `merge.merge_wave`.

Findings, all minor:

- NEEDS-HUMAN [human] — template/src/pdca_harness/merge.py:499-505: this adds a new refusal. A COMPLETE, published merge-mode bundle with no `brief.md`, or with no usable `Repo + branch target` in it, used to merge and now stops the run. That is fail-closed and the brief allows it ("resolving the target any way other than the one parser publish uses" is out of scope). But it is a change in behavior that the brief's success criteria don't list, and it is why five existing test fixtures had to gain a brief (test_merge.py `_brief`, test_merge_onto_branch.py, test_merge_third_remote.py). In practice a published bundle always has a brief, so the risk is low. The maintainer should confirm that refusing here, rather than skipping the check, is what they want.
- template/src/pdca_harness/merge.py:569-571: the dry run returns before `_target_base`, so `merge --dry-run` prints a plain `gh pr merge` line for a PR the real run would retarget or refuse. That includes a #411 route-2 target, which needs no network call to detect. The `"stacked"` refusal (#658) was put above the dry run for this reason. The route-2 check (`publish._batch_branch_producer`, local files only) could move above the dry run the same way. This is optional and outside the brief's criteria, so it is not tagged.
- template/src/pdca_harness/merge.py:502,506 vs :546,629: the route-2 check uses the brief's `repo_spec`, while `_merge_one` picks the checkout from the publish record's `repo`. These agree whenever publish wrote the record from the same brief, which is the normal case. If someone edits the brief's repo after publish, the two disagree and nothing reports it. This is an edge case and matches publish's own use of the brief, so it is noted only.
- Efficiency, template/src/pdca_harness/merge.py:589 then :637: under `"all"` each PR now costs one more `gh pr view` (`_target_base` reads the base, then `_base_read` reads it again right after the ready-mark). The second read can't be dropped, because it is what catches a base edited during or after `gh pr ready` (the test covers this at test_merge_retarget.py, case "moved after the ready-mark"). The cost is one host call per PR. No change suggested.

No reuse issue found. The edit call copies the `gh pr ready` pattern next to it (stderr print, then refuse), and the base reads reuse `_pr_head`. No existing helper covers `gh pr edit --base`.

- [x] template/src/pdca_harness/merge.py:499-505: this adds a new refusal. A COMPLETE, published merge-mode bundle with no `brief.md`, or with no usable `Repo + branch target` in it, used to merge and now stops the run. That is fail-closed and the brief allows it ("resolving the target any way other than the one parser publish uses" is out of scope). But it is a change in behavior that the brief's success criteria don't list, and it is why five existing test fixtures had to gain a brief (test_merge.py `_brief`, test_merge_onto_branch.py, test_merge_third_remote.py). In practice a published bundle always has a brief, so the risk is low. The maintainer should confirm that refusing here, rather than skipping the check, is what they want.
- [x] **The check would retarget a PR onto a batch-produced branch, which is the exact hazard #411 blocks.** #411 has two refusal routes. The brief carries over only route 1 (`pr_base != base`). Route 2 refuses when the brief's resolved target base is itself a branch another bundle in the batch produced (publish.py:781-785, 798-802, via `_batch_branch_producer`). The issue says its trigger is "switching an existing batch from stack mode to merge mode", and chained `Repo + branch target`s are "the documented stack-mode practice" (publish.py:782-783). In that case the brief's design would either merge a PR into a predecessor's fix branch with no stop (host base == target, step 2 "continue exactly as today"), or actively `gh pr edit --base` a correctly-based PR *onto* that branch. The invariant as worded ("merges … only into that bundle's resolved target base") does not rule this out. Revise the invariant, scope and criterion so the merge-time check applies route 2 (`_batch_branch_producer`, or reuse `_merge_base_refusal` whole) before any retarget. Add a criterion leg: a target that is a sibling bundle's published branch refuses, with no `gh pr edit` call.
- [x] **The brief reverses a recorded design decision and a documented user contract without saying so.** The #411 comment that the brief cites (publish.py:283-292) goes on to say: "Refuse here rather than at merge time: the publisher is an interactive step with a human present" (publish.py:288-290). The brief quotes lines 286-287 and leaves this part out. The user docs also promise: "the harness never retargets a PR for you" (docs/07-crosscutting.md:897). That paragraph is at :888-897, not in the :858 bullet the Scope names. As written, Do updates the :858 bullet and leaves :897 contradicting the new behavior. The Scope should name docs :888-897, and Motivation should state that the merge-time-check / auto-retarget decision is being reversed. That reversal is a maintainer call, not something Do should settle by default.
- [x] **This is two changes (a missing safety guard plus an enhancement), and the issue's premise is wrong.** The issue assumes a merge-time check already exists: "When the merge-mode base check finds `baseRefName != resolved target base`" and "stop with the existing message … The refusal path stays exactly as #411 shipped it". Triage graded it `sev:minor` because "Current fail-closed behaviour is safe" (notes.json comment). The brief itself finds there is no merge-time stop at all, so a wrong-based PR merges silently (Motivation, "this also closes a silent wrong-merge"). So the bundle adds (1) a fail-closed refusal that does not exist today, which is a bug fix on the invariant, and (2) the retarget the issue asked for. Each has its own review surface and risk. The human should decide whether to split them (refuse-only floor first, retarget stacked on it) and whether to re-grade sev/priority. The triage's basis for P3 is false according to the brief's own reading.
- [x] **The Open-questions answer depends on a claim the code does not back.** "under `"all"` the rollup gate re-verifies the new combination" is only partly true. After a retarget, `_base_read` asks whether the head contains the *new* base's tip (merge.py:384, 393). Only a behind head gets `gh pr update-branch` and so a new head SHA with new CI (merge.py:556-572). If the head already contains the target tip (the usual stack→merge case: old base was a predecessor branch on top of main), no update happens. `_wait_for_green` then reads the existing rollup for that head SHA, earned against the *old* base, and a base edit by itself does not normally re-run CI. Either add a criterion leg for that case (e.g. require a fresh rollup after a retarget, or refuse when the old base held commits the target lacks), or state in the brief that the residual risk is accepted.
- [x] **The brief contradicts itself on where the refusal happens.** Design step 1/3 puts the check *before* `gh pr ready` ("the PR is still a draft, so there is nothing to undo"). Citations expected says "refuse through `merge._refuse` … when the PR is already readied, so the ready-mark is undone". `_refuse` always calls `_undo_ready` (merge.py:453-460), so using it pre-ready sends a spurious `gh pr ready --undo`. Criterion (b)'s "no `gh pr ready` without a matching `--undo`" is satisfied whether or not `ready` is ever called, so it does not pin which design Do built. Pick one placement and make (b) assert it, e.g. "no `gh pr ready` call at all for that PR". "Still a draft" is also not guaranteed for a PR from an earlier run or one a human readied, which is another reason to pin this down.
- [x] **The placement relative to the existing pre-ready refusal is unspecified.** Design step 1 says "after the `"stacked"` refusal and the `is_merged` skip". It does not say whether the check goes before or after the `expected_checks_error` refusal (merge.py:507-511). If it goes before that refusal, a malformed config still lets the driver edit a PR's base on the host before stopping, which is a host-side mutation on a run that was going to refuse anyway. State the order: after merge.py:511.
- [x] T5 Judgment — Approve unattended retargeting as a reversal of the previous promise, or choose the brief’s refuse-only fallback — changing a base can enlarge the PR’s contribution; docs/07-crosscutting.md:887 and docs/07-crosscutting.md:905, publish policy at template/src/pdca_harness/publish.py:288.
