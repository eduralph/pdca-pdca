## Refutation attempts that landed

- NEEDS-HUMAN [impl] — `template/src/pdca_harness/flow.py:1546-1549` breaks criterion (c) when origin already has the batch's line. Failing case: fold P onto the line at H1, push a fixup so P's PR head is H2 (the "fixup pushed after the fold" the docs describe), squash-merge P, then re-issue `P, Q, D`. `_finished_head` does classify P as squashed (it read the merge commit), but `foreign_commit` then finds H1 unaccounted for and the `if bad:` block overwrites every `why` entry. P's and Q's lines both say only "origin's … holds 20323128dc40 … delete … on origin", with no mention of a squash or rebase merge. The advice is not wrong, and a run after deleting the line should name the merge (not run), but P's own line fails (c) on this run. No test has a line on origin in the squash shape. Fix: keep the `squashed` and `built_on_squashed` entries when `bad` is set, or add the squash reason to the `line` message, and add this case as a test.

- NEEDS-HUMAN [impl] — `template/src/pdca_harness/flow.py:1301-1303` has no test pinning the "on the line" half of "head on neither the base nor the line", though the patch rewrote this condition. Mutation: change `(base_ref, tip)` to `(base_ref,)`. All 25 new tests still pass, and in the full suite only the 2 `test_settings_permissions` tests fail, which also fail on my unpatched copy. The mutation does change behaviour. With P folded onto the line and then squash-merged, the patched code carries P and Q, builds D and makes no extra `mergeCommit` read. The mutated code reads the merge commit and holds P, Q and D. Add that case to `ReissueCarry` as a negative test.

- NEEDS-HUMAN [human] — `template/src/pdca_harness/flow.py:1338-1341` and `docs/07-crosscutting.md:816-819`: the hold lasts only while P is in the batch, not until Q is updated. Brief Design item 4 says a squash-merged prerequisite "**holds** its dependents until they are updated from the base". Failing case: after the hold, skip "Update branch" and re-issue `Q, D`. Q is carried, D reaches COMPLETE, and `fix/Q` still lacks the squash commit (`_ancestor(oid, fix/Q)` is False). So Q's PR keeps showing P's diff, and only the wording asks for the update. The harness could check this, because the base's merge commit would be an ancestor of Q's head. Decide whether wording is enough or whether the carry should enforce the update. The patched docs avoid saying "until", so they are accurate; the gap is between the patch and the brief.

- NEEDS-HUMAN [impl] — `template/tests/test_stack_squash_merge.py:483`: `test_the_way_out_the_hold_gives_works` does not show that the update step matters. I removed the `_update_branch("Q")` call and kept the assertions I re-ran (hold line, Q carried, D built, both ancestry checks), and they all still passed. I did not re-check its `results["D"]` assertion in that copy, but the same scenario in the attempt above ended COMPLETE. The test's comment says the way out is "followed", but it only proves that dropping P from the batch releases the hold. Assert that `fix/Q` holds the squash commit after the update, or say plainly that the update is not checked.

- NEEDS-HUMAN [impl] — `template/src/pdca_harness/publish.py:225-228` returns to `_publish_stacked` before the new warning at `publish.py:373`, so a depended-on bundle with an `Onto branch` field gets no warning. I found this by reading the code and did not run it. Either warn on that path or record that `Onto branch` is out of scope.

- NEEDS-HUMAN [impl] — `docs/07-crosscutting.md:735-736` overstates the fold. It says that when the base has the merge commit "the stop says so", but `template/src/pdca_harness/integrate.py:1444-1451` raises first for an `Onto branch` record or a recorded base that differs from the target (a legacy `Stacks on:` PR).
