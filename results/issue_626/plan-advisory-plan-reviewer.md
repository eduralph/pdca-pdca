I read the brief's citations against the target and they check out. publish.py:370-371 and :820, integrate.py:1406-1455 (the generic message is at :1447-1453), flow.py:1283-1305, :1316-1335 and :1395, merged.py:151-171, and docs/07-crosscutting.md:650-652, :689 and :811 all match what the brief says. `StackFoldGit` exists (test_integrate_stack_bases.py:123), and the squash-merge test at test_flow_merged_prereq_on_line.py:252 uses it through `sb.StackFoldGit()` (:62, with `_squash` at :97). The root cause matches the thread: the issue body's "Decide whether stack mode supports … or refuses them up front … Document the choice and pin it with a test", plus the owner's 2026-10-10 comment on the `edge` cascade. These are the faults I found:

- NEEDS-HUMAN — **Criterion (a) needs a batch view that `publish` does not have, and the brief does not say where it comes from.** `publish.publish(cfg, issue_id, *, dry_run, open_pr, by, today, skip_if_no_target, pending_id, texts_prevalidated)` (publish.py:120-131) takes no batch or dependents argument. It has three callers (cli.py:495 for standalone `pdca publish <id>`, cli.py:1555 for accept at sign-off, and flow.py:491/:657), and none of them passes the batch. The Goal says "that a later wave or a dependent builds on". Criterion (a) says "a bundle that another bundle of the batch names in `Depends on`". Meeting that means either threading a new parameter through flow (and deciding what the two cli paths do), or scanning every bundle's brief for a reverse `Depends on`. Either one is a design choice with its own review surface, and it is missing from Scope and Citations. The brief should name the mechanism and the expected behaviour of standalone `pdca publish`, since a human publishing a wave-0 prerequisite by hand is the likeliest squash case.

- NEEDS-HUMAN — **Criterion (a) does not say what "stack mode" means at publish time.** Today "stack" in publish means `stack_branch` is set (publish.py:238, :370). The brief's new meaning is the config `[driver].wave_mode` (default `"stack"`, config.py:363), but the brief never says so. Without that, Do could gate the new warning on either `cfg.wave_mode != "merge"` or something else, and criterion (a)/(d) do not pin which. State it, and add a case: a `wave_mode = "merge"` publish of a depended-on bundle prints no warning. That case is a real distinction, because merge mode picks the method itself (see the brief's own out-of-scope line).

- NEEDS-HUMAN — **Criterion (d) can be read as removing an existing warning.** (d) says "a stack-mode publish of a bundle no other bundle depends on prints no such warning". But a wave>0 bundle with a stack base and no dependents warns today (publish.py:370-371), and Design §1 says "not only for a PR cut from a stack base", which keeps that warning. As written, (d) either contradicts Design §1 or quietly removes the #123 warning. Narrow (d) to "wave 0, no stack base, no dependent". Better, add the inverse pin: a stack-base PR with no dependent still warns.

- NEEDS-HUMAN — **Criterion (c) contradicts Design §3.** Design §3: "Whether the dependent is still held or now carried is Do's call". Criterion (c): "Q's hold line names P as squash- or rebase-merged". If Do carries Q, there is no hold line, and (c) cannot be met or is vacuous. Pick one outcome now: still held with corrected advice, or carried, which is how it was before #670 per the owner's comment ("Before #670, Q was carried"). Otherwise the red→green test cannot be written before Do. The owner listed both options ("Either an `edge` hold doesn't cascade, or the hold's advice says…"), so this is exactly the decision the design proposal exists to make.

- NEEDS-HUMAN — **P's own new hint is never pinned.** Design §3 gives P "its own reason and hint (not `edge`)". The `edge` hint today is "remove the `Depends on: {iid}` edge from the dependent's brief" (flow.py:1319). Criterion (c) only asserts on Q's line. Add an assertion that P's own line names the squash/rebase merge and no longer gives the `edge` advice. Also add a negative case: a MERGED P whose merge commit is *not* on the base keeps `edge`. Without that pair, the reclassification in `_finished_head` (flow.py:1301-1303) has no falsifiable pin.

- NEEDS-HUMAN — **The carry change reads a new field, and the brief does not say so.** `_finished_head` gets its state from `merged.pr_state` (flow.py:1293), which asks only for `state,headRefOid` (merged.py:180). To tell "merge commit on base" apart from "merged elsewhere", it must also call `merged.merge_and_head` (`mergeCommit`), which is one more `gh` call per finished MERGED bundle. The fold has the same issue: `_gone_branch` uses `merged.merged_head` (integrate.py:1427, headRefOid only, merged.py:133). The out-of-scope line allows `merge_and_head`, but neither path's "unreadable merge commit" behaviour is specified. What happens when `mergeCommit` comes back "" (merged.py:171)? It should fail closed to today's message or hint, as test_flow_merged_prereq_on_line.py:263 does for the build path. Add that as a criterion.

- NEEDS-HUMAN — **The docs are in scope, but there is no criterion for them.** Scope edits docs/07-crosscutting.md at three places (:646-652, :686-691, :809-811). The issue's "Done when" requires "Document the choice". No criterion or gate checks the docs, and the Known-limits line at :811 currently says such a prerequisite "holds the dependents". If Do carries Q (see the (c) finding), that line becomes false. Tie the docs change to the chosen outcome and have a reviewer check it, or the docs drift is unfalsifiable.
