# Adversarial review — issue #725 (hold a bundle whose own base cannot be built)

The toolchain was available. I re-ran the new suite on the patched target (7 tests OK) and drove six extra scenarios through the same harness (`BundleBaseHolds` loaded by path; scratch file in my sandbox only). Four of them break the fix's stated invariant. All outputs quoted below are from those runs.

- NEEDS-HUMAN [impl] — **A `Conflicts with` partner of a base-held bundle is built without that bundle's work.** `template/src/pdca_harness/flow.py:2739-2750`: the `_runnable` call never sees `held_base`. It is not in `held=` and not in `conflict_held=`, and `conflicts=` is only computed `if held_unpushed or held_conflict`. `_closure_members` only walks bundles in `built`, so the partner just loses the edge. Failing case: case (4)'s shape (B's base fetch fails) plus X with `Conflicts with: B`, which the scheduler puts in wave 2. Result: `B` held, `X` built on `('', '')` (the plain base) and COMPLETE, holds `{'B': 'base'}`, rc 3. With `held_unpushed` (#629) or `held_conflict` (#674), X would be held. The brief's Scope says the base hold "puts `d` in a held set that `_runnable` already honours (as `held_unpushed` / `held_conflict` do)" and "its dependents and partners are held through `_runnable`". The new docs exclude this case on purpose (`template/PCDA/quality-cycle/09-parallel-lanes.md:69`: "or, for a fold hold, share a `Conflicts with` edge"). That contradicts the same file's `Conflicts with` rule at `:60` ("the later one's base holds the earlier one's accepted work"). Fix: pass `held_base` to `_runnable`'s partner check, as `unpushed` is passed.

- NEEDS-HUMAN [impl] — **A cross-wave clash with a finished bundle that the run carried onto the line still stops the run, and the message says no bundle is involved.** At `template/src/pdca_harness/integrate.py:672-675`, `_held_across` gets `on=list(took.items())`. `took` only holds the bundles this fold walks, which are the run's `accepted` (`flow.py:2911-2912`). It never holds the finished ids `_carry_finished` put on the line before wave 0. Failing case: F finished in an earlier run (adds `shared.txt`); G (`Depends on: F`, so F is carried); A; Y (`Depends on: A`, adds its own `shared.txt`, built on its own base); C (`Depends on: Y`); unrelated chain W→V→U. Output: `flow: wave 1 did not integrate (issue_Y's branch origin/fix/Y does not merge cleanly … (conflicts in shared.txt): no bundle's own change on … accounts for its conflict in shared.txt, so the clash is with other work on the line … not one with a bundle …); STOPPING`. U stays PLANNED, rc 1. Under the Scope rule ("every conflicting path is owned by a bundle branch already on the line"), this is Y's clash with F and should be a hold naming F. Fix: include the carried finished ids' heads in `on`.

- NEEDS-HUMAN [human] — **Case (1)'s hold only lasts until the next fold, so the test passes only because B's wave is the last one.** `template/tests/test_flow_bundle_base_holds.py:203-216` has two waves, so no fold runs after B is held. Add one dependent of W (V, `Depends on: W`) so a fold runs after wave 1. Output: `issue_B held — …` and then `flow: wave 1 did not integrate (issue_W's branch origin/fix/W does not merge cleanly … (conflicts in a.txt): no bundle's own change … accounts for its conflict in a.txt …); STOPPING`. V stays PLANNED, rc 1. Cause: W's own base was fetched from the moved `main`, so W carries main's new `a.txt` and clashes with A on the line. `_partners` (`integrate.py:1933-1934`) skips A because A no longer merges onto the new main. In any run where the held bundle's wave is not the last, the moved-base case still stops the run. The person signing off needs to decide whether this is "the line's failure" (then case (1)'s promise and `template/pdca.toml.jinja:131` "Only a failure of the line itself stops the run" only hold in the final wave, and the docs should say so), or whether the fold should handle a line bundle that the base moved under.

- NEEDS-HUMAN [impl] — **The stop message in the previous item blames an unrelated bundle and gives a fix that cannot work.** `template/src/pdca_harness/integrate.py:1862-1866` tells W's owner to "Update its branch from a base holding that work". But W was cut from the newest main and did nothing wrong. The real cause is A on the line against the moved main. The fix that works is the one B's hold already prints: "Rebuild issue_A's branch on the new origin/main". This breaks the brief's invariant: "Every message names the cause and a fix that works for that cause."

- NEEDS-HUMAN [impl] — **When a rewrite holds a bundle, the rewritten branch is dropped from the end-of-run check, even though the run now goes on and cuts more PRs from the stale line.** `template/src/pdca_harness/flow.py:2962` (`d.name not in base_rewrites`). Failing case: case (2b)'s shape plus S (`Stacks on: A`, a seam in B's own wave). B is held for A's rewrite. S is then cut from the line, and its PR holds A's old head (`_ancestor(old A head, S head)` is True). No stderr line names `issue_S`. B's hold line only says "Restore origin/fix/A … then re-run", because it was written before S was pointed (bases are built before any seam is pointed). Before #725 the run stopped before S was built, so the same exclusion (`stop_named`) lost nothing. Now S's stale PR goes unnamed. rc is still 1.

- NEEDS-HUMAN [impl] — **Case (2a)'s test never reaches the foreign-ancestry check the brief asks for.** In `template/tests/test_flow_bundle_base_holds.py:220-237`, `cut_from["P"]` makes the fixture write `"mode": "stacked-pr"` (`template/tests/test_integrate_stack_bases.py:168`). So `_member_cut_point` rule 4 (`integrate.py:989-1000`, "published stacked … but has no stack-base record") refuses first, and `_foreign_refusal` (`integrate.py:917-919`) never runs. The C4 red log shows the actual line, and it never mentions X. Brief (2a) asks for "D's base build refuses the foreign ancestry … naming P, and X". The test asserts neither X nor any foreign-work wording. Its `assertTrue(_ancestor(X, P))` sets up a condition the refusal never reads. The hold is generic, so the code is probably fine, but this evidence does not show what the test docstring says it shows. Fix: give P a non-stacked publish record so `_foreign_refusal` fires, and assert X is named.

- NEEDS-HUMAN [human] — **Case (5) has no red→green evidence and does not test the patch.** The C4 red leg for the new file is `FFFFFF.`: `test_two_finished_prerequisites_that_clash_hold_only_their_dependent` (`test_flow_bundle_base_holds.py:311-323`) passes with the fix reverted. The test docstring (`:24-30`) admits that on this base, dependents of carried prerequisites are seams (#728 left that to #735). So the brief's "carried" cases (2) and (5) describe a base-build path that does not exist yet. The C4 gate's overall "pass" in `check-gates.json` hides this one test staying green. Decide whether to accept the substitution or move (5) to #735.
