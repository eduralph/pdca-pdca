# Advisory code review — issue_725 (hold a bundle whose own base cannot be built)

Scope: correctness bugs the patch adds, and reuse/simplification. Cited lines are on the patched tree at `$PDCA_TARGET`. Gates: C4 passes (6 of the 7 new or flipped tests in the new suite fail before the fix), and the T3 suite is green (2601 tests). I re-ran the brief's wrap-aware search for criterion (6) on the patched tree. All five patterns match nothing.

## Findings

- NEEDS-HUMAN [human] — `template/tests/test_flow_bundle_base_holds.py:311` (case 5) does not test what the brief asks for. The brief wants "`D`'s base build refuses the member clash" through `integrate.build_bundle_base`. The file's own docstring (`:28-30`) says the carry's fold (#694) refuses the P/Q clash before any base is built. So the brief's premise ("carried members never met on a line") is false on this base. The C4 log confirms it: this is the only new test in the file that passes before the fix. It guards no part of the change, and it does not check `self.holds` or `self.rc`. A human should decide whether that is acceptable, or whether Do must add a test that reaches the member-clash refusal in `_bundle_bases` (for example in-batch prerequisites on separate bases, or a direct `_bundle_bases` call with a clashing pair).
- NEEDS-HUMAN [human] — `template/tests/test_flow_bundle_base_holds.py:220` and `:239` (cases 2a/2b) use in-batch prerequisites that a fold of this run carried. The brief asks for prerequisites "carried" from an earlier run. The docstring (`:24-27`) explains why: on this base, a dependent of a prerequisite finished in an earlier run is cut from the line, so it never gets a base of its own (left to #735). The reasoning holds up. Still, the brief's wording is not met as written, so this needs sign-off.
- NEEDS-HUMAN [human] — `template/src/pdca_harness/cli.py:736`: only the bundle held with reason `"base"` is left out of the "did every bundle finish" check. Its dependents are skipped by `_runnable` ("prerequisite(s) not ready", `flow.py:840-842`), stay PLANNED, and are not in `holds`. So a run whose only problem is one base hold with one dependent exits 1, not 3. The docstring says this on purpose (`cli.py:424-426`), and it matches how conflict holds already treat dependents. But the brief's invariant counts the dependents as held too. A human should confirm that 1 is the intended exit code there.
- NEEDS-HUMAN [impl] — `template/src/pdca_harness/integrate.py:1862`: `_held_across` holds the bundle only when every conflicting path appears in the files of a single partner (`_partners` tries each partner alone, base + partner + head). A path that conflicts only against two earlier-wave bundles combined stops the run, with the message "a base an earlier fold took in?". That message is wrong in this case. `_held_by` (`:1817`) handles the same "only together" case by naming all of `kept`. This is safe, because it stops as before rather than hold wrongly. The fix is either to name all the bundles involved in that case, or to reword the message so it does not guess "a base".
- `template/src/pdca_harness/integrate.py:1820-1867` (simplification, not blocking): `_held_across` mostly re-does `_clash` (`:1870-1914`). The trial onto `base_ref` alone and the `_partners` call are the same as `_clash`'s `"base"` and `"batch"` steps, with the same `IntegrationError → fallback` handling. `_held_across` could call `_clash(wt, branch, head, base_ref, paths, on, (), under)`, then add only its two extra checks: the trial onto `pre` first, and the "every path accounted for" rule. That leaves one classifier instead of two that can drift apart.
- `template/src/pdca_harness/integrate.py:672-675` (no defect, just noting): when `_held_by` returns None because the head merges onto `pre` plus `kept` (a conflict with a base taken in mid-wave), `_held_across`'s first trial (`:1842`) sends it to the "clashes with what the fold took in" stop. That keeps `test_flow_same_wave_conflict.py:399`'s stop as the brief requires. I checked this order and it is correct.
- `template/src/pdca_harness/flow.py:2809` / `:2975` (no defect): `base_rewrites` records the rewritten member (for example `A`), which then appears in `holds` as `"rewritten"` and drops out of the end-of-run check. This keeps the old `stop_named` behaviour and makes the run exit 1. The member is an in-batch id here, so it is a key of `results` as the `holds` contract requires.

No other correctness bugs found in the flow loop. The `failed`-filter plus `continue` at `flow.py:2810-2812` follows the same pattern as the existing `if not runnable: continue` at `:2751`, and the `_prepare_worktree` wrapper (`integrate.py:878-885`) always has a `cause` (`IntegrationError.__init__` defaults it, `:123`).
