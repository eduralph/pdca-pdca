# Adversarial review — issue 395 (same-wave conflict refused at accept)

Verdict: the main fix holds. Two things I could break are in the leg (h) "one more session" bound. One case gets past the brief's own conflict rule. One case falls outside the trial's on/off condition. All are reproduced on the patched target except the split case, which is from reading the code.

## Evidence

- Red→green holds. `template/tests/test_flow_same_wave_accept_trial.py` gives 10 OK when I run it on the patched target. The frozen `gate-logs/C4-verify.log` red leg shows 7 failures (`FF.FF.F.FF`). The 3 that pass on `main` are the legs that are meant to stay unchanged: (b) clean merge, plain C6, (g) last wave. Accepts go through the real `flow._drive_wave` → `_apply_decision` → `integrate.same_wave_clash` on real git. The publish step is a test copy (`test_flow_same_wave_conflict.py:131-142`), but the trial's branch cut uses the real `publish.cut_base` (`template/src/pdca_harness/publish.py:779`).
- Test gap, not a failure: every trial leg runs in wave 0. That means `tip=None` and the cut is `origin/main`. The path wave k>0 takes (folded tip, cut from the recorded stack-base tip, `publish.py:792-798`) is never tested, and neither are the `Onto branch` / `Stacks on` branches of `cut_base`. I tried a wave-1 pair myself: 12 → {30, 31 same line, 32} → 40. Result: 31 refused, 30/32/40 published, `holds` empty, exit code 1. That path works.

## Refutations

- NEEDS-HUMAN [impl] — A dropped sign-off session still counts as "the one more session" and parks the bundle. `flow.py:2733-2734` calls `_session_offered(d)` before `leaves.run_signoff_batch` at `flow.py:2736`, and the `except` at :2737 does not undo the count. I reproduced it with leg (a)'s setup and `run_signoff_batch` raising: one failed call, then 11 is parked. The wave-end line says "the sign-off session after that recorded nothing new, so wave 0 offers it no more", which is false because no session ran. A plain C6 refusal is offered again on the next pass after a dropped session; this one never is. Fix: count only after `run_signoff_batch` returns without raising.
- NEEDS-HUMAN [impl] — On a re-run, the refused bundle spins until the pass budget runs out and gets the "raise [driver].max_passes" hint that leg (h) was meant to remove. `flow.py:2673-2675` deletes `same-wave-refusal.json` when each wave starts. On `pdca flow 10 11 12 20` after leg (a)/(h), 11 is driven alone. Its trial row is still open and its `accept` decision is still on disk, so it falls back to the plain C6 path. Reproduced with `max_passes=5`: 5 sessions in 5 passes, then `pass budget exhausted after 5 pass(es) … raise [driver].max_passes`. `test_a_later_run_offers_the_refused_bundle_a_session_again` only tests the run where the human ticks the row. Fix: when a wave starts, reset `sessions` to 0 instead of deleting the record. Each run then offers one session and parks the bundle with the conflict step.
- NEEDS-HUMAN [human] — The "hold more bundles" rule (`integrate.py:834`, `if len(held) <= len(alone)`, required by brief.md:45) lets a new conflict through after an override in the same wave. Reproduced: 10 and 11 conflict in shared.txt and 11 is overridden (row ticked, accepted again). Then 09, which conflicts with 10 only, in other.txt, is accepted with no row: held {10} against alone {11}, and 1 ≤ 1. All five PRs open and the fold holds 10, which was the bundle accepted first. So the docs claim "whichever of the two you accept first is the one kept" (`docs/07-crosscutting.md:732`) is false here, and the invariant "acceptance never creates an accepted bundle whose PR would conflict" breaks for a bundle the human never overrode. A rule of "refuse if any bundle is newly held" (`held.keys() - alone.keys()` is not empty; `integrate.py:836-843` already computes that difference to name partners) would catch it. That changes the brief's stated definition, so a human has to decide.
- NEEDS-HUMAN [human] — A split during the last wave makes the fold run when the trial was off. `trial` is decided from `len(wave_list)` at `flow.py:3246-3249`, before `_drive_wave`. `_adopt_split_children` at `flow.py:3258` can then replace `wave_list[k+1:]` with the split's children. The fold condition at `flow.py:3307` reads the list again, so it runs with `held_out`. Result: in a one-wave run where any bundle splits, two conflicting same-wave bundles are both accepted and published, and the fold holds one. That is the #674 behaviour the Goal says is gone "in the waves the fold runs after". `docs/07-crosscutting.md:751` ("no fold follows") is also wrong for this case. I did not reproduce it, because setting up a split is heavy. Decide whether to cover it now or add it to follow-up 1.
- Low, not lifted: when the trial cannot run, the fallback (`integrate.py:858`, `flow.py:305`) refuses based on `waves.diff_files`. That function's own docstring (`waves.py:336-339`) calls it a best-effort heuristic that is "never a hard gate". Its regex (`waves.py:329`) misses git's quoted headers (`diff --git "a/caf\303\251.txt" …`), so two bundles editing a non-ASCII path look like they share nothing and both are accepted.

## Tried and could not break

- Lock deadlock: no integration lock is held across `_drive_wave`, since `_fold_lines` releases its lock at `flow.py:1442-1456`. `integ_lock` blocks rather than failing, so a lock held by another run means waiting, not a fallback.
- Tree reset: the build loop is now inside the `try/finally` (`integrate.py:827-833`), and (e) checks that the tree ends clean on the line after a failed trial.
- Publish refactor: `_checkout_base` (`publish.py:767-776`) gives exactly the old `wave_stacked and bool(wave_tip)` result.
- Guard order: `unrecordable` runs before both C6 and the trial (`flow.py:197-206`), so `ensure_needs_human_item` cannot silently skip a summary that has no §6 and wrongly accept.
- Override text: the override row matches by its normalized text (`signoff.py:199-205`), and the trial gives the same text when it runs again, so a ticked row is honoured.
- Trial condition: the on/off condition matches the fold's (`flow.py:3307` plus `dry = stub`, stack mode).
