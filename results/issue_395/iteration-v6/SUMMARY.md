# Result — issue 395 / same-wave-conflict-refused-at-accept

## 1. Spec (from brief.md)              ← Check verifies against THIS
- Defect / goal: In a `pdca flow` run in stack mode, a bundle is not accepted if its branch would textually conflict with a bundle of its own wave that is already accepted. This covers the waves the fold runs after: `k < len(wave_list) - 1`, `do_publish`, publisher not `stub` — the same condition as `flow.py:3078` plus the fold's non-dry `held_out` (flow.py:3115). "Would conflict" means the fold's own #674 rule, in the fold's order. When an accept (from a session, or a decision already recorded in the bundle) would add such a bundle, the driver refuses it the way C6 refuses an accept today. The bundle gets an open §6 NEEDS-HUMAN row naming the partner(s), the conflicting file(s) and the step (declare `Conflicts with: <partner>` in its brief, then `iterate-plan`). It stays AWAITING_SIGNOFF. Its siblings are accepted and published as before. So, in those waves, a run no longer accepts two same-wave bundles whose branches conflict, and it never opens two such PRs. A bundle the trial refuses is never COMPLETE without a PR. The last wave, a one-wave run, single-issue `flow`, `--no-publish`, merge mode, a dry run and the standalone `pdca signoff --accept` do not change. This is a partial fix of #395: the PR says `refs #395`, not `closes`.
- Success criterion: These run on the real-git `StackFoldGit` fixture with `gh` stubbed and the publisher in `command` mode. Every accept goes through the real `flow._drive_wave` → `flow._apply_decision` path: Do+Check are stubbed, the decision is written to the bundle (`leaves.SIGNOFF_DECISION`), and nothing calls `signoff.record(... "accept")` directly. A later wave exists in every case except (g), so the fold condition holds.
  - (a) A and B are in wave 0, with no `Conflicts with` between them. Their patches change the same lines of a shared file, and both carry `accept`. After the run: A is COMPLETE, its branch is pushed and `gh pr create` is called for it. B is AWAITING_SIGNOFF (`state.state`). B's SUMMARY §6 has an open row naming `issue_A` (or A's id) and the shared file. `signoff.open_needs_human` returns that row. B's branch is not on origin and no `gh pr create` names B. The run's `holds` has no entry for B. `cli._results_rc` is 1 (B did not finish). A wave-1 bundle that depends on neither still builds and completes.
  - (b) A and B change different lines of the same file (no textual conflict). Both are COMPLETE and both are published. Neither §6 gains a row.
  - (c) The refusal does not depend on which accept is applied first. With B's decision applied before A's (for example, B carries a recorded decision, which the pre-apply at flow.py:2516-2522 applies first, and A's is written by the stubbed session), A is the one refused, and the accepted one publishes. Either way, exactly one of the pair is COMPLETE and the fold holds nothing (`holds` empty).

Leg (a)'s setup, but the stubbed sign-off session offered to B after its refusal ticks B's new row and writes `accept` again. B is then accepted and published in that run. The row is not added a second time (`signoff.ensure_needs_human_item` leaves a ticked row alone, `signoff.py:177-207`).
  - (e) The trial cannot run for the target: inject a failure of its git step (a fetch or a commit build). ## Refutations

- NEEDS-HUMAN [impl] — A dropped sign-off session still counts as "the one more session" and parks the bundle. `flow.py:2733-2734` calls `_session_offered(d)` before `leaves.run_signoff_batch` at `flow.py:2736`, and the `except` at :2737 does not undo the count. I reproduced it with leg (a)'s setup and `run_signoff_batch` raising: one failed call, then 11 is parked. The wave-end line says "the sign-off session after that recorded nothing new, so wave 0 offers it no more", which is false because no session ran. A plain C6 refusal is offered again on the next pass after a dropped session; this one never is. Fix: count only after `run_signoff_batch` returns without raising.
- NEEDS-HUMAN [impl] — On a re-run, the refused bundle spins until the pass budget runs out and gets the "raise [driver].max_passes" hint that leg (h) was meant to remove. `flow.py:2673-2675` deletes `same-wave-refusal.json` when each wave starts. On `pdca flow 10 11 12 20` after leg (a)/(h), 11 is driven alone. Its trial row is still open and its `accept` decision is still on disk, so it falls back to the plain C6 path. Reproduced with `max_passes=5`: 5 sessions in 5 passes, then `pass budget exhausted after 5 pass(es) … raise [driver].max_passes`. `test_a_later_run_offers_the_refused_bundle_a_session_again` only tests the run where the human ticks the row. Fix: when a wave starts, reset `sessions` to 0 instead of deleting the record. Each run then offers one session and parks the bundle with the conflict step.
- NEEDS-HUMAN [human] — The "hold more bundles" rule (`integrate.py:834`, `if len(held) <= len(alone)`, required by brief.md:45) lets a new conflict through after an override in the same wave. Reproduced: 10 and 11 conflict in shared.txt and 11 is overridden (row ticked, accepted again). Then 09, which conflicts with 10 only, in other.txt, is accepted with no row: held {10} against alone {11}, and 1 ≤ 1. All five PRs open and the fold holds 10, which was the bundle accepted first. So the docs claim "whichever of the two you accept first is the one kept" (`docs/07-crosscutting.md:732`) is false here, and the invariant "acceptance never creates an accepted bundle whose PR would conflict" breaks for a bundle the human never overrode. A rule of "refuse if any bundle is newly held" (`held.keys() - alone.keys()` is not empty; `integrate.py:836-843` already computes that difference to name partners) would catch it. That changes the brief's stated definition, so a human has to decide.
- NEEDS-HUMAN [human] — A split during the last wave makes the fold run when the trial was off. `trial` is decided from `len(wave_list)` at `flow.py:3246-3249`, before `_drive_wave`. `_adopt_split_children` at `flow.py:3258` can then replace `wave_list[k+1:]` with the split's children. The fold condition at `flow.py:3307` reads the list again, so it runs with `held_out`. Result: in a one-wave run where any bundle splits, two conflicting same-wave bundles are both accepted and published, and the fold holds one. That is the #674 behaviour the Goal says is gone "in the waves the fold runs after". `docs/07-crosscutting.md:751` ("no fold follows") is also wrong for this case. I did not reproduce it, because setting up a split is heavy. Decide whether to cover it now or add it to follow-up 1.
- Low, not lifted: when the trial cannot run, the fallback (`integrate.py:858`, `flow.py:305`) refuses based on `waves.diff_files`. That function's own docstring (`waves.py:336-339`) calls it a best-effort heuristic that is "never a hard gate". Its regex (`waves.py:329`) misses git's quoted headers (`diff --git "a/caf\303\251.txt" …`), so two bundles editing a non-ASCII path look like they share nothing and both are accepted.

# Advisory code review — issue 395 (same-wave conflict refused at accept)

Lens: bugs the patch adds, plus reuse / simplification / efficiency. Advisory only. Line
numbers are on the patched target at `$PDCA_TARGET`.

Overall: no blocking correctness bug found. I traced the main risk, the "one more session"
count in leg (h), and it holds. After the first refusal, the trial's own §6 row is open, so
every later apply in that wave is stopped by C6 at `template/src/pdca_harness/flow.py:200-202`
before it reaches `_refused_for_wave`. So `_write_refusal(..., "sessions": 0)` at
`flow.py:322` runs once per refusal and does not reset the count that `_session_offered`
(`flow.py:2734`) raises. The `publish._checkout_base` refactor (`publish.py:767-776`) gives the
same result as the old inline rule (`wave_stacked = cfg.wave_mode != "merge" and
bool(wave_base)`, `publish.py:251`). The new `trial` condition (`flow.py:3246-3249`) matches
the fold's own guard (`flow.py:3307-3308`, where dry run means `publisher.mode == "stub"`).
Gates C4 (7 of 10 red before the fix, all green after) and T3 pass.

- NEEDS-HUMAN [impl] — `template/src/pdca_harness/flow.py:303` catches every
  `integrate.IntegrationError`, and that includes `IntegrationTreeError` and `_LineBroken`
  (both are subclasses, `integrate.py:104`, `integrate.py:113`). The fold treats those two as
  "the integration tree is in an unknown state, stop" (`integrate.py:675-676`,
  `flow.py:3220`). Here they are handled like a failed fetch: the code falls back to the
  shared-path rule and may go on to accept. The trial can raise them itself:
  `integrate.py:909` (`_would_be` could not return to the line) and `_back_on`
  (`integrate.py:947`). After that, the next trial and the fold each run `_prepare_worktree`
  and `checkout -B` again, so the damage is probably limited. Still, the stderr line and the
  §6 row only say "the check could not run", so a broken worktree is reported as a soft
  fallback. Suggested fix: re-raise these two (or at least name the tree state in the message)
  instead of falling back.
- `template/src/pdca_harness/integrate.py:916-919` and `:929-931`: a `_LineBroken` raised in a
  `finally` (in `_would_be` and in `same_wave_clash`'s `_back_on`) replaces the
  `IntegrationError` that started the unwind. The caller then reports "could not put … back"
  and loses the first cause (for example "its patch does not apply onto …"). This is minor
  because both are `IntegrationError` and are caught the same way. Chaining the first error
  (`raise … from`) would keep it.
- Efficiency, `template/src/pdca_harness/integrate.py:814-833`: each accept that gets past C6
  runs a full `_fetch` (origin, the base remote and any stack remotes), rebuilds the would-be
  commit of every already-accepted sibling on the same target, and replays the fold twice
  (`alone` and `held`). With n accepts in a wave, that is O(n²) apply/commit/merge steps plus
  n fetches, all while the sign-off sweep waits. Waves are small, so this is fine for now. If
  it starts to matter, cache the built commits and the `alone` result per wave (both depend
  only on the accepted set and `tip`).
- Reuse looks right. The trial reuses `_held_by`, `_merge`, `integ_lock`, `_integ_worktree`,
  `_prepare_worktree`, `signoff.ensure_needs_human_item` and `waves.diff_files`. It does not
  copy the fold's rule. `publish.cut_base` shares `_checkout_base` with `publish()`, so the
  base the trial builds on cannot drift from the base publish cuts from.
- Tests (`template/tests/test_flow_same_wave_accept_trial.py`): every leg goes through the real
  `_drive_wave` → `_apply_decision` path, as the brief asks. `_drive_wave` and
  `signoff.record` are not stubbed. I found no test that passes for the wrong reason. One gap:
  no test covers the `_LineBroken` / `IntegrationTreeError` path from the first bullet. Leg (e)
  only injects a failed `git apply` (`template/tests/test_flow_same_wave_accept_trial.py:313`).
