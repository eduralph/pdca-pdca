## Motivation

Two real pdca-pdca batches (2026-07 and 2026-08-01) had same-wave bundles whose branches conflicted with no `Conflicts with` declared. Then, the fold stopped the batch. Since #674 it holds one bundle and the run goes on — but only after both bundles were published, so two draft PRs now conflict with each other at merge time, and the held one's PR is work the human must close or redo. The issue's point stands for that part: the conflict is knowable from the patches before publish, and git can tell for sure.

## Design

- After the wave's bundles are accepted and their publish texts are drafted and T4-gated, and before any push, run the same trial the fold runs: the wave's accepted work in fold order onto the line the wave was built from. Every bundle the trial would hold for a same-wave conflict is taken out of `to_publish` and recorded in `held_conflict` with its partners and files, so the existing `_runnable` holds, the end-of-run report and the exit code all treat it as they treat a fold-time conflict hold today.
- Before publish there is no pushed branch to read. The trial therefore needs each bundle's would-be commit built locally — the base that bundle was built on plus its `patch.diff`, committed in the integration worktree and never pushed — and judged with the fold's own clash rule (`integrate._held_by`, integrate.py:1785). The rule (fixed here, not Do's call): each would-be commit is the bundle's `patch.diff` applied onto the exact commit publish cuts its PR branch from — `checkout_base` as `publish` computes it (`template/src/pdca_harness/publish.py:261-265`: the recorded line tip when stacked, i.e. the commit the bundle was built on, or its own base under #738's `own_bases`; else `origin/<stack_branch>` or `<base_remote>/<base>`) — so it has the same parent and the same tree as the branch publish pushes. The trial runs in the fold's shared integration worktree under the same lock: take each target tree's lock with a `contextlib.ExitStack` exactly as `_fold_lines` does (`flow.py:1253`, passing `locks=` into `integrate`), and leave the tree reset as the fold expects to find it.
- Only `ready` bundles (texts drafted and T4-passed) are in the trial; a bundle that will not be pushed this run cannot hold a sibling.
- If A's push fails after the trial held B for A, B stays held (criterion e).
- A held, unpublished bundle must not also be reported as "pushed no branch" (`held_unpushed`): it is a conflict hold.
- The fold's own #674 check stays — the trial is an early answer, not the only one (a branch can change between the trial and the fold).

## Alternatives considered

- **Footprint overlap only** (the advisory that exists, flow.py:1586). Shared files are not proof of a conflict; using it to block would hold bundles that merge cleanly.
- **Plan-exit advisory** (issue's layer 1). Useful, but needs a structured file-list on briefs; out of scope.
- **Re-sequence automatically.** Move the held bundle to the next wave and rebuild it on the line. Gives the best outcome (it lands in the same run) but means an unprompted iterate; left as an open question.

## Impact & compatibility

- Fewer conflicting draft PRs; the held bundle has no PR until it is rebuilt.
- No config or brief change.

## Open questions

- Should a held bundle be re-queued automatically into the next wave (iterate-do on the line), instead of waiting for the human to declare `Conflicts with` and re-run? Recommended: not in this change.
