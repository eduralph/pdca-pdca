# Adversarial review — issue 395 (round 5)

I re-ran `tests.test_flow_same_wave_prepublish` on the patched target: 30/30 pass. The C4 log shows 25 of those 30 fail on their assertions with the production change reverted, not on imports. They drive the real `flow._drive_and_act` and the real `publish.publish` against a bare origin. I could not break the red→green proof or the trial itself. The bullets below are about the two round-4 fixes: the re-run hint and naming the stale PR. Each one was confirmed with a probe in my scratch folder, using the test file's own fixture.

- NEEDS-HUMAN [impl] — **A batch re-run after a trial hold still exits 0 and says "nothing to do".** `template/src/pdca_harness/flow.py:3506` drops every COMPLETE bundle from the batch sweep before `_terminal_hint` (`flow.py:1895`) can see the hold record. When nothing else is in flight, `flow.py:3514-3517` returns `{}`, and `cli._report_batch` returns 0. Probe (`scratch/probes/probe_batch_rerun.py`): run 1 holds 11 (rc 3, `conflict-hold.json` written). `flow.flow_batch(csv=…)` with the Plan session stubbed then prints `flow: nothing to do — no in-flight briefs (all COMPLETE …)` and exits 0 with `holds == {}`. The same disk state through `pdca flow 10 11 12 20` exits 3. That is the false "nothing to do" plus exit 0 that round-4 item 2 asked to fix, on the route a `--from-csv` batch uses. The motivating real batches were CSV batches. `docs/07-crosscutting.md:771-772` says without limits that "a re-run that finds it finished, still with no PR of its work, exits 3". Either have the batch route name and record finished bundles that still have a hold on record, or scope the docs to `pdca flow <ids>`. Add a test either way.
- NEEDS-HUMAN [impl] — **When the partner's PR is closed because the partner is being redone, the held bundle is told to publish anyway.** `template/src/pdca_harness/flow.py:1370-1377` (`_pr_closed`) counts a partner as "will not land" as soon as its recorded PR reads CLOSED. It never checks that the partner bundle is still finished. `publish.json` survives an iterate, so a partner that was closed in order to be rebuilt still counts as gone. Probe (`scratch/probes/probe_partner_redone.py`): run 1 holds 11 for 10. Then 10's PR is closed and 10 is iterated (state PLANNED, `publish.json` kept). `pdca flow 11` then says "that PR is closed unmerged now, so that hold no longer stands … `pdca publish 11`" (rc 3, `unpushed`). Following that opens 11's PR, and 10's rebuild then publishes a PR that conflicts with it, which is the outcome this change exists to prevent. Fix: treat a partner as gone only when it is COMPLETE and its PR is CLOSED. Add a test.
- NEEDS-HUMAN [impl] — **The step after a stale PR is named still says "re-open it", and doing so changes nothing.** `template/src/pdca_harness/flow.py:1432-1433` returns the `open` hint (`flow.py:1317`: "re-open it, `pdca publish {iid}`, or re-drive {name}") for a trial-held bundle whose partners all closed. When an earlier attempt's PR is on record, the same line now says that PR "still shows what an earlier publish of it pushed". So the advice reads as "re-open the PR that shows the rejected attempt". Re-opening it also changes nothing: the carry (`flow.py:1584-1586`) and `_terminal_hint` (`flow.py:1895`) decide from the hold record and never read 11's own PR state. The next re-issue gives the same verdict again. "Re-drive" a COMPLETE bundle also needs an iterate. For this case only `pdca publish <iid>` works. `test_a_held_bundle_whose_partners_pr_closed_is_asked_to_publish_onto_its_pr` (`template/tests/test_flow_same_wave_prepublish.py:1026-1030`) checks that `pdca publish 11` is there, but not that "re-open it" is gone. Give the trial-held "hold no longer stands" case its own step.
- NEEDS-HUMAN [impl] — **A dry-run re-run calls GitHub and records a hold.** `template/src/pdca_harness/flow.py:1895-1902` (`_terminal_hint`) runs `_held_before` → `_pr_closed` → `merged.pr_state` (`gh pr view`) with no stub-publisher check. Probe (`scratch/probes/probe_dry_rerun.py`): after run 1, the same ids re-run with `publisher.mode = "stub"` make one `gh pr view https://example.test/pr/fix/10-10` call, and the run exits 3 with `holds == {"11": "conflict"}`. The carry's own rule is "A dry-run (stub publisher) asks no host and holds nothing" (`flow.py:1564-1568`). Skip the PR-state lookup (and maybe the hold) when the publisher is a stub.
- Not a refutation, just a note on the evidence: in `template/tests/test_flow_reissue_after_conflict_hold.py` all 24 cases are red in C4 only because `mock.patch.object(flow, "_held_before_publish", …)` raises `AttributeError` on the reverted tree (C4 log lines 962-1582). The real red→green proof is the 25 assertion failures in `test_flow_same_wave_prepublish.py`, and that proof holds.
