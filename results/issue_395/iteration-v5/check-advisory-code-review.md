# Advisory code review — issue 395 (same-wave conflict caught before publish)

Lens: bugs the patch adds, plus reuse / simplification / efficiency. Advisory only. All gates in check-gates.json pass (C4 red→green, T3 2660 tests OK). The core trial is sound. The `checkout_base` refactor in publish behaves the same as the old inline code (`template/src/pdca_harness/publish.py:251` `wave_stacked` ≡ the new `cfg.wave_mode != "merge" and wave_base`). The trial applies the patch the same way publish does (`apply`, `add --all`, `commit`, compare `publish.py:298-308`). It follows the fold's order and clash rule (`_held_by`). Trial-held bundles are kept out of the fold and out of the "pushed no branch" notice (`flow.py:3303`). Findings, most important first:

- NEEDS-HUMAN [impl] — `template/src/pdca_harness/integrate.py:826-841`: when try 1 succeeds but some bundle in it could not be built (`unbuilt` not empty), the loop runs try 2. If try 2 then raises, `found` is set to `None`, and the whole target drops to the "publish only the first bundle" fallback. Try 1's good result is thrown away. So one bundle whose patch does not apply, plus one flaky fetch on the retry, stops every clean sibling from publishing, and changes a real `"conflict"` hold from try 1 into an `"unpushed"` one. Fix: keep the last good `(found, unbuilt)` and only fall back when no try succeeded. Add a test: try 1 has an unbuilt bundle, try 2's fetch fails, and the clean siblings still publish.
- NEEDS-HUMAN [impl] — `template/src/pdca_harness/integrate.py:876-881` (the build loop in `_same_wave_trial`) sits outside the `try/finally` that starts at :887, so a `_LineBroken` from `_would_be` (:930-947, raised at :944) leaves the trial without `_reset_tree(wt, pre)`. The docstring at :861-862 says "The line is put back at its start, clean, before it returns or raises", which is not true on this path. Nothing breaks today: the retry, or the fold's own reset, recovers the tree. Either move the build loop inside the `try`, or fix the docstring.
- `template/src/pdca_harness/integrate.py:836-837` (the `if not unbuilt: break` test): the retry also runs when a bundle failed for a reason that will fail again the same way (its patch does not apply onto `ref`). That costs a 1 s sleep plus a second full fetch of origin and the base remote per target per wave, just to get the same `unbuilt`. Cheap fix: retry only when try 1 raised, or when an unbuilt cause came from a git step, not from `git apply`. Low priority.
- `template/src/pdca_harness/flow.py:1895-1902` (`_terminal_hint`), reached from `flow.py:3673-3677`: a skipped COMPLETE bundle with a conflict hold on record now asks the host for each partner's PR state (`_pr_closed` → `merged.pr_state`) and records a hold (exit 3), even when the publisher is `stub`. The carry says "A dry-run (stub publisher) asks no host and holds nothing" (`flow.py:1536`, `_carry_finished` docstring). A dry re-run therefore now makes `gh` calls and exits 3. Probably harmless, but it does not match the carry's dry-run rule. Consider skipping the network check under `stub`. No test covers the skip path in a dry run (`test_a_dry_run_keeps_the_hold` covers a driven bundle, not a skipped one).
- `template/src/pdca_harness/flow.py:3677` writes the holds key with `removeprefix("issue_")`, while the existing collector at `flow.py:3383-3386` uses `.replace("issue_", "")`. They give the same result for normal ids, but use one form in both places.
- `template/src/pdca_harness/flow.py:1729-1733` and `:1812-1815`: the "no branch pushed, no PR opened" + `_earlier_pr` sentence is built twice in slightly different words. A small helper would keep the two lines in step. Cosmetic.

No other correctness bugs found in the diff. The new test file (`template/tests/test_flow_same_wave_prepublish.py`) runs the production `flow._drive_and_act` path (C5 confirms) and covers brief legs (a)–(f), plus the fail-closed and re-run/re-issue cases.
