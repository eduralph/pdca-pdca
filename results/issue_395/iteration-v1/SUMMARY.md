# Adversarial review — issue 395 (same-wave conflict caught before publish)

Advisory only. I tried to break the evidence, the fix and the verdict. The red→green proof holds up, and the trial itself matches the fold. I found one real defect: what happens when the batch is run again after a trial hold.

## Findings

- NEEDS-HUMAN [impl] — **Re-running the batch after a trial hold gives the advice #694 removed, and following it opens the conflicting PR this change exists to prevent.** A bundle the trial holds ends COMPLETE with no `publish.json` (flow.py:3102-3108, 3113-3114). On a re-run, the pre-wave carry treats it as a finished id with no PR. `_finished_head` returns the `"open"` hint (template/src/pdca_harness/flow.py:1291-1292), which reads ``get issue_11's PR open … `pdca publish 11`, or re-drive issue_11`` (flow.py:1317). It never names issue_10. Concrete case, run in my sandbox against the patched tree with the trial left on (10 and 11 in wave 0 change the same line, 20 depends on 11, then a re-run driving only 20):
  - Run 1 ends: ``Proposed, for you to confirm: declare `Conflicts with: 10` in issue_11's brief, then rebuild issue_11 on a base that holds issue_10. issue_11 was not published …``
  - Run 2 says: ``issue_11 (finished in an earlier run) is not carried …: no PR with a pushed branch on record (publish.json) — holding issue_20 this run; get issue_11's PR open with its branch on origin (re-open it, `pdca publish 11`, or re-drive issue_11), then re-issue.``

  `pdca publish 11` opens exactly the PR that conflicts with 10's. Re-driving gives the same patch on the same base, so it conflicts again. The flow.py:1460-1461 docstring promises this case gets "never the `open` hint". The patch hides the regression: template/tests/test_flow_reissue_after_conflict_hold.py:123-124 mocks `_held_before_publish` to `{}` (with `create=True`). Its new docstring (:115-119) claims the mocked state is "the state a re-issue judges here". That is true only in the rare case where a branch changed after the trial; it is not the normal outcome of a run. With that mock removed in a copy, 18 of 24 tests in that file error: run 1 no longer leaves 11 with a PR (`_finished_open`, :145 via :177). Fix: let the carry recognise a bundle held before publish, for example from a marker the trial writes into the bundle, or by re-running the same-wave trial for finished ids that have no `publish.json`. Give it the `_CONFLICT_STEP` with its partner, and add a re-run test with the trial on.

- NEEDS-HUMAN [human] — **Criterion (e) holds strictly more work than `main` when the partner's publish fails for a reason the trial cannot see.** The trial runs after T4 but before checks that live inside publish: the host-CI gate (publish.py:379-383), the line-tip refusal (publish.py:364-367), and commit hooks (publish.py:309; the trial commits with `--no-verify`, integrate.py:846). Example: A's host CI is red. A pushes nothing, B is held for A with no PR, and B's dependents and `Conflicts with` partners are held too. On `main`, B would have been published and folded cleanly, because the unpushed A is left out of the fold (flow.py:3169), and its dependents would have been built. The brief asks for this behaviour on purpose (criterion e: "A is still accepted work and will be re-published"), so it is a scope call for sign-off, not a bug.

- Minor, no rebuild needed: the hold line for a trial hold still says the partner was "merged before it in the same wave k" (flow.py:1644, called from flow.py:3109). Nothing has been merged at that point, and in case (e) the partner is never pushed. The added "Found before publishing" suffix partly covers this.

- Minor, no rebuild needed: the trial's cost grows with the square of the wave size. integrate.py:819 re-merges every kept head from `pre` for each new bundle, and each `_would_be` (integrate.py:816) and `_trial` does two full checkouts. N bundles on one target means about N²/2 merges and 4N checkouts before anything publishes, where the fold does about N merges. Chaining through `_trial`'s `made=` would make it linear. This only matters for large waves in large repos.

- Test gap, not a defect: every shipped test where the trial actually holds a bundle is in wave 0, where the cut point is `<base_remote>/<base>`. No shipped test holds a bundle in wave ≥1, where the would-be commit is cut from a recorded line tip or an own base (#727/#738). My scratch tests ran that path (20 and 21 in wave 1 on one own base, and on two different own bases): 20 published, 21 held as `"conflict"` with no branch. So it works, but nothing guards it.

- **Red→green, reproduced.** On the target tree, `tests.test_flow_same_wave_prepublish` plus `tests.test_flow_same_wave_conflict` pass 15/15. # Advisory code review — issue_395 (same-wave conflict caught before publish)

Lens: correctness bugs the patch adds, plus reuse / simplification / efficiency. Advisory only. Gates: C4 is red pre-fix (2 of 7 new cases fail: legs a and e) and green post-fix; T3 suite green.

The core logic looks right. `publish._checkout_base` is a faithful extraction of the old inline rule. `cut_base` picks the same remote and ref that `publish` fetches and cuts from. The trial mirrors the fold's order and calls the fold's own `_held_by`. The `held_unpublished` guard keeps a trial-held bundle out of the `"unpushed"` bookkeeping. No blocking correctness bug found. Findings, all minor:

- NEEDS-HUMAN [impl] — `template/src/pdca_harness/flow.py:1673` — the fail-open path (a trial that raises `IntegrationError` holds nothing, prints a warning, and the wave publishes as before) has no test. It is a deliberate design branch, and the brief's leg list doesn't cover it. A small case would pin it down: a stubbed `integrate.same_wave_holds` that raises, then assert both bundles publish, the warning is printed, and the fold still holds B. Without that case, a later change that lets the exception escape, or that keeps the partial `held` dict, would go unnoticed.
- NEEDS-HUMAN [impl] — `template/tests/test_flow_reissue_after_conflict_hold.py:123-124` — the test turns the trial off with `mock.patch.object(flow, "_held_before_publish", ..., create=True)`. The symbol now exists, so `create=True` is not needed. It also hides a rename: if `_held_before_publish` is renamed, the patch silently adds a dead attribute, the trial runs again, and these cases quietly test something else. Drop `create=True`.
- `template/src/pdca_harness/integrate.py:819-826` — wasted work. Each candidate replays the whole `[*kept, head]` merge chain from `pre`. On a failure, `_held_by` (`integrate.py:1890`) runs that same chain again, along with its own `pre`+`head` check. The `elif kept and at == len(kept)` guard also repeats a check `_held_by` already makes. Merges grow roughly as N² per target for a wave of N bundles. The fold builds the line one merge at a time (`integrate.py:647-686`). Waves are small, so this is a cleanup, not a bug. The simpler form is to call `_held_by` whenever `at is not None and kept`, or to merge each kept head onto `branch` as you go, the way the fold does.
- `template/src/pdca_harness/publish.py:261` vs `publish.py:767-775` — the "cut from the recorded tip" rule now lives in two places: `cut_from_tip` (still used at :340 and :360 for the host-CI pin and `_line_tip_refusal`) and the condition inside `_checkout_base`. The docstring calls `_checkout_base` "the ONE rule", but the two conditions could drift apart. Better to derive `cut_from_tip` from that helper, or have the helper return it too.
- `template/src/pdca_harness/flow.py:3102-3104` — the trial only sees `to_publish` (`complete` minus `published`). The fold's wave is all of `complete` (`wave_names`), so a bundle of the wave that was already published earlier in the run is in the fold's merge order but not the trial's. I found no path in this diff that puts a wave's bundle in `published` before its own wave runs, so today this is theoretical, and the fold's own #674 check still catches it. Noting it only because the brief says "mirror the order".
