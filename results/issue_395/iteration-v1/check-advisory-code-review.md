# Advisory code review — issue_395 (same-wave conflict caught before publish)

Lens: correctness bugs the patch adds, plus reuse / simplification / efficiency. Advisory only. Gates: C4 is red pre-fix (2 of 7 new cases fail: legs a and e) and green post-fix; T3 suite green.

The core logic looks right. `publish._checkout_base` is a faithful extraction of the old inline rule. `cut_base` picks the same remote and ref that `publish` fetches and cuts from. The trial mirrors the fold's order and calls the fold's own `_held_by`. The `held_unpublished` guard keeps a trial-held bundle out of the `"unpushed"` bookkeeping. No blocking correctness bug found. Findings, all minor:

- NEEDS-HUMAN [impl] — `template/src/pdca_harness/flow.py:1673` — the fail-open path (a trial that raises `IntegrationError` holds nothing, prints a warning, and the wave publishes as before) has no test. It is a deliberate design branch, and the brief's leg list doesn't cover it. A small case would pin it down: a stubbed `integrate.same_wave_holds` that raises, then assert both bundles publish, the warning is printed, and the fold still holds B. Without that case, a later change that lets the exception escape, or that keeps the partial `held` dict, would go unnoticed.
- NEEDS-HUMAN [impl] — `template/tests/test_flow_reissue_after_conflict_hold.py:123-124` — the test turns the trial off with `mock.patch.object(flow, "_held_before_publish", ..., create=True)`. The symbol now exists, so `create=True` is not needed. It also hides a rename: if `_held_before_publish` is renamed, the patch silently adds a dead attribute, the trial runs again, and these cases quietly test something else. Drop `create=True`.
- `template/src/pdca_harness/integrate.py:819-826` — wasted work. Each candidate replays the whole `[*kept, head]` merge chain from `pre`. On a failure, `_held_by` (`integrate.py:1890`) runs that same chain again, along with its own `pre`+`head` check. The `elif kept and at == len(kept)` guard also repeats a check `_held_by` already makes. Merges grow roughly as N² per target for a wave of N bundles. The fold builds the line one merge at a time (`integrate.py:647-686`). Waves are small, so this is a cleanup, not a bug. The simpler form is to call `_held_by` whenever `at is not None and kept`, or to merge each kept head onto `branch` as you go, the way the fold does.
- `template/src/pdca_harness/publish.py:261` vs `publish.py:767-775` — the "cut from the recorded tip" rule now lives in two places: `cut_from_tip` (still used at :340 and :360 for the host-CI pin and `_line_tip_refusal`) and the condition inside `_checkout_base`. The docstring calls `_checkout_base` "the ONE rule", but the two conditions could drift apart. Better to derive `cut_from_tip` from that helper, or have the helper return it too.
- `template/src/pdca_harness/flow.py:3102-3104` — the trial only sees `to_publish` (`complete` minus `published`). The fold's wave is all of `complete` (`wave_names`), so a bundle of the wave that was already published earlier in the run is in the fold's merge order but not the trial's. I found no path in this diff that puts a wave's bundle in `published` before its own wave runs, so today this is theoretical, and the fold's own #674 check still catches it. Noting it only because the brief says "mirror the order".
