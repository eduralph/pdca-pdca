# Advisory code review — issue_727 (dependency-scoped bases)

Lens: correctness bugs the patch adds, plus reuse / simplification / efficiency. Grounded on the patched tree at `$PDCA_TARGET`. All gates in `check-gates.json` pass (T4 is deferred to publish). I found no blocking correctness bug. The core logic holds up: the closure walk (`_closure_members`), the "build every base, then point" order in `_bundle_bases`, the `merged_heads` record filled only after the push succeeds, and the split between line and per-bundle rewrite reports. The findings below are smaller.

- NEEDS-HUMAN [impl] — `template/src/pdca_harness/flow.py:1042` — `_line_prs` names a line-cut PR only when the head the line had when that PR was cut equals the line's *current* head for the branch (`had.get(name) == took`). If a later fold took a newer, fast-forwarded head of the same branch (`carried_heads[name]` moves forward), a seam PR cut earlier drops out of the list. But it still holds the older head, and any rewrite that loses the newer head also loses the older one (the older head is an ancestor of the newer). So the #633/#695 messages can leave out a PR that needs a rebuild. Fix: list every pushed seam PR whose `had` has *any* head for `name` (`name in had`). The fold refuses rewrites, so every head the line took is an ancestor of the current one. No test covers a branch the line takes twice.
- `template/src/pdca_harness/flow.py:2714` — a failed per-bundle base build now sets `line_stopped`, which also skips the end-of-run #695 check (`flow.py:2864`). The comment there says a stopped run "reported the rewrite a fold refused". That is true for a rewrite stop. It is not true for a base that fails for another reason (member merge clash, foreign work, refused push), where branches the earlier folds carried go unchecked at the end. This matches how a non-rewrite fold failure already behaves, so it is not a new class of gap, and the restated test `_stopped_at_b` (`test_integrate_carried_rewrite_late.py`) asserts this skip on purpose. Noted, not tagged.
- `template/src/pdca_harness/flow.py:937` (efficiency) — `_closure_members` calls `integrate._fold_candidates` over all of `built` (which reads each bundle's `publish.json` and target) once per runnable bundle, and `publish._resolve_target(d)` is resolved again at `flow.py:~1022` for each seam. Computing `cands`, `on_target` and `onto` once in `_bundle_bases` (`flow.py:1000`) and passing them in would remove an O(runnable × built) file-read loop. This is a small cost at today's batch sizes. A cleanup, not a bug.
- `template/src/pdca_harness/flow.py:2926` (wording nit) — the line's `unchecked` message adds `({'; '.join(cut…)) or 'none'})`. With no line-cut PRs it reads "rebuild … every PR this run cut from the line after it took that commit (none)". With some, it reads "(issue_S after issue_A's; …)". Both are understandable but clumsy. `_late_line_rewrite` (`integrate.py`) already splits the no-PR case into its own sentence, and the `unchecked` path could do the same.
- Reuse: no duplicate logic added. `_holds_took` is pulled out cleanly and now shared by `_carried_rewrite`, `_carried_tips` and `rewritten_carried`. `build_bundle_base` still uses `_carried_rewrite` for its own refusal (`integrate.py:833`), which is right.
- Tests: the restated suites keep content checks rather than dropping them. Each `base == self.line` became "own base branch + holds closure + `rev-list --no-merges … --not main <closure>` is empty", which is stricter. Two inversions are intended behaviour changes and need to appear in build-notes' before/after list, which I cannot see: `test_flow_slice.py`'s renamed `test_a_dependent_carries_only_its_prerequisite_…` (ZZ is now *not* an ancestor of `fix/issue_ZB`, one merge base, `_update_from_main` removed), and `test_integrate_carried_rewrite_late.py`'s fault-injection points moved from the line's push to B's base push.
