# Advisory code review — issue 673

Overall: the patch does what the brief asks, and I found no blocking correctness bug. The new check reuses the #623 machinery (`_undone_paths`, `_own_commits`, `_reset_line`) instead of copying it. Pulling the message builder out into `_removed` keeps the base-merge wording byte-identical. `_merge` always uses `--no-ff` (`template/src/pdca_harness/integrate.py:1026`), so `HEAD^1` in `_keep_merge` is always the line tip from before the merge. Gate logs agree: C4 shows 4 of the 6 new tests red without the fix and all 6 green with it, and T3 is green.

Findings (small, in priority order):

- NEEDS-HUMAN [impl] — `template/src/pdca_harness/integrate.py:997`: `_reset_line`'s error still says "after refusing to take the base in". The patch now calls it from `_keep_merge` (`:726`, `:730`) for a bundle-branch refusal too. If that reset fails, the user gets a `_LineBroken` that blames the base merge when it was really the merge of `d`'s branch. Fix: make the wording neutral ("after refusing a merge"), or pass in what was refused.

- `template/src/pdca_harness/integrate.py:916-940` (missed case, low impact; I'm not filing it NEEDS-HUMAN): `_own_change` exempts a path when ANY own commit touches it. It does not check that the branch's final content of the path came from that commit. Example: B is cut from the line, and B's own commit edits `a.txt` to `a2`. Then B is updated from the reverted `main`, which gives a modify/delete conflict that gets resolved by deleting. The update merge matches `main`'s side, so on its own it is not an own change. But the earlier edit puts `a.txt` in `mine`, so the deletion goes through unflagged. You could argue the author chose that deletion while resolving the conflict. The brief also allows "an equivalent rule; say which". If you want it tight: exempt a path only when `head`'s content of the path matches what the newest own commit touching it left.

- `template/src/pdca_harness/integrate.py:970` and `:982` (minor duplicate work): `d` is always in `owners` (`fold` builds `owners` from `bundles`, `:535-538`). So when something is undone, `_own_commits` walks `d`'s branch twice: once for `head`, and again in the owners loop, where `_rev(wt, pub[1])` gives the same tip. This only runs after a hit, so the cost is small. Reusing the first result for `d.name` would remove the second walk.

- `template/src/pdca_harness/integrate.py:926-939` (simpler option, optional): the loop starts one `git diff` per parent per own commit. `git diff-tree -r -c --name-only --root <commits> -- <paths>` may do the same thing in one call. `-c` (combined diff, the merge-aware diff mode) lists only paths that differ from every parent, which is the intersection the loop builds by hand. Before switching, check that combined diff reports a path deleted in a merge on the git versions you support. The current code is correct, and it only runs when a path was undone.

- `template/src/pdca_harness/integrate.py:933` and `:961` (nit): the empty-tree hash is computed in two places. A small shared helper would remove the repeat. Computing it at runtime instead of hard-coding the constant is right, because SHA-256 repositories use a different hash.

- `template/tests/test_integrate_revert_via_branch.py:393-400` (test nit): the "edits the file" case only checks `a.txt == "a2\n"` on the tip. It does not check that the fold pushed (`tip != t1`) or that `fix/C` is an ancestor of the tip, as the delete case does (`:389-391`). The content check already implies a push, so this is about matching the other test, not about a gap in coverage. No test covers the other exempt case the docstring at `:921-922` mentions: a merge on the branch that resolves the path to new content.
