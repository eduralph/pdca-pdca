The C5 concern is a concrete implementation defect, not a disagreement with the accepted scope. `_own_change` unions every path touched by any candidate own commit, and `_undone_paths` excludes that entire path from protection. Neither step establishes that the commit produced the removal now being merged. Consequently an earlier addition, or an edit subsequently restored, can authorize a later deletion inherited solely from the base (target/template/src/pdca_harness/integrate.py:936, target/template/src/pdca_harness/integrate.py:970).

I exercised two additional histories against the patched production code with the existing `StackFoldGit` fixture:

1. Fold A, which adds `a.txt`. Publish B adding only `b.txt`, based directly on `origin/fix/A`. Merge A into main, revert A there, update B from main, and fold `[A, B]`. A's original addition remains reachable through B without crossing a skipped first-parent commit, so it enters the exemption. B's own change never deletes `a.txt`.
2. Fold A. Publish B from the integration line adding `b.txt`; on B, edit `a.txt` and then restore it to A's content. Merge A into main, revert A there, update B from main, and fold `[A, B]`. B's net change still does not delete `a.txt`, but its earlier touches exempt the inherited deletion.

Both runs returned without `IntegrationError`, advanced the origin line, left `a.txt` absent, and made the base revert an ancestor of the line tip (review-probe.log:1, review-probe.log:6).
