# Plan advisory — issue 673 / fold-stops-on-a-revert-brought-by-a-bundle-branch

I tried to fault the root cause, the success criterion and the scope. **The root cause holds.** `_merge_published` (`integrate.py:622-626`) merges a live branch and returns on `rc == 0` without any `_undone_paths` check. The only caller of `_undone_paths` is `_take_in_base` (`:727`), and the only way to reach it is `_gone_branch` (`:620`, `:687`). `_merge` uses `--no-ff` (`:874`), so the line's first-parent chain and `_cut_point` behave the way the brief's walkthrough assumes. The citations resolve on the target. Two things in the existing code back gap 2: the test comment at `test_integrate_stack_bases.py:589-590` ("one cut from the reverted main would carry the revert itself") and the issue thread ("A later bundle whose branch was cut from a base that already holds the revert…"). The gap 1 decision (document it) is one of the two outcomes the issue's "Done when" allows, so it is not hidden scope.

The remaining faults are in the criterion and the ordering:

- NEEDS-HUMAN — **The "updated from" path is in the defect statement but no test covers it.** The Defect line says the bug hits a branch "cut from (or updated from) a base that already holds a revert". Criterion (1) only builds the "cut from" case (`b = _publish("B", …)` off `origin/main`). The "updated from" case is the one where the new "absent its own commits doing so" exemption can go wrong. `_own_commits` counts a merge commit made on the PR branch as the bundle's own work (docstring at `integrate.py:789-790`). GitHub's "Update branch" merge of the reverted `main` into `fix/B` is exactly such a commit, and it is the commit that brings the revert. If the implementation decides "B's own commits touched `a.txt`" in a way that counts that merge commit, the check is silently exempted. The fixture already has the helper for this (`StackFoldGit._update_branch`, `test_integrate_stack_bases.py:199-204`). Suggest adding a criterion: B is cut from the old `main`, then `_update_branch("B")` runs after the revert, and the fold raises naming `a.txt` / `issue_A` / `issue_B`.
- NEEDS-HUMAN — **Part of criterion (2) cannot be checked as written.** It says "(a later bundle in the same call that brings no revert is still merged)", but the history it specifies is `fold(cfg, [a, b], …, skipped=skipped)`. That list has no bundle after `B`, so the clause cannot be asserted, and it is the only part of (2) that shows `skipped` skips one bundle rather than ending the fold. Suggest naming a third bundle, e.g. `d = _publish("D", {"d.txt": …}, cut_from=f"origin/{LINE}")` folded as `[a, b, d]`, and asserting `list(skipped) == ["issue_B"]`, `d.txt` and `a.txt` on the tip, and that the revert is not an ancestor of the tip. The existing test at `:585-602` does this.
- NEEDS-HUMAN — **The brief says it builds on 672, but 672 is not declared as a dependency.** The Ordering note says "672 (wave 0) edits the fold's skip handling, so this slice builds on it". 672 appears only under `Conflicts with`, and the brief says it is "Verified against … `d6057eb`", where nothing references #672 (no `#672` anywhere in the target). No `dependency-state.json` was provided, so I could not check 672's state. Criterion (2) asserts the `skipped` semantics of `fold` (`integrate.py:537-539`), which is the code 672 changes. If 672 lands first, (2) and the `:5xx` line citations may no longer match. If building on 672 is required, it should be a `Depends on: 672` (so it is checked), not a conflict edge that only sets the order. Otherwise the note should say that (2) is written against pre-672 `skipped` behavior.
- NEEDS-HUMAN — **One citation in the peer-callsite guidance points at the wrong lines.** "Citations expected" says to mirror `_take_in_base` at `integrate.py:719-746`: "record the tip before the merge, call `_undone_paths(…)`". On `d6057eb` the tip is recorded at `:713`, the merge is at `:716`, and `:719-725` is the conflict error message. The correct span is `:712-743`. The same field puts the bundle merge at `:626-635`, but the merge call itself is at `:624`, and the fix's hook point is the `rc == 0` return at `:625-626`. These are small, but Do must cite `path:line`, and Check will compare against these spans.
- NEEDS-HUMAN — **Criterion (4) covers existing tests by line range, so it can miss changed message assertions.** The existing #623 tests assert the base-merge wording ("taking origin/main in would remove", `test_integrate_stack_bases.py:523-524`, `:597`). The brief asks the new refusal to also name "the bundle whose branch brought the change". If Do changes the shared message helper so both refusals use the new wording, these assertions break, and "stay green" will push Do to keep two message formats. It would help to state explicitly whether the base-merge message must stay byte-compatible.
