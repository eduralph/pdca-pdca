The findings below are small.

- NEEDS-HUMAN [impl] — `template/src/pdca_harness/flow.py:1080-1083`: `_holds_work` checks that `at`, `tip` and `since` resolve before running `rev-list`, but it never checks `base_ref`. If the target checkout lacks `<base_remote>/<base>` (for example, a checkout left from an earlier run that this run never fetched because nothing on that target was carried or folded), `integrate._out` raises `IntegrationError` and the whole run stops. The docstring (`flow.py:1049-1052`, `:1076-1078`) promises the opposite: a commit the clone does not have "names nothing". This only bites when two finished `Conflicts with` partners both have recorded tips, so the risk is low. Fix: add `base_ref` to the `_rev` guard. Then a missing base gives "not below", which only leads to a refusal, never to a wrong base.
- `template/src/pdca_harness/flow.py:992-996` (efficiency, not a defect): `_bundle_bases` runs once per wave, and each call rebuilds `graph` and re-runs `_finished_after`, which does up to two `git rev-list` calls per finished×finished partner pair. The inputs (`finished`, `carried`, recorded tips) do not change after the carry, so the result could be computed once in `_drive_and_act` next to `carry_took` and passed in. The cost is small (pairs of finished `Conflicts with` partners are rare), so this is optional.
- `template/src/pdca_harness/flow.py:1435-1440` (wording): the carry message now says the run's bundles "ordered after them build on a base that holds them". That is not true at a seam: a bundle with `Stacks on` / `Onto branch` in its closure still builds on the line itself (`_closure_members`, `flow.py:944-947`). The message is only slightly off, but a reader debugging a seam case could be misled. Optional.
- NEEDS-HUMAN [human] — `template/tests/test_flow_dependency_scoped_bases.py:375` and `:390`: two tests are renamed and restated (`…keeps_the_line` → `…is_built_on_a_base_holding_it` / `…is_on_the_base`, with `_on_line` + `_has_all` replaced by `_own_base`). The brief's list of expected restatements does not include them, and it says "any change outside this list is a finding." The new assertions are not weaker: `_own_base` still checks COMPLETE and every closure commit. The change follows from the fix, because both tests are about a dependent's base. Iteration 1 raised the same point. I cannot see `build-notes.md`, so I cannot confirm it now lists these with before/after. The same goes for the `_built_on_own_base` swaps at `template/tests/test_flow_merged_prereq_on_line.py:235`, `:243`, `:321` (beyond the listed `:269`) and the `_publish_bundle` fixture change that keeps the brief at `template/tests/test_flow_resume_stack_prereqs.py:126-135`. The human should confirm these are accepted as in-scope restatements.
- `template/tests/test_flow_resume_stack_prereqs.py:188-200` (test strength, minor): the shared `_on_own_base` helper only checks that the base holds the listed prerequisites. It does not check that the base lacks the excluded ones. The brief's restatement wording asks for both ("holds the same prerequisite commits and lacks the same excluded ones"). The B case adds the lacks check by hand (`assertFalse(... fix/P ...)` near `:287`). In the other restated cases, the line held nothing beyond the prerequisite, so nothing is lost today.
