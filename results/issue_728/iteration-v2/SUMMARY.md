# Adversarial review: issue_728 (carried prerequisites in dependency bases)

**Bottom line:** the red→green evidence holds up. I re-ran it and it is real. But the fix has two regressions that I reproduced. In both, a run that finished cleanly before the patch now stops entirely, and an unrelated bundle in the same run never builds. No test covers either case.

## Evidence (could not refute)

- Re-ran the green leg on a scratch copy of `$PDCA_TARGET`: all 72 tests in the four bundle files pass. Swapped in the pre-fix `flow.py` (`git show HEAD:template/src/pdca_harness/flow.py`): 10 of the 11 new tests fail. That matches `gate-logs/C4-verify.log`. The tests drive the real `flow._drive_and_act` on real git, with only build, sign-off, publish and `gh` stubbed (`template/tests/test_flow_carried_prereq_bases.py:147-160`). Criteria (4) and (5) reach the real `_unowned_work` / `_carried_rewrite` refusals in `integrate.py`. No test re-implements production logic. One side note: criterion (5) (`test_flow_carried_prereq_bases.py:438`) also fails before the fix (`D` is built on the line and COMPLETE). So it is part of the red leg, not only the "guard" the brief expected.
- The restated assertions keep their "lacks" checks. For example, `test_flow_resume_stack_prereqs.py:286-289` still asserts that `P` is on neither `B`'s base nor the line, and `:469-471` keeps the `P`/`Q` exclusions. I found no weakened assertion.

## Refutations

- NEEDS-HUMAN [impl] — **Regression: the whole run stops when a held prerequisite sits behind a patchless node below a carried bundle.** The patch treats patchless finished ids as nodes for the carry's `dependents` (`template/src/pdca_harness/flow.py:1359-1364`) and for `held` (`flow.py:1455`). It does not do the same for `_cascade_not_clean`, which still reads only direct `Depends on` edges (`flow.py:1268`). **Concrete case** (reproduced on the new fixture): run 1 `[A, N, P, D, U]`, where `N` (`Depends on: A`) closes with no patch, `P` (`Depends on: N`) is built on a base holding `A`, and `D` (`Depends on: P`) and the unrelated `U` both fail. Then `A`'s PR is closed and run 1's line is deleted. Re-issue driving `D, U`: `A` is held, but nothing marks `P` as not clean, so `P` is carried onto the line along with `A`'s closed-PR commit. `D`'s base then refuses that commit with "No bundle of the run owns it … rebuild issue_P's branch", and the run prints `STOPPING — wave 0 and later waves not run`. **`U` is never built.** Before the patch, `D` and `U` were both COMPLETE (`D` on the line). With a direct `P Depends on: A` edge instead of going through `N`, the same run holds only `D` ("prerequisite(s) not ready (P)") and builds `U`. This also contradicts the new docstring at `flow.py:931-933` ("whose plain `Depends on` dependents wait — directly or through finished ids with no patch"). Fix I checked in a scratch copy: build `_cascade_not_clean`'s `prereqs` from `_plain_prereqs(cfg, d, through)`. With that change, `D` is held, `U` is COMPLETE, and `test_flow_carried_prereq_bases` and `test_flow_resume_stack_prereqs` stay green. Add this shape as a test.
- NEEDS-HUMAN [impl] — **Regression: a carried prerequisite whose PR was squash- or rebase-merged, with its branch deleted, stops the run.** The carry accepts a MERGED PR when the line holds its head (`flow.py:1188`). Its fold skips the gone branch for the same reason. `took` then records the bundle (`flow.py:1436`), and `_bundle_bases` makes it a member (`flow.py:992`, `:1013`). But `D`'s own base starts fresh from `origin/main`, which lacks the head after a squash or rebase merge. So `_gone_branch` raises (`template/src/pdca_harness/integrate.py:1409`, "a commit neither …-bD nor origin/main has"). **Concrete case** (reproduced): run 1 `[P, D, U]`, `D` (`Depends on: P`) and `U` fail. `P`'s PR is then squash-merged into main and `fix/P` is deleted (GitHub's auto-delete setting); `gh` reports MERGED with the old head. Re-issue driving `D, U`: `flow: carried issue_P`, then `could not build issue_D's own base from issue_P … STOPPING`. Neither `D` nor `U` is built. **Before the patch, both were COMPLETE.** `P`'s work is already on main, so there was nothing wrong to fix here. Possible fix: a carried id whose PR has merged into the base is not a member. Walk through it the way a patchless node is walked, since its work is on the base. No test covers a MERGED carried member.
- NEEDS-HUMAN [human] — **An out-of-batch prerequisite behind a patchless node is still skipped silently.** Run 1 `[A, N, D]`: `N` (`Depends on: A`) closes with no patch and `D` (`Depends on: N`) fails. Then re-issue `[N, D]` without naming `A`, with `A`'s PR still open and unmerged. `D` is built on plain main, COMPLETE, and `fix/D` lacks `A`. With a direct `D Depends on: A` edge, `_runnable` holds `D` ("issue_A not merged into main … name issue_A in the same `pdca flow <ids>` command"). The behavior was the same before the patch, so this is not a regression. But it is the brief's "ships missing a transitive prerequisite" defect, and the new docstring says otherwise (`flow.py:931`: "an out-of-batch prerequisite, on the real base once merged (`_runnable`)"). Nothing makes `D` wait for that merge when the edge goes through `N`. The fix belongs in `_runnable`'s #647 branch (`flow.py:769-806`), which the brief reserves for #729. You need to decide whether to file it as a follow-up there.
- How bad the two regressions are: a failed base build stops the **whole run** (`flow.py:1016`, then `:2808`), not just the dependent. The brief's goal says "stop the dependent". Criterion (4)'s test (`test_flow_carried_prereq_bases.py:418`) has no unrelated bundle, so it cannot tell "stop D" from "stop the run". Turning base-build failures into holds is #725's job and out of scope here. Until #725 lands, though, every wrong refusal from this patch (the two cases above) costs the entire run. And even after #725, the squash-merge case would still hold `D` for no reason.
- Conformance, not a defect: the resume suite's `_publish_bundle` fixture now saves and restores `brief.md` (`template/tests/test_flow_resume_stack_prereqs.py:126-135`). The change is sound: real `publish.py` never writes `brief.md`, and without it the walk would lose built bundles' edges. But it falls outside the brief's list of expected restatements, as do the `test_flow_dependency_scoped_bases.py` renames already raised in iteration 1. I could not see `build-notes.md`, so I can't confirm both are listed with before/after.
