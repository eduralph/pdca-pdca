# Adversarial review: issue_728 (iteration 3)

**Evidence: reproduced, holds.** In a scratch copy of `$PDCA_TARGET`, `tests.test_flow_carried_prereq_bases` passes 15/15 with the patch. With only `template/src/pdca_harness/flow.py` reverted to `HEAD`, 13 of the 15 fail on their assertions. The two that pass are the no-brief and missing-base guards. This matches `gate-logs/C4-verify.log`. The tests drive the real `flow._drive_and_act` on real git, so they test the production code, not a copy. Criterion (5) also fails before the fix (`D` is built), so it is part of the red leg, not just a guard. That does not hurt the proof.

I then tried to break the fix with scratch probes: the new test class plus new setups, run on both the patched and the reverted `flow.py`. Three probes break it.

- NEEDS-HUMAN [impl] — **Regression: squash-merging the bottom PR of a stack, then re-issuing, stops the whole run.** The patch walks a carried id in `on_base` but never makes it a member (`template/src/pdca_harness/flow.py:1003`, set at `:1474`). `_unowned_work` then counts a commit as owned only if it is a *member's* own work (`template/src/pdca_harness/integrate.py:1002-1005`). After a squash or rebase merge, main has the merged *content* but not the original commits. So when a member stacked on that id brings those commits in from below its cut point, nobody owns them. **Concrete case (reproduced):** run 1 `[A, P, D, U]`: `P` (`Depends on: A`) is built on a base holding A; `D` (`Depends on: P`) and the unrelated `U` fail. A's PR is then squash-merged into main and `fix/A` is deleted (GitHub auto-delete); P's PR stays open. Re-issue the same batch, driving `D, U`. Output: `flow: carried issue_A, issue_P`, then `could not build issue_D's own base from issue_P: … would hold <A's original head> … It is in the published head of issue_A, which issue_D does not build on … STOPPING — wave 0 and later waves not run`. `D` and `U` both stay PLANNED. **Before the patch, both were COMPLETE** (`D` on the line, which holds A and P). The message is also wrong: D does build on A, through P. Its advice to "add issue_A to issue_D's members" cannot be acted on. Merging the bottom of a stack first is the normal order, so this will be common. The new test `template/tests/test_flow_carried_prereq_bases.py:513` covers only a merged id with nothing stacked on it. Possible fix: count each `on_base` id's merged head as owned work in `_unowned_work` (the brief allows changes to that function). Or hold `D` with a "rebase P onto main" hint instead of stopping the run. Add this shape as a test.

- NEEDS-HUMAN [impl] — **Regression: a re-issue whose batch leaves out a carried bundle's prerequisite stops the whole run, and the advice it gives would break P.** The walk drops any edge to an id outside `graph` (`template/src/pdca_harness/flow.py:955`). Before the patch, every edge to a finished id was a seam that kept the line. Now a carried `P` becomes a member even when its own `Depends on` target was neither carried nor built. P's branch still brings that target's commits from below P's cut point, so the base is refused. **Concrete case (reproduced):** run 1 `[A, P, D, U]` as above (P on a base holding A; D and U fail; A's PR still open). Re-issue as `pdca flow P D U` (batch `[P, D, U]`). Output: `flow: carried issue_P`, then `could not build issue_D's own base from issue_P: … would hold <A's commit> … No bundle of the run owns it … rebuild issue_P's branch on a base without that work … STOPPING`. `D` and `U` stay PLANNED. **Before the patch, both were COMPLETE**, and D's content was correct (P and A). Following the advice would strip a declared prerequisite out of P. A prerequisite that is not a requested id, such as an adopted split child (`flow.py:1376-1378`), probably takes the same path, but I did not run that case. Possible fix: when the walk leaves the graph from a finished node at an id whose work is not on the base, fall back to the line (a seam) or hold `D`. Do not stop the run.

- NEEDS-HUMAN [impl] — **A carried PR squash-merged after the carry but before its dependent's base is built still stops the run.** `on_base` is decided once, at carry time (`template/src/pdca_harness/flow.py:1473-1475`, `_merged_on_base` at `:1201`). It is not checked again when `_bundle_bases` builds the base. **Concrete case (reproduced):** run 1 `[P, D, U]`, `D` and `U` fail. On the re-issue, a hook squash-merges P's PR and deletes `fix/P` right after the carry's fold. Result: `issue_P's branch origin/fix/P is gone and its PR … merged at …, a commit neither …-bD nor origin/main has … STOPPING`, and neither D nor U is built. Before the patch, both were COMPLETE. For a dependent in wave 0 this window is seconds. For one in a later wave it lasts as long as the earlier waves run. #727's built members have the same race, so the patch makes an existing hazard reach carried ids. It does not create a new kind of failure. Lower priority than the two above. Possible fix: re-check `_merged_on_base` for gone carried members inside `_bundle_bases`, after its fetch.

- NEEDS-HUMAN [human] — **A carry defect stops every bundle in the run, not just the dependent, and the patch makes this path more common.** Criterion (4) says the dependent "stays PLANNED". The implementation also leaves unrelated bundles unbuilt (`template/src/pdca_harness/flow.py:2848-2853`). With criterion (4)'s setup plus an unrelated planned `U`, U stays PLANNED after the patch; before it, U was COMPLETE (reproduced). Every stack-mode bundle built before #727 in wave 1 or later was cut from a line holding all earlier waves' work. So resuming any such in-flight run whose finished bundle has a dependent will now stop the run. The suggested remedies ("add issue_X to issue_D's members", i.e. declare a false edge, or re-publish P) are not ones a user can act on cleanly. The brief leaves base-build holds to #725. A human should decide whether that is acceptable until #725 lands, given the three regressions above that go through the same stop.

- Note, not a blocker: the patch changes the `_publish_bundle` stub in `template/tests/test_flow_resume_stack_prereqs.py:130` so it keeps the bundle's brief. Before, the fixture's `_publish` overwrote it. That makes the stub more realistic, since real publish keeps the brief. `test_the_fold_after_wave_0_continues_the_carried_line` needs it (with the old stub, that is the only test in the file that fails). It is a fixture change, not one of the assertions the brief lists, so it should be in `build-notes.md` (I could not see that file). The other restatements I checked are not weaker: each assertion about a base moved to the dependent's own base, and every check on the line's own tip was kept.

Tried and could not break: `_finished_after`'s ordering of finished `Conflicts with` pairs (built before vs after, a patchless partner, a partner rewritten after a cut); `_plain_prereqs` loops and chains through several patchless bundles; holds and the not-clean cascade spreading through patchless nodes (iteration 2's case); a branch deleted without a fetch prune (the fetch does prune, `integrate.py:2035`); a merged PR whose branch is still present (it stays a member and merges cleanly); a cross-target walk (`on_target` filters it).
