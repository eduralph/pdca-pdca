# Adversarial review — issue_728 (iteration 4)

The red→green proof holds. I could not refute criteria (1)–(5) as written. I did find two new cases where the patch stops the **whole run**, so an unrelated bundle `U` is never built, where the code before the fix built both bundles. That is the same kind of regression rounds 2 and 3 sent back. I also found one older gap the patch documents but leaves open.

How I checked: I re-ran `tests.test_flow_carried_prereq_bases` on a copy of `$PDCA_TARGET` and got 21/21 green. `gate-logs/C4-verify.log` shows 19 of those 21 fail with the production change reverted, including every criterion (1)–(4) test. I then wrote probes on the same `StackFoldGit` fixture, driving `flow._drive_and_act`, and ran each one twice: on the patched tree and on a pre-fix tree rebuilt from the target's `HEAD` (`flow.py`/`integrate.py` only). The probes live in scratch copies; nothing was committed.

- NEEDS-HUMAN [impl] — **Regression: a closed `Conflicts with` partner below a carried bundle stops the whole run.** `template/src/pdca_harness/flow.py:1104` refuses to own a member's cut point when it holds work of an id whose PR is CLOSED. The build then raises at `flow.py:1070`, and `flow.py:2975` stops wave 0 and every later wave. The docstring at `flow.py:1091-1093` admits that such a member is still carried, because the not-clean cascade (`flow.py:1413`) follows only plain `Depends on` edges. **Concrete case (reproduced):** run 1 `[K, P, D, U]`, where `P` has `Conflicts with: K` and is built on `…-bP` holding K, and `D` (`Depends on: P`) and the unrelated `U` fail. K's PR is then closed. Re-issue driving `D, U`: `flow: carried issue_P`, then `could not build issue_D's own base from issue_P: … would hold e1f401d6c139 … No bundle of the run owns it … STOPPING — wave 0 and later waves not run`. **Both D and U stay PLANNED.** On the pre-fix tree the same run gives **D and U both COMPLETE** (D on the line). The new test `template/tests/test_flow_carried_prereq_bases.py:670-700` asserts the stop, but its run has no unrelated bundle, so it hides what the stop costs. The brief says carry defects "stop the dependent", and round 2 already ruled that a held prerequisite reached indirectly must hold `D`, not stop the run. Possible fix: run the `_holds_rejected` test at carry time. A finished id whose recorded cut point holds a CLOSED id's work would then go into `why` as `built_on`, the same way `_cascade_not_clean` handles a plain edge. P is then held, D waits, and U is built. Add `U` to that test.

- NEEDS-HUMAN [impl] — **Regression: a carried prerequisite merged into another branch, with its branch deleted, stops the whole run.** `_merged_on_base` (`flow.py:1319-1336`) treats a gone branch as fine only when `origin/main` has the merge. Otherwise the member stays in place, `integrate.py:1421` raises "merged somewhere other than origin/main", and `flow.py:2975` stops the run. **Concrete case (reproduced):** run 1 `[P, D, U]`, where D (`Depends on: P`) and U fail. P's PR is then merged with a merge commit into `release` and `fix/P` is deleted. Re-issue driving `D, U`: the carry still carries P (the line holds its head), then `could not build issue_D's own base from issue_P … STOPPING`. **D and U both stay PLANNED.** On the pre-fix tree, **D and U are both COMPLETE**, and D's content was right, because the line D was built on holds P's carried head. `test_flow_carried_prereq_bases.py:538-559` treats the stop as intended but has no `U`. This is rarer than the first case (someone has to edit the PR's base on the host), so it is lower priority. Possible fix: for this case only, fall back to the line seam (the line holds the carried head), or hold D. Don't raise.

- NEEDS-HUMAN [human] — **Older gap the patch documents but doesn't close: a prerequisite behind a patchless bundle that the re-issue leaves out ships missing.** The `_closure_members` docstring (`flow.py:933-935`) says `_runnable` waits for an unmerged out-of-batch prerequisite "only for an edge of the bundle's own brief, never for one reached through a finished id with no patch". **Concrete case (reproduced):** run 1 `[A, N, D, U]`, where `N` (`Depends on: A`) closes with no patch and D (`Depends on: N`) and U fail. Re-issue as batch `[N, D, U]`, driving `D, U`, with A's PR open and unmerged. Result: no carry, no hold, D is built on plain main, COMPLETE, and `fix/D` lacks A's commit. The control, the same run with `D Depends on: A` directly, holds D: "prerequisite(s) issue_A not merged into main … not built on a base missing them". The pre-fix tree does the same thing, so this is not a regression. But it is still the brief's "ships missing a transitive prerequisite" defect, and it breaks the invariant "a bundle with no patch is still a node in the graph its dependents' edges pass through". Closing it means extending `_runnable`'s #647 hold through patchless nodes, and the brief puts `_runnable` out of bounds (#729). That is a scope call for a human: fold it in here or file a follow-up.
