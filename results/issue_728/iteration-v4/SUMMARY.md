# Advisory code review — issue #728 (round 4)

Lens: bugs the patch introduces, plus reuse/simplification/efficiency. Gates are green (C4 red→green, T3 2602 tests OK). The three round-3 regressions are each covered by a new test: `template/tests/test_flow_carried_prereq_bases.py:563`, `:622` and `:645`. I ran two probes against the patched tree, each as a scratch test in this sandbox that subclasses the patch's own fixtures. Nothing was written to the target.

- NEEDS-HUMAN [impl] — **A closed partner PR stops being "rejected" once its head moves and its branch is deleted, so a dependent ships with the turned-down work.** `template/src/pdca_harness/flow.py:1308` records a CLOSED PR in `closed` only when the head the host reports resolves in the checkout (`integrate._rev(repo, head)`). Without that record, `rejected` at `flow.py:1005` is empty. `_owned_work` (`flow.py:1104-1106`) then counts the carried member's whole cut point as owned work, including the closed partner's commits. Probe (reproduced): the setup of `test_flow_carried_prereq_bases.py:670` (`K`; `P` `Conflicts with: K`, built on `…-bP` holding K; `D` `Depends on: P` fails). Then push one more commit to `fix/K`, delete `fix/K`, and have gh report CLOSED at the new head. Re-issue driving `D`: "issue_K … is not carried …: its PR is CLOSED", but `D` is **COMPLETE** on `…-bD`, built from P, and so holds K's original commit. With the branch kept, or the head unchanged, the same run refuses `D`, as the test at `:670` expects. Deleting a branch after closing its PR is a normal cleanup step, so this will happen. Possible fix: when the CLOSED head does not resolve, record the name anyway and judge it by what is still reachable. One option is to treat every member whose cut holds work above the closed id's own recorded tip as unowned. Another is to hold the dependent. Add this shape as a test. Pre-patch, `D` went on the line, which also held K through P, so this is not a new kind of wrong content. But it gets around the rule this patch adds (`closed` docstring, `flow.py` `_carry_finished`).

- NEEDS-HUMAN [human] — **A finished `Conflicts with` partner is never carried when only a `Conflicts with` edge reaches it, so the dependent's base lacks it.** The carry starts only from plain `Depends on` edges (`flow.py:1520`, `_plain_prereqs` at `:1444`). The walk drops any edge to an id outside `graph` (`flow.py:955`). Probe (reproduced): run 1 `[K, X, D]`, `D` `Depends on: X`, `Conflicts with: K`; X fails. Re-issue driving `X, D`: no carry, `D` is COMPLETE on `…-bD`, and K's commit is not in it. The new test `template/tests/test_flow_dependency_scoped_bases.py:390` passes only because `W` (`Depends on: K`) triggers the carry. This is the same pattern round 1 flagged for criterion (2). **Not a regression:** on the pre-fix tree the same run builds `D` on the line, which also lacks K. The brief's invariant covers the closure "the run built or carried", so K being outside it may be by design. A human should decide whether `Conflicts with` should trigger the carry (scope beyond this brief) or be left as a follow-up.

- `template/src/pdca_harness/flow.py:1062-1071` — `owned=_owned_work(...)` is evaluated inside the `try`. So a git failure in `_holds_rejected`/`_holds_work`, which happens before any build, also triggers `_merged_since` (one `gh` call per gone carried member) and gets the "could not build … own base" wrapper. The `_bundle_bases` docstring says instead that a failure in that read "names the two bundles". Low impact. Computing `owned` before the `try` would make the two error paths match their docs. Also on a retry: when the retry fails for some other reason, the re-raised message lists only the members still left. The dropped merged member is missing from it, which can confuse the reader.

- `template/src/pdca_harness/flow.py:1013` (efficiency, minor) — `cands`/`mine` are computed once per wave, before `_build_own_base` adds a late-merged member to `on_base`. Every later dependent in the same wave that names that member does one full failed base build (fetch, worktree, merges) plus a `gh` call before it retries without it. The result is correct, just repeated work. Skipping members already in `on_base` at the top of `_build_own_base`'s loop would avoid it.

Nothing else found on either lens. The restated assertions in the existing suites keep or tighten what they check. `_on_own_base` / `_own_base` / `_built_on_own_base` each still assert COMPLETE, the per-bundle base name, and that the prerequisites are present. `_built_on_own_base` also asserts there is no extra non-merge work.
