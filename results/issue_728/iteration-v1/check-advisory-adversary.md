# Adversarial review — issue_728 (carried prerequisites in dependency bases)

**Evidence: holds.** I re-ran the proof on sandbox copies of `$PDCA_TARGET` (patched, and with `flow.py` reverted to `HEAD`). `tests.test_flow_carried_prereq_bases`: 5 of 6 fail before the fix (criteria 1–5; the no-brief guard passes both ways) and all 6 pass after. The four touched suites pass after (67 tests). This matches `gate-logs/C4-verify.log`. The new tests drive `flow._drive_and_act` through real git and import only the production modules. They are not a copy of production code, and their assertions check what each base holds, not just branch names. Criterion (5) is red before the fix as well, which is stronger than the brief expected. The criteria as written are met. The findings below are inputs the criteria do not cover.

- NEEDS-HUMAN [impl] — **Regression: a false STOPPING through a `Conflicts with` edge between two carried bundles.** `template/src/pdca_harness/flow.py:951-952` skips a partner edge when `graph[n][1] >= wave`. Every finished id sits at wave -1 (`flow.py:986`), so the walk never follows a `Conflicts with` edge from one carried bundle to another. Concrete case (reproduced on `DependencyScopedBases`): run 1 `[J, K, W]`, `K` `Conflicts with: J`, `W` `Depends on: K`, `W` fails. Run 1 builds `K` on `…-bK`, which holds `J`. Re-issue driving `W`: J and K are carried, `W`'s members are `[K]` only, and `J`'s commit sits below K's recorded cut point. `_unowned_work` refuses: "could not build issue_W's own base from issue_K … It is in the published head of issue_J … STOPPING — wave 0 and later waves not run". `W` stays PLANNED. **Before the fix the same run built `W` COMPLETE** (on the line, which held J and K, which is W's true closure). The same happens with `D` `Conflicts with: K`. This is exactly the "wrongly stopped as holding foreign work" outcome the brief sets out to remove. The docstring's reason, "which of the two an earlier run built first is not known here" (`flow.py:927-928`), is not true. The member's recorded cut point (`_member_cut_point`) shows whether the partner's head is below it. A possible fix: walk a finished→finished partner when its PR head is an ancestor of the member's recorded stack-base tip. Add a test for this shape.
- NEEDS-HUMAN [impl] — **A patchless resume still ships without its transitive prerequisite when nothing else makes the carry run.** The new tests' criterion (2) (`template/tests/test_flow_carried_prereq_bases.py:233-254`) only passes because `W` (`Depends on: A`) forces A to be carried. Remove W: run 1 `[A, N, D]`, `N` `Depends on: A` closed with no patch, `D` `Depends on: N` fails. Run 1 builds D's base `…-bD` holding A. Re-issue driving `D`: the carry starts only from a drive-set bundle's plain `Depends on` that names a fold candidate (`flow.py:1269-1274`). D names only N, which has no patch, so nothing is carried. `graph` is `{N}` (`flow.py:986-988`), the edge N→A leaves the graph, and D is built **on plain main, COMPLETE, and `fix/D` lacks A's commit** (reproduced). The pre-fix code does the same, so this is not a regression. But it is the defect the brief names ("the dependent ships missing a transitive prerequisite") and breaks its invariant ("a bundle with no patch is still a node in the graph its dependents' edges pass through"). The fix is in the carry's `dependents` map, in `flow.py`, by walking plain `Depends on` edges through finished patchless bundles.
- NEEDS-HUMAN [human] — **The same shape, with A not clean, also ships without A.** Run `[A, N, D, W]` as in criterion (2), but on the re-issue A cannot be carried (held). `W` is held correctly ("prerequisite(s) not ready (A)"), but `D` is built on main and COMPLETE without A (reproduced; also true before the fix). `_runnable` (`flow.py:803-806`) holds only a bundle whose *own* plain `Depends on` names a held finished id, and N is not held. The new docstring says such dependents wait (`flow.py:929-930`: "a finished id this run did not carry, whose plain `Depends on` dependents wait (:func:`_runnable`)"), which is wrong for an edge through a patchless node. Fixing it means changing `_runnable`, and the brief says the patchless-node change stays out of `_runnable`. So this is a scope call: widen this bundle, or file a follow-up. At least fix the docstring.
- NEEDS-HUMAN [human] — **A carry defect stops the whole run, not just the dependent, and this patch sends many more resumes into that stop.** The brief's goal says "carry defects stop the dependent". The code stops the run (`flow.py:2714-2719`: "wave k and later waves not run"). Concrete case: criterion (4) plus an unrelated `U` with no edges in the drive set. `U` stays PLANNED and is never built (reproduced). Before the fix, D and U were both built. Before #727, every stack-mode bundle was cut from the shared line, so any batch started then and resumed after this patch hits this stop whenever a dependent's closure does not cover everything below a carried bundle's cut point. The way out it gives is to re-publish the finished bundle. The brief puts base-build-failure holds in #725, so the code follows the agreed scope. A human should still decide whether #728 can ship before #725, and whether the brief's "stop the dependent" needs rewording.
- Restated assertions outside the brief's list (the brief says "any change outside this list is a finding"): `template/tests/test_flow_dependency_scoped_bases.py:375-403` (two "keeps the line" tests become own-base tests), and in `template/tests/test_flow_merged_prereq_on_line.py` the `_built_on_line` helper (both branches) and `test_the_way_out_is_to_delete_the_line_then_re_run` (`:303`). I compared each before and after. Each still checks the same prerequisite content, or more, and none got weaker. The resume suite's `_publish_bundle` now keeps the brief, as real publish does (`test_flow_resume_stack_prereqs.py:125-134`). That is needed because the walk now reads finished bundles' briefs, and it hides nothing. The reviewer should confirm `build-notes.md` (withheld from me) lists these changes.

Attempted to refute and could not: the red/green proof (re-run, matches the gate log); the rewrite check for carried members (`heads = {**carried, **carried_heads}` reaches `_carried_rewrite`/`_lost`, test (5)); member order and ownership when carried A and P are both members (criterion 3); a patchless finished bundle with no brief (guarded at `flow.py:987`); a re-gate-red or skipped carry (those ids never reach `took`, so they are not members, and their direct dependents are held).
