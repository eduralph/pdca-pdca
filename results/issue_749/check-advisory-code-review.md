# Advisory code review — issue 749 (frame for the moved-base stakes)

Scope: the new stake frame in `template/src/pdca_harness/integrate.py` (`_stakes` and its helpers, the `_NotJudged` stop in `fold`) and the new `StakeFrame` tests. Line numbers are on the patched target at `$PDCA_TARGET`.

I found no clear correctness bug in the hunk code. I hand-checked these against git's rules and found them right: the `-U0` header parsing (`integrate.py:1915-1922`, pure insertions included), the old-to-new line map (`_keep`, `:1936`), the region joining (`_regions`, `:2002`; touching hunks join, matching xdiff's `i1+chg1 < i2` test), the carried partner (`_carried`, `:1967`) and the `cat-file --batch` reader (`_texts`, `:1844`). To check that the random probe is not passing by default, I ran it once with a counter (TMPDIR inside my sandbox). Over 750 shapes, 2,049 `_stakes` calls came back 1,257 tied, 786 not tied and 6 not judged. So it really tests the tie decision.

- NEEDS-HUMAN [impl] — The frame does not model `lead` (what the head already holds of bundles on the line). `integrate.py:2327-2333` runs the "after" trial as `rebuilt + lead + head` and the "before" trial against `there = its + lead`. But `_stakes` (`integrate.py:1826-1834`) always uses `held` as the "after" base and `held → head` as the own change, and uses `merge-base(head, there)` as `O`. When `lead` is not empty, `O` can be the lead's merge-base instead of an ancestor of `held`. Then the "move" diff (`O → held`) is partly the lead's change run backwards, and the own change counts the lead's lines as the head's. If the lead touches the conflicting file, the keys no longer match git's real trials. My guess is this mostly adds keys to "after", which ends in a stop (the safe side), but I could not prove it never removes one. No test covers it: every prerequisite in `test_flow_cross_wave_stranded_holds.py` (e.g. `:405-407`, `:463`) edits a file other than the one in conflict. Suggested fix: a real-git case where W depends on a bundle that edits the conflicting file. If that case shows a wrong key, take `S`/`O` from the commit the trial actually merges the head onto.
- `integrate.py:1826` / `:1838` — `_texts` reads each conflicting path under the same name in `O`, `held`, `head` and `there`. If either side renamed the file (ort follows renames and reports the new path), the old commits show the file as missing. The frame then finds no clash and stops with "the line diffs show no clash in it". The same thing happens with `.gitattributes` merge drivers or `binary`, which the frame never reads. These cases stop the run, so there is no false hold, but the stop message points the user at the wrong cause. A rename-specific reason, or a test that pins the current wording, would help. Low priority.
- `integrate.py:1819-1822` — `len(bases) != 1` also matches zero merge bases, but the message says "more than one merge base". It can't happen in practice: `_out` already raises when `git merge-base --all` exits 1 with no base. Writing `> 1` would make the code match its message. Cosmetic.
- `tests/test_flow_cross_wave_stranded_holds.py:1733-1738` — the probe checks the shape count, the compared share, mismatches and the exempt bound, but sets no minimum on how many shapes come out tied or how many are not judged. Today it is clearly meaningful (numbers above). A future change that made `_stakes` raise `_NotJudged` almost every time would still pass, because `_variant` (`:1672`) treats not-judged as "not tied" for both the shape and its twin. A floor such as "at least 25% of compared shapes tied" would close that gap. Optional.
- Reuse / simplicity: nothing to file. `_bytes` (`integrate.py:1876`) overlaps `_out`, but it is needed because file text must stay as bytes. `_stakes` runs one `cat-file` per file plus up to three `git diff` runs. `_diff_algorithm` is read lazily, once per target (`integrate.py:690`). Changing `raise` to `raise exc` at `integrate.py:706` is needed because `exc` may now be the rebuilt `_Conflict`.
