  **What counts:**
  - **The frame** is the head's own version of each file. The head is the bundle being folded, the same commit in both trials (clash with the partner as it is on the line, and clash with the partner rebuilt on the base the head holds, `S = git merge-base head <remote>/main`), so positions compare. Line numbers in the merge base or on the partner's side differ between the two trials and must not be used.
  - **A conflict block** is one region git's own trial merge leaves in a file, with its head side and its merge-base side. Read it from git's output (the diff3-style markers), never from a re-implemented merge.
  - **Pinned git settings, trial only.** The trial merges that capture blocks run with `-c merge.conflictStyle=diff3 -c rerere.enabled=false`, so neither a user's conflict style nor a recorded rerere resolution changes or hides blocks. The pin goes through a keyword on `_merge` that only `_trial` passes. The real fold merge, which runs through the same `git merge` call in `_merge` (`integrate.py:1719`), keeps running exactly as today. A file the trial leaves conflicting without readable diff3 blocks (a binary file, a custom `.gitattributes` merge driver) is "a block the code cannot place" below.
  - **Placing a block in the head's file.** Positions come from git's hunk headers, never from matching text. For each conflicted file, take the head's index stage and the base stage from the conflicted index (before `_reset_tree`) and run `git diff -U0` between them. Its hunk headers give the head-side line ranges the head changed. Assign those hunks to the conflict blocks in file order. A block's head side must equal the head file's text over the hunks assigned to it, checked at those positions only. Hunks outside every block merged cleanly and are not at stake. Repeated lines elsewhere in the file cannot cause a wrong match, because only hunk positions are candidates (case 10).
  - **A head line is at stake** in a block when it is on the block's head side and the head changed it from that block's base side. A head-side deletion counts as the position it leaves. For each trial, the clash is the set of (file, head line) pairs at stake across all files.
  **The rule:**
  - The move is part of the head's clash with a partner exactly when the set after the rebuild is a strict subset of the set before.
  - A file that drops out is just the case where all its lines leave the set, so one-file and multi-file clashes follow one rule.
  - **Partial overlaps:** a block that shrinks but does not vanish counts (case 7). Which block a line came from does not matter, only the line set.
  - **Not judged → stop as today:** the "after" set holds a line the "before" set does not (cases 8, 8b); the sets are equal (case 9); or git leaves a block the code cannot place in the head's file. The last one has no case: with diff3 pinned and positions taken from git's own hunks, git's text output always places. It covers binary files and custom merge drivers. It must not be silent: the stop line on stderr names the file and says its conflict could not be placed.

# Advisory code review — issue 749 (iteration 6 patch)

Lens: bugs the patch adds, and reuse / simplification / efficiency. Everything is cited on the patched target at `$PDCA_TARGET`. Gates: C4 shows the new file red before the fix (20 of 27 fail with `STOPPING`) and green after it. T3 runs the full suite green (2652 tests).

I found no correctness bug that would hold the wrong bundle. The trial plumbing is sound. `_merge` reads the conflicted index and git's conflict text before `_reset_tree` and reads attributes after it (`integrate.py:1763-1777`). `_trial`'s `finally` still puts the line back when `_Unplaced` is raised from inside it. `_held_by_line` re-raises `_Unplaced` instead of swallowing it as a plain `IntegrationError`. Python's `Counter` strict-subset check (`after < before`) is correct on the declared floor (`requires-python >=3.11`). Two small items and one note:

- NEEDS-HUMAN [impl] — `template/src/pdca_harness/integrate.py:1844-1846` / `:1940`: the hunk diff copies the user's `diff.algorithm` setting, on the assumption that `git merge` (ort, git's default merge engine) builds its conflict blocks with the same setting. Whether ort reads `diff.algorithm` depends on the git version. git 2.53's own `git-merge(1)` says "ort defaults to diff-algorithm=histogram, while regular diffs currently default to the diff.algorithm config setting". If the merge and the diff ever use different algorithms, the blocks and hunks stop matching. Usually that ends in the named "could not be placed" stop, which is safe but surprising. A simpler fix that holds on any git version: pin the algorithm in the trial, e.g. add `-c diff.algorithm=histogram` (or `-X diff-algorithm=histogram`) to the `pin` tuple at `:1763`, always pass `--diff-algorithm=histogram`, and drop the per-trial `git config` call. That also removes one subprocess per conflicting trial.
- `template/src/pdca_harness/integrate.py:695-707`: when `_Unplaced` is caught, `exc` is replaced by a new `_Conflict` and re-raised with `raise exc` outside the `except` block. The new exception carries neither the original `_Conflict` nor the `_Unplaced` as its cause, so a traceback no longer shows where the placement failed. This only affects debugging; the stderr wording is right and tested. To fix, keep `why` and use `raise exc from why` on that path. Not a blocker.
- Efficiency note, no action needed now: `_placed` (`integrate.py:2000`, loop at `:2024`) tries every hunk as the start of every block. Each try scans forward and compares slices, so the cost is roughly blocks × hunks × offset × slice length. This only runs after a fold merge has already conflicted and no other rule named a partner. Test fixtures are tiny, but a large generated file (a lockfile with hundreds of blocks) could make this slow. If it shows up in practice, starting each block's search at the hunk index where the previous block's runs ended (blocks take runs in file order) would make it close to linear.

The tests check the right things. Each new case confirms its git setup with real `diff3` output (`_one_block`, the marker-size and twice-dropped-line cases) before checking the hold. The one-file/two-file twins compare holds, `BaseMove`, exit code and the hold line with the file list masked out. The binary-file case checks the full "could not be placed … names the file" stop line. I found no duplicated logic: `_where`, `_overlap_step` and `_pinned` each pull existing code into one place and the old call sites now use them.
