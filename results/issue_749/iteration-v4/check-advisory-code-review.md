# Advisory code review — issue_749 (stranded partner after a moved base)

I found no correctness bugs this patch adds, and nothing that needs a human. Below are two small cleanups and what I checked.

## Findings

- `template/src/pdca_harness/integrate.py:1978` / `:1983` / `:1991` — repeated work (efficiency nit, not blocking). When `held` differs from `base_ref`, `_unfit(..., held, ...)` already computes `_own_change(wt, head, held, on)` and `_built_on(wt, held, tips, ...)` (`:2037-2038`). `_held_by_move` then computes both again: `_built_on` at `:1983` and `_own_change` at `:1991`. Each one runs extra `git merge-base` / `rev-list` calls. This only happens after a fold merge has already conflicted, so the cost is small. Still, `_unfit` could return or accept `lead`/`under` so they are computed once.
- `template/src/pdca_harness/integrate.py:2017` vs `:1901` and `:2194` — docstring is wrong, the code is not. The check `kind != "line"` on the rebuilt line only works because `_clash`'s `"line"` trial merges `head` onto the real line checked out in `wt` (`_trial(wt, branch, "HEAD", [head])`, `:2194`), not onto `held` plus `on_held`. That real-line merge always conflicts here, so `kind` is `"line"` whenever no batch partner is found, and `_explains(..., (), stay=stranded)` then does the real check against the rebuilt line. But `_pinned`'s docstring (`:1901`) says the rules are "judged on commit `base_ref`", which hides this. A short comment at `:2017` saying that `"line"` comes from the real line, not `held`, would stop someone from "fixing" `_clash` later and quietly breaking the stranded-only hold.
