Brief rule (ii) says it should be held.** The cause is the file-level test at `template/src/pdca_harness/integrate.py:2000` (`not set(files) - set(after)`), described at `:1953-1955`. Concrete case, run with real git in my sandbox on the case (1) fixture: base `shared.txt` = nine lines; A (wave 0) edits lines 2 and 8; after fold 1, main edits line 8; W (`Depends on: Z`, built on the moved main) edits line 2. The two-file version of the same situation (A adds `a.txt` and edits `shared.txt` line 2; main adds `a.txt`; W edits line 2) is held with both steps: "rebuild issue_A's branch on the new origin/main" plus the `Conflicts with: A` proposal. To a user these are the same situation, but one stops and one holds. The stop is the old behaviour, so the advice is never wrong. It is still a gap against rule (ii): A does not merge onto `S`, and W's own change does. No test pins this stop, and the test file's list of cases that "still stop" (`test_flow_cross_wave_stranded_holds.py:26-30`) does not mention it. Decision needed: accept the stop as rule (iii), or ask for a hunk-level test (compare the conflict hunks, not the file names) so this case holds too.
- NEEDS-HUMAN [impl] — **Unclear pronoun in the stranded-plus-own hold line.** `template/src/pdca_harness/flow.py:1640` adds "; and its change also conflicts with …" right after "…: origin/main moved since it was cut".
