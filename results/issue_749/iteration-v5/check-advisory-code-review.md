The real fold merge is unchanged: `_merge` adds the `-c` pin only when `stake` is passed (`template/src/pdca_harness/integrate.py:1759-1761`), and only `_trial` passes it, for the last rev only (`integrate.py:2551-2552`). The `got not in (None, len(lead))` guard stops a lead-merge failure from leaving an empty `after` set that would pass as a strict subset (`integrate.py:2253`). One test gap, plus two small notes:

- NEEDS-HUMAN [impl] — The "equal sets → not judged" branch of the new rule is never exercised. Case (9) (`template/tests/test_flow_cross_wave_stranded_holds.py:1003-1041`) never reaches `_held_by_move`'s tie loop. Main's line-8 edit doesn't touch A, so A still merges onto main, `now`/`lost` are empty, and `_held_by_move` returns at `integrate.py:2230-2232` before any stake trial runs. The test's own comment says so ("no move is looked for at all"). None of the other cases I traced gives equal sets either: (8) and the take-the-move-back-out guard at `:616` give before ⊂ after, and (8b) gives an overlap. So changing `not after < before` to `not after <= before` at `integrate.py:2253` would probably not turn any test red, and v1's counterexample ("an unrelated move is not tied") has no guard under the new rule. This comes from the brief's (9) shape, not from the builder. Suggested fixture that reaches the loop with equal sets: A edits lines 2 and 8, main then edits line 8, and W (built on that main) edits line 2 and sets line 8 to A's own line-8 text. A fails onto both main and `held`, but line 8 is the same change on both sides in both trials, so only line 2 is at stake before and after → expect `STOPPING` and no "rebuild issue_A's branch" advice. Confirm with one mutation run of `<=`.
- Minor, no action needed — `_diff3_blocks` (`integrate.py:1895-1909`) finds markers by a 7-character prefix. A file whose merge-base text holds a line of exactly `=======` (a setext/RST heading underline over a 7-character title) would end the base side early. A file with a `conflict-marker-size` attribute gets longer markers, so no blocks are found, and the stop line then blames "a binary file, or one a custom merge driver merges" (`integrate.py:1826-1828`). Both cases fail safe: `_placed` finds no fit or there are no blocks, so `_Unplaced` stops the fold and names the file. A wrong hold doesn't seem reachable. Only the wording of the stop reason can be off.
- Minor, no action needed — Efficiency is fine. The extra git calls (`ls-files -u`, `config --get diff.algorithm`, up to two `cat-file` and one `diff -U0` per conflicted file) run only in the two stake trials per lost partner, after a fold merge has already conflicted. `_placed`'s loops (`integrate.py:1930-1949`) grow with blocks × hunks × block length, which is small for real conflicts. No existing helper covers hunk-header parsing or diff3 parsing, so the new helpers don't duplicate anything. `_bytes` (`integrate.py:1844`) is a bytes version of `_out`, and that's justified because blob text can be in any encoding.
