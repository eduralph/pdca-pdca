# Adversarial review — issue 749 (hunk/line-set tie rule)

The toolchain was available (git 2.53.0, Python 3.14.4), so these results come from real runs on a scratch copy of the patched tree, not from reading alone. The red→green evidence holds up. The fix still breaks the brief's main promise (one file and several files give the same result) for one class of input: deletions.

- NEEDS-HUMAN [impl] — **One-file and two-file results still differ when a deletion shares a hunk with the move.** `template/src/pdca_harness/integrate.py:1839` records a head hunk as the head lines it covers, or as a "place" `(c, True)` only when it covers no head line. The two trials use different merge bases (the old base before the rebuild, `held` after), so the same head-side deletion is recorded one way in the first trial and the other way in the second, and the sets can never compare as a subset. Two concrete cases, both run through `flow._drive_and_act` on `StackFoldGit`:
  (a) Case (7) with W's own change being a deletion. Base `NINE`. A edits line 7. Main then edits line 7. W, built on that main, keeps main's line 7 and deletes line 8. Git leaves one conflict block both times; the diff3 output confirms the block shrinks from base `line 7/line 8` to `main's line 7/line 8`. Sets: before `{(shared.txt,7,False)}`, after `{(shared.txt,7,True)}`. Result: **STOPPING**. The two-file twin (main adds `a.txt`; A adds `a.txt` and edits shared line 7; W deletes shared line 8) gives before `{(a.txt,1,F),(shared.txt,7,T)}` and after `{(shared.txt,7,T)}`. That twin is **held** with the stranded-plus-own advice (`BaseMove('origin/main', ['issue_A'], [], ['issue_A'])`).
  (b) The move is a deletion. A edits line 7, main deletes line 7, and W, on that main, edits line 8. Before and after are both `{(shared.txt,7,False)}`, so the sets are equal and the run **stops**. The twin (main deletes `a.txt`, which A edits) is **held**.
  This is the defect class the human rejected in iteration 4, and it breaks the brief's "a block that shrinks but does not vanish counts". A possible fix, to check against (7), (8) and (8b): when a hunk drops more base lines than it adds (`b > d`), also put its place at stake.

- NEEDS-HUMAN [impl] — **The equal-sets branch has no test; case (9) never reaches the new rule.** Changing `not after < before` to `not after <= before` at `integrate.py:2253` leaves all 30 tests in both cross-wave files green. Case (9) (`template/tests/test_flow_cross_wave_stranded_holds.py:1003`) never reaches the comparison: A still merges onto main, so `_held_by_move` is never called. The test's own comment says so, and an instrumented run printed no before/after sets for it. Case (9) therefore does not guard "the sets are equal → stop", whatever the brief calls it. A test that does: A edits lines 2 and 8, main edits line 8, and W, on that main, edits line 2 and takes A's line 8. Before and after are both `{line 2}`. The shipped code prints STOPPING; the `<=` mutant holds W with "rebuild issue_A's branch on the new origin/main". Add this case.

- NEEDS-HUMAN [human] — **The brief says plain text "always places". It does not.** When the head deletes the same line text in two places of a conflicted file, one inside a conflict block and one merged cleanly, both hunks fit the block. `_placed` (`integrate.py:1913`, tie-break at `:1950`) then returns None, and `_Unplaced` is raised at `:1833`. A real fold run: base `a1 } a3 } a5 } a7 a8 a9`. A changes line 4 to `} // A` and edits line 8. Main edits line 8. W, on that main, deletes lines 4 and 6 (both `}`) and keeps main's line 8. The run prints STOPPING with "the conflict in shared.txt could not be placed on issue_W's own lines (its diff3 blocks do not fit the lines the branch changed in exactly one way)". A smaller git-only repro: base `t3 t1 t3 t1 t0 t2 t0`, theirs deletes both `t1`, ours inserts a `t3`. A fuzzer on random merges hit this 4 times in 2,800, every time from repeated deletions. Deleted blank lines and `}` lines are common in real code. The stop is named and no worse than before the fix. But case (10) covers only edited repeated lines, no test covers this text-file path (the binary test covers only "no diff3 blocks"), and the brief planned this branch as unreachable. A human should decide whether a named stop is acceptable here, or whether the builder should break the tie, for example using the other side's (stage 2) hunks to work out where the block sits.

- Tried and could not refute: **the red→green evidence.** On a scratch copy the new file is green (21 tests). With iteration 4's file-level rule put back at `integrate.py:2253`, cases (5), (6), (7) and (10) go red. With the weaker "some line left the set" rule, only (8b) goes red. Both match the brief and the C4 log (`gate-logs/C4-verify.log`). Instrumented runs show (8), (8b) and (10) reach the comparison with exactly the sets the brief predicts: (8) `{2}`→`{2,5}`, (8b) `{2,8}`→`{2,5}`, (10) `{5,11}`→`{5}`. The tests import the production modules and drive `flow._drive_and_act`; nothing re-implements the merge.

- Tried and could not refute: **placement when no line repeats.** On 523 random conflicts with no repeated lines, the head lines `_at_stake` put at stake matched a text-located ground truth every time.

- Tried and could not refute: **diff-algorithm drift.** `git merge` does follow `diff.algorithm`: setting myers or histogram changed the merge result in 23 of 300 random merges. Reading that setting at `integrate.py:1804` for `_own_hunks` therefore matches what the merge used.
