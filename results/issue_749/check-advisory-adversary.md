# Adversarial review: issue 749 (one frame for both trials' stakes)

I re-ran the green leg myself: 35/35 pass in `template/tests/test_flow_cross_wave_stranded_holds.py` on the patched target (git 2.53.0, Python 3.14, about 60 s). Everything below was checked with real git: through `flow._drive_and_act` on `StackFoldGit`, by calling the production `integrate._stakes` directly, or with mutations of a copy of the source in my sandbox. Nothing below is a false tie (the frame holding where it shouldn't). The worst case I found is a stop where the twin layout holds, which is the same kind of defect this bundle exists to fix.

## Findings

- NEEDS-HUMAN [human] — **The outcome still depends on layout when W's prerequisite edits the clash file.** `template/src/pdca_harness/integrate.py:2330` runs the "after" trial as rebuilt A, then `lead`, then W. `lead` comes from `:2318` and holds what W holds of the line: Z's head in this file's standard held setup (`template/tests/test_flow_cross_wave_stranded_holds.py:874`, W `depends_on="Z"`). But `_stakes` builds the "after" frame on `held` alone (`integrate.py:1826`, `:1833`). So any line of Z's that sits in the clash file counts as W's own change "after", while it cancels out "before". **Concrete failing case** (real flow, `_moved_run`'s layout): base `NINE`; A changes lines 2 and 8; after fold 1, main changes line 8; W (depends on Z) changes line 3 and keeps main's line 8.
  - Z = `{"z.txt": "z\n"}`: W is held with `BaseMove(stranded=['issue_A'], own=['issue_A'])` and the stranded-plus-own advice.
  - Z = `shared.txt` line 4 → `Z's line 4` (W keeps it): `wave 1 did not integrate … STOPPING`, holds `{}`.
  - Traced `_stakes` for the second case: before = {base 2, base 3, base 7, head 2, head 3, head 7}; after = {base 2, head 2, head 3, **('move', 0, 0)**}. The extra key is Z's line 4, read as a line W removes that "the move brought in". After is not a strict subset, so the rule refuses.

  Z's change is not part of the clash, yet moving it from its own file into `shared.txt` flips hold → stop. That breaks the invariant ("the same clash gets the same outcome … in one file or several"). The cause is the brief's definition of `S` (`git merge-base head <remote>/main`), which leaves out the lead. A likely fix is to use `held` with `lead` merged in (the commit `_unfit` already builds) as the "after" frame's base and as the far end of the move. That changes the approved frame, so a human needs to decide.

- NEEDS-HUMAN [human] — **"More than one merge base → not judged" only covers the "before" trial.** `integrate.py:1819-1822` checks `merge-base --all head there` and nothing else. The "after" trial (onto rebuilt A plus `lead`) is never checked. In the standard held setup it *does* have two merge bases: `git merge-base --all` of W and (A rebuilt on main1, then Z merged) gives `main1` and Z's head, while the "before" trial has one (Z's head). The brief's Scope ("Not judged, named: … a trial with more than one merge base") and the `_stakes` docstring (`integrate.py:1810`) both claim this rule for either trial. Applied as written, it would stop most of the kept held cases (5)-(12). So either the claim is wrong or the code is incomplete. Test (15) only exercises the "before" case. This shares a root with the finding above: the "after" frame's base is not the base git's "after" trial merges against.

- NEEDS-HUMAN [impl] — **No test checks that the fold passes the right diff algorithm.** I replaced `algo = algo or _diff_algorithm(wt)` at `integrate.py:690` with `algo = "histogram"`, and all 35 tests still pass. Test (13a) (`test_flow_cross_wave_stranded_holds.py:1422-1441`) only asserts the result is the same under unset, myers and patience, which is also true when the setting is ignored. Test (13b) (`:1585-1613`) calls `_stakes` directly with `_diff_algorithm(repo)`, so it never goes through `fold`. Fix: add a flow-level case with `diff.algorithm=myers` on a shape where porcelain merge conflicts under myers and a histogram frame finds no conflict region, so the forced-histogram mutation stops where the real code judges.

- NEEDS-HUMAN [impl] — **No test checks the hunk trim the brief requires.** Deleting the two trim loops in `_hunks` (`integrate.py:1927-1930`) still passes all 35 tests plus `test_flow_cross_wave_fold_holds.py`. (14) builds its twin from the test's own trimmed reading (`test_flow_cross_wave_stranded_holds.py:1526-1529`), so production's trim is never compared against anything. A related point: the trim is the one place `_carried` differs from git's real `-X theirs` rebuild, despite its docstring (`integrate.py:1969-1974`, "as the partner's rebuild there makes it"). With the trim, 7 of about 6,000 random shapes (insertions included) differed; without it, 0 of 4,000. Example: base `} x } } x }`, move `x M1 } M2 }`, A `} x A0 } x }`. Git's rebuild is `} x A0 } x }`; `_carried` gives `x A0 } x }`. On the shapes I checked, the trimmed and untrimmed builds made the same tie / no-tie decision, so this is a test gap and an inaccurate docstring, not a wrong verdict.

- NEEDS-HUMAN [impl] — **No test checks the rerere pin** (`integrate.py:1758`). Setting `pin = ()` passes both bundle test files. The brief counts #747/#748 staying green as "its check". That shows the pin does no harm, not that it does anything. Low priority. To cover it: enable `rerere.enabled=true`, record a resolution that would settle a trial's conflict, and assert the trial still conflicts.

There, (11) and (12) fail because the whole feature is missing, and (13b)/(14)/(15) fail with `AttributeError` (`integrate._stakes` / `_NotJudged` / `_diff_algorithm` missing).
