# Advisory code review — issue #738 (hold a bundle whose own base cannot be built)

Scope: correctness bugs the patch adds, plus reuse/simplification. Grounded on the patched tree at `$PDCA_TARGET`. The production change is small and matches the brief. The try/except narrowing, the held set fed to `_runnable`, the `_results_rc` exemption, and keeping the rewritten member in the end-of-run check all read correctly. Existing suites keep their expected exit codes; only test names and the stop-vs-hold assertions changed. One real edge-case bug, plus two minor nits.

- NEEDS-HUMAN [impl] — `template/src/pdca_harness/flow.py:2872` computes `fold_next=k < len(wave_list) - 1`, but the new early exit at `flow.py:2875` (`if not runnable: continue`) skips this wave's fold whenever every bundle left in the wave was base-held. The same goes for a later wave that `_runnable` empties (the `continue` at `flow.py:2813-2814`). Example: waves `{A}`, `{B: Depends on A}`, `{V}` (V not tied to B), with `fix/A` rewritten after wave 0's fold. B is held, wave 1 has nothing left so no fold runs, and wave 2 is the last wave so no fold runs there either. B's hold line still says "the next fold stops the run unless origin/fix/A is restored first" (`flow.py:1119-1120`). No such stop happens: the end-of-run check gives exit 1 instead. That breaks the brief's rule "never promises more than the run does". Case 2c doesn't catch it, because W is still built in B's wave, so that fold does run. Fix: pass `fold_next` as "this wave still folds (something of it is left runnable) and a later wave remains", or word the warning as "a later fold". Then add a case where B is alone in a non-last wave.
- `template/src/pdca_harness/flow.py:3033` (`holds.update({...: "base" ...})`) writes the literal `"base"`, while `cli._results_rc` matches it against `cli._BASE_HOLD` (`cli.py:699`, read at `cli.py:741`). The two copies must stay equal. If they drift, every base hold silently flips from exit 3 to exit 1. The tests would catch that today, since they assert `holds == {"B": "base"}` and `rc == 3`. The older reasons (`"unpushed"`, `"conflict"`) follow the same pattern, so this is consistent with existing code. Not a blocker; at most, add a comment pointing at the constant.
- `template/src/pdca_harness/flow.py:1117` gets the rewritten branch's name again with `integrate._published_ref(cfg.find_bundle(exc.name.removeprefix("issue_")))`. `build_bundle_base` already has that ref when it raises `_Rewritten` (`integrate.py:847`, `refs[m.name][1]`). Storing it on the exception would be simpler, but the brief limits `integrate.py` to docstring changes, so the re-read is acceptable. The fallback `f"{exc.name}'s branch"` covers a missing record. No action needed.

No other correctness, resource or concurrency problems found. The shared worktree left behind after a refused base build is reset by the next build (`integrate.py:855`) or fold (`integrate.py:598`). The integration lock is released on the exception path because `integ_lock` is a context manager (`with`). The new test file stubs only git calls (the fetch, the push, `_reset_tree`) scoped to B's build, not the new `except`, so the C4 red leg is real.
