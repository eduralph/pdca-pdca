# Adversarial review — issue 738 (hold a bundle whose own base cannot be built)

**Bottom line:** The red→green evidence holds up. The fix still has three gaps I could reproduce on the patched target, all fixable by the builder. Each one comes from the new `except` in `_bundle_bases` or from the wave loop around it.

## Evidence (could not refute)

- Re-ran the new file on the patched target: `tests.test_flow_bundle_base_holds`, 13 tests OK. The frozen C4 log (`gate-logs/C4-verify.log`) shows the red leg failing 12 of 13 with the real `STOPPING` line at B's base. Case (8) passes on both legs, as designed. The tests drive `flow._drive_and_act` (the production path). Faults are injected at `integrate._git` or on disk, never at the new `except`, so the red leg cannot pass by accident. Expected exit codes in the edited existing suites are unchanged (1d/1e in `test_integrate_carried_rewrite_late.py` still assert 1).

## Findings

- NEEDS-HUMAN [impl] — **The "next fold stops the run" warning is printed when no fold follows.** `flow.py:2872` sets `fold_next=k < len(wave_list) - 1`. But when every bundle of wave k is held, `flow.py:2875-2876` (`if not runnable: continue`) skips that wave's fold, and the later waves hold only B's dependents, which are skipped. Failing case (real git, the test file's fixture): `A` in wave 0, `B` (`Depends on: A`) in wave 1, `C` (`Depends on: B`) in wave 2, `fix/A` force-pushed after wave 0's fold. B's hold line ends "But the next fold stops the run unless origin/fix/A is restored first" (`flow.py:1116-1120`). Only one fold runs in the whole run, and the run's own end-of-run line then says "No fold of this run ran after the rewrite". The two lines contradict each other, which breaks the brief's rule that a hold line never promises more than the run does. Fix: set `fold_next` only when a later wave remains AND something of this wave is still left to build after the holds. Case (2c) still passes with that rule, since W is left in wave 1. Add this shape as a test.

- NEEDS-HUMAN [impl] — **A held bundle's cause is lost when a later base in the same wave hits a broken worktree.** `_bundle_bases` stores B in `held` and carries on (`flow.py:1051`). If W's build then raises `IntegrationTreeError` (`flow.py:1048-1050`), the handler at `flow.py:2868-2871` prints only W's error and `break`s, so `_announce_base_holds` never runs for `failed`. Failing case: A, Z in wave 0; B (`Depends on: A`) and W (`Depends on: Z`) in wave 1. B's fetch fails, then W's `git reset` fails. Result: the only stderr line is W's `STOPPING`. Nothing mentions B or "could not fetch", and `holds == {}` (rc 1). Before this patch, B's failure was itself the `STOPPING` line, so this is a new silent drop (the code base's #260 rule is "never silent"). Fix: announce `failed` (with `fold_next=False`) in the `IntegrationTreeError` handler before the `STOPPING` line, and add this two-fault case.

- NEEDS-HUMAN [impl] — **`_LineBroken` is held per bundle, but the code base treats it as run-level next to `IntegrationTreeError`.** The patch re-raises only `IntegrationTreeError` (`flow.py:1048`; the handler at `flow.py:2868`). `_LineBroken` (the line checked out in the shared worktree could not be put back) subclasses `IntegrationError` directly (`integrate.py:110`). The carry's per-bundle skip mode re-raises both classes together (`integrate.py:649-651`, and again at `:1815`). `build_bundle_base` can raise it: `_member_clash` → `_trial` (`integrate.py:973` → `:1919`), and `_merge_published` → `_keep_merge` → `_reset_line` (`integrate.py:1322` → `:1668`). Failing case: make B's `build_bundle_base` raise the real `integrate._LineBroken` in the case (1) shape. Result: B held, W COMPLETE, no `STOPPING`, rc 3. Real harm is limited, because the next build and the fold both start with `_reset_tree` (`integrate.py:855`), which raises `IntegrationTreeError` if the tree is still broken. But it bends decision 3 ("a broken shared integration worktree still stops the run"). The brief names only the class, not `_LineBroken`. Suggested fix: re-raise `(IntegrationTreeError, _LineBroken)` in both places, the same way as the carry. If the human reads decision 3 as covering only `IntegrationTreeError`, leave it as is and say so in a comment.

## Smaller notes (not filed)

- `cli.py:638-641`: this comment still says `holds` lists bundles "a fold of this run held out of its line" that "read COMPLETE in the results map". A `"base"` hold is neither. It's a stale comment in a file this patch edits, one line to fix.
- Case (1) passes only because B's wave is the last. With a fold after it (A, Z / W, Y(`Depends on: A`) / V(`Depends on: W`), `main` moved), Y is held correctly, but the fold after wave 1 then stops the run on W ("undeclared cross-wave overlap"), because W's base was built from the moved `main`. That happens with or without the hold, and the brief puts it in #739's scope, so it is not this diff's defect.
- Two existing test files outside the brief's Surfaces were edited (`test_flow_dependency_scoped_bases.py`, `test_integrate_carried_rewrite_late.py`): 4 methods moved from asserting `STOPPING` to asserting a hold. This was unavoidable, because they pinned the old stop. I checked that each keeps its fault trigger and its exit code.

## Attacks that did not land

- **Half-done merge left by a failed build leaking into later work:** the next build and the fold both run `_reset_tree` and `checkout -B` first (`integrate.py:855-856`, and the same in `fold`). A probe with the held bundle built last in its wave, followed by a fold, showed no leaked state.
- **A `Conflicts with` partner declared from B's side:** `waves.conflict_map` is two-way (`waves.py:136-153`), so the partner is held whichever side declares the edge.
- **The `_results_rc` exemption hiding a failure:** only a `"base"` reason exempts a key (`cli.py:741-742`). A late `"rewritten"` key can't overwrite B, because B is never in `accepted`. PLANNED dependents and partners still give 1.
- **The fetch fix leaking to other errors:** `_BASE_HOLD_STEPS` keys on the start of `exc.cause`. The push, checkout-missing and worktree cases assert the fetch fix is absent.
