# Adversarial review — #738 (hold a bundle whose own base cannot be built)

I re-ran the green leg on the patched target: `tests.test_flow_bundle_base_holds` passes 8/8. The frozen C4 log shows all 8 new tests failing before the fix, each on `STOPPING`. The tests drive the real `flow._drive_and_act` with real git, and the two stubs fail a git step (fetch, push), not the new `except`. I could not break the four brief cases. I did find three places where the patch's behaviour or wording goes wrong just outside those cases. Probe scripts are in `scratch/` in this sandbox.

- NEEDS-HUMAN [human] — **A rewrite hold in any wave but the last still stops the run at the next fold.** Concrete case: `A`, `Z` in wave 0; `B` (`Depends on: A`), `W` (`Depends on: Z`), `U` (`Depends on: Z`) in wave 1; `V` (`Depends on: W`) and `U2` (`Depends on: U`) in wave 2; `fix/A` is force-pushed after wave 0's fold. Result: `B` is held, and its line (`template/src/pdca_harness/flow.py:1069-1071`) promises "the rest of the run goes on". Then the fold after wave 1 re-checks `A` (`template/src/pdca_harness/integrate.py:1139-1146`), refuses it, and prints `wave 1 did not integrate (…); STOPPING — later waves not run` (`flow.py:2972-2978`). `V` and `U2` stay PLANNED (rc 1), though neither has anything to do with `A` or `B`. The same rewrite is also named twice, with two different fixes ("then re-run" vs "re-issue the run; or let this run stop"). Brief case (2) only passes because `B`'s wave is the last one, and the last wave never folds (`flow.py:2935`). This is not a regression: before the patch the run stopped one step earlier. But the brief's invariant ("holds that bundle … and nothing else") only holds when the rewrite hold lands in the last wave. The out-of-scope clause covers "any clash at the line fold", and a rewrite is not a clash. A human should decide whether this belongs here (for example, the fold stops re-merging a member already in `base_rewrites`) or in a follow-up like #739. Either way, the hold line's unconditional "the rest of the run goes on" is wrong in this case.

- NEEDS-HUMAN [human] — **The same rewrite exits 1 or 3 depending on whether some dependent's base happens to read it.** Probe P1: `A`, `Z`, `W` (`Depends on: Z`), with `fix/A` force-pushed after the fold. The end-of-run check says the line "still carries the old commits … no PR … holds them", holds = `{"A": "rewritten"}`, rc **1**. Probe P2: the same run plus `B` (`Depends on: A`). `B` is held, `A` is left out of the end-of-run check (`flow.py:3015`), and `in_prs` stays empty because only the line holds the old commits (`flow.py:2861-2865`). Holds = `{"B": "base"}`, rc **3**. In both runs the line carries exactly the same commits `fix/A` lost. The patch does what the brief asks (case (2): rc 3). But `_results_rc`'s own docstring (`template/src/pdca_harness/cli.py:709-714`) still says a rewrite where "the line carries commits no PR holds any more" is exit 1 (#695). The new comment at `flow.py:2773-2776` ("one only the run's line holds is a hold like any other") quietly overrides that rule. The edited test `template/tests/test_integrate_carried_rewrite_late.py:317` (1d, rc 1 → 3) locks the new rule in. A CI job reading rc 3 treats P2 as "held, not failed". A human should decide which rule wins and make the docstring and #695's rule agree.

- NEEDS-HUMAN [impl] — **The new hold lines promise things the run does not do.** (a) The `Conflicts with` partner line (`flow.py:866-871`) says "the re-run builds issue_B first and issue_X on a base holding it". Probe: after case (5)'s run, fix the fetch and re-run only the two held ids (`B X`). `B` is held by #647 (`issue_A not merged into main`), and `X` is built on the plain base (stack base `''`) and goes COMPLETE. That is the exact outcome this hold exists to prevent. The promise is only true for a re-run of the same full batch. The underlying gap (a #647-held bundle's partner is not held) predates this diff, but the sentence is new. Say "re-run the same ids", or reuse the #629 wording at `flow.py:850-854`. (b) `_announce_base_holds` (`flow.py:1069-1070`) says dependents "are held with it". `_runnable` actually reports them as "skipped — prerequisite(s) not ready" (`flow.py:844-846`), and they make the run exit 1, which is what brief case (7) asks for.

- Minor, no action needed: the fetch wrapper (`integrate.py:851-855`) also wraps `_prepare_worktree`'s "could not create the integration worktree" and `_fetch`'s "checkout not found" (`integrate.py:2054`, `:2078`). For those it gives "Check that remote (its URL, the network, credentials)". That part is the wrong fix, but the same sentence also says "and that checkout", so the user still gets pointed at the right place.

What I tried that did **not** break the fix:
- **Test sharpness.** I ran each mutation on a copy of `src` in this sandbox. Dropping `unbuilt=held_base` from the `_runnable` call (`flow.py:2805`) fails case (5). Dropping `_built_on_lost_heads` (`flow.py:2868`) fails both stale-head tests. Dropping the `base_rewrites` filter (`flow.py:3015`) fails 4 tests. Dropping the `exc.prs → in_prs` step (`flow.py:2864-2865`) fails `test_flow_dependency_scoped_bases`. Every hole the brief named has a test that goes red on its own, not just under C4's revert of everything at once.
- **Fetch hold in a non-last wave** (probe P4): `V` (`Depends on: W`) in wave 2 completes, rc 3. Transient causes (fetch, push) really do leave the rest of the run running.
- **Shared worktree and lock after a failed build.** `integ_lock` is a context manager (`integrate.py:842`), and `_reset_tree` drops a half-done merge (`integrate.py:2025`). Case (1) builds `W`'s base after `B`'s clash in the same worktree, and that works.
- **Gate claims.** C4, C5, T2 and T3 match their logs (2602 tests OK, 2 skips). I found nothing in `check-gates.json` that is overstated.
