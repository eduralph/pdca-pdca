- NEEDS-HUMAN — **The exit-3 cases need a change to `_results_rc`'s first rule, and the brief does not say so.** Cases (1), (2b), (3) and (4) expect exit **3** with `B` held. A base-held `B` is never built, so it stays PLANNED in `results` (`flow.py:2896`). `_results_rc` returns 1 on any non-OK state *before* it looks at `holds` (`cli.py:728-729`). Every hold that exits 3 today is a COMPLETE bundle: the docstring says "Such a bundle is COMPLETE in the map" (`cli.py:713`), and `_RC_HELD` means "finished every bundle but held one" (`cli.py:692`). So the change must let a base-held PLANNED bundle through rule 1, while a dependent left PLANNED (7) or a partner left PLANNED (5) still fails it. The brief only says "`_results_rc` gains the base-hold reason as a hold (exit 3), and its docstring stays true". That docstring cannot stay true; its "3" bullet has to be rewritten. The brief should name this rule-1 exemption, saying which PLANNED keys it lets through and why, as a planned change. It should also confirm the human accepted that exit 3 ("finished") now covers a bundle that did no work.

- NEEDS-HUMAN — **Case (3)'s stub point bypasses the code whose wording the case is meant to test.** The real fetch failure is raised in `_fetch` (`integrate.py:2042-2044`, "could not fetch {remote} … the fold cannot see the branches it merges"). The criterion then cannot catch a fix that gives the wrong remedy for "could not create the integration worktree" or "checkout not found" (`:2032`), which the Scope line names. Fix: stub the fetch `_git` call inside `_fetch` (return non-zero for `B`'s build only), or stub `_fetch`, so the real raise and its wording run. Also add a negative case that `:2056` does not get the "check the remote" fix.

- NEEDS-HUMAN — **The new fetch wording in `integrate.py` leaks into fold messages.** "Cause/fix wording in `integrate.py` where the cause is raised" points at `_fetch`. But `_fetch` is shared by the fold, the carry and the end-of-run `rewritten_carried`, which have their own `cause=` handling (`integrate.py:2024-2030`, `flow.py:2942-2944`). - NEEDS-HUMAN — **Decision 2 makes a load-bearing docstring and comment false, and Scope does not list them.** `_Rewritten`'s docstring says it names every PR "so the flow's end-of-run check (#695) does not report that branch again" (`integrate.py:127-129`). - NEEDS-HUMAN — **Where the exit code comes from is not stated.** The criterion drives everything "through `flow._drive_and_act`" and "asserts … the exit code". Otherwise a test can check the holds map and quietly skip the rule-1 change in the first finding, which is the main way the exit codes can come out wrong.

- NEEDS-HUMAN — **Case (8)'s stub as written also catches other `_reset_tree` calls.** The base build runs in the shared integration worktree, under the same lock and the same `wt` as the fold (`integrate.py:829-835`). `_reset_tree` is also called by the fold and the carry.
