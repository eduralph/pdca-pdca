# Adversarial review — issue_738 (hold a bundle whose own base cannot be built)

I re-ran the new suite on a copy of the patched tree at `$PDCA_TARGET`: 11/11 green. The C4 log (`gate-logs/C4-verify.log`) shows all 11 failing on the reverted tree, each for the intended reason (`STOPPING` printed before the unrelated bundle builds). The tests drive the real `flow._drive_and_act`, `_runnable`, `_bundle_bases`, `integrate.build_bundle_base` and `integrate.fold`. Only one bundle's `git fetch` or `git push` is made to fail, so the red→green evidence holds. Scratch probes are in `work/template/tests/test_adv_probe*.py`. Two of them broke the fix.

- NEEDS-HUMAN [impl] — **A rewrite the human fixes mid-run is still reported as stale, and the run fails.** `_report_stale_prs` (`template/src/pdca_harness/flow.py:1092-1126`) judges a head "lost as the refusal judged it" (`flow.py:1102-1104`) and never reads the branch again. Line `flow.py:3032` also drops the member from `_report_late_rewrites`, which is the only end-of-run check that would re-read it. Failing case (probe P1): take case (6)'s shape (`A`,`Z` / `B` dep `A`, `W` dep `Z`, `S` stacks on `A`, `fix/A` force-pushed after the fold). After `S` publishes and before the run ends, do what B's hold line says and put `fix/A` back on origin at the head the line took. The run still prints `flow: issue_S is cut from … that branch was rewritten without it … issue_S's PR holds those old commits too. Restore origin/fix/A … or rebuild issue_S's PR`, returns `holds={'B': 'base', 'A': 'rewritten'}`, and exits **1**, even though `fix/A` is at that head again. This window is real: the hold line is printed before the rest of the wave builds (model leaves, minutes to hours). Fix: at the end of the run, re-check each `base_rewrites` member's current tip against its lost heads (`integrate._carried_rewrite` after a fetch, as the end-of-run check does) before naming a PR or adding `"rewritten"`. Pin it with the P1 probe as a test.

- NEEDS-HUMAN [human] — **A rewrite hold in any wave but the last only delays the STOP by one fold.** The next fold re-reads `fix/A` (`template/src/pdca_harness/integrate.py:1143-1145`) and stops the whole run (`flow.py:2980-2986`). Failing case (probe P2): case (2)'s shape plus `V` (`Depends on: W`) in wave 2. `B` is held, then `flow: wave 1 did not integrate (issue_A's branch origin/fix/A was rewritten …); STOPPING`. `V` has no tie to `A` or `B` (it is built on its own base of `Z`+`W`), yet it stays PLANNED, and the run exits 1. The same rewrite is also named twice, with different advice: "then re-run" on B's hold line, "re-issue the run; or let this run stop" on the stop line. The brief's invariant says a base failure holds the bundle, its dependents and partners, "and nothing else". The brief's cases all sit in the last wave, so the gate never sees this. Someone has to decide whether this is accepted #633 fold behaviour (then say so and pin it with a test) or whether the fold should treat a rewrite a base already refused as a hold. Either way it is a scope call, not a builder iteration. (The moved-base case behaves the same way in a middle wave, probe P3: the next fold stops on `W`'s `a.txt`. The brief already puts that out of scope as #739, so I am not filing it.)

- NEEDS-HUMAN [impl] — **The new test file's docstring claims something the run does not do.** `template/tests/test_flow_bundle_base_holds.py:10-11` says "the rest of the run goes on, through later waves and their folds" for every listed cause, including "an in-batch prerequisite's branch was rewritten" (`:5-6`). That is only true for the fetch and push causes (see P2/P3). The file's own `NOT_DONE` (`:63`) says "a later fold can still stop the run". Scope the sentence to the causes it holds for. The hold line itself correctly says "the rest of this wave goes on" (`flow.py:1069-1071`), so only the docstring is wrong.

Things I tried to break and could not:
- **Same-wave `Conflicts with` partner slipping past `_runnable`** (it runs before `_bundle_bases`): this can't happen. The scheduler always puts the two sides of a conflict pair in different waves (`template/src/pdca_harness/waves.py:17-21`). A partner in an earlier wave is already built and goes into the held bundle's closure.
- **Shared integration worktree left mid-merge by a refused base:** the next base build and the next fold both reset the tree first (`integrate.py:871`, `:603`).
- **Exit-code masking by `_results_rc` (`template/src/pdca_harness/cli.py:740-745`):** only `"base"` holds are exempt. A base-held bundle is never accepted, so it can't also be a `stale`/`late` member that gets overwritten. Dependents and partners stay PLANNED, which gives exit 1 (case 7).
- **"Fix that works" claims:** after fetch, push and rewrite holds, I fixed the cause and re-ran only the unfinished ids (`batch` = all ids, as `flow_ids` does). `B` went COMPLETE with rc 0 each time, built on the line the carry rebuilt (probes P4-P6). The partner line now asks for "wait until issue_B is built … and its PR merges", which matches what iteration 1's probe showed a narrow re-run does.
- **No-patch bundle on the stale line** (iteration-1 hole): filtered by `pushed` in `_heads_taken` (`flow.py:1141`). The new case covers it and goes red on revert.
