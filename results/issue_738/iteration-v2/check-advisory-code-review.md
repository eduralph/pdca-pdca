# Advisory code review — issue #738 (hold a bundle whose own base cannot be built)

Overall: no correctness bug found in the production change. The tests run the real flow and fail without the fix: C4 shows all 11 new cases plus the 4 changed existing ones red pre-fix, green post-fix (`gate-logs/C4-verify.log:29-237`). The full suite is green (`gate-logs/T3-suite.log:1874-1877`). The three iteration-1 findings are fixed. The partner line no longer promises "a re-run builds B first" (`template/src/pdca_harness/flow.py:863-869`). The hold line says dependents are "skipped" (`flow.py:1061-1072`). A four-wave case checks the hold across two folds (`template/tests/test_flow_bundle_base_holds.py:480-506`).

Findings (one wording nit, two notes; none blocks):

- NEEDS-HUMAN [impl] — `template/src/pdca_harness/integrate.py:850-854`: the new wrapper around `_prepare_worktree` gives the same fix for every error that function raises: "Check that remote (its URL, the network, credentials) and that checkout, then re-run". That fits a failed fetch (`integrate.py:2063`). It does not fit the other two raises in that path, "checkout not found at …" (`integrate.py:2053`) and "could not create the integration worktree at …" (`integrate.py:2077`). Neither of those is a remote problem. The brief asks for "a fix that works for that cause". Cheap fix: say "check that remote" only when `exc.cause` comes from `_fetch`, or say "check that checkout" first. The original cause still prints at the front, so the message is not wrong, just less precise than it could be.

- Note (no action needed) — `template/src/pdca_harness/flow.py:2995`: `base_rewrites.clear()` after a fold that did not stop assumes that fold re-checked every member a base refused. That holds today. The fold checks every carried branch of `accepted` minus `held_unpushed`/`held_conflict`. A refused member is always a carried, folded prerequisite: a held_conflict/unpushed bundle cannot be a base member, because `_runnable` skips its dependents. If a later change lets a non-carried branch become a base member, this clear would silently drop its stale-PR report. The comment at `flow.py:2992-2994` states the assumption. A short assertion or a test would pin it down. Not filed as NEEDS-HUMAN.

- Note (no action needed) — `template/src/pdca_harness/cli.py:740-741`: `_results_rc` leaves any bundle `holds` marks `"base"` out of the "not a successful terminal" check, whatever its state. A held bundle is never driven this run, so its state is whatever the run found. That is PLANNED in every tested case, but it could be a mid-cycle state left by a resumed run. That run would then exit 3, not 1. This looks like what the docstring intends ("held … not failed", the `_results_rc` docstring at `cli.py:705`ff.), so no change is needed. Flagged only so the human sees the trade-off.

Reuse / simplification: nothing to flag. The partner hold reuses the existing `_runnable` path (`flow.py:769-771`, `:863-869`) the way the #629/#674 holds do. `_report_stale_prs` (`flow.py:1092`) reuses `integrate._rebuild` and the existing `_heads_taken` result, and does no extra git work.
