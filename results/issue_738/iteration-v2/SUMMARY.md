Line `flow.py:3032` also drops the member from `_report_late_rewrites`, which is the only end-of-run check that would re-read it. Failing case (probe P1): take case (6)'s shape (`A`,`Z` / `B` dep `A`, `W` dep `Z`, `S` stacks on `A`, `fix/A` force-pushed after the fold). This window is real: the hold line is printed before the rest of the wave builds (model leaves, minutes to hours). Fix: at the end of the run, re-check each `base_rewrites` member's current tip against its lost heads (`integrate._carried_rewrite` after a fetch, as the end-of-run check does) before naming a PR or adding `"rewritten"`. Pin it with the P1 probe as a test.

- NEEDS-HUMAN [human] — **A rewrite hold in any wave but the last only delays the STOP by one fold.** The next fold re-reads `fix/A` (`template/src/pdca_harness/integrate.py:1143-1145`) and stops the whole run (`flow.py:2980-2986`). Failing case (probe P2): case (2)'s shape plus `V` (`Depends on: W`) in wave 2. `B` is held, then `flow: wave 1 did not integrate (issue_A's branch origin/fix/A was rewritten …); STOPPING`. `V` has no tie to `A` or `B` (it is built on its own base of `Z`+`W`), yet it stays PLANNED, and the run exits 1. The same rewrite is also named twice, with different advice: "then re-run" on B's hold line, "re-issue the run; or let this run stop" on the stop line. The brief's invariant says a base failure holds the bundle, its dependents and partners, "and nothing else". The brief's cases all sit in the last wave, so the gate never sees this. Someone has to decide whether this is accepted #633 fold behaviour (then say so and pin it with a test) or whether the fold should treat a rewrite a base already refused as a hold. Either way it is a scope call, not a builder iteration. (The moved-base case behaves the same way in a middle wave, probe P3: the next fold stops on `W`'s `a.txt`. The brief already puts that out of scope as #739, so I am not filing it.)

- NEEDS-HUMAN [impl] — **The new test file's docstring claims something the run does not do.** `template/tests/test_flow_bundle_base_holds.py:10-11` says "the rest of the run goes on, through later waves and their folds" for every listed cause, including "an in-batch prerequisite's branch was rewritten" (`:5-6`). That is only true for the fetch and push causes (see P2/P3). The file's own `NOT_DONE` (`:63`) says "a later fold can still stop the run". Scope the sentence to the causes it holds for. The hold line itself correctly says "the rest of this wave goes on" (`flow.py:1069-1071`), so only the docstring is wrong.

Things I tried to break and could not:

The scheduler always puts the two sides of a conflict pair in different waves (`template/src/pdca_harness/waves.py:17-21`). A partner in an earlier wave is already built and goes into the held bundle's closure.
- **Shared integration worktree left mid-merge by a refused base:** the next base build and the next fold both reset the tree first (`integrate.py:871`, `:603`).
- **Exit-code masking by `_results_rc` (`template/src/pdca_harness/cli.py:740-745`):** only `"base"` holds are exempt. A base-held bundle is never accepted, so it can't also be a `stale`/`late` member that gets overwritten. Dependents and partners stay PLANNED, which gives exit 1 (case 7).

Findings (one wording nit, two notes; none blocks):

- NEEDS-HUMAN [impl] — `template/src/pdca_harness/integrate.py:850-854`: the new wrapper around `_prepare_worktree` gives the same fix for every error that function raises: "Check that remote (its URL, the network, credentials) and that checkout, then re-run". That fits a failed fetch (`integrate.py:2063`). It does not fit the other two raises in that path, "checkout not found at …" (`integrate.py:2053`) and "could not create the integration worktree at …" (`integrate.py:2077`). Neither of those is a remote problem. The brief asks for "a fix that works for that cause". Cheap fix: say "check that remote" only when `exc.cause` comes from `_fetch`, or say "check that checkout" first. The original cause still prints at the front, so the message is not wrong, just less precise than it could be.

- Note (no action needed) — `template/src/pdca_harness/flow.py:2995`: `base_rewrites.clear()` after a fold that did not stop assumes that fold re-checked every member a base refused. That holds today. The fold checks every carried branch of `accepted` minus `held_unpushed`/`held_conflict`. A refused member is always a carried, folded prerequisite: a held_conflict/unpushed bundle cannot be a base member, because `_runnable` skips its dependents. If a later change lets a non-carried branch become a base member, this clear would silently drop its stale-PR report. The comment at `flow.py:2992-2994` states the assumption. A short assertion or a test would pin it down. Not filed as NEEDS-HUMAN.

- Note (no action needed) — `template/src/pdca_harness/cli.py:740-741`: `_results_rc` leaves any bundle `holds` marks `"base"` out of the "not a successful terminal" check, whatever its state. A held bundle is never driven this run, so its state is whatever the run found. That is PLANNED in every tested case, but it could be a mid-cycle state left by a resumed run. That run would then exit 3, not 1. This looks like what the docstring intends ("held … not failed", the `_results_rc` docstring at `cli.py:705`ff.), so no change is needed. Flagged only so the human sees the trade-off.

Reuse / simplification: nothing to flag. The partner hold reuses the existing `_runnable` path (`flow.py:769-771`, `:863-869`) the way the #629/#674 holds do. `_report_stale_prs` (`flow.py:1092`) reuses `integrate._rebuild` and the existing `_heads_taken` result, and does no extra git work.
