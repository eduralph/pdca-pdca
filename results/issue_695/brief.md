- **Slug:** run-catches-a-late-carried-rewrite-and-retries-the-fetch
- **Defect:** Two gaps #633 (PR #685) listed as known limits.
  (a) **A late rewrite is never reported.** The run checks that every branch a fold of the run carried still holds the head the line took from it, but only at the start of the *next* fold (`integrate._carried_tips`, `template/src/pdca_harness/integrate.py:568-605`, called from `fold` at `:440`; the run's record is `carried_heads`, `template/src/pdca_harness/flow.py:2306-2308`). A fold runs only between waves (`k < len(wave_list) - 1`, `flow.py:2503`), so nothing checks after the run's last fold. A carried branch rewritten during the last fold (after `_carried_tips` read its tip, before the push) or after it (while the last wave builds, publishes, or Act runs) leaves the line with commits no PR holds any more, and the run ends as if all is well: every bundle COMPLETE, exit 0.
  (b) **The up-front fetch fails the run on a transient clash.** `_carried_tips` fetches each checkout (`integrate.py:587`, through `_fetch`, `:960-977`) before `fold` takes any integration lock (`:472-485`, the lock is entered at `:477`). A concurrent git process in the same checkout holding a ref lock makes that fetch fail, `_fetch` raises "could not fetch …", and the run stops ("wave k did not integrate", `flow.py:2541-2544`) for a reason that has nothing to do with the bundles. It fails closed, but on the first try.
- **Success criterion:** Real-git tests with the `StackFoldGit` fixture of `template/tests/test_integrate_stack_bases.py:123-256`:
  (1) **A rewrite after the last fold is reported by the run.** Mirror `test_a_run_stops_when_a_branch_it_carried_is_rewritten` (`test_integrate_stack_bases.py:1343-1384`) with only two waves: `A`, then `B` (`Depends on: A`). The fold after wave 0 carries `fix/A`; while wave 1 (the last) builds, `fix/A` is force-pushed with a rewrite (`_push_from_human({"a2.txt": …}, to="fix/A", force=True)`). After the run, stderr has one line that names `issue_A`, says its branch `origin/fix/A` was rewritten after this run folded it onto the line, and names the commit the line took from it, in the same terms as `_carried_tips`' message (`integrate.py:595-604`), plus what to do. The run's exit code is **1**, read only from what `cli._flow` returns (the route 693's brief pins; the test drives the run through `cli._flow`, never a helper either fix adds).
  (1b) **A rewrite outranks a hold.** Same as (1), plus a third bundle `C` in wave 0 whose publish pushes no branch (the stubbed `_publish_bundle` returns False for it), so the fold after wave 0 holds `C` as unpushed (693's exit 3). The exit code is **1**, not 3.
  (1c) **A rewrite during the last fold is reported too** (the issue's own "rewritten during the last fold" case). Same two-wave run, but `fix/A` is force-pushed with a rewrite from inside the fold after wave 0: an `integrate._git` spy (as `test_integrate_stack_bases.py:223-235` builds one) does the force-push on the fold's `push` call, before passing the push through. The line took `fix/A`'s old head (`carried` records it, `integrate.py:563`), so the end-of-run check reports `issue_A` as in (1) and the exit code is 1.
  (2) **No false report.** The same two-wave run where `fix/A` only gets a fast-forward commit during wave 1 (`_push_from_human(…, to="fix/A", off="origin/fix/A")`), or is merged and deleted, reports nothing and exits 0.
  (2b) **No double report.** The three-wave peer run (`test_a_run_stops_when_a_branch_it_carried_is_rewritten`, `test_integrate_stack_bases.py:1343-1384`, where the next fold already stops the run on the rewrite) prints exactly one stderr line naming `issue_A`'s rewrite: the end-of-run check does not run after the wave loop broke out on a fold error or a red re-gate (`flow.py:2539-2544`, `:2555-2559`), since that run already ends non-zero with later bundles PLANNED.
  (3) **One fetch clash does not stop the fold.** `integrate.fold(cfg, [a, b], folded_this_run={TARGET: t1}, carried={"issue_A": head})` where the first `git fetch` made for the carried-branch check fails once (an `integrate._git` spy, as `test_integrate_stack_bases.py:223-235` builds one, returns non-zero for that first fetch only; or a real `*.lock` file on the ref, removed after the first attempt) completes and pushes.
  (4) **A persistent failure still stops it.** Same, with every such fetch failing: the fold raises `IntegrationError` with "could not fetch", nothing is pushed.
  (5) **Nothing else changes.** Every #633 test (`test_integrate_stack_bases.py:1151-1384`) and every test in `template/tests/test_flow_same_wave_conflict.py` stays green.
  Pre-fix, (1), (1b) and (1c) fail (no line; exit 0, or 3 once 693 is on the base) and (3) fails (the fold raises "could not fetch"). That is the RED.
- **Falsifiability:** RED is reachable offline with real git. For (1), the peer test already rewrites `fix/A` while a wave builds; with two waves instead of three, no later fold runs, so on main nothing reports it and every result is COMPLETE. For (3), a fetch failure is produced either by a `_git` spy or by a real ref lock file; on main `_fetch` raises on the first non-zero fetch (`integrate.py:975-977`). The C4 gate (`engine/scripts/run-verify.sh`) reverts the production hunks and keeps the test, which imports only modules (never a symbol either fix adds), so with the fix reverted it loads and fails on its assertions.
- **Invariant to restore:** A run never ends reporting success while its integration line carries commits that a carried branch which still resolves no longer holds (it was rewritten), whenever the rewrite happened during the run; and a step outside the bundles' control that may succeed on a second try (a ref-lock clash on a fetch) does not by itself stop the run. Source: #633's contract, "the line never carries commits no PR holds any more" (`integrate.fold` docstring, `integrate.py:380-391`; `docs/07-crosscutting.md:668-675`), which today holds only up to the last fold; and #695's acceptance criterion. Scoped to rewritten branches that still resolve: a carried branch deleted after the last fold (its PR closed unmerged, or squash-merged) is not judged at the end of the run (in-fold that judgment belongs to `_gone_branch`); that stays out of scope.
