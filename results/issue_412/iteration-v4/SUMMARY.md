# Result — issue 412 / merge-mode-atomic-merge-group

## 1. Spec (from brief.md)              ← Check verifies against THIS
- Defect / goal: A brief can declare `- **Merges with:** <id>[, <id>…]` — an atomic merge group: these bundles must not land on the base separately. In merge mode the driver does not ready or merge a COMPLETE group member while any member of its group is not yet COMPLETE; once all are COMPLETE it merges the whole group back-to-back, in dependency order, at one wave boundary, each through the normal `merge._merge_one` gates. A bundle that depends on a held group member is held too (not built on a base without it). A group that is also a dependency chain (one member `Depends on` another) cannot work in merge mode — the consumer can only build after the producer merges, which the group forbids — so such a batch is refused before anything is built, with a message giving the two ways out: make the pair one bundle, or run the batch in `wave_mode = "stack"`. Two more group shapes are refused the same way in merge mode, for the same reason: members that `Conflicts with` each other (the later one is built on a base without the held earlier one, so its PR needs `gh pr update-branch` across a declared overlap at the release boundary — the half-landed STOP this field exists to prevent), and a `Merges with` id that is not in this run's batch (`merge_wave` only ever sees this run's bundles, so the group could never be merged together). In stack mode the field changes nothing (the human already merges the stack and can take the pair together).
- Success criterion: With `wave_mode = "merge"` and `gh` stubbed: (a) A and B both declare `Merges with` each other and have no edge between them; D (no group) is in wave 0, B `Depends on: D` (so A in wave 0, B in wave 1), and C `Depends on: B` (so wave 2) — at the wave-0 boundary no `gh pr ready` / `gh pr merge` is called for A's PR and the run goes on; at the wave-1 boundary A's and B's PRs are both merged, A first, before C builds; (b) if B ends not COMPLETE (e.g. DISCONTINUED), A is never merged by the run and stderr names A as held for its group with B; (c) a bundle `Depends on: A` while A is held is not built and is named as held; (d) a batch where B `Depends on: A` and they declare `Merges with` each other makes `pdca flow` exit non-zero before any Do runs, stderr naming both ids and both ways out; (e) the same batch with `wave_mode = "stack"` runs as it does today (the field is ignored); (f) `Merges with` declared on one side only is treated as symmetric (as `Conflicts with` is); (g) in merge mode, a group whose members `Conflicts with` each other, and a group naming an id outside the batch, are each refused the same way as (d), before any Do. Cases (d) and (g) are tested at the CLI: `cli.main(["flow", …])` returns 2 and stderr carries the `Ways out:` line (`template/src/pdca_harness/cli.py:673-679`, which turns `waves.DependencyGraphError` into rc 2 with `exc.remedy`); the remedy names both ways out.
- Repo + branch target: eduralph/pdca-harness @ main
- Scope (one logical fix) / out of scope: The `Merges with` field (parse, symmetric, ids only), merge-mode hold-and-merge-together, the dependents' hold, the up-front refusal of a chained group in merge mode, and docs plus the brief template line (`template/templates/brief.md.tpl`, next to `Conflicts with`). / out of scope: building the consumer of a chained group on the producer's unmerged branch in merge mode (alternative A — see Open questions); making the sizer or `pdca split` refuse to split across a group (follow-up); host-side atomicity (GitHub has no multi-PR merge — if a later member's merge fails after an earlier one merged, the run stops and says which landed, see Impact); stack mode behaviour.

# Adversarial review — issue 412 / merge-mode-atomic-merge-group (round 4)

Only the build leaf, publish and `gh` are stubbed. So the evidence holds. I wrote probe tests (subclasses of `MergeGroup`, run from my scratch dir) for the cases below. One of them breaks the field's core promise.

- NEEDS-HUMAN [human] — **When a group member is split, its partner merges alone, with no warning and rc 0.** `split.accept` leaves the parent as a close disposition (`template/src/pdca_harness/split.py:1008` writes `close-disposition` = `split`). `state.state` reads that as COMPLETE with no patch (`template/src/pdca_harness/state.py:351`). The group check looks only at state (`template/src/pdca_harness/merge.py:229-236`). `_premerge` then says "skip, nothing to merge" for that member (`merge.py:663-665`). So the group is released, and the partner lands while the split's children have not. The end-of-run report skips members with no patch (`template/src/pdca_harness/flow.py:3337`), so it says nothing.
  - **Probe P1:** A `Merges with: B`. A splits in wave 0 into A1 and A2, where A2 `Depends on: A1` (the children do not repeat the field). B `Depends on: D`, and C `Depends on: B`. Result: built `[A, D, A1, B, A2, C]`; merged `{A1, B, D}`. A2 sits in the final wave as a draft, `holds == {}`, rc 0, and stderr has no `Merges with` line at all. B landed with only half of A's work.
  - **Probe P1b:** an earlier run split A (A1 still PLANNED). Then `pdca flow B C D` merges B at wave 1's boundary with none of A's work landed. rc 0, and stderr is empty.
  - The up-front check doesn't catch this either: a COMPLETE member is never "away" (`template/src/pdca_harness/waves.py`, `_shape_refusal`).
  - **Unwarranted claim:** the test module docstring says "A split mid-run does not break a group" (`template/tests/test_merge_group.py:20`). That is only tested for a split of a *non-member* (`test_a_split_before_the_last_member_does_not_break_the_group`).
  - **Why [human]:** the brief releases a group on COMPLETE state and puts split/group interplay out of scope (Scope: "making the sizer or `pdca split` refuse to split across a group (follow-up)"). So whether a split parent should block its group, or pass its membership to its children, is a scope call.
  - **Cheap fail-closed fix if the human wants it now:** in `group_blocker`, treat a member whose close marker reads `split` the way a DISCONTINUED member is treated (hold it, and name the split and the way out). Also refuse such a group up front in `_shape_refusal`.

- A member an earlier run finished, whose `publish.json` has no `repo` field (a record from before that field existed, per `template/src/pdca_harness/publish.py:813-814`), holds its group on every re-run. This happens even after a human has merged its PR into the right base. `_groups()` asks `merged.merged_into`, which treats a missing `repo` as not merged (`template/src/pdca_harness/merged.py:109`). Then `group_blocker` runs `_foreign_refusal` before `_premerge`'s already-merged skip (`template/src/pdca_harness/merge.py:243-245`, `:275`).

  - **Half-landing from a refusal the run could see coming.** No PR, an `Onto branch` record, a record with no repo under `merge_requires = "all"`, and a malformed `expected_checks` all hold or STOP before the first `gh pr ready`. `group_blocker` asks the same `_premerge` that `_merge_one` uses.
  - **Re-running after a STOP, or after a member was DISCONTINUED.** Both go through.
  - **One-sided declarations from bundles that are held, archived or adopted then dropped.** All still bind the partner.
  - **Rings of groups through `Conflicts with` edges.** `_wait_edges` reads which side builds first from `_build_order`, the same function `compute_waves` levels with.

It is not a refutation, but the "narrower window" there means every multi-member release under the default setting, not a rare case.

## Findings

- `template/src/pdca_harness/merge.py:245` and `template/src/pdca_harness/merge.py:729` — when a group is released, each member runs `_premerge` twice. Once is ahead of time, from `group_blocker`; the second is inside `_merge_one`. Each run makes a `merged.is_merged` call, which is a `gh pr view` round trip. So every group member costs one extra `gh` call at the boundary, and `_report_groups` adds one more per member at the end of the run. Nothing breaks, because the answers agree. If it matters, `merge_wave` could keep the `_premerge` verdicts that `group_blocker` already computed. Advisory only.
- `template/src/pdca_harness/waves.py:198` — `merge_groups` globs every `issue_*` folder under `results/` and `results/completed/` and reads each brief, every time it is called. In merge mode it is called by every `check_dep_graph` (so every `compute_waves`) and by `partition_schedulable` (`waves.py:667`). In `_drive_and_act` it runs at the start of every wave (`flow.py:3026`), at every boundary (`flow.py:3186`) and once at the end (`flow.py:3270`). The cost grows with waves × all bundles ever on disk, and most of those are archived ones that never change. That is fine at today's sizes, and stack mode never calls it. Reading it once per run, and again only after a split adds bundles, would be enough. Advisory only.
- `template/src/pdca_harness/flow.py:3002` and `template/src/pdca_harness/merge.py:272` — both new hunks contain the same "target, or `("", "")` when the brief is gone" expression: `publish._resolve_target(p)[:2] if (p / "brief.md").is_file() else ("", "")`. A small shared helper, for example next to `waves.member_path`, would stop the two copies drifting apart, which is the same kind of drift the round-3 `_member` finding was about. Advisory only.
- `template/src/pdca_harness/waves.py:198` with `template/src/pdca_harness/waves.py:295` — NEEDS-HUMAN [human] — `merge_groups` reads every brief on disk, archived ones included. A `Merges with: A` line in any bundle that ended DISCONTINUED or RESOLVED therefore stops every later merge-mode run that includes A, up front, with rc 2, and that lasts forever. The remedy text says to "remove the `Merges with` edge … in whichever brief declares it", which means editing a frozen, possibly archived bundle. The same applies to `_ring_refusal` (`waves.py`, the "if …'s PR has already merged, remove the `Merges with` edge" remedy). The up-front check cannot ask `gh` whether an archived member's PR has merged, so it refuses a ring through a long-merged member, and the only way out it offers is editing that member's brief. This follows on purpose from the round-2/3 fix (a one-sided declaration must keep binding), and success criterion (b) wants a DISCONTINUED member to hold its group. But how long an old declaration should keep binding (forever, or only while the declarer is in flight or unmerged) is a scope decision for the maintainer, not a builder fix.

The diff has no other correctness or reuse problems that I could confirm.

Failing case: run 1 ends as in test (b) (B DISCONTINUED, A held). `_report_group_holds` says "merge it together with the rest of the group once every member is COMPLETE" (`flow.py:3236`). The docs say the same at `docs/07-crosscutting.md:899`. The human re-plans B and runs `pdca flow A B C D`, which exits **2** with `Ways out: add A to this run's ids` — but A is already in the ids. The `--from-csv` sweep (`flow_batch` → `partition_schedulable`) holds B forever the same way. The only real ways out are stack mode or deleting the `Merges with` edge. A human has to decide whether a finished named member should count as a group member and be merged at a later boundary. At minimum, the remedy text at `waves.py:280` should not tell the user to add an id they already passed.
- [ ] **A group declared only by a bundle outside the run is ignored, so A merges alone.** `waves._merges_with` reads only the briefs of the bundles passed in (`waves.py:180-184`). Failing case: X's brief says `Merges with: A`, and A's brief says nothing. `pdca flow A Z` (Z `Depends on: A`, so A is in a non-final wave) exits 0 with A's PR merged at wave 0's boundary. The brief says one-sided declarations bind both sides (f), and that an out-of-batch member is refused (g). Neither holds when the outside bundle is the one declaring. The builder copied `conflict_map`, which only reads in-batch briefs. The brief named it as the model, and for conflicts that is harmless. For a merge group it is not. Whether the check should scan other bundles on disk for `Merges with` lines that name an id in the batch is a scope call.
- [ ] **Same gap with explicit ids.** `pdca flow A`, where an out-of-batch X declares `Merges with: A` and A says nothing: `check_dep_graph` only reads in-batch briefs (`waves.py:180`), so nothing is refused and A merges alone. Success criterion (f) says either side binds both, and (g) refuses an out-of-batch member. Catching this needs a scan of on-disk briefs beyond the batch. That is a scope call, not a simple fix.
- [ ] C1 Spec — Confirm that refusing chained pairs meets the motivating use cases, or return to Plan for alternative A — the brief leaves this choice open, and those pairs cannot use the proposed merge-mode feature; template/src/pdca_harness/waves.py:317.
- [ ] **A one-sided `Merges with` declared by a bundle outside the run is not seen, so the partner merges alone without a word.** `waves._merges_with` reads only the briefs of the bundles it is given (`waves.py:177-190`). Failing case: B (in flight, not in this run) declares `Merges with: A`, A's brief is silent, and E `Depends on: A`. `pdca flow A E` exits **0**, readies and merges A at wave 0's boundary, and prints nothing about the group. If A's brief declares the same pair instead, the identical run is refused with rc 2. Read together, (f) "one side only is treated as symmetric" and (g) "a group naming an id outside the batch is refused" call for a refusal here. The brief told the builder to read the field "as `waves.conflict_map` does" (`waves.py:136`), and that reader is limited to the batch too. So this needs a scope decision: should the relation be read off every brief under `bundle_root` (cheap, but a new reach), or is batch-only accepted and documented?
- [ ] C1 Spec — Confirm that refusing chained producer/consumer pairs is acceptable — the motivating cases remain unsupported in merge mode under this design; brief.md:51.
- [ ] **A group member that gets split lets its partner land alone, with no message.** A split parent is COMPLETE with no patch (`state.py:351`, `split.accept`). So `group_blocker` (`merge.py:211-225`) sees every member COMPLETE, and `_unmergeable` returns "" because there is no patch. The children do not inherit the field: `split.rewrite_ordering` carries only `Depends on` / `Conflicts with` (`split.py:66`). Failing case: A `Merges with: S`; S, D plain; C `Depends on: D`; S's build splits it into S1. At wave 0's boundary A is readied and merged, and S1 (S's real work) is built later, in wave 1. The run exits 0 with no group line on stderr. The brief makes "`pdca split` refuses to split across a group" a follow-up, so a human should decide whether this PR covers it. A cheap in-scope option: treat a split parent in a group as a blocker (`flow._is_split_parent`, `flow.py:1926`), so the partner is held and the split is named. That way it fails safe instead of half-landing.
- [ ] `template/src/pdca_harness/waves.py:196` builds the group relation from **every** active bundle on disk (`results/issue_*`), not just this run's bundles. Then `_shape_refusal` (`waves.py:289-290`) refuses any group that has a member outside the run that is not COMPLETE. So a stale brief left in `results/` (one that was PLANNED and never run, or one that ended DISCONTINUED) and says `Merges with: A` will block every later merge-mode `pdca flow A` with rc 2. The run of A never named that bundle. This is a deliberate fix for the "one-sided declaration lost" finding from round 2, and the remedy line does say what to remove. But it goes beyond what the brief describes: a `Merges with` id named *by a batch member* that is outside the batch. A human should decide whether a declaration from a bundle outside the run should be able to veto a run, or whether it should only bind when the declaring bundle is in the run or COMPLETE.
