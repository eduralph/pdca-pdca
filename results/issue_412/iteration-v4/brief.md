## Motivation

Some pairs must not land separately: a producer must not reach the base without its consumer, or two issues are planned to "merge as one unit" (getwyrd/wyrd-pdca's alpha plan: wyrd #653 never without #658; #625→#633 as one unit). Stack mode allows this because the human merges the stack. Merge mode merges every completed non-final wave at its boundary, so a pair split across waves lands one at a time — or only half, if the run stops between them. `wave_mode` is global, and briefs cannot say "hold this until X merges with it".

## Design

- **Field.** `Merges with: <ids>` on the brief; ids only on the value line, trailing note ignored; symmetric (either side declaring it binds both); a group is the connected set.
- **Hold.** At a merge-mode wave boundary, a COMPLETE bundle whose group has a member not yet COMPLETE is skipped by `merge_wave`: not readied, not merged, PR stays a draft, one stderr line names the members it waits for. The run goes on.
- **Release.** At the boundary where the last member becomes COMPLETE, all members merge in dependency order (then name order), each through `_merge_one`. The final wave is the exception: its PRs stay drafts for the human today (`merge_wave` is only called for non-final waves, merge.py:515-518). A group whose last member completes in the final wave therefore stays all-draft, and the run says so, so the human merges the group together.
- **A member that ends DISCONTINUED (or otherwise not COMPLETE)** leaves the rest held; stderr says the group can no longer complete.
- **Dependents** of a held member are held as for an unmet prerequisite.
- **Chained group in merge mode** (an edge `Depends on` / `Depends on (merged)` / `Stacks on` between members), **a `Conflicts with` edge between members**, or **a member outside the batch**: refused before any build, naming the ids and the two ways out.
- **Carry.** Held members live in a run-scoped set in `flow._drive_and_act`, fed into each later boundary's `merge_wave` call.

## Alternatives considered

- **A — build the consumer on the producer's unmerged branch for the held span** (the issue's first suggestion). Solves the chained case inside merge mode by reusing the per-bundle base stack mode got in #727 (`integrate.build_bundle_base`, integrate.py:758). Much larger: merge mode has no line or bundle bases today (`own_bases` is stack-only, flow.py:2901-2905), and the consumer's PR would show the producer's diff until it merges. Recommended as a follow-up only if the refusal proves too strict in practice.
- **Document "a chained atomic pair must be one bundle" and do nothing else.** No mechanism holds a non-chained group; the forbidden intermediate state stays possible.

## Impact & compatibility

- New optional brief field; briefs without it behave as today. Template gains one line.
- GitHub cannot merge two PRs atomically. If the second member's merge is refused after the first merged, the run stops (as merge mode does today) and names which members landed — a narrower window than today, not zero.
