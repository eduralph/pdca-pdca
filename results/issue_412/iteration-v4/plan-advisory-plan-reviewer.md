- NEEDS-HUMAN — **The design doesn't fix any of the cases in the issue.** Both real-world cases in the thread are chained pairs: "wyrd 635.6→636.5: '#653 is never merged without #658 stacked behind it'; wyrd #625→#633: 'merge as one unit'" (notes.json body), and the issue says "a chained pair (consumer builds on the merged producer) forces the producer onto the base". Its two ways out, "make the pair one bundle, or run the batch in `wave_mode = "stack"`", are the same workarounds the issue already rejects: "folding each pair into a single over-budget bundle or pulling the pair out of the driver… both give up part of what the harness is for". The brief admits this under Open questions but still lists the mechanism as the goal. The maintainer should decide between refusal and alternative A **before** Do. As written, Do would spend a "high"-difficulty cycle on a field that, for the motivating batches, only produces a nicer error.

- NEEDS-HUMAN — **The test fixture in criterion (a) sets up the failure that Impact calls a narrow window.** In (a), B declares `Conflicts with` A, so B lands in wave 1. In merge mode B is built on the base without A, because A is held and not merged. At the wave-1 boundary A merges first. B's head is then behind the base, and `_merge_one` runs `gh pr update-branch`. If that fails ("a conflict with the base", `template/src/pdca_harness/merge.py:559-565`), the merge is refused and the run STOPs (`flow.py:3081-3084`) with A landed and B not: the forbidden half-landed state. `Conflicts with` exists to declare that these two touch the same code, so this is the expected outcome, not an edge case. The brief's Impact says "a narrower window than today, not zero" and doesn't name it. In stack mode the `Conflicts with` partner builds on a line that holds the earlier bundle; in merge mode a held group member gives no such base. The brief should do one of these:
  - refuse or warn when a group member also `Conflicts with` another member, or
  - state that criterion (a) passes only because `gh` is stubbed, and that real hosts will often STOP mid-group.

- NEEDS-HUMAN — **Carrying a held member across waves isn't scoped to a code site.** At the boundary, `merge.merge_wave` is called with only the current wave's `complete` list (`flow.py:3081`; `complete` is per wave, `flow.py:3071-3072`). Under (a), merging A at the wave-1 boundary means the flow loop has to keep a run-scoped set of held members and pass them back into a later wave's merge call. The Design section ("Hold"/"Release") describes this as a skip inside `merge_wave`. That framing hides the state carry in `flow._drive_and_act`. The Citations list should name that site, and the brief should say how held state relates to `_runnable`'s `held` parameter (`flow.py:682`), which today means "no branch pushed" (#593).

- NEEDS-HUMAN — **The brief doesn't say what happens to a group member that is outside the batch or left over from an earlier run.** It never says what happens when `Merges with` names an id that isn't in this run's batch, or when a member was left held by an earlier run (case (b): "A is never merged by the run"). `merge_wave` only ever gets this run's wave bundles (`flow.py:3081`), so a later run that completes B can't merge an A that finished in an earlier run. A stays a draft forever, or else B merges alone. Out-of-batch ids are already a known hazard for the other edge fields: see `_runnable`'s long out-of-batch handling at `flow.py:703-714` and 793-830. Without a rule (refuse, treat as stack-only, or hold until both are in one batch) and a criterion for it, Do will choose one silently.
