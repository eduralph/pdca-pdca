# Adversarial review — issue 412 / merge-mode-atomic-merge-group (round 4)

I re-ran the new suite on the patched target: `tests.test_merge_group` passes, 41 OK. The frozen red leg (`gate-logs/C4-verify.log`) fails 37 of 41 on assertions, for the right reasons: `rc 0 != 2`, `'E' unexpectedly found in built`, B readied and merged. The 4 tests that pass both ways are labelled guards. The tests drive the real `flow._drive_and_act` and `cli.main`, plus the real `waves` and `merge` code. Only the build leaf, publish and `gh` are stubbed. So the evidence holds. I wrote probe tests (subclasses of `MergeGroup`, run from my scratch dir) for the cases below. One of them breaks the field's core promise.

- NEEDS-HUMAN [human] — **When a group member is split, its partner merges alone, with no warning and rc 0.** `split.accept` leaves the parent as a close disposition (`template/src/pdca_harness/split.py:1008` writes `close-disposition` = `split`). `state.state` reads that as COMPLETE with no patch (`template/src/pdca_harness/state.py:351`). The group check looks only at state (`template/src/pdca_harness/merge.py:229-236`). `_premerge` then says "skip, nothing to merge" for that member (`merge.py:663-665`). So the group is released, and the partner lands while the split's children have not. The end-of-run report skips members with no patch (`template/src/pdca_harness/flow.py:3337`), so it says nothing.
  - **Probe P1:** A `Merges with: B`. A splits in wave 0 into A1 and A2, where A2 `Depends on: A1` (the children do not repeat the field). B `Depends on: D`, and C `Depends on: B`. Result: built `[A, D, A1, B, A2, C]`; merged `{A1, B, D}`. A2 sits in the final wave as a draft, `holds == {}`, rc 0, and stderr has no `Merges with` line at all. B landed with only half of A's work.
  - **Probe P1b:** an earlier run split A (A1 still PLANNED). Then `pdca flow B C D` merges B at wave 1's boundary with none of A's work landed. rc 0, and stderr is empty.
  - The up-front check doesn't catch this either: a COMPLETE member is never "away" (`template/src/pdca_harness/waves.py`, `_shape_refusal`).
  - **Unwarranted claim:** the test module docstring says "A split mid-run does not break a group" (`template/tests/test_merge_group.py:20`). That is only tested for a split of a *non-member* (`test_a_split_before_the_last_member_does_not_break_the_group`).
  - **Why [human]:** the brief releases a group on COMPLETE state and puts split/group interplay out of scope (Scope: "making the sizer or `pdca split` refuse to split across a group (follow-up)"). So whether a split parent should block its group, or pass its membership to its children, is a scope call.
  - **Cheap fail-closed fix if the human wants it now:** in `group_blocker`, treat a member whose close marker reads `split` the way a DISCONTINUED member is treated (hold it, and name the split and the way out). Also refuse such a group up front in `_shape_refusal`.

- A member an earlier run finished, whose `publish.json` has no `repo` field (a record from before that field existed, per `template/src/pdca_harness/publish.py:813-814`), holds its group on every re-run. This happens even after a human has merged its PR into the right base. `_groups()` asks `merged.merged_into`, which treats a missing `repo` as not merged (`template/src/pdca_harness/merged.py:109`). Then `group_blocker` runs `_foreign_refusal` before `_premerge`'s already-merged skip (`template/src/pdca_harness/merge.py:243-245`, `:275`).
  - **Probe P2:** A finished with a record that has no repo, merged by hand. `pdca flow B C D` gives rc 1, with B held and C not built. The message is confusing: it says A's PR was opened "on ? @ `main`", though merge mode would merge it "into … `main`".
  - This is fail-closed, and the end-of-run line gives a way out (drop the edge). Iteration 3 raised the same gap and it was fixed for run members only (`test_a_member_merged_by_hand_whose_record_names_no_repo_holds_nothing`). It is a minor gap, so I am not routing it for a rebuild.

- I tried to refute these and could not:
  - **Half-landing from a refusal the run could see coming.** No PR, an `Onto branch` record, a record with no repo under `merge_requires = "all"`, and a malformed `expected_checks` all hold or STOP before the first `gh pr ready`. `group_blocker` asks the same `_premerge` that `_merge_one` uses.
  - **Re-running after a STOP, or after a member was DISCONTINUED.** Both go through.
  - **One-sided declarations from bundles that are held, archived or adopted then dropped.** All still bind the partner.
  - **Rings of groups through `Conflicts with` edges.** `_wait_edges` reads which side builds first from `_build_order`, the same function `compute_waves` levels with.
  - **Duplicate bundles in `again + complete`.** None: `accepted` grows before the merge block, but `held_group` only holds members from earlier boundaries.
  - **Stack mode.** It is unchanged. `_build_order` is a straight move of the old loop: the same `_reaches` over the same growing edge set.

- About the verdict: the gate claims in `check-gates.json` hold up. One limit applies to all the group tests: they pin `merge_requires = "required"` (`template/tests/test_merge_group.py:69`). So a group release under the default `"all"` is never run. In that mode the second member is always behind its base once the first merges, so it needs `gh pr update-branch` and a fresh checks run before it can merge. That is the host-side half-landing window the brief's Impact section accepts. It is not a refutation, but the "narrower window" there means every multi-member release under the default setting, not a rare case.
