# Advisory code review — issue 412 (merge-mode atomic merge group)

Scope: correctness bugs the patch adds, plus reuse/simplification. All gates in `check-gates.json` pass or are deferred. `gate-logs/T3-suite.log` shows the root and driver suites green (2648 tests). `gate-logs/C4-verify.log` shows 16 of 18 new tests red before the fix and green after it. Every finding the previous round listed in the brief now has a test in `template/tests/test_merge_group.py`: the split, the one-sided declaration, the missing PR, the `Onto branch` record, and the final-wave group. Both findings below come from reading the code. I did not run them.

- NEEDS-HUMAN [impl] — **A held group member's `Conflicts with` partners outside the group are not held.** `template/src/pdca_harness/flow.py:2992` passes `held_group` only as `group_held`. `_runnable` (`flow.py:802`) uses that set only for prerequisite edges. The conflict-partner hold (`partners`, `flow.py:773`) is still fed only `held_unpushed`, and the relation is only built when `held_unpushed or held_conflict or held_base` (`flow.py:2983-2985`). Failing case: fixture (a) plus a bundle E with `Conflicts with: A` and no group. The scheduler puts E after A. A is held unmerged at wave 0, so E is built at wave 1 on a base without A. At the release, `_back_to_back` merges A first and then E across the declared overlap. That is the half-landed `gh pr update-branch` risk the brief gives for refusing in-group conflicts (`template/src/pdca_harness/waves.py:261-264`). Before this patch, A always merged before E was built. Fix direction: treat `held_group` like `held_unpushed` for the conflict-partner hold (#629), or refuse this shape up front. Add a test either way.
- NEEDS-HUMAN [impl] — **A group can't be re-run once one member is already terminal, and the remedy it prints doesn't work.** `flow_ids` drops terminal ids (COMPLETE / DISCONTINUED) from the drive set (`template/src/pdca_harness/flow.py:3575`, "already terminal … skipped"). The merge-mode check then treats a member that is COMPLETE on disk as "outside the batch" (`_group_refusal`, `template/src/pdca_harness/waves.py:294-301`) and tells the operator to "add <id> to this run's ids". Adding it changes nothing, because the id is dropped again as terminal. Typical case: a run leaves A COMPLETE and held as a draft because B ended DISCONTINUED (exactly what `_report_groups` reports, `flow.py:3244`). The operator re-plans B and runs `pdca flow B` (or `pdca flow A B`), and it is refused every time. The only way out is to delete the `Merges with` line. Fix direction: count a member that is COMPLETE on disk with an unmerged PR as in the batch, and pass it into the boundary's `merge_wave` as a held member. Or at least make the remedy say what actually works. Add a test.
- `template/src/pdca_harness/flow.py:3276` (`_report_groups`): `missing` is built for every member, and then only the non-COMPLETE ones are used. Filtering when building the list would be simpler. This is a small tidy-up, not a bug.
- `template/src/pdca_harness/merge.py:156`: `group_blocker` runs once per group member, and each call re-reads every member's state and publish record. So the same answer is computed once per member. Caching it per group (for example, keyed by `frozenset(members)`) would remove the repeated reads. The groups are small, so this costs almost nothing in practice. It's a simplification only.

No other correctness problems found in `brief.merges_with`, `waves._merges_with` / `merge_groups` / `_prereq_path`, the hold fixpoint in `partition_schedulable`, `merge._back_to_back`, the half-landed message in `merge_wave`, or the `**kw` changes to the existing test stubs.
