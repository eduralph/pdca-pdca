# Result — issue 412 / merge-mode-atomic-merge-group

## 1. Spec (from brief.md)              ← Check verifies against THIS
- Defect / goal: A brief can declare `- **Merges with:** <id>[, <id>…]` — an atomic merge group: these bundles must not land on the base separately. In merge mode the driver does not ready or merge a COMPLETE group member while any member of its group is not yet COMPLETE; once all are COMPLETE it merges the whole group back-to-back, in dependency order, at one wave boundary, each through the normal `merge._merge_one` gates. A bundle that depends on a held group member is held too (not built on a base without it). A group that is also a dependency chain (one member `Depends on` another) cannot work in merge mode — the consumer can only build after the producer merges, which the group forbids — so such a batch is refused before anything is built, with a message giving the two ways out: make the pair one bundle, or run the batch in `wave_mode = "stack"`. Two more group shapes are refused the same way in merge mode, for the same reason: members that `Conflicts with` each other (the later one is built on a base without the held earlier one, so its PR needs `gh pr update-branch` across a declared overlap at the release boundary — the half-landed STOP this field exists to prevent), and a `Merges with` id that is not in this run's batch (`merge_wave` only ever sees this run's bundles, so the group could never be merged together). In stack mode the field changes nothing (the human already merges the stack and can take the pair together).
- Success criterion: With `wave_mode = "merge"` and `gh` stubbed: (a) A and B both declare `Merges with` each other and have no edge between them; D (no group) is in wave 0, B `Depends on: D` (so A in wave 0, B in wave 1), and C `Depends on: B` (so wave 2) — at the wave-0 boundary no `gh pr ready` / `gh pr merge` is called for A's PR and the run goes on; at the wave-1 boundary A's and B's PRs are both merged, A first, before C builds; (b) if B ends not COMPLETE (e.g. DISCONTINUED), A is never merged by the run and stderr names A as held for its group with B; (c) a bundle `Depends on: A` while A is held is not built and is named as held; (d) a batch where B `Depends on: A` and they declare `Merges with` each other makes `pdca flow` exit non-zero before any Do runs, stderr naming both ids and both ways out; (e) the same batch with `wave_mode = "stack"` runs as it does today (the field is ignored); (f) `Merges with` declared on one side only is treated as symmetric (as `Conflicts with` is); (g) in merge mode, a group whose members `Conflicts with` each other, and a group naming an id outside the batch, are each refused the same way as (d), before any Do. Cases (d) and (g) are tested at the CLI: `cli.main(["flow", …])` returns 2 and stderr carries the `Ways out:` line (`template/src/pdca_harness/cli.py:673-679`, which turns `waves.DependencyGraphError` into rc 2 with `exc.remedy`); the remedy names both ways out.
- Repo + branch target: eduralph/pdca-harness @ main
- Scope (one logical fix) / out of scope: The `Merges with` field (parse, symmetric, ids only), merge-mode hold-and-merge-together, the dependents' hold, the up-front refusal of a chained group in merge mode, and docs plus the brief template line (`template/templates/brief.md.tpl`, next to `Conflicts with`). / out of scope: building the consumer of a chained group on the producer's unmerged branch in merge mode (alternative A — see Open questions); making the sizer or `pdca split` refuse to split across a group (follow-up); host-side atomicity (GitHub has no multi-PR merge — if a later member's merge fails after an earlier one merged, the run stops and says which landed, see Impact); stack mode behaviour.

# Adversarial review — issue 412 / merge-mode-atomic-merge-group

**Evidence: it holds.** I re-ran `template/tests/test_merge_group.py` against the patched target: 18/18 pass. The frozen C4 log (`gate-logs/C4-verify.log`) shows 16/18 fail with the production change reverted. The two that pass there are the stack-mode case (e) and the `expected_checks_error` guard, and both are meant to pass either way. The tests drive the real `flow._drive_and_act` and `cli.main`. Only the build leaf, publishing and `gh` are stubbed. I found no tautology and no mocked-away defect. My attack therefore lands on what the tests do not cover. I confirmed each case below with a scratch test that subclasses the shipped `MergeGroup` fixture, so all of them run through the same production path.

- NEEDS-HUMAN [impl] — **A merge-mode run that stops can never finish its group on a re-run.** `flow_ids` drops ids that are already COMPLETE from the drive set (`template/src/pdca_harness/flow.py:3575`). The sweep drops them too (`flow.py:3410-3415`). The group check counts as "in the run" only the drive set plus `offered` (`flow.py:2883`, `waves.py:150-151`, `waves.py:294`). So a member held as a draft in run 1 reads as outside the batch in run 2. Failing case: fixture (a) with D's `gh pr merge` refused by the host. At wave 0's boundary A is held, D fails, and the run STOPs, as merge mode tells the user to do ("re-run … the run resumes idempotently", `merge.py:719`). After the fix, `pdca flow A B C D` exits **2**: `issue_B: their Merges with group names issue_A, which is not in this run's batch … Ways out: add A to this run's ids`. A *was* in the ids. `pdca flow --from-csv` holds B and C instead and prints the same "add A to this run's ids" advice, though the sweep takes no ids. Inside merge mode this is a dead end, and before the patch the same re-run worked. Relaxing the refusal alone is not enough. `group_pool` starts as the drive set only (`flow.py:2958`), and `merge_groups` cuts each group down to the given bundles (`waves.py:219`). So B would have no partner left and would merge alone at its boundary. Fix direction: count the run's finished named ids (`_finished_named`, `flow.py:2915`, computed after `compute_waves` today) as in the run for the check. Also seed a finished, unmerged member into `group_pool` and `held_group`, so the first boundary releases it with its partner. The sweep needs the same for a COMPLETE partner on disk. No test covers a re-run.

- NEEDS-HUMAN [impl] — **Two groups that depend on each other deadlock, and nothing refuses them up front.** `_group_refusal` looks only for a `Depends on` path between two members of the *same* group (`waves.py:312-313`, `_prereq_path` over `deps`). It misses a path that goes through another group's hold. Failing case: G1 = {A, B}, G2 = {C, D}, B `Depends on: C`, D `Depends on: A`, and `pdca flow A B C D` in merge mode. The run is not refused. It builds A and C, holds both at wave 0's boundary, then holds B (C is held for its group) and D (A is held). It ends rc 1 with two draft PRs, nothing landed, and the advice "Merge the group together once that is resolved", which no re-run can resolve. This is the deadlock the chained-group refusal exists to stop. The docs already promise that a member depending on another "directly or through other bundles" is refused (`docs/07-crosscutting.md` hunk). Fix direction: run the path search on the graph with each group collapsed to one node. A cycle there, or a path from a group back to itself, means refuse.

- NEEDS-HUMAN [human] — **A one-sided `Merges with` declared by a bundle outside the run is not seen, so the partner merges alone without a word.** `waves._merges_with` reads only the briefs of the bundles it is given (`waves.py:177-190`). Failing case: B (in flight, not in this run) declares `Merges with: A`, A's brief is silent, and E `Depends on: A`. `pdca flow A E` exits **0**, readies and merges A at wave 0's boundary, and prints nothing about the group. If A's brief declares the same pair instead, the identical run is refused with rc 2. Read together, (f) "one side only is treated as symmetric" and (g) "a group naming an id outside the batch is refused" call for a refusal here. The brief told the builder to read the field "as `waves.conflict_map` does" (`waves.py:136`), and that reader is limited to the batch too. So this needs a scope decision: should the relation be read off every brief under `bundle_root` (cheap, but a new reach), or is batch-only accepted and documented?

- Test gap, not a refutation: every case sets `merge_requires="required"` (`test_merge_group.py` `_cfg`). The default is `"all"` (`config.py:374`). Under `"all"`, a held member released at a later boundary is behind its base, because the earlier wave merged past it. That sends it through `gh pr update-branch` and the rollup wait (`merge.py:680-696`), and no group test drives that path. The third `_unmergeable` check (no repo, `merge.py:234-236`) only applies under `"all"`, so no test reaches it either.

- Minor, scope: in merge mode the up-front refusal also fires with `--no-publish` (checked: `pdca flow A B --no-publish` on the chained pair returns 2), though that run merges nothing. The `pdca waves` preview now prints "unschedulable" for such a batch too (`cli.py:1096-1099`). This is stricter than needed, but the brief's (d) does not exempt it, so I flag it only.

Things I tried and could not break: a split before the last member (in-run names are passed as `in_run`, `flow.py:2394`); a split child dropped later (`group_pool` keeps its declaration); a member with no PR record or an `Onto branch` record (checked for every member before the first `gh` call, `merge.py:153-167`, `merge.py:212-213`); a group wholly in the final wave, or finished in it (named at the end, exit codes as the brief says); the host refusing a later member (the STOP names what landed); merge order (held members first, the group back to back, `merge.py:240-252`).

# Advisory code review — issue 412 (merge-mode atomic merge group)

Scope: correctness bugs the patch adds, plus reuse/simplification. All gates in `check-gates.json` pass or are deferred. `gate-logs/T3-suite.log` shows the root and driver suites green (2648 tests). `gate-logs/C4-verify.log` shows 16 of 18 new tests red before the fix and green after it. Every finding the previous round listed in the brief now has a test in `template/tests/test_merge_group.py`: the split, the one-sided declaration, the missing PR, the `Onto branch` record, and the final-wave group. Both findings below come from reading the code. I did not run them.

- NEEDS-HUMAN [impl] — **A held group member's `Conflicts with` partners outside the group are not held.** `template/src/pdca_harness/flow.py:2992` passes `held_group` only as `group_held`. `_runnable` (`flow.py:802`) uses that set only for prerequisite edges. The conflict-partner hold (`partners`, `flow.py:773`) is still fed only `held_unpushed`, and the relation is only built when `held_unpushed or held_conflict or held_base` (`flow.py:2983-2985`). Failing case: fixture (a) plus a bundle E with `Conflicts with: A` and no group. The scheduler puts E after A. A is held unmerged at wave 0, so E is built at wave 1 on a base without A. At the release, `_back_to_back` merges A first and then E across the declared overlap. That is the half-landed `gh pr update-branch` risk the brief gives for refusing in-group conflicts (`template/src/pdca_harness/waves.py:261-264`). Before this patch, A always merged before E was built. Fix direction: treat `held_group` like `held_unpushed` for the conflict-partner hold (#629), or refuse this shape up front. Add a test either way.
- NEEDS-HUMAN [impl] — **A group can't be re-run once one member is already terminal, and the remedy it prints doesn't work.** `flow_ids` drops terminal ids (COMPLETE / DISCONTINUED) from the drive set (`template/src/pdca_harness/flow.py:3575`, "already terminal … skipped"). The merge-mode check then treats a member that is COMPLETE on disk as "outside the batch" (`_group_refusal`, `template/src/pdca_harness/waves.py:294-301`) and tells the operator to "add <id> to this run's ids". Adding it changes nothing, because the id is dropped again as terminal. Typical case: a run leaves A COMPLETE and held as a draft because B ended DISCONTINUED (exactly what `_report_groups` reports, `flow.py:3244`). The operator re-plans B and runs `pdca flow B` (or `pdca flow A B`), and it is refused every time. The only way out is to delete the `Merges with` line. Fix direction: count a member that is COMPLETE on disk with an unmerged PR as in the batch, and pass it into the boundary's `merge_wave` as a held member. Or at least make the remedy say what actually works. Add a test.
- `template/src/pdca_harness/flow.py:3276` (`_report_groups`): `missing` is built for every member, and then only the non-COMPLETE ones are used. Filtering when building the list would be simpler. This is a small tidy-up, not a bug.
- `template/src/pdca_harness/merge.py:156`: `group_blocker` runs once per group member, and each call re-reads every member's state and publish record. So the same answer is computed once per member. Caching it per group (for example, keyed by `frozenset(members)`) would remove the repeated reads. The groups are small, so this costs almost nothing in practice. It's a simplification only.

No other correctness problems found in `brief.merges_with`, `waves._merges_with` / `merge_groups` / `_prereq_path`, the hold fixpoint in `partition_schedulable`, `merge._back_to_back`, the half-landed message in `merge_wave`, or the `**kw` changes to the existing test stubs.
