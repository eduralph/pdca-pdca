# Result — issue 412 / merges-with-field-refused-in-merge-mode

## 1. Spec (from brief.md)              ← Check verifies against THIS
- Defect / goal: A brief has no way to say "these bundles must not land on the base separately" (an atomic merge group: a caller-first pair, or two issues planned to "merge as one unit"). In `wave_mode = "merge"` the driver `gh pr merge`s every completed non-final wave at its boundary, so a group member can land on the base alone, and nothing warns anyone. In stack mode this is harmless: the human merges the stacked PRs and can take a group together.
- Success criterion: A new optional brief field `- **Merges with:** <id>[, <id>…]` is parsed like `Conflicts with` (ids only on the value line, a trailing note ignored, `#12` / `12` / `issue_12` all accepted). A run's bundle is a **group member** when its own brief declares a non-empty `Merges with`, or when the brief of another bundle in the same run names it there. With `wave_mode = "merge"`: (a) `waves.compute_waves(cfg, bundles)` raises `waves.DependencyGraphError` for a batch {A, B} where A declares `Merges with: B`; the message names A and B, and `remedy` names both ways out: set `wave_mode = "stack"`, or fold the group into one bundle. (b) The same refusal happens when only B declares it (A's brief is silent), and for a run of A alone whose brief declares `Merges with: X` with X not in the run. (c) `pdca flow A B` on batch (a), driven through `cli._flow` the way `template/tests/test_flow_dependency_refusal.py:91-97` does, returns 2 with no traceback; stderr carries the `Ways out:` line; `driver.run_issue` is never called; and both bundles stay PLANNED with no `patch.diff` (that file's `_assert_nothing_built`, :99-104). (d) `waves.partition_schedulable(cfg, [A, B, C, D])`, where A declares `Merges with: B`, C `Depends on: A`, and D has no edges, returns D as schedulable and holds A, B and C. A's and B's hold reasons name `Merges with`. It does not raise. With `wave_mode = "stack"`: (e) the batches from (a), (b) and (d) give the same waves from `compute_waves`, and the same result from `partition_schedulable`, as the identical batches without the `Merges with` lines. Nothing is refused or held. With `wave_mode = "merge"` again: (f) bare `pdca waves` (no ids) through `cli.main`, over a `results/` holding A (declares `Merges with: B`), B, and an unrelated D, returns 1 and prints `unschedulable:` naming A and B on stderr. ## Correctness

- `template/src/pdca_harness/waves.py:170-196` (`merge_groups`): the union-find (grouping members by a shared root) is correct. `root()` creates missing nodes through `setdefault`, so a partner outside the run (`X`) becomes a node and stays in the group, as the docstring says. A self-reference (`A` declares `Merges with: A`) makes a one-member group, and merge mode refuses it. That matches the brief's "declares a non-empty `Merges with`" rule, so it is fine.
- `template/src/pdca_harness/waves.py:377-386`: the holds are added before the first `_propagate_holds`, so dependents are held too. Every in-run member of every group is held, so the set left over has no group the strict `compute_waves` call could still refuse. That means the `compute_waves(schedulable)` calls after the tolerant path (`flow.py:2180` and the sweep) cannot start raising because of this change. The split re-levelling at `flow.py:2175` is safe for the same reason. Split children do not carry the field, and the brief already names that gap.
- `template/src/pdca_harness/waves.py:149-157`: the group check runs after the cycle and unresolved-dependency checks. A batch with both problems reports the dependency error first, and the group error only once that is fixed. This is fine, but the operator may need two tries to see both.
- Low priority (not marked NEEDS-HUMAN because `flow.py` is out of scope): the sweep's "nothing to schedule" message at `template/src/pdca_harness/flow.py:3338-3339` still says every bundle is "held on an unresolved dependency or a cycle". A run held only by a merge group now shows that wrong reason. Each bundle's real reason is still printed above it by `_report_held` (`flow.py:1793`), so nothing is lost. A follow-up (or #778) could fix the wording.

## Tests

- NEEDS-HUMAN [impl] — `template/tests/test_merge_group.py:158-172`: the tolerant path is only tested on batch (d), where `A` declares the group. Nothing tests `partition_schedulable` in merge mode when only the partner declares the group (`BATCH_B`), or when the partner is outside the run (`BATCH_B_OUT`, :44). The strict path tests both.
