# Result — issue 412 / merge-mode-atomic-merge-group

## 1. Spec (from brief.md)              ← Check verifies against THIS
- Defect / goal: A brief can declare `- **Merges with:** <id>[, <id>…]` — an atomic merge group: these bundles must not land on the base separately. In merge mode the driver does not ready or merge a COMPLETE group member while any member of its group is not yet COMPLETE; once all are COMPLETE it merges the whole group back-to-back, in dependency order, at one wave boundary, each through the normal `merge._merge_one` gates. A bundle that depends on a held group member is held too (not built on a base without it). A group that is also a dependency chain (one member `Depends on` another) cannot work in merge mode — the consumer can only build after the producer merges, which the group forbids — so such a batch is refused before anything is built, with a message giving the two ways out: make the pair one bundle, or run the batch in `wave_mode = "stack"`. Two more group shapes are refused the same way in merge mode, for the same reason: members that `Conflicts with` each other (the later one is built on a base without the held earlier one, so its PR needs `gh pr update-branch` across a declared overlap at the release boundary — the half-landed STOP this field exists to prevent), and a `Merges with` id that is not in this run's batch (`merge_wave` only ever sees this run's bundles, so the group could never be merged together). In stack mode the field changes nothing (the human already merges the stack and can take the pair together).
- Success criterion: With `wave_mode = "merge"` and `gh` stubbed: (a) A and B both declare `Merges with` each other and have no edge between them; D (no group) is in wave 0, B `Depends on: D` (so A in wave 0, B in wave 1), and C `Depends on: B` (so wave 2) — at the wave-0 boundary no `gh pr ready` / `gh pr merge` is called for A's PR and the run goes on; at the wave-1 boundary A's and B's PRs are both merged, A first, before C builds; (b) if B ends not COMPLETE (e.g. DISCONTINUED), A is never merged by the run and stderr names A as held for its group with B; (c) a bundle `Depends on: A` while A is held is not built and is named as held; (d) a batch where B `Depends on: A` and they declare `Merges with` each other makes `pdca flow` exit non-zero before any Do runs, stderr naming both ids and both ways out; (e) the same batch with `wave_mode = "stack"` runs as it does today (the field is ignored); (f) `Merges with` declared on one side only is treated as symmetric (as `Conflicts with` is); (g) in merge mode, a group whose members `Conflicts with` each other, and a group naming an id outside the batch, are each refused the same way as (d), before any Do. Cases (d) and (g) are tested at the CLI: `cli.main(["flow", …])` returns 2 and stderr carries the `Ways out:` line (`template/src/pdca_harness/cli.py:673-679`, which turns `waves.DependencyGraphError` into rc 2 with `exc.remedy`); the remedy names both ways out.
- Repo + branch target: eduralph/pdca-harness @ main
- Scope (one logical fix) / out of scope: The `Merges with` field (parse, symmetric, ids only), merge-mode hold-and-merge-together, the dependents' hold, the up-front refusal of a chained group in merge mode, and docs plus the brief template line (`template/templates/brief.md.tpl`, next to `Conflicts with`). / out of scope: building the consumer of a chained group on the producer's unmerged branch in merge mode (alternative A — see Open questions); making the sizer or `pdca split` refuse to split across a group (follow-up); host-side atomicity (GitHub has no multi-PR merge — if a later member's merge fails after an earlier one merged, the run stops and says which landed, see Impact); stack mode behaviour.

# Adversarial review — issue 412 (merge-mode atomic merge group), round 3

Verdict: the red→green evidence is real, but the fix breaks on four concrete inputs: three
`[impl]` and one `[human]`. Each was reproduced against the patched tree at `$PDCA_TARGET`
using the new test module's own harness (production `flow._drive_and_act` / `cli.main`, `gh`
stubbed, merge mode).

## Evidence

- Tried to refute C4's red→green and could not. In `gate-logs/C4-verify.log`, 28 of 31
  cases in `template/tests/test_merge_group.py` fail with the production change reverted.
  They fail on assertions, not on import errors. The 3 that pass both ways are the declared
  guards: `test_a_malformed_expected_checks_…` (`test_merge_group.py:381`), leg (e)
  `test_the_chained_group_runs_as_today_in_stack_mode` (`:476`, which should be green before
  the fix) and `test_a_finished_member_already_merged_holds_nothing` (`:742`). Re-run here:
  31/31 green. Only the build leaf, the publish texts and `gh` are stubbed, so C5's claim
  that the tests run production code, not a copy, holds.

## Refutations

- NEEDS-HUMAN [impl] — **The up-front "group waits for itself" check gets a conflict pair's
  build order wrong, so it misses a real deadlock.** `_wait_edges`
  (`template/src/pdca_harness/waves.py:362-367`) decides which side of a `Conflicts with`
  pair builds first from `Depends on` edges only (`ordered`). Otherwise it assumes name
  order. `compute_waves` (`waves.py:510-516`) also counts the conflict edges it already
  added for earlier pairs, so it can build the name-higher bundle first. Failing case:
  K `Merges with: L`; L `Depends on: H`; H `Depends on: G` and `Conflicts with: K`;
  G `Conflicts with: F`; F `Depends on: K`. The waves are [K] [F] [G] [H] [L], so H is built
  after K. `pdca flow F G H K L --no-act` is **not** refused. K is held at wave 0's boundary,
  F is held (its prerequisite K is held), H is held (it conflicts with the held K), and L is
  never built. The run exits 1 with K left as a draft, and the closing line says "Merge the
  group together once that is resolved", which no re-run can resolve. The docs say this
  shape is refused before anything builds (`docs/07-crosscutting.md:925-928`). Fix: take
  the conflict direction from the same loop `compute_waves` uses (one shared helper), not
  from a second derivation.

- NEEDS-HUMAN [impl] — **Same root cause, other direction: a batch that works is refused
  with rc 2.** H `Merges with: L` and `Depends on: G`; L `Depends on: K`; K
  `Conflicts with: H`; G `Conflicts with: F`; F `Depends on: K`. The scheduler builds K in
  wave 0 and H in wave 3 (waves [K] [F, L] [G] [H]), so no member waits for its own group.
  But `_wait_edges` (`waves.py:367-368`) assumes name order (H before K), and
  `pdca flow F G H K L --no-act` exits 2 with "issue_K `Conflicts with` issue_H and is built
  after it … the group would never complete". No test has a conflict pair that the scheduler
  orders against name order; one such test per direction would pin both cases.

- NEEDS-HUMAN [impl] — **A member an earlier run finished is readied and merged into
  whatever base its old PR targets, which can be another bundle's branch.** The release now
  merges PRs this run did not open (`flow.py:2979-2995` adds them to `group_finished`, and
  `merge._back_to_back` at `merge.py:256` pulls them in). That breaks the module's own rule
  at `merge.py:86`: "Merge mode readies and merges only a PR this run opened".
  `_unmergeable` (`merge.py:232-253`) checks `pr_url`, `"stacked"` mode and `repo`, but not
  the record's `base`. Merge mode's publish guard against run-made bases (`publish.py:293`,
  #411) never saw a PR that a stack-mode run opened. Such a PR records `"base": pr_base`
  (`publish.py:436`), which can be a parent's fix branch (`publish.py:282`). Stack mode is
  also the way out that this patch's own refusals print. Failing case: A finished earlier
  with `Merges with: B` and a publish record `{"mode": "stacked-pr", "base": "fix/P", …}`;
  B `Depends on: D`; C `Depends on: B`. `pdca flow A B C D --no-act` runs `gh pr ready` and
  `gh pr merge` on A's PR, which merges A into `fix/P`, not `main`. It merges B into `main`,
  counts the group as landed, and exits 0 with no warning. Fix: for a member this run did
  not publish, hold the group and say why, unless its recorded base is its brief's target
  and not a branch another bundle produced. `publish._merge_base_refusal` already applies
  that check.

- NEEDS-HUMAN [human] — **A group member that gets split lets its partner land alone, with
  no message.** A split parent is COMPLETE with no patch (`state.py:351`, `split.accept`).
  So `group_blocker` (`merge.py:211-225`) sees every member COMPLETE, and `_unmergeable`
  returns "" because there is no patch. The children do not inherit the field:
  `split.rewrite_ordering` carries only `Depends on` / `Conflicts with` (`split.py:66`).
  Failing case: A `Merges with: S`; S, D plain; C `Depends on: D`; S's build splits it into
  S1. At wave 0's boundary A is readied and merged, and S1 (S's real work) is built later, in
  wave 1. The run exits 0 with no group line on stderr. The brief makes "`pdca split` refuses
  to split across a group" a follow-up, so a human should decide whether this PR covers it.
  A cheap in-scope option: treat a split parent in a group as a blocker
  (`flow._is_split_parent`, `flow.py:1926`), so the partner is held and the split is named.
  That way it fails safe instead of half-landing.

## Tried and could not break

- A re-run after a stop, a member that ends DISCONTINUED, a member with no PR or an
  `Onto branch` record, one-sided declarations (including from held or dropped split
  children), the sweep, finished members already merged, and same-wave groups. Each behaved
  as the brief asks.
- Coverage note, no action asked: every case sets `merge_requires = "required"`
  (`test_merge_group.py:67`). Under the default `"all"`, each member after the first is
  behind its base once the first merges. `_merge_one` then runs `gh pr update-branch` and
  waits for a fresh green rollup (`merge.py:701-745`) while the group is half landed. That is
  the host-side window the brief's Impact section accepts, but no test runs a group release
  on that path.

# Advisory code review — issue 412 (`Merges with` atomic merge group)

Lens: correctness bugs the patch adds, plus reuse / simplification / efficiency. I read
`patch.diff`, `brief.md`, `check-gates.json` and `gate-logs/`, and grounded each line below on
`$PDCA_TARGET`. The gates are green: C4 is red pre-fix (28 of 31 new tests fail) and green
post-fix, and T3 passes. The new tests check the success-criterion legs (a)–(g) directly,
including call order (`_merge_index`), so I found no test that misses what it claims to cover.
I did not find a logic bug that breaks one of the brief's legs. The findings are smaller.

- NEEDS-HUMAN [human] — `template/src/pdca_harness/waves.py:196` builds the group relation from **every** active bundle on disk (`results/issue_*`), not just this run's bundles. Then `_shape_refusal` (`waves.py:289-290`) refuses any group that has a member outside the run that is not COMPLETE. So a stale brief left in `results/` (one that was PLANNED and never run, or one that ended DISCONTINUED) and says `Merges with: A` will block every later merge-mode `pdca flow A` with rc 2. The run of A never named that bundle. This is a deliberate fix for the "one-sided declaration lost" finding from round 2, and the remedy line does say what to remove. But it goes beyond what the brief describes: a `Merges with` id named *by a batch member* that is outside the batch. A human should decide whether a declaration from a bundle outside the run should be able to veto a run, or whether it should only bind when the declaring bundle is in the run or COMPLETE.
- NEEDS-HUMAN [impl] — `template/src/pdca_harness/merge.py:226-229` (`_member`) is a byte-for-byte copy of `waves.member_path` (`template/src/pdca_harness/waves.py:223-227`). Both are new in this patch. `merge.py` could import and use `waves.member_path`, or both could call `cfg.find_bundle` inline. As written, the two copies can drift apart.
- NEEDS-HUMAN [impl] — `template/src/pdca_harness/merge.py:232-253` (`_unmergeable`) re-implements three of `_merge_one`'s refusal checks: no `pr_url` (`merge.py:620`), a `"stacked"` record (`merge.py:631`), and no repo when `merge_requires != "required"` (`merge.py:688`). These are now two hand-kept copies of one rule. If `_merge_one` gains a new local refusal and `_unmergeable` does not, the group half-lands again, which is the bug round 1 fixed. A simpler shape is to pull these checks out of `_merge_one` into one helper that both call. A smaller step is a test that ties the two lists together. There is also one gap between them: `_merge_one` returns 0 for a PR that is already merged (`is_merged`, about `merge.py:646`) *before* it checks for a repo. `_unmergeable` checks for a repo with no "already merged" check, so a member with no repo whose PR was merged by hand (and is not in `landed`) holds its whole group, even though `_merge_one` would skip it.
- NEEDS-HUMAN [impl] — The exit code is not consistent for the same end state. When a group sits wholly in the final wave, the run prints "Merge its PRs together" and exits 0 with `holds == {}` (`template/tests/test_merge_group.py:399-414`). When only the group's last member is in the final wave, the run prints the same message but exits 3 with `holds == {"A": "group"}` (`test_merge_group.py:416-430`, via `template/src/pdca_harness/flow.py:3281`). In both cases every member is COMPLETE and every PR is a draft waiting for the human to merge them together. A script reading the exit code will treat the two differently. Either is defensible, but the docstring (`flow.py` `_drive_and_act`, the `"group"` paragraph) should say on purpose which one is meant.
- Efficiency (no action needed): in merge mode, `waves.merge_groups` reads and parses every brief under `results/` each time it is called. It runs once in `check_dep_graph` (`waves.py:157`), once in `partition_schedulable` (`waves.py:646`), and twice per wave in `flow._drive_and_act` through `_groups()` (`flow.py:2983`, called at `flow.py:3013` and again at the boundary). `_clash` and `_wait_edges` read briefs again. This is O(bundles on disk) per call, which is fine at today's sizes. Reading the relation once per wave and passing it down would be simpler. `merged.is_merged` (a `gh` call) runs at most once per finished member (`flow.py:2992`), because the result is cached in `group_landed` / `group_finished`. That part is fine.
- Stack mode: every new path checks `cfg.wave_mode == "merge"` (`waves.py:156`, `waves.py:646`, and `grouping` in `flow._drive_and_act`). The only stack-mode changes are the extra keyword-only parameters, and the two existing test doubles were updated to match (`template/tests/test_flow_adopt_split.py:1260`, `template/tests/test_flow_single_driver.py:285`). I found no change in stack-mode behaviour.
