- **Slug:** merges-with-field-refused-in-merge-mode
- **Defect:** A brief has no way to say "these bundles must not land on the base separately" (an atomic merge group: a caller-first pair, or two issues planned to "merge as one unit"). In `wave_mode = "merge"` the driver `gh pr merge`s every completed non-final wave at its boundary, so a group member can land on the base alone, and nothing warns anyone. In stack mode this is harmless: the human merges the stacked PRs and can take a group together.
- **Success criterion:** A new optional brief field `- **Merges with:** <id>[, <id>…]` is parsed like `Conflicts with` (ids only on the value line, a trailing note ignored, `#12` / `12` / `issue_12` all accepted). A run's bundle is a **group member** when its own brief declares a non-empty `Merges with`, or when the brief of another bundle in the same run names it there. With `wave_mode = "merge"`: (a) `waves.compute_waves(cfg, bundles)` raises `waves.DependencyGraphError` for a batch {A, B} where A declares `Merges with: B`; the message names A and B, and `remedy` names both ways out: set `wave_mode = "stack"`, or fold the group into one bundle. (b) The same refusal happens when only B declares it (A's brief is silent), and for a run of A alone whose brief declares `Merges with: X` with X not in the run. (c) `pdca flow A B` on batch (a), driven through `cli._flow` the way `template/tests/test_flow_dependency_refusal.py:91-97` does, returns 2 with no traceback; stderr carries the `Ways out:` line; `driver.run_issue` is never called; and both bundles stay PLANNED with no `patch.diff` (that file's `_assert_nothing_built`, :99-104). (d) `waves.partition_schedulable(cfg, [A, B, C, D])`, where A declares `Merges with: B`, C `Depends on: A`, and D has no edges, returns D as schedulable and holds A, B and C. A's and B's hold reasons name `Merges with`. It does not raise. With `wave_mode = "stack"`: (e) the batches from (a), (b) and (d) give the same waves from `compute_waves`, and the same result from `partition_schedulable`, as the identical batches without the `Merges with` lines. Nothing is refused or held. With `wave_mode = "merge"` again: (f) bare `pdca waves` (no ids) through `cli.main`, over a `results/` holding A (declares `Merges with: B`), B, and an unrelated D, returns 1 and prints `unschedulable:` naming A and B on stderr. This is the existing strict-preview behaviour (an unresolved `Depends on` does the same today, while the `--from-csv` sweep holds it), applied to groups; the divergence from the tolerant sweep is accepted and documented, not fixed here.
- **Falsifiability:** RED offline, on the plain driver unit suite. On `main` today, `compute_waves` levels batch (a) into one wave without raising, `partition_schedulable` holds nothing in (d), `pdca flow A B` goes on to build, and bare `pdca waves` returns 0. So (a)–(d) and (f) fail on assertions. (e) is green before and after, and guards against the field changing stack mode. The fixtures are bundle directories with `brief.md` files under a temp `results/`, as `template/tests/test_waves.py` builds them. The CLI case copies the setup of `template/tests/test_flow_dependency_refusal.py` (stub config, `driver.run_issue` wrapped to count builds, `cli._flow` with `--no-publish --no-act`). No network, no live tracker.
- **Invariant to restore:** In merge mode, no bundle that is a group member *as seen by this run* (its own brief declares `Merges with`, or another in-run brief names it) is built: the strict path refuses the run, the tolerant path holds the group and its dependents, and both say why. This is narrower than the issue's goal ("never merge one member onto the base without the rest"). Two known holes stay open and are tracked in #778: a group declared only by a bundle outside the run is not seen, and `Merges with` is not carried to split children (`split.py:66` `ORDERING_FIELDS` lists only `Depends on` / `Conflicts with`). Check signs off this narrower invariant, which (a)–(f) test. Source: the issue body ("pairs that must not land separately") and the merge-mode contract in `docs/07-crosscutting.md:858-862` (the driver merges each non-final wave's PRs unattended). Not a structural or lifecycle defect, so the Plan-exit gate does not apply.

## Why this brief is narrow

Iterations v1–v4 built full hold-and-release. At sign-off (2026-10-23) the human sent it back to Plan for two reasons. Both of the issue's real cases (wyrd #653→#658, #625→#633) are chained pairs, which that design refused anyway. And the patch was too big. At this re-plan the human weighed how often the case comes up: two known pairs, both in one wyrd plan, and no instance runs merge mode today (wyrd went back to stack mode on 2026-10-01; this instance uses stack mode). Merge mode may come back as more is automated, so the field and a fail-safe refusal ship now. Real merge-mode support is #778.

Do must not bring back any hold, carry or release logic from the earlier iterations. If a criterion above seems to need it, stop and say so in `build-notes.md`.
