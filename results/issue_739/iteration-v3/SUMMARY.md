# Advisory code review — issue_739 (hold a cross-wave clash at the line fold)

Scope: `patch.diff` against the target at `$PDCA_TARGET` (patch applied). Gates: C4 is red before the fix (13 of 14 new tests fail) and green after; T3 (the full offline suite) is green. I found no correctness bug that breaks a case in the brief. The bullets below are smaller risks and cleanups.

- NEEDS-HUMAN [human] — The fix is bigger than the brief planned. The brief says to reuse `_clash` / `_partners`, and that "the only new trial is the 'together' fallback, mirrored from `_held_by`". The patch adds about 150 lines of new trial logic: `_held_on_line` (`template/src/pdca_harness/integrate.py:1804`) with its own stranded / rebuild trials (`:1873-1883`), `_holds_newer` (`:1891`), and `_together` (`:1901`). `_together` does a per-file leave-one-out search plus a walk over the bundles that carry a partner's change (`:1943-1952`), which `_held_by` (`:1797-1801`) does not do. Each piece answers a finding from rounds 1 and 2, and `_clash` itself is unchanged, as the brief asked. Still, this is now a second classifier with its own rules next to `_clash`, which is what the iteration-v1 review objected to. A human should decide whether this much new logic is wanted, or whether some of the edge cases (joint clashes in several files, stranded partners stacked on other bundles) should stop the run instead.
- `template/src/pdca_harness/integrate.py:1928-1952` — Cost. `_together` runs one `_trial` per bundle on the line, and each trial merges every other bundle on the line again. That is about N² merges for each held bundle (N = bundles on the line), plus an `_in_line` check for every pair of bundles (`:1947-1948`). `_partners` and the stranded checks add about 4N more trials. This only runs when the fold hits a conflict, so it is fine for today's batch sizes. On a long line with several held bundles, the fold could slow down noticeably while holding the worktree lock. Not a blocker; a comment, or a cap that falls back to stopping the run, would make the limit explicit.
- `template/src/pdca_harness/integrate.py:1857-1863` — When `_clash` hits a git-step failure it returns `"line"` (`:1999-2000`). `_held_on_line` cannot tell that apart from a real `"line"` result, so it still runs the `_together` trials on a tree where a git step just failed. In practice `_together` will most likely fail the same way, and that returns None (the run stops, which is safe). It is wasted work, and in a rare case it could name partners after a failed read. A cheap fix is to treat a `"line"` that came from the exception path as a stop. That needs `_clash` to say which `"line"` it was, so it is optional.
- `template/src/pdca_harness/flow.py:1512-1513` — `on_line` records each carried finished id with its **PR head** (`heads[name]`). The carry's fold merges the branch tip it read (`integrate.py:645-647`). If those two differ, the `_carries` filter at `integrate.py:1850-1851` drops that id, and a clash with it stops the run instead of being held. That is a safe failure, not a wrong hold. Recording the tip the fold actually merged (what `carried` / `took` hold) would be more exact. Low priority.
- `template/src/pdca_harness/flow.py:1582` — `_line_hold` builds `base_ref` again from `publish._resolve_target(d)` and `cfg.default_branch`. The fold already used `f"{base_remote}/{base}"` (`integrate.py:669`) to decide "stranded", so the message and the decision could in theory name different refs. Passing the ref the fold used (for example in the `across` tuple) would remove the duplicate. Cleanup only.
- `template/src/pdca_harness/flow.py:863-869`, `:2934-2935`, `:3114` — Each held bundle's brief is read by `_line_hold` up to three times: in the announce, once per `Conflicts with` partner in `_runnable`, and in the end-of-run report. This is cheap, so it is not worth changing.

Tests: the new file covers all five brief cases. It also covers each probe from the earlier rounds as its own named test: the unrelated earlier-wave bundle in the "together" case, a stranded partner stacked on another bundle, an ordinary overlap that the base move is not to blame for, and a `Conflicts with` partner (X) of a stranded hold in case 3. The renamed `test_flow_same_wave_conflict.py` test checks the exit code with `cli._results_rc`, as the brief asks. I found no weak or copied-logic tests.
