# Adversarial review — issue_739 (hold a cross-wave clash at the line fold)

Verdict: the red→green evidence holds, but the fix has two concrete wrong-answer cases and one cascade the human should look at. Probes were written in this sandbox (`probe_739*.py`). They reuse the patch's own `CrossWaveFoldHolds` fixture (real git, real `integrate.fold`, through `flow._drive_and_act`) against the patched tree at `$PDCA_TARGET`.

## The evidence: could not refute

- `gate-logs/C4-verify.log`: with production reverted, cases (1)-(4) and the flipped `test_a_conflict_with_its_own_prerequisite_on_the_line_holds_it_not_the_run` fail on `assertNotIn("did not integrate")`. That is the right reason: the old `STOPPING` path. The base-clash stop pin passes on both sides, as it should. I re-ran the green side on the target (`tests.test_flow_cross_wave_fold_holds` + `tests.test_flow_same_wave_conflict`): 13 OK. The tests wrap the real `integrate.fold` (`template/tests/test_flow_cross_wave_fold_holds.py:706-713`) instead of replacing it, so they run the production path. Case (2) is not a tautology: with the carry's heads withheld from `_held_on_line` (probe E), it fails as it should.
- The case-(5) stop (`test_a_conflict_only_with_a_base_taken_in_mid_wave_still_stops_the_run`) still stops. But it stops on the first condition, `template/src/pdca_harness/integrate.py:1834` (22 does not merge onto `origin/main`), not for the brief's stated reason ("no trial names 20"). That is harmless, but that test does not exercise the "together" fallback at all.

## The fix: concrete failing cases

- NEEDS-HUMAN [impl] — **The "together" fallback names unrelated bundles.** At `template/src/pdca_harness/integrate.py:1847-1850`, when `_clash` finds no single partner and `base + every bundle on the line + head` conflicts at the head, it names **every** bundle on the line except the head's own ancestors. `_held_by` does the same with "all of `kept`", but `kept` is only one wave; here the set is the whole run's line. Failing case (probe B): case (4) exactly, plus `X` in wave 0 that only adds `x.txt`. The result is `issue_H held … conflicts with issue_P's, issue_R's, issue_X's … declare \`Conflicts with: P, R, X\``, exit 3. The brief says "held naming both". Probe E shows the same flaw from another side: when the true partner is missing from `on` (the carry's heads withheld), `Y` is held naming `G, W, V`, all unrelated, instead of stopping. Case (4)'s test (`template/tests/test_flow_cross_wave_fold_holds.py:341-358`) can't see this, because no unrelated bundle sits on the line before `H`. Suggested fix, still decided by trial merges: name a bundle only if leaving it out of the trial lets the head merge (leave-one-out). Also add an unrelated earlier-wave bundle to case (4).
- NEEDS-HUMAN [human] — **A stranded partner hides a real overlap.** `template/src/pdca_harness/integrate.py:1855-1857` marks a partner "stranded" when its head does not merge onto the new base. `template/src/pdca_harness/flow.py:1566-1568` then puts each partner in exactly one bucket, so a stranded partner never gets the `Conflicts with` proposal. Failing case (probe A): `A` edits `shared.txt` and `a.txt`; after wave 0's fold, `main` edits `a.txt`; `Y` (wave 1, built on the moved main) edits `shared.txt`. The output is `issue_Y held … issue_A's branch … does not merge cleanly onto origin/main itself … (conflicts in a.txt, shared.txt) … rebuild issue_A's branch on the new origin/main`, and nothing is said to Y's owner. After A rebuilds, Y still clashes with A on `shared.txt` (both add the file), so the advice takes two re-runs and wrongly suggests Y's change is not involved. The patch implements the brief's discriminator ("partner's head does not merge onto the base alone → fix aimed at the partner") faithfully, so this needs a human call on the rule. One trial-based fix would be to also try `base + partner (its side winning, _merge_over) + head` and give both steps when that still conflicts.
- NEEDS-HUMAN [human] — **A stranded line bundle holds every later bundle, after building it.** In probes A and C, once `main` moves in a file a line bundle touched, every bundle built on the moved main carries that change and clashes with the line bundle in that file. Each one is fully built, then held, each naming `issue_A`. Probe C is case (3)'s shape with a plain `Depends on` chain (`S` depends on `R`, `T` depends on `S`). `S`, which only adds `s.txt`, is held "for a.txt", `T` is skipped, and the result is `holds={'S','W': 'conflict'}`, exit 1. Case (3)'s test meets "an unrelated bundle completes" only because `S` is `Stacks on: R` (`template/tests/test_flow_cross_wave_fold_holds.py:308`), which cuts it from the old line without the moved main. Before the patch the run stopped once, with one message. Now it spends a build on every later bundle and folds none of them. Decision 2 may not have meant this. One option is to treat a stranded line bundle as a failure of the shared line (stop, or hold later waves before building).

# Advisory code review — issue_739 (cross-wave fold clash held, not stopped)

Grounded on the patched target at `$PDCA_TARGET` (`template/src/pdca_harness/integrate.py`, `flow.py`, `tests/test_flow_cross_wave_fold_holds.py`). All gates pass (C4 red→green, T3 suite green). I found no crash-level bug. The new code reuses `_clash` / `_partners` / `_trial` as the brief asked, and the only new trial is the "together" fallback. Three findings, none blocking:

- NEEDS-HUMAN [impl] — `template/src/pdca_harness/integrate.py:1856-1857`: the "stranded" test (`_trial(base_ref, [partner head])` conflicts) does not allow for what the partner was built on. A partner cut from the line, or stacked on another bundle's branch (it has an `under` entry from `_built_on`, computed at `:1843`), can fail to merge onto the base because of the line commits or another bundle's work under it, not because of its own change. The held bundle's message would then tell that partner's owner to "rebuild … on the new <remote>/main" (`flow.py:1571-1580`) when the cause is elsewhere. `_partners` (`integrate.py:1930-1934`) already handles `under` for this reason, and the stranded check should do the same, e.g. trial `base_ref + under[n] + heads[n]`. The brief words the rule as "partner head alone onto base", so this is a gap the brief left open, not a departure from it. No test covers a stranded partner that has an `under` entry: case (3) stacks S on R, but neither is a partner.
- NEEDS-HUMAN [human] — `template/src/pdca_harness/integrate.py:1847-1850`: the "together" fallback names every bundle on the line except the ones `head` already holds. That means every earlier wave's bundles plus the carried finished ids, not only the same-wave `kept` that `_held_by` names (`:1798`). On a long line one combined clash can produce a `Conflicts with:` proposal listing many unrelated bundles (`flow.py:1589-1593`). No smaller set is searched for. Case (4) only has three bundles on the line, so the test cannot show this. Is "name all of them" acceptable at this scale, or should the set be narrowed (e.g. drop each partner whose removal still leaves the trial conflicting)?
- `template/src/pdca_harness/integrate.py:1834` and `:1844`: when the line was cut from the current base (`root == base_ref`, the common case), `_clash`'s first trial (`integrate.py:1893`) repeats the base-alone trial just done at `:1834`. It is one extra trial merge, and only on the conflict path, so the cost is small. A cleanup could skip the `:1834` trial when `root == base_ref` and read `kind == "base"` instead. Advisory only.

Other things I checked and found correct: `on_line` entries are filtered by `_carries` against the current line (`integrate.py:1837-1838`), so a carried id that later folds dropped, or another target's id (the map is keyed by name, not target), is never named. Dropping `kept` from the entry guard (`integrate.py:657-659`) still requires `ours`, `pre` and a `_Conflict`, so the carry and direct callers (with `held_out=None`) behave as before. `_line_hold`'s split into moved, prerequisite and other partners (`flow.py:1546-1595`) matches case (3) and the flipped case (5) wording. The new test file asserts holds, partner names, absent blame text and `_results_rc` exit codes for every case in the brief, plus a base-clash case that must still stop.
