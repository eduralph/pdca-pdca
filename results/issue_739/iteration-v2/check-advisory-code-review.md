# Advisory code review — issue_739 (hold a cross-wave clash at the line fold)

Lenses: correctness bugs the patch introduces, plus reuse / simplification / efficiency. All gates in `check-gates.json` pass (C4 red→green, T3 suites green). Anchors are on the patched tree at `$PDCA_TARGET`.

Both round-1 findings were addressed. `_together` (`template/src/pdca_harness/integrate.py:1864-1902`) now names a bundle only if leaving it out lets the head merge, and case (4) now has an unrelated `X` on the line. The stranded check (`integrate.py:1854-1856`) now tries `base_ref + under[n] + head`, and the new test `test_a_partner_built_on_a_stranded_branch_is_not_told_to_rebuild_on_the_base` covers a partner with an `under` entry. The classification reuses `_clash` / `_partners` as the brief asks, and `_clash`'s contract for the carry is unchanged. Remaining findings:

- NEEDS-HUMAN [human] — `template/src/pdca_harness/integrate.py:1854-1856` → `template/src/pdca_harness/flow.py:1571-1580`: the "stranded" test asks only whether the partner's own change conflicts with `<remote>/main` *somewhere*. It never checks that this conflict has anything to do with the clash that held the bundle. Failing shape: the base moved and now conflicts with partner `A` in `x.txt`, while `Y` (built on the new base) clashes with `A` only because both add `shared.txt`. `A` is called stranded, so `Y`'s line says only "rebuild issue_A's branch on the new origin/main". That rebuild fixes `x.txt` but leaves the `shared.txt` clash, so `Y` is held again on the next run, and no `Conflicts with` is proposed. The brief words the rule exactly this way ("`_trial(base, [partner head])` conflicts"), so this is a gap in the rule, not a departure from it. One possible tightening, still decided by trial merges: count a partner as stranded only when the files of its own conflict with the base overlap the held bundle's conflict `paths`. Otherwise treat it as an `other` partner. Untested either way.
- `template/src/pdca_harness/integrate.py:1886-1902` (efficiency, low): `_together` does about 2n trials, and each one merges up to n heads, plus about n² `merge-base --is-ancestor` calls for `on_it`. `n` here is every bundle on the run's line (`took` + carried finished), not one wave. It also runs `_built_on` over all of them first (`:1845`). This only happens on the conflict path, so it is fine at current batch sizes. If runs grow large, `on_it` could be computed once (one ancestry map) instead of once per `n`. Not blocking.
- `template/src/pdca_harness/flow.py:1546-1595` (minor): `_line_hold` re-reads the held bundle's brief and re-resolves its target each time it is called. It is called twice per held bundle (when announced at `:1598` and again in the end-of-run report at `:1620`). This is harmless. Joining partner names with " and " for `moved` / `own` but ", " for `_conflict_partners` gives mixed wording when there are three or more partners. Cosmetic only.

No other correctness problems found. Things checked and found sound:
- `_held_by` is now skipped when `kept` is empty (`integrate.py:660`), so the cross-wave path also runs for a wave's first bundle.
- Carried finished heads are filtered with `_carries`, so a fresh line that doesn't carry them never names them (`:1839-1840`).
- Git failures in the new helpers turn into a stop, and a tree that won't reset still raises (`:1858-1861`).
- Dry-run passes `across=None` and `held_out=None` (`flow.py` fold call).
- `heads[name]` in `_carry_finished` is defined for every carried id, because `clean` is a subset of the keys of `heads`.
- The `base` / `line` / `moved` outcomes still stop the run unless the together-fallback names someone, and `test_a_branch_that_also_clashes_with_the_base_itself_still_stops_the_run` and the unchanged mid-wave-base test pin this.
