## Findings

- NEEDS-HUMAN [impl] — **The stranded check blames the base move for an ordinary overlap.** `template/src/pdca_harness/integrate.py:1854-1856` calls a partner "stranded" whenever the partner's own change doesn't merge onto `base_ref`. It never checks that this is *why* the held bundle clashes with it. `template/src/pdca_harness/flow.py:1566-1580` then says "`{name}` was built on the new `{base_ref}`" (the code never checks this) and gives only "rebuild A's branch on the new main", with no `Conflicts with` proposal for the held bundle. **Failing case (run on the real-git fixture):** the base has `shared.txt`. A (wave 0) adds `a.txt` and edits `shared.txt`. Q is in wave 0. Y (`Depends on: Q`) edits `shared.txt`. W→V→U makes a fold run after wave 1. After Y publishes, `main` gets its own `a.txt`. Output: `issue_Y held … issue_A's branch, already on the line, does not merge cleanly onto origin/main itself: origin/main moved since it was cut, and issue_Y was built on the new origin/main (conflicts in shared.txt) … To fold it, rebuild issue_A's branch on the new origin/main`. What is actually true: neither Y's base tip nor Y's head holds the moved `main` commit, so "built on the new origin/main" is false. The clash is in `shared.txt`, not `a.txt`. After A is rebuilt on the new `main` (`merge -X theirs`), merging Y onto it **still conflicts**. So A's owner does work that doesn't unblock Y, and Y's owner is told nothing. The same thing happens when the held bundle *is* built on the new `main` but also overlaps the partner's own change: only the partner's rebuild is given. The code follows the brief's case-(3) rule exactly ("the partner's head doesn't merge onto the base alone"), so the brief left this gap. Closing it stays within the brief's own invariant ("a fix aimed at the bundle that can actually act"). Suggested fix: call a partner stranded only when the clash really comes from the base. For example, require that `head` holds `base_ref` commits that `root` lacks, and that the paths of `root + partner + head` overlap the paths `base_ref + partner` conflicts in. Otherwise (or for the leftover paths) also give the `Conflicts with` proposal. Add this probe as a test.
- NEEDS-HUMAN [impl] — **A `Conflicts with` partner of a stranded hold gets the opposite advice.** The diff puts across-holds into `held_conflict`, which reaches `_runnable` as `conflict_held` (`template/src/pdca_harness/flow.py:2905`). The partner's hold line there, `flow.py:859-864`, is unchanged: "it `Conflicts with` issue_W, which this run's fold held out of the line (its change conflicts with issue_A's) … wait until issue_W is rebuilt on a base that holds issue_A". **Failing case (run on the real-git fixture):** case (3) exactly, plus X (`Depends on: T`, `Conflicts with: W`; its id sorts after W, so it lands in wave 3). W's own line correctly says W is not at fault and A must be rebuilt. X's line in the same run blames W's change and waits for a W rebuild "on a base that holds issue_A". No such base can be built while A is stranded; that is exactly why B is held in the same run. The brief, case (3), says the message "must not blame W or tell W's owner to update its branch". No test has a `Conflicts with` partner of an across-held bundle. Suggested fix: pass `held_across` into `_runnable` (or build that line from `_line_hold`), and add X to case (3)'s test.

## Attempted and could not refute

- Base-clash stop: `_held_on_line`'s first trial, onto the fetched base (`integrate.py:1836`), pinned by `test_a_branch_that_also_clashes_with_the_base_itself_still_stops_the_run`. The brief's case-(5) stop (`test_a_conflict_only_with_a_base_taken_in_mid_wave_still_stops_the_run`) is still green.
- `_together` naming bundles that have nothing to do with the clash: X in case (4) is not named. When the true partner is missing from `on`, the trial `root + on + head` merges cleanly, so it returns `[]` and the run stops. It fails safe; iteration-1's probe E no longer applies.
- `_clash`'s contract for the #694 carry: the diff only changes `_held_by`'s docstring, and the carry still passes `held_out=None`.
- Exit codes: computed through `cli._results_rc` the way the CLI does (3 for holds alone, 1 when a dependent is left PLANNED), as the brief pins them.
- Low-priority note, not a refutation: on the fallback path, `_together` (`integrate.py:1886-1901`) runs up to 2n+1 trials of up to n+1 merges each, per held bundle, under the fold lock. That is O(n²) merges for n bundles on the line: fine at test scale, slow on a long line.

## The verdict

`check-gates.json` `overall: pass` is right for what it measures; I re-ran the C4 red→green myself. The weak spot is what the case-(3) tests prove. They only show the stranded wording when the base move really is the cause. Nothing shows that wording is withheld when it isn't the cause (finding 1), or that a held bundle's `Conflicts with` partners get advice that matches (finding 2).
