# Result — issue 464 / wave-mode-none

## 1. Spec (from brief.md)              ← Check verifies against THIS
- Defect / goal: `[driver].wave_mode = "none"`: every accepted bundle publishes as a draft PR against its real target base, exactly as a single-bundle run does. At a wave boundary nothing happens — no integration line is created or pushed, nothing is folded, readied or merged, and the pre-wave carry of finished ids (#646) does not run. Waves still decide build order. A bundle whose prerequisite (any edge: `Depends on`, `Depends on (merged)`, `Stacks on`) has not merged into the bundle's own target base is held with a one-line reason and the way out (merge the prerequisite's PR, then re-run). This is NEW logic in `flow._runnable`, modelled on the #647 out-of-batch hold but not a reuse of it: today that hold fires only for an out-of-batch prerequisite (`flow.py:789`, :798, with `cand` tied to the fold at :795-797), and an in-batch prerequisite takes the branch at :831, which never asks `merged.merged_into`. The `"none"` branch covers in-batch and out-of-batch prerequisites and every edge kind. Its message is `"none"`-specific: no "no line of this run carries them" and no "name X in the same `pdca flow <ids>` command so the run's line carries them" advice (flow.py:836-841), since no line exists. The hold is recorded in the run's `holds` collector with a new kind `"unmerged"`, and `cli._results_rc` (cli.py:707) must count it as held-before-built: today only `_BASE_HOLD` (`"base"`) is in that set (cli.py:741), so a PLANNED B with any other hold kind returns 1. `"unmerged"` joins that set, so the run returns **3**, not 1. An unknown `wave_mode` value is reported at config load instead of silently behaving as `"stack"`.
- Success criterion: On the real-git fixture with `gh` stubbed and the publisher in `command` mode: (a) a `wave_mode = "none"` run of A and C (independent) and B (`Depends on: A`) publishes A and C as PRs whose `gh pr create --base` is the target base, pushes no `pdca-integration/*` branch to origin, calls neither `gh pr ready` nor `gh pr merge`, and holds B with a stderr line naming A as not merged into B's base (B stays PLANNED; the stderr line does NOT contain "line of this run" or "carries them"; `holds` has B as `"unmerged"`; `pdca flow` exits **3** per `cli._results_rc`); (a2) the same with B `Stacks on: A` instead: B is held the same way, and once released (b) its branch is cut from and its PR opened against the target base, not A's branch; (b) once A's PR reads MERGED into the base and the base has it, a re-run builds B from the fetched base and publishes it against the base; (b2) if A's PR reads MERGED but `origin/<base>` as fetched lacks the merge, B is still held (the #729 check, `_base_lacks_merge`, must run in `"none"`: today flow.py:807-809 skips it with `line is None → continue` whenever no line exists, which is always in `"none"`); (c) `Config.load` with `wave_mode = "bogus"` prints a config note naming the value and the allowed ones and falls back to `"stack"` (today it silently keeps `"bogus"`, config.py:733); (d) `"stack"` and `"merge"` runs behave as before (the existing suites stay green). Leg (c) is not in the issue; it is included because adding a third value makes a silent fallback worse, and the human confirms at sign-off that it belongs here.
- Repo + branch target: eduralph/pdca-harness @ main
- Scope (one logical fix) / out of scope: The new `"none"` value end to end, the dependency hold for it, validation of `wave_mode` at load, the `pdca.toml.jinja` comment block (:111-138) and the `wave_mode` section of `docs/07-crosscutting.md` (:639 onward). / out of scope: making `"none"` the default (changes what every instance gets on `copier update` — a separate decision); letting some bundles stack while others stay on the base inside a `"none"` run (the issue's "second, better behaviour"; overlaps the dependency-scoped bases #727 already gave stack mode); any change to `"stack"` or `"merge"` behaviour.

# Adversarial review: issue 464, `wave_mode = "none"`

The red→green proof holds, and the brief's named legs pass. But I found two concrete inputs that break the fix, both when a prerequisite is iterated. There are also two smaller cases where the printed way out is wrong.

I ran every case below on a scratch copy of the patched tree at `$PDCA_TARGET`, using real git and a stubbed `gh`.

## Findings

- NEEDS-HUMAN [impl] — **Iterating a prerequisite whose draft PR is still open blocks its dependent for good.** The way out it prints cannot work. Cause: `template/src/pdca_harness/flow.py:868` makes `publish.json`'s `pr_url` the only sign that a PR exists, but on a re-publish `gh pr create` refuses a head that already has an open PR, and `template/src/pdca_harness/publish.py:412` and `:440` then overwrite the good URL with `""`. The repo already documents this `gh` failure at `flow.py:651-652` ("an iterated bundle whose old draft PR is still open"). Case: run 10 and 11 (11 `Depends on: 10`), iterate 10, run again.
  - The new commit reaches the open PR, but the run gives `holds={'10': 'no-pr'}`, rc 1, and says "no PR of that work is on record".
  - `pdca publish 10`, the advice printed, returns 1 and leaves `pr_url` as `""`.
  - After the PR merges on the host, 11 is still held with rc 1. `pdca publish 10` still returns 1 and `pr_url` stays `""`, so 11 stays held. I found no way out through the harness; hand-editing `publish.json` or dropping the edge looks like the only one left.
  - A lone iterated bundle with no dependents gets `no-pr` and rc 3, though its PR is open and up to date. The same iterate in `"stack"` gives rc 0, so iterating is a normal path that only this mode turns into a failure.
  - Fix: when `gh pr create` fails, look up the open PR (`_existing_pr`, `publish.py:582`) or keep the earlier URL, without changing stack mode's result.
  - Why the tests missed it: the stub at `template/tests/test_flow_wave_mode_none.py:139` lets a second `gh pr create` for the same head succeed, and the iterate test (`:466`) only fails the texts. Add a case where the stub refuses the second create.

- NEEDS-HUMAN [impl] — **One run after a failed re-publish, the dependent is released on the old, rejected PR.** `template/src/pdca_harness/flow.py:868` only catches a stale record through `unpushed_set`, which lasts one run. Case: 10 has an open PR, is iterated and rebuilt, and its texts fail. That run correctly gives `holds={'10': 'unpushed'}`, rc 1, and tells the user to publish first. The next `pdca flow 10 11` does not drive 10 (it is COMPLETE), so the stale `pr_url` counts again:
  - That run gives `holds={'11': 'unmerged'}`, rc 3, and "merge their PR into main", which points at the rejected attempt.
  - Following that advice gives `results={'11': 'COMPLETE'}`, rc 0, and `a.txt` on `main` has the old text, not the rebuilt `a, again`.
  - The new test `test_an_iterated_prerequisite_not_published_again_is_not_waited_on_by_its_old_pr` stops after the first run, so it never sees this.
  - Fix: tell a record from an earlier attempt without relying on this run's `pushed` set, for example by comparing `publish.json` with the current `patch.diff`, and treat a stale record as having no PR.

- NEEDS-HUMAN [impl] — **The hold can tell the user to do something that cannot help.** `template/src/pdca_harness/flow.py:876-879` sends every "not merged into d's base" answer to the same message, "merge their PR into main, then re-run".
  - Case 1: prerequisite 10 has an `Onto branch` record (mode `stacked`) and its PR has already merged into `main`. `merged_into` (`template/src/pdca_harness/merged.py:109`) never counts that record, so the run gives `holds={'11': 'unmerged'}`, rc 3, on every run. The docs say this kind of commit does not count (`docs/07-crosscutting.md:925`), but the printed step is already done and nothing else is offered.
  - Case 2: 10's PR targets `dev`, is open, and 11 targets `main`. It prints the same advice, but merging that PR puts it on `dev`, so 11 stays held.
  - I hand-wrote the `publish.json` records for both cases, using the fields `publish.py:440` and `:562` write. I did not run a real `Onto branch` publish.
  - `test_a_merge_into_another_base_does_not_release_the_dependent` (`template/tests/test_flow_wave_mode_none.py:403`) pins the hold but not the advice.
  - Fix: use a separate line when the PR is already merged, or when its recorded base is not d's base. That line should say merging this PR will not release the bundle.

- NEEDS-HUMAN [impl] — **A chain above a merged PR that the fetched base lacks gets the wrong advice, and no test covers it.** At `template/src/pdca_harness/flow.py:892`, a prerequisite already merged on the host still goes into `to_merge`. Case: 10 ← 11 ← 12, 10's PR is MERGED, and `origin/main` as fetched lacks the merge. 11 is correctly told to fix the fetch. 12 is told "merge the PRs of issue_10, issue_11 in that order", but 10 is already merged and the real fault is the fetch. Deleting line 892 leaves all 43 tests green, so nothing pins that line. This is low severity, but it is the only mutant of the seven I tried that survived.

# Code review (advisory): wave_mode = "none"

The gates in `check-gates.json` pass, except T4, which is deferred until publish. I found no failure in their logs. The findings below are ones those gates don't cover. I reproduced the first two on the patched source, with `gh` stubbed, using the same `WaveModeNone` fixture as the new tests. The rest come from reading the code.

- NEEDS-HUMAN [impl] — **An iterated bundle whose draft PR is still open blocks its dependents for good, even after that PR merges.** `template/src/pdca_harness/publish.py:440` overwrites `publish.json` with an empty `pr_url` whenever `gh pr create` fails. `flow.py:651-652` names an open draft PR on an iterated bundle as a case where it fails. The force-push has already updated that PR, so the PR exists and holds the new work. The patch then treats it as missing at `flow.py:694` (`no-pr`) and `flow.py:868` (dependent held). Reproduced: 10 published, iterated, `gh pr create` fails. The run reports "no PR of that work is on record" and exits 1. After PR 10 merges, a re-run prints the same line and exits 1 again. The advice to run `pdca publish 10` can't clear it either: it hits the same `gh pr create` failure, or with the PR merged may open a new one. `publish.py:431` also offers "Open the draft PR by hand", and that doesn't help because nothing records the PR it opens. Stack mode doesn't hit this path because the fold only needs the branch; in `"none"`, `pr_url` decides whether the dependent is released. Fix: when `gh pr create` fails, look up the branch's existing PR (`publish._existing_pr`, `publish.py:582`) before recording an empty URL. Add a test where `gh pr create` fails and the lookup finds the PR. The existing `test_a_prerequisite_whose_pr_was_not_opened_has_no_pr_and_its_dependent_fails` only covers the case where no PR exists.

- NEEDS-HUMAN [impl] — **A re-run forgets that the recorded PR holds rejected work, and its merge releases the dependent.** `flow.py:868` only knows the PR is stale through `unpushed_set`, which covers this run alone. Reproduced: 10 iterated, its texts fail, and the run correctly exits 1 with "no PR of that work". A re-run (`pdca flow 10 11`, where 10 is COMPLETE and not driven) then changes to `holds={'11': 'unmerged'}`, exit 3, "merge their PR". If the old PR is merged, 11 builds and the run exits 0, although 10's accepted rebuild was never published. So the run reports clean on a base that lacks the accepted work. `test_an_iterated_prerequisite_not_published_again_is_not_waited_on_by_its_old_pr` stops at the first run and misses this. Fix: save something on disk that shows the record is from an older attempt, for example compare the record against the accepted patch, or mark it as stale when the bundle is iterated. Then check that in `_runnable`.

- NEEDS-HUMAN [human] — **A prerequisite whose PR can't reach the dependent's base holds the dependent for good, and the message gives a way out that can't work.** `flow.py:876` holds whenever `merged.merged_into` is false, and `merged.py:109-110` returns false for a different repo, a different base or an `Onto branch` record (`mode == "stacked"`). So these in-batch cases, which all build in stack mode, can never be released: B targeting `org/b` and depending on a PR in `org/a`; B on `main` and its prerequisite on `dev`; a prerequisite published with `Onto branch`. Each run still exits 3 and prints "merge their PR into main" (`flow.py:950`), even when the PR already reads MERGED. `test_a_merge_into_another_base_does_not_release_the_dependent` asserts that hold with the same advice. The brief asks for "merged into the bundle's own target base", so the hold itself follows the spec. The human needs to decide whether these edges should stay held, be refused up front, or count as ready like a prerequisite with no target. Whatever the decision, the message needs fixing: when the PR has already merged elsewhere, it should say that no merge into this base can release the bundle.

- Low, simplification: `flow.py:872` reads the PR state, then `merged.merged_into` at `flow.py:876` reads it again (`merged.py:102`), so a merged prerequisite costs two `gh pr view` calls. If only the second call fails, the run files a fault as `"unmerged"` and exits 3, the outcome `flow.py:871` was added to prevent. Moving the repo/base/mode comparison at `merged.py:109-110` into a helper that takes the state already read would remove the second call and that gap.

- Low, simplification: `flow.py:3232` passes the cumulative `accepted` list to `_hold_without_pr` each wave. Earlier bundles have already been judged, and `complete` would give the same result. That removes the repeat work and the "already named" checks at `flow.py:687`, except the `unpushed` check in the second loop at `flow.py:694`.
