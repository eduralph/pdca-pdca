# Code review (advisory): wave_mode = "none"

The gates in `check-gates.json` pass, except T4, which is deferred until publish. I found no failure in their logs. The findings below are ones those gates don't cover. I reproduced the first two on the patched source, with `gh` stubbed, using the same `WaveModeNone` fixture as the new tests. The rest come from reading the code.

- NEEDS-HUMAN [impl] — **An iterated bundle whose draft PR is still open blocks its dependents for good, even after that PR merges.** `template/src/pdca_harness/publish.py:440` overwrites `publish.json` with an empty `pr_url` whenever `gh pr create` fails. `flow.py:651-652` names an open draft PR on an iterated bundle as a case where it fails. The force-push has already updated that PR, so the PR exists and holds the new work. The patch then treats it as missing at `flow.py:694` (`no-pr`) and `flow.py:868` (dependent held). Reproduced: 10 published, iterated, `gh pr create` fails. The run reports "no PR of that work is on record" and exits 1. After PR 10 merges, a re-run prints the same line and exits 1 again. The advice to run `pdca publish 10` can't clear it either: it hits the same `gh pr create` failure, or with the PR merged may open a new one. `publish.py:431` also offers "Open the draft PR by hand", and that doesn't help because nothing records the PR it opens. Stack mode doesn't hit this path because the fold only needs the branch; in `"none"`, `pr_url` decides whether the dependent is released. Fix: when `gh pr create` fails, look up the branch's existing PR (`publish._existing_pr`, `publish.py:582`) before recording an empty URL. Add a test where `gh pr create` fails and the lookup finds the PR. The existing `test_a_prerequisite_whose_pr_was_not_opened_has_no_pr_and_its_dependent_fails` only covers the case where no PR exists.

- NEEDS-HUMAN [impl] — **A re-run forgets that the recorded PR holds rejected work, and its merge releases the dependent.** `flow.py:868` only knows the PR is stale through `unpushed_set`, which covers this run alone. Reproduced: 10 iterated, its texts fail, and the run correctly exits 1 with "no PR of that work". A re-run (`pdca flow 10 11`, where 10 is COMPLETE and not driven) then changes to `holds={'11': 'unmerged'}`, exit 3, "merge their PR". If the old PR is merged, 11 builds and the run exits 0, although 10's accepted rebuild was never published. So the run reports clean on a base that lacks the accepted work. `test_an_iterated_prerequisite_not_published_again_is_not_waited_on_by_its_old_pr` stops at the first run and misses this. Fix: save something on disk that shows the record is from an older attempt, for example compare the record against the accepted patch, or mark it as stale when the bundle is iterated. Then check that in `_runnable`.

- NEEDS-HUMAN [human] — **A prerequisite whose PR can't reach the dependent's base holds the dependent for good, and the message gives a way out that can't work.** `flow.py:876` holds whenever `merged.merged_into` is false, and `merged.py:109-110` returns false for a different repo, a different base or an `Onto branch` record (`mode == "stacked"`). So these in-batch cases, which all build in stack mode, can never be released: B targeting `org/b` and depending on a PR in `org/a`; B on `main` and its prerequisite on `dev`; a prerequisite published with `Onto branch`. Each run still exits 3 and prints "merge their PR into main" (`flow.py:950`), even when the PR already reads MERGED. `test_a_merge_into_another_base_does_not_release_the_dependent` asserts that hold with the same advice. The brief asks for "merged into the bundle's own target base", so the hold itself follows the spec. The human needs to decide whether these edges should stay held, be refused up front, or count as ready like a prerequisite with no target. Whatever the decision, the message needs fixing: when the PR has already merged elsewhere, it should say that no merge into this base can release the bundle.

- Low, simplification: `flow.py:872` reads the PR state, then `merged.merged_into` at `flow.py:876` reads it again (`merged.py:102`), so a merged prerequisite costs two `gh pr view` calls. If only the second call fails, the run files a fault as `"unmerged"` and exits 3, the outcome `flow.py:871` was added to prevent. Moving the repo/base/mode comparison at `merged.py:109-110` into a helper that takes the state already read would remove the second call and that gap.

- Low, simplification: `flow.py:3232` passes the cumulative `accepted` list to `_hold_without_pr` each wave. Earlier bundles have already been judged, and `complete` would give the same result. That removes the repeat work and the "already named" checks at `flow.py:687`, except the `unpushed` check in the second loop at `flow.py:694`.
