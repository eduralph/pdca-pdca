# Design proposal — issue 464 / wave-mode-none

> Plan artifact for a new `[driver].wave_mode` value. Do reads ONLY this file.

- **Slug:** wave-mode-none
- **Kind:** enhancement (design proposal)
- **Goal:** `[driver].wave_mode = "none"`: every accepted bundle publishes as a draft PR against its real target base, exactly as a single-bundle run does. At a wave boundary nothing happens — no integration line is created or pushed, nothing is folded, readied or merged, and the pre-wave carry of finished ids (#646) does not run. Waves still decide build order. A bundle whose prerequisite (any edge: `Depends on`, `Depends on (merged)`, `Stacks on`) has not merged into the bundle's own target base is held with a one-line reason and the way out (merge the prerequisite's PR, then re-run). This is NEW logic in `flow._runnable`, modelled on the #647 out-of-batch hold but not a reuse of it: today that hold fires only for an out-of-batch prerequisite (`flow.py:789`, :798, with `cand` tied to the fold at :795-797), and an in-batch prerequisite takes the branch at :831, which never asks `merged.merged_into`. The `"none"` branch covers in-batch and out-of-batch prerequisites and every edge kind. Its message is `"none"`-specific: no "no line of this run carries them" and no "name X in the same `pdca flow <ids>` command so the run's line carries them" advice (flow.py:836-841), since no line exists. The hold is recorded in the run's `holds` collector with a new kind `"unmerged"`, and `cli._results_rc` (cli.py:707) must count it as held-before-built: today only `_BASE_HOLD` (`"base"`) is in that set (cli.py:741), so a PLANNED B with any other hold kind returns 1. `"unmerged"` joins that set, so the run returns **3**, not 1. An unknown `wave_mode` value is reported at config load instead of silently behaving as `"stack"`.
- **Success criterion:** On the real-git fixture with `gh` stubbed and the publisher in `command` mode: (a) a `wave_mode = "none"` run of A and C (independent) and B (`Depends on: A`) publishes A and C as PRs whose `gh pr create --base` is the target base, pushes no `pdca-integration/*` branch to origin, calls neither `gh pr ready` nor `gh pr merge`, and holds B with a stderr line naming A as not merged into B's base (B stays PLANNED; the stderr line does NOT contain "line of this run" or "carries them"; `holds` has B as `"unmerged"`; `pdca flow` exits **3** per `cli._results_rc`); (a2) the same with B `Stacks on: A` instead: B is held the same way, and once released (b) its branch is cut from and its PR opened against the target base, not A's branch; (b) once A's PR reads MERGED into the base and the base has it, a re-run builds B from the fetched base and publishes it against the base; (b2) if A's PR reads MERGED but `origin/<base>` as fetched lacks the merge, B is still held (the #729 check, `_base_lacks_merge`, must run in `"none"`: today flow.py:807-809 skips it with `line is None → continue` whenever no line exists, which is always in `"none"`); (c) `Config.load` with `wave_mode = "bogus"` prints a config note naming the value and the allowed ones and falls back to `"stack"` (today it silently keeps `"bogus"`, config.py:733); (d) `"stack"` and `"merge"` runs behave as before (the existing suites stay green). ## Motivation

`wave_mode` has two values and both act at the wave boundary: `"stack"` folds onto an integration line (rewritten per run; PRs based on an old line go stale, getwyrd/wyrd#675/#676), `"merge"` readies and merges PRs the human has not looked at. An instance that only wants each accepted bundle as a plain draft PR off the real base — the STOP discipline the rest of the harness describes — has no way to say "do neither". For a batch of independent bundles neither mode is a no-op.

## Design

- `Config.load` accepts `"stack" | "merge" | "none"`; anything else prints a note and falls back to `"stack"` (same shape as `merge_requires`).
- Wave boundary: in `"none"` neither `integrate.fold` nor `merge.merge_wave` runs; `_carry_finished` does not run; no bundle gets a stack base, so publish cuts every branch from the target base and opens the PR against it (the merge-mode #411 guard does not apply: nothing is merged).
- Dependencies: in `"none"`, every prerequisite — in-batch or not — counts as ready only once its PR has merged into the dependent's own target base, judged as `merged.merged_into` already judges an out-of-batch one. Until then the dependent is held, named on one line with the prerequisite and the way out. So a `"none"` batch with dependencies builds its first wave and holds the rest; the human merges and re-runs.
- `pdca waves` prints `none mode` in its summary (cli.py:1099 already prints `cfg.wave_mode`), and its "each wave builds on the prior's accepted work" tail (cli.py:1100) must not be printed for `"none"`, where that is false.

## Alternatives considered

- **Refuse a `"none"` batch that has any dependency edge** (the issue's first option). Simpler, but throws away the independent part of a batch; holding only the dependents keeps the rest running; the hold is new code, modelled on the #647 one.
- **Let dependents stack on their prerequisite's branch inside `"none"`** (the issue's second option). That is stack mode with per-bundle bases (#727); out of scope here.

## Impact & compatibility

- No change for instances on `"stack"` or `"merge"`. An instance that already had a typo in `wave_mode` now gets a config note (behaviour unchanged: stack).
- `pdca.toml.jinja` gains documentation for the third value → render/update suites must stay green.
- Step 6 of the target architecture (#715, 0.70) will turn the modes into strategy objects; `"none"` becomes the trivial strategy there.

## Open questions

- Should `"none"` become the default? Out of scope here (issue calls it a candidate); a separate maintainer decision because it changes every instance on `copier update`.
