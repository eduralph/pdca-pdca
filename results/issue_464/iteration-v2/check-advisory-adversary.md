# Adversarial review — issue 464 / wave-mode-none

**Evidence: holds up.** I re-ran `tests.test_flow_wave_mode_none` on the patched target: 17/17 pass. `gate-logs/C4-verify.log` shows 14 of 17 failing with the production change reverted, and they fail on assertions, not imports. The two tests that also pass red are the stack-mode control and the `--no-publish` case. They are guards, not proof. The tests drive the real `flow._drive_and_act`, `flow._runnable` and `publish.publish` against a bare git origin. Only the build leaf, `draft_texts` and `gh` are stubbed, so this is the production path.

**The fix: four inputs break it.** I wrote probes in my scratch dir that subclass the bundle's own test class and use the same fixture and stubs. Each bullet gives the observed `results` / `holds` / exit code.

- NEEDS-HUMAN [impl] — **A prerequisite with no `Repo + branch target` blocks its dependent forever, and the advice it prints cannot work.** `template/src/pdca_harness/flow.py:818-823` counts any *patched* prerequisite with no `publish.json` as "unpublished", whether or not it has a target. Case: 10 has a patch but no target; 11 is targeted, with `Depends on: 10`. In `"none"`, every run gives `results={'10': COMPLETE, '11': PLANNED}`, `holds={}`, rc=1, and says "publish them (`pdca publish <id>` for 10), merge their PR into main". But `pdca publish 10` refuses an untargeted bundle (`publish.py:183-190`; `cli.py:495` passes no `skip_if_no_target`), so no PR can ever exist. The same input in `"stack"` builds both, rc=0. The peer rule says this case is excluded: `integrate.unpublished` at `template/src/pdca_harness/integrate.py:263` reads "A patched bundle with no target is neither." The docs (`docs/07-crosscutting.md:932-937`) name only failed texts or a failed publish as causes. Fix: filter on a usable target, as `integrate._fold_candidates` does, and choose what an untargeted prerequisite means. It could count as ready, the way `merged.merged_into` treats a no-patch prerequisite. Or it could be held with a line that says it can never land. No test covers this.

- NEEDS-HUMAN [human] — **An iterated prerequisite whose re-publish cannot open a second PR blocks its dependent for good, even after the human merges the PR.** On re-publish, `publish.py:426-440` and `:452` overwrite `publish.json` with `pr_url: ""` whenever `gh pr create` fails. Real `gh` refuses a second PR for a head branch that already has an open one, which is the normal case after `signoff --iterate-do` of a published bundle. In `"none"`, `flow.py:820-821` then files the dependent as "unpublished" on every later run. I simulated this with `create_fails` on the second run. After `PR 10` was marked MERGED, a re-run of 11 was still held "no PR of that work is on record", rc=1. The advice (`pdca publish 10`) hits the same refusal. In `"stack"`, the in-batch dependent builds, because the pushed branch is folded. The test stub at `template/tests/test_flow_wave_mode_none.py:120-124` always opens a new PR for the same head, so the suite cannot see this. Caveat: I simulated gh's refusal rather than running real `gh`. The publish behaviour predates this diff, but this diff is what makes an in-batch dependent rely on `pr_url`. The real fix (find the open PR for the branch) belongs in publish, outside this brief, so a human should decide whether it belongs here.

- NEEDS-HUMAN [human] — **A prerequisite that targets a different base or repo, or one published with `Onto branch`, can never satisfy the hold, and the run reports a normal hold (rc 3) forever.** See `flow.py:824-826` together with `merged.py:109-114`. Case: 10 targets `org/repo @ dev`, 11 targets `@ main`, and 11 has `Depends on: 10`. Run 1 gives `holds={'11': 'unmerged'}`, rc=3, and "merge their PR into main", but 10's PR targets `dev`. After it merges into `dev`, the re-run logs "merged, but into org/repo @ dev; treating as not merged into org/repo @ main" and is held again with rc=3, with no end. `"stack"` builds both, rc=0. A mode `"stacked"` (`Onto branch`) prerequisite is refused the same way at `merged.py:109`. The brief asks for exactly this rule ("merged into the bundle's own target base"), so this is a scope decision. Either such edges are refused up front in `"none"`, or the hold line says they can never be met, not "merge their PR into main".

- NEEDS-HUMAN [human] — **A chain of three exits 1 on an ordinary `"none"` run, which defeats the point of rc 3.** Case: 10 ← 11 ← 12 (`Depends on`). Run 1 gives `holds={'11': 'unmerged'}` and "issue_12 skipped — prerequisite(s) not ready (11)", rc=**1**. The cause is `flow.py:810-812`: 11 is PLANNED, so for 12 it is `unmet`, and `flow.py:950` adds only bundles with no `unmet` to `waiting`. Then `cli.py:757-758` fails the run. In `"none"` a chain is the expected shape, and every run except the last two exits 1. A CI script cannot tell "waiting for a merge" from a real failure, which is what rc 3 is for. The docs admit it (`docs/07-crosscutting.md:931-932`). But `template/pdca.toml.jinja:132` says "(`flow` exits 3)" with no exception. Decide whether a bundle blocked only by an `"unmerged"` hold should itself count as `"unmerged"`. If not, at least fix the jinja comment.

- NEEDS-HUMAN [impl] — **A `gh` failure looks like "not merged yet" and exits 3, not 1.** `merged.py:102-106` returns False for a PR it cannot read, the same as for an OPEN one. `flow.py:824-826` then files it as "unlanded", and `flow.py:950-951` records `"unmerged"`. Case: `gh pr view` exits 1 (expired auth, `gh` missing). The run gives `holds={'11': 'unmerged'}`, rc=3, and "merge their PR into main". Every run looks like a normal hold while the host cannot be asked at all. Under `"stack"` the #647 hold for the same failure records no hold, so rc=1. It is low severity, since stderr does print "merged: could not read PR state". Fix: use `merged.pr_state` to tell "unreadable" from "OPEN", and treat unreadable as `unmet`.

**Tried to refute, could not:**
- A stale `stack-base` from an earlier stack-mode run leaking into `"none"`. It does not: `integ` stays empty, and `flow.py:3095` → `:1043` clears it for every runnable bundle.
- The `Stacks on` publish path: `publish.py:241`, `:771`, and `worktree._target` all fall back to the base.
- The b2 fetched-base check running without a line.
- The dry-run and `--no-publish` paths.
- `Conflicts with` partners after a failed publish.
- Config validation, including non-string values.
- The `pdca waves` summary.

**The verdict.** I have only the gate rows, not the reviewer's prose. `overall: pass` is right for the gates. The unwarranted claims are in the patch's own docs. `docs/07-crosscutting.md:932-937` says the only ways a prerequisite has no PR are failed texts or a failed publish; findings 1 and 2 show two more. `pdca.toml.jinja:132` promises exit 3; finding 4 shows it is often 1.
