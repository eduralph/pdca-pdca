# Result — issue 464 / wave-mode-none

## 1. Spec (from brief.md)              ← Check verifies against THIS
- Defect / goal: `[driver].wave_mode = "none"`: every accepted bundle publishes as a draft PR against its real target base, exactly as a single-bundle run does. At a wave boundary nothing happens — no integration line is created or pushed, nothing is folded, readied or merged, and the pre-wave carry of finished ids (#646) does not run. Waves still decide build order. A bundle whose prerequisite (any edge: `Depends on`, `Depends on (merged)`, `Stacks on`) has not merged into the bundle's own target base is held with a one-line reason and the way out (merge the prerequisite's PR, then re-run). This is NEW logic in `flow._runnable`, modelled on the #647 out-of-batch hold but not a reuse of it: today that hold fires only for an out-of-batch prerequisite (`flow.py:789`, :798, with `cand` tied to the fold at :795-797), and an in-batch prerequisite takes the branch at :831, which never asks `merged.merged_into`. The `"none"` branch covers in-batch and out-of-batch prerequisites and every edge kind. Its message is `"none"`-specific: no "no line of this run carries them" and no "name X in the same `pdca flow <ids>` command so the run's line carries them" advice (flow.py:836-841), since no line exists. The hold is recorded in the run's `holds` collector with a new kind `"unmerged"`, and `cli._results_rc` (cli.py:707) must count it as held-before-built: today only `_BASE_HOLD` (`"base"`) is in that set (cli.py:741), so a PLANNED B with any other hold kind returns 1. `"unmerged"` joins that set, so the run returns **3**, not 1. An unknown `wave_mode` value is reported at config load instead of silently behaving as `"stack"`.
- Success criterion: On the real-git fixture with `gh` stubbed and the publisher in `command` mode: (a) a `wave_mode = "none"` run of A and C (independent) and B (`Depends on: A`) publishes A and C as PRs whose `gh pr create --base` is the target base, pushes no `pdca-integration/*` branch to origin, calls neither `gh pr ready` nor `gh pr merge`, and holds B with a stderr line naming A as not merged into B's base (B stays PLANNED; the stderr line does NOT contain "line of this run" or "carries them"; `holds` has B as `"unmerged"`; `pdca flow` exits **3** per `cli._results_rc`); (a2) the same with B `Stacks on: A` instead: B is held the same way, and once released (b) its branch is cut from and its PR opened against the target base, not A's branch; (b) once A's PR reads MERGED into the base and the base has it, a re-run builds B from the fetched base and publishes it against the base; (b2) if A's PR reads MERGED but `origin/<base>` as fetched lacks the merge, B is still held (the #729 check, `_base_lacks_merge`, must run in `"none"`: today flow.py:807-809 skips it with `line is None → continue` whenever no line exists, which is always in `"none"`); (c) `Config.load` with `wave_mode = "bogus"` prints a config note naming the value and the allowed ones and falls back to `"stack"` (today it silently keeps `"bogus"`, config.py:733); (d) `"stack"` and `"merge"` runs behave as before (the existing suites stay green). Leg (c) is not in the issue; it is included because adding a third value makes a silent fallback worse, and the human confirms at sign-off that it belongs here.
- Repo + branch target: eduralph/pdca-harness @ main
- Scope (one logical fix) / out of scope: The new `"none"` value end to end, the dependency hold for it, validation of `wave_mode` at load, the `pdca.toml.jinja` comment block (:111-138) and the `wave_mode` section of `docs/07-crosscutting.md` (:639 onward). / out of scope: making `"none"` the default (changes what every instance gets on `copier update` — a separate decision); letting some bundles stack while others stay on the base inside a `"none"` run (the issue's "second, better behaviour"; overlaps the dependency-scoped bases #727 already gave stack mode); any change to `"stack"` or `"merge"` behaviour.

# Adversarial review — issue 464 / wave-mode-none

**Evidence: holds up.** I re-ran `tests.test_flow_wave_mode_none` on the patched target: 17/17 pass. `gate-logs/C4-verify.log` shows 14 of 17 failing with the production change reverted, and they fail on assertions, not imports. The two tests that also pass red are the stack-mode control and the `--no-publish` case. They are guards, not proof. The tests drive the real `flow._drive_and_act`, `flow._runnable` and `publish.publish` against a bare git origin. Only the build leaf, `draft_texts` and `gh` are stubbed, so this is the production path.

**The fix: four inputs break it.** I wrote probes in my scratch dir that subclass the bundle's own test class and use the same fixture and stubs. Each bullet gives the observed `results` / `holds` / exit code.

- NEEDS-HUMAN [impl] — **A prerequisite with no `Repo + branch target` blocks its dependent forever, and the advice it prints cannot work.** `template/src/pdca_harness/flow.py:818-823` counts any *patched* prerequisite with no `publish.json` as "unpublished", whether or not it has a target. Case: 10 has a patch but no target; 11 is targeted, with `Depends on: 10`. In `"none"`, every run gives `results={'10': COMPLETE, '11': PLANNED}`, `holds={}`, rc=1, and says "publish them (`pdca publish <id>` for 10), merge their PR into main". But `pdca publish 10` refuses an untargeted bundle (`publish.py:183-190`; `cli.py:495` passes no `skip_if_no_target`), so no PR can ever exist. The same input in `"stack"` builds both, rc=0. The peer rule says this case is excluded: `integrate.unpublished` at `template/src/pdca_harness/integrate.py:263` reads "A patched bundle with no target is neither." The docs (`docs/07-crosscutting.md:932-937`) name only failed texts or a failed publish as causes. Fix: filter on a usable target, as `integrate._fold_candidates` does, and choose what an untargeted prerequisite means. It could count as ready, the way `merged.merged_into` treats a no-patch prerequisite. Or it could be held with a line that says it can never land. No test covers this.

- NEEDS-HUMAN [human] — **An iterated prerequisite whose re-publish cannot open a second PR blocks its dependent for good, even after the human merges the PR.** On re-publish, `publish.py:426-440` and `:452` overwrite `publish.json` with `pr_url: ""` whenever `gh pr create` fails. Real `gh` refuses a second PR for a head branch that already has an open one, which is the normal case after `signoff --iterate-do` of a published bundle. In `"none"`, `flow.py:820-821` then files the dependent as "unpublished" on every later run. I simulated this with `create_fails` on the second run. After `PR 10` was marked MERGED, a re-run of 11 was still held "no PR of that work is on record", rc=1. The advice (`pdca publish 10`) hits the same refusal. In `"stack"`, the in-batch dependent builds, because the pushed branch is folded. The test stub at `template/tests/test_flow_wave_mode_none.py:120-124` always opens a new PR for the same head, so the suite cannot see this. Caveat: I simulated gh's refusal rather than running real `gh`. The publish behaviour predates this diff, but this diff is what makes an in-batch dependent rely on `pr_url`. The real fix (find the open PR for the branch) belongs in publish, outside this brief, so a human should decide whether it belongs here.

- NEEDS-HUMAN [human] — **A prerequisite that targets a different base or repo, or one published with `Onto branch`, can never satisfy the hold, and the run reports a normal hold (rc 3) forever.** See `flow.py:824-826` together with `merged.py:109-114`. Case: 10 targets `org/repo @ dev`, 11 targets `@ main`, and 11 has `Depends on: 10`. Run 1 gives `holds={'11': 'unmerged'}`, rc=3, and "merge their PR into main", but 10's PR targets `dev`. After it merges into `dev`, the re-run logs "merged, but into org/repo @ dev; treating as not merged into org/repo @ main" and is held again with rc=3, with no end. `"stack"` builds both, rc=0. A mode `"stacked"` (`Onto branch`) prerequisite is refused the same way at `merged.py:109`. The brief asks for exactly this rule ("merged into the bundle's own target base"), so this is a scope decision. Either such edges are refused up front in `"none"`, or the hold line says they can never be met, not "merge their PR into main".

- NEEDS-HUMAN [human] — **A chain of three exits 1 on an ordinary `"none"` run, which defeats the point of rc 3.** Case: 10 ← 11 ← 12 (`Depends on`). Run 1 gives `holds={'11': 'unmerged'}` and "issue_12 skipped — prerequisite(s) not ready (11)", rc=**1**. The cause is `flow.py:810-812`: 11 is PLANNED, so for 12 it is `unmet`, and `flow.py:950` adds only bundles with no `unmet` to `waiting`. Then `cli.py:757-758` fails the run. In `"none"` a chain is the expected shape, and every run except the last two exits 1. A CI script cannot tell "waiting for a merge" from a real failure, which is what rc 3 is for. The docs admit it (`docs/07-crosscutting.md:931-932`). But `template/pdca.toml.jinja:132` says "(`flow` exits 3)" with no exception. Decide whether a bundle blocked only by an `"unmerged"` hold should itself count as `"unmerged"`. If not, at least fix the jinja comment.

- NEEDS-HUMAN [impl] — **A `gh` failure looks like "not merged yet" and exits 3, not 1.** `merged.py:102-106` returns False for a PR it cannot read, the same as for an OPEN one. `flow.py:824-826` then files it as "unlanded", and `flow.py:950-951` records `"unmerged"`. Case: `gh pr view` exits 1 (expired auth, `gh` missing). The run gives `holds={'11': 'unmerged'}`, rc=3, and "merge their PR into main". Every run looks like a normal hold while the host cannot be asked at all. Under `"stack"` the #647 hold for the same failure records no hold, so rc=1. It is low severity, since stderr does print "merged: could not read PR state". Fix: use `merged.pr_state` to tell "unreadable" from "OPEN", and treat unreadable as `unmet`.

# Advisory code review — issue 464 / wave-mode-none

The main paths look right. The `"none"` branch in `_runnable` (template/src/pdca_harness/flow.py:813-837) covers in-batch and out-of-batch prerequisites and every edge kind. It runs the #729 fetched-base check without a line. It names a prerequisite with no PR as "publish it first", not as "waiting for a merge". The round-1 findings (stub dry-run, unpushed bookkeeping, missing edge-kind tests) are dealt with at flow.py:2980-2981, flow.py:3164-3176 and the new tests. The stale-stack-base clear still runs in `"none"`, because `own_bases` is False and the `else` branch calls `_point_at_integration` (flow.py:3094-3095). Two findings:

- NEEDS-HUMAN [impl] — template/src/pdca_harness/flow.py:810-812 with :950-951: a chain gets no hold of its own past the first dependent. Take A ← B ← C (B `Depends on: A`, C `Depends on: B`) in one `"none"` run. B goes into `waiting`, stays PLANNED and becomes an `"unmerged"` hold. In the next wave, C finds B is not COMPLETE, so it lands in `unmet`. It prints "skipped — prerequisite(s) not ready (issue_B)" with no way out, gets no hold, and `cli._results_rc` (template/src/pdca_harness/cli.py:757-759) returns **1** for the whole run. That happens every time until A merges. In `"none"`, a chain is the normal case, not a failure: the brief says each dependent is "held with a one-line reason and the way out", and that a `"none"` batch "builds its first wave and holds the rest". Fix: when `wait_for_merge` is on and a not-COMPLETE prerequisite is in `waiting`, record the dependent as waiting too, with the advice "wait for B, which waits for A's merge". Then add a three-bundle chain test to template/tests/test_flow_wave_mode_none.py. No current test has a chain longer than one edge.
- template/src/pdca_harness/publish.py:238-241, :253 — publish still trusts a recorded `stack-base` (`_read_stack_base`) in `"none"`. Only `_stacks_on_branch` was made mode-aware (publish.py:771). Inside `pdca flow` this is safe, because `_point_at_integration` clears the marker first (flow.py:1043). But a standalone `pdca publish <id>` on a bundle that a past stack-mode run stamped would cut from, and open its PR against, the old integration line, with `wave_stacked` True. The same goes for `_stack_base_branch` (publish.py:761), which Do reads. This only bites an instance that switched modes while bundles were in flight. A one-line guard would close it: `wave_base = "" if cfg.wave_mode == "none" else _read_stack_base(d)`. Low priority, so not tagged.

Nothing else found on either lens. The config check (template/src/pdca_harness/config.py:740-747) follows the `merge_requires` pattern. The `_UNBUILT_HOLDS` set (cli.py:709) is a small, clean generalisation of the old `_BASE_HOLD` test, and the per-wave `lacks` cache is reused as before.
