# Result — issue 464 / wave-mode-none

## 1. Spec (from brief.md)              ← Check verifies against THIS
- Defect / goal: `[driver].wave_mode = "none"`: every accepted bundle publishes as a draft PR against its real target base, exactly as a single-bundle run does. At a wave boundary nothing happens — no integration line is created or pushed, nothing is folded, readied or merged, and the pre-wave carry of finished ids (#646) does not run. Waves still decide build order. A bundle whose prerequisite (any edge: `Depends on`, `Depends on (merged)`, `Stacks on`) has not merged into the bundle's own target base is held with a one-line reason and the way out (merge the prerequisite's PR, then re-run). This is NEW logic in `flow._runnable`, modelled on the #647 out-of-batch hold but not a reuse of it: today that hold fires only for an out-of-batch prerequisite (`flow.py:789`, :798, with `cand` tied to the fold at :795-797), and an in-batch prerequisite takes the branch at :831, which never asks `merged.merged_into`. The `"none"` branch covers in-batch and out-of-batch prerequisites and every edge kind. Its message is `"none"`-specific: no "no line of this run carries them" and no "name X in the same `pdca flow <ids>` command so the run's line carries them" advice (flow.py:836-841), since no line exists. The hold is recorded in the run's `holds` collector with a new kind `"unmerged"`, and `cli._results_rc` (cli.py:707) must count it as held-before-built: today only `_BASE_HOLD` (`"base"`) is in that set (cli.py:741), so a PLANNED B with any other hold kind returns 1. `"unmerged"` joins that set, so the run returns **3**, not 1. An unknown `wave_mode` value is reported at config load instead of silently behaving as `"stack"`.
- Success criterion: On the real-git fixture with `gh` stubbed and the publisher in `command` mode: (a) a `wave_mode = "none"` run of A and C (independent) and B (`Depends on: A`) publishes A and C as PRs whose `gh pr create --base` is the target base, pushes no `pdca-integration/*` branch to origin, calls neither `gh pr ready` nor `gh pr merge`, and holds B with a stderr line naming A as not merged into B's base (B stays PLANNED; the stderr line does NOT contain "line of this run" or "carries them"; `holds` has B as `"unmerged"`; `pdca flow` exits **3** per `cli._results_rc`); (a2) the same with B `Stacks on: A` instead: B is held the same way, and once released (b) its branch is cut from and its PR opened against the target base, not A's branch; (b) once A's PR reads MERGED into the base and the base has it, a re-run builds B from the fetched base and publishes it against the base; (b2) if A's PR reads MERGED but `origin/<base>` as fetched lacks the merge, B is still held (the #729 check, `_base_lacks_merge`, must run in `"none"`: today flow.py:807-809 skips it with `line is None → continue` whenever no line exists, which is always in `"none"`); (c) `Config.load` with `wave_mode = "bogus"` prints a config note naming the value and the allowed ones and falls back to `"stack"` (today it silently keeps `"bogus"`, config.py:733); (d) `"stack"` and `"merge"` runs behave as before (the existing suites stay green). Leg (c) is not in the issue; it is included because adding a third value makes a silent fallback worse, and the human confirms at sign-off that it belongs here.
- Repo + branch target: eduralph/pdca-harness @ main
- Scope (one logical fix) / out of scope: The new `"none"` value end to end, the dependency hold for it, validation of `wave_mode` at load, the `pdca.toml.jinja` comment block (:111-138) and the `wave_mode` section of `docs/07-crosscutting.md` (:639 onward). / out of scope: making `"none"` the default (changes what every instance gets on `copier update` — a separate decision); letting some bundles stack while others stay on the base inside a `"none"` run (the issue's "second, better behaviour"; overlaps the dependency-scoped bases #727 already gave stack mode); any change to `"stack"` or `"merge"` behaviour.

### Advisory — adversary

# Adversarial review: issue 464, wave-mode-none

The core feature held up. I found four concrete failures at the edges: three are reachable on an ordinary path, and the last needs a mode switch. All four are builder-fixable. I reproduced each one by running the real `flow`/`publish` code in a scratch copy of the patched tree, using the test file's own fixture. Finding 4 has one part I read but did not run, marked there.

## Refutations

- NEEDS-HUMAN [impl] — **Re-running the same command turns a bundle with no PR into a clean exit 0.** `template/src/pdca_harness/flow.py:3705` returns early when every named id is finished, and `flow.py:3279-3282` only checks bundles driven this run, so a finished bundle's missing PR is never looked at again. Case: 10 with `gh pr create` failing. `pdca flow 10` exits 3 with `holds={'10': 'no-pr'}`. The same `pdca flow 10` again exits 0, `publish.json` still has `pr_url: ""`, and stderr says "already complete — nothing to run". `pdca flow 10 12` with a new independent 12 also exits 0 and says nothing about 10's missing PR. The rejected-work variant is worse: 10 is published, iterated, and its texts fail. That run exits 3, the re-run exits 0, and `publish.accepted_pr` returns `""`, so the accepted rebuild is on no PR and the old PR still holds the rejected attempt. `template/pdca.toml.jinja:135-136` says an accepted bundle left with no PR is "never a clean run", and a CI retry would read this 0 as success. Single-wave stack mode also exits 0 here, so this is not a regression, but stack mode makes no such promise. Fix: under `"none"` with publishing on, run the `publish.accepted_pr` check over the finished named ids too, including before the early return. Or narrow the promise in the TOML comment and `docs/07-crosscutting.md:956-959` to "the run that tried to publish it".

- NEEDS-HUMAN [impl] — **A `Depends on (merged)` edge is dropped in a real run but enforced in a dry-run.** `template/src/pdca_harness/flow.py:893` treats any prerequisite with no usable target as ready, whichever edge names it. Case: 10 has a patch and no target, and 11 is `Depends on (merged): 10`, run after 10 finished. In `"none"` with publishing on, 11 is built without 10's work and the run exits 0. In `"none"` as a dry-run, 11 is held and exits 1. In `"stack"`, 11 is held and exits 1. So the rehearsal is stricter than the real run, and the edge that exists to require a merge gives less protection here than in stack mode. `docs/07-crosscutting.md:922` says the hold applies "whichever edge names the prerequisite", while `:939-941` carves out this case without mentioning the edge kind. The tests only cover it with a plain `Depends on` (`template/tests/test_flow_wave_mode_none.py:967-968`), where building is the right answer and matches stack mode. Fix: keep the hold when `dep in merged_deps`, say it can never be satisfied, and add a test.

- NEEDS-HUMAN [impl] — **A PR opened by hand and merged leaves the dependent stuck, and the only advice given cannot work.** `template/src/pdca_harness/publish.py:444` still says "Open the draft PR by hand". The added note at `:440` warns against merging before a re-run, but nothing covers the case where that merge already happened. Case: 10's push succeeds and `gh pr create` fails, then the branch is merged into `main` (my probe merged the pushed branch directly, as a hand-opened PR would). `pdca flow 11` then exits 1 on every run with "publish them (`pdca publish <id>` for 10), merge their PR" (`flow.py:1014`). `pdca publish 10` then exits 1 at `git apply` ("a.txt: already exists in working directory"), because the work is already on the base. So `publish.json` never changes and the hold line never changes, though the work has landed. Removing the edge is the only exit, and this line does not say so. Fix: when no PR is on record but a branch is, ask the host for a merged PR of that branch before holding. Or have the line name removing the edge as the way out.

- NEEDS-HUMAN [impl] — **`pdca publish` under `"none"` still reads an old `stack-base` file.** `template/src/pdca_harness/publish.py:239` and `:254` read it with no mode check, though the patch gates the `Stacks on` half at `:818`. The flow clears the file only for bundles it drives (`flow.py:1161`), so a COMPLETE bundle keeps it. Case: a bundle finished under `"stack"` with a recorded stack base, the instance switches to `"none"`, and the operator runs `pdca publish 10`, as the hold lines say to. In my probe, with a line name that no longer exists on origin, it exits 1 at `git checkout -B fix/10-10 origin/pdca-integration/main-rOLD`. If the line still exists, the code at `publish.py:254-266` cuts the PR from it, so the PR would carry other bundles' work against the real base. That is what `docs/07-crosscutting.md:914-918` says `"none"` never does; I read this branch but did not run it. Low severity, since it needs a mode switch. Fix: ignore `wave_base` when `cfg.wave_mode == "none"`, and add a test.

### Advisory — code-review

# Advisory code review: issue 464, `wave_mode = "none"`

Two correctness gaps and one small cleanup. I reproduced both gaps with a throwaway probe built on the patch's own test fixture (real git, `gh` stubbed). I did not run the same probes under `"stack"`, so I make no claim about how that mode compares at exit-code level.

- NEEDS-HUMAN [impl] — **A re-run reports a bundle with no PR as a clean run.** `template/src/pdca_harness/flow.py:3077` skips `_carry_finished` in `"none"`, and `_hold_without_pr` (`flow.py:678`) only sees bundles driven this run. Nothing else looks at a finished bundle named on the command line. Reproduced: `pdca flow 20` with failed texts exits 3 (`holds={'20': 'unpushed'}`). The next `pdca flow 20` exits 0 and prints only "already terminal (COMPLETE), skipped", though no PR exists. These cases give the same result: `gh pr create` failed (first run 3, re-run 0), an iterated bundle whose rebuild was never published (3, then 0), and `pdca flow 20 21` with a new independent 21 (0). `docs/07-crosscutting.md:956` says such a bundle is reported and "the run does not exit 0", and that holds only for the run where the publish failed. The first-run report is also easy to lose, because the "already complete" message gives `rm -rf` as the way to redo it and does not mention `pdca publish`. Fix: in `"none"` with `wait_for_merge` on, check each id from `finished` (`flow.py:3076`) with `publish.accepted_pr`, then name and record it as `"no-pr"` (or as `"unpushed"`, if that is the better fit). Then add a re-run test, since `test_pdca_flow_of_one_id_exits_3_when_held_and_when_left_with_no_pr` (`template/tests/test_flow_wave_mode_none.py:1250`) stops at the first run. If "reported once" is the intended behaviour, correct the docs line instead.

- NEEDS-HUMAN [impl] — **A `Stacks on` bundle is refused once its merged parent is archived.** `template/src/pdca_harness/waves.py:111` (and `:370`, the same rule in the scheduler's other path) looks up a `Stacks on` parent with `cfg.bundle()`, which ignores `completed/`. The comment above that line gives the reason: the dependent bases its work on the parent's live branch. That reason no longer applies in `"none"`, where `_stacks_on_branch` returns None (`publish.py:818`) and the bundle is built on its target base. Reproduced: 10 and 11, with 11 `Stacks on: 10`. Merge 10's PR, move the bundle to `completed/` (the manual archive convention at `config.py:535`), then run `pdca flow 11`. It exits 2 with "declared dependency '10' is neither in this batch nor an existing COMPLETE bundle". The same steps with `Depends on: 10` build 11 and exit 0, which contradicts the promise that all three edge kinds are held and released the same way (`docs/07-crosscutting.md:924`). Fix: use `find_bundle` for every edge when `cfg.wave_mode == "none"`, at both call sites, and add a test.

- Cleanup, low priority: `template/src/pdca_harness/flow.py:914` calls `merged.pr_state` once per dependent and prerequisite pair. Two dependents of one prerequisite make two `gh pr view` calls, and those calls can disagree within a run (one dependent held as a fault, the other as a wait). The same function already caches `_base_lacks_merge` results in `lacks` (`flow.py:842`), so a similar per-call dict keyed on `pr_url` would make one read per PR per wave.

Nothing else to report on this lens. `merged.lands_on` matches the condition it replaces in `merged_into`. The new `publish.py` paths leave `"stack"` and `"merge"` unchanged, apart from one extra `patch_sha256` key in the record. The other callers of `_stacks_on_branch` (`worktree.py:96`, `drift.py:67`) get the target base in `"none"`, as intended.
