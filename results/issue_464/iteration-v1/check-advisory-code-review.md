# Advisory code review — issue 464 / wave-mode-none

Lens: bugs the patch introduces, plus reuse and simplification. All gates in
check-gates.json pass (C4 red→green, T3 suites green). The core change looks right:
`"none"` turns off the carry, the fold/merge branch and per-bundle bases
(flow.py:2933, :2946, :3131). Stale `stack-base` markers are still cleared, because
`_point_at_integration` runs with an empty `integ` (flow.py:3067). `held_unpushed` stays
empty in `"none"`, since it is only filled inside the gated fold branch (flow.py:3149).
The findings below are edge cases and test gaps, not blockers.

- NEEDS-HUMAN [impl] — template/src/pdca_harness/flow.py:2954 — `wait_for_merge = do_publish and cfg.wave_mode == "none"` does not exclude the stub publisher. `hold_unmerged`, two lines up (flow.py:2946-2947), and the carry (flow.py:1530, "dry-run: ask no host, hold nothing") both do. In a `"none"` dry-run, `_runnable` calls `merged.merged_into` (a real `gh pr view`) for every prerequisite. An in-batch prerequisite published by the stub has no `pr_url`, so every dependent is held as `"unmerged"` and the dry-run exits 3, with stderr telling the user to "merge their PR" when no PR exists. Either add `and cfg.publisher.mode != "stub"`, or decide on purpose that a dry-run rehearses the hold, and add a test for whichever is chosen.
- NEEDS-HUMAN [impl] — template/src/pdca_harness/flow.py:810-815, :873-877 — an in-batch prerequisite that was accepted but whose publish failed this run (texts not ready, or `_publish_bundle` false at flow.py:3114) has no `pr_url`, so `merged_into` returns False and its dependent is recorded as `"unmerged"` (exit 3). The message says "merge their PR into main, then re-run", but there is no PR to merge. In stack mode the same case is named as "pushed no branch this run" (flow.py:3150-3153). Consider checking `pushed` / a missing publish record first and giving the "publish it first" advice, or at least not claiming a PR exists.
- NEEDS-HUMAN [human] — docs/07-crosscutting.md:931-932 and flow.py:928 — in a three-bundle chain A→B→C under `"none"`, the first run builds A, holds B (`"unmerged"`) and skips C as "not ready" because B is not COMPLETE. C gets no hold, so `_results_rc` returns **1**, a failure, on a run where nothing went wrong and every step is waiting on a human merge. The docs state this on purpose, but it means any `"none"` batch with a chain deeper than one edge always reads as failed to CI. One option is to also add C to `waiting` when every unmet prerequisite is itself in `waiting`. This is a scope and exit-code decision.
- NEEDS-HUMAN [human] — template/src/pdca_harness/flow.py:3131 — in `"none"`, a `Conflicts with` pair is still put into separate waves by the scheduler, but the later one is now built on the plain base without its partner's work, with no hold and no message. Both PRs then open against main and the conflict shows up only at merge time. This may be the intended "waves still decide build order" behaviour, but neither the brief nor the new docs paragraph (docs/07-crosscutting.md:914-946) says what happens to `Conflicts with` in this mode. Confirm, and document it if it is intended.
- NEEDS-HUMAN [impl] — template/tests/test_flow_wave_mode_none.py:614-691 — the docs (docs/07-crosscutting.md:928-929) and the `_runnable` docstring (flow.py:761-764) promise the hold for every edge kind, in batch or not. The tests cover only an in-batch `Depends on` and an in-batch `Stacks on`. Nothing exercises `Depends on (merged)`, an out-of-batch prerequisite (the path that used to go through the #647 branch), the untargeted-dependent fallback (flow.py:813-814, `unmet` rather than `unlanded`), or `--no-publish` in `"none"`. One case each for out-of-batch and `Depends on (merged)` would pin the "every edge" claim.
- flow.py:816-822 copies the `lacks` cache-and-check block at flow.py:851-856 line for line (same key shape, same `_base_lacks_merge` call, same `off_base.append`). A small local helper such as `_check_base(p, dep)` would remove the duplication. This is cleanup only; behaviour is the same.
- publish.py:240 — the extra `and cfg.wave_mode != "none"` is needed, because otherwise a `Stacks on` bundle returns 1 now that `_stacks_on_branch` gives None (publish.py:770). Correct, but the mode check now lives in two places for one rule. Optional: leave a short comment at :240 pointing to :770 so the two stay in step.

No resource leaks, off-by-one errors or API misuse found in the diff. `_UNBUILT_HOLDS` (cli.py:709) is used correctly in `_results_rc` (cli.py:755). The config fallback (config.py:744-747) has the same shape as the existing `merge_requires` check.
