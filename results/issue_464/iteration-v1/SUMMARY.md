# Result — issue 464 / wave-mode-none

## 1. Spec (from brief.md)              ← Check verifies against THIS
- Defect / goal: `[driver].wave_mode = "none"`: every accepted bundle publishes as a draft PR against its real target base, exactly as a single-bundle run does. At a wave boundary nothing happens — no integration line is created or pushed, nothing is folded, readied or merged, and the pre-wave carry of finished ids (#646) does not run. Waves still decide build order. A bundle whose prerequisite (any edge: `Depends on`, `Depends on (merged)`, `Stacks on`) has not merged into the bundle's own target base is held with a one-line reason and the way out (merge the prerequisite's PR, then re-run). This is NEW logic in `flow._runnable`, modelled on the #647 out-of-batch hold but not a reuse of it: today that hold fires only for an out-of-batch prerequisite (`flow.py:789`, :798, with `cand` tied to the fold at :795-797), and an in-batch prerequisite takes the branch at :831, which never asks `merged.merged_into`. The `"none"` branch covers in-batch and out-of-batch prerequisites and every edge kind. Its message is `"none"`-specific: no "no line of this run carries them" and no "name X in the same `pdca flow <ids>` command so the run's line carries them" advice (flow.py:836-841), since no line exists. The hold is recorded in the run's `holds` collector with a new kind `"unmerged"`, and `cli._results_rc` (cli.py:707) must count it as held-before-built: today only `_BASE_HOLD` (`"base"`) is in that set (cli.py:741), so a PLANNED B with any other hold kind returns 1. `"unmerged"` joins that set, so the run returns **3**, not 1. An unknown `wave_mode` value is reported at config load instead of silently behaving as `"stack"`.
- Success criterion: On the real-git fixture with `gh` stubbed and the publisher in `command` mode: (a) a `wave_mode = "none"` run of A and C (independent) and B (`Depends on: A`) publishes A and C as PRs whose `gh pr create --base` is the target base, pushes no `pdca-integration/*` branch to origin, calls neither `gh pr ready` nor `gh pr merge`, and holds B with a stderr line naming A as not merged into B's base (B stays PLANNED; the stderr line does NOT contain "line of this run" or "carries them"; `holds` has B as `"unmerged"`; `pdca flow` exits **3** per `cli._results_rc`); (a2) the same with B `Stacks on: A` instead: B is held the same way, and once released (b) its branch is cut from and its PR opened against the target base, not A's branch; (b) once A's PR reads MERGED into the base and the base has it, a re-run builds B from the fetched base and publishes it against the base; (b2) if A's PR reads MERGED but `origin/<base>` as fetched lacks the merge, B is still held (the #729 check, `_base_lacks_merge`, must run in `"none"`: today flow.py:807-809 skips it with `line is None → continue` whenever no line exists, which is always in `"none"`); (c) `Config.load` with `wave_mode = "bogus"` prints a config note naming the value and the allowed ones and falls back to `"stack"` (today it silently keeps `"bogus"`, config.py:733); (d) `"stack"` and `"merge"` runs behave as before (the existing suites stay green). Leg (c) is not in the issue; it is included because adding a third value makes a silent fallback worse, and the human confirms at sign-off that it belongs here.
- Repo + branch target: eduralph/pdca-harness @ main
- Scope (one logical fix) / out of scope: The new `"none"` value end to end, the dependency hold for it, validation of `wave_mode` at load, the `pdca.toml.jinja` comment block (:111-138) and the `wave_mode` section of `docs/07-crosscutting.md` (:639 onward). / out of scope: making `"none"` the default (changes what every instance gets on `copier update` — a separate decision); letting some bundles stack while others stay on the base inside a `"none"` run (the issue's "second, better behaviour"; overlaps the dependency-scoped bases #727 already gave stack mode); any change to `"stack"` or `"merge"` behaviour.

# Adversarial review — issue 464 / wave-mode-none

**Evidence holds up.** I re-ran the proof myself. The new test `template/tests/test_flow_wave_mode_none.py` fails 6 of 8 cases on the pre-fix source (`git archive HEAD`). Each failure has the right cause: B was built on `pdca-integration/main-r…`, a PR was opened for 11, the `waves` text was wrong, and `bogus` was kept. All 8 pass on the patched tree. The test runs the real `flow._drive_and_act`, `_runnable` and `publish.publish` against a bare git origin; only `gh` and the build leaf are stubbed. It is not a copy of production code.

I also tried four partial fixes, and the test caught every one:
- dropping the fetched-base check in the `"none"` branch (flow.py:816-822)
- dropping the `"none"` guard in `_stacks_on_branch` (publish.py:770)
- dropping the guard on the "Stacks on with no branch" refusal (publish.py:240)
- applying the hold to in-batch prerequisites only

So the red→green proof is sound for what the brief asked. The refutations below are inputs the brief's legs (a)–(c) do not cover. I ran each one through the real `_drive_and_act` on the same fixture (probe scripts in my scratch dir).

- NEEDS-HUMAN [impl] — **A prerequisite whose publish failed is reported as "waiting for a merge", and the run exits 3 instead of 1.** template/src/pdca_harness/flow.py:810-812: when `merged.merged_into` returns False because the prerequisite has **no PR at all** (merged.py:99), the bundle still goes to `unlanded`. Concrete case: A and B, B `Depends on: A`, and A's texts fail draft/T4 (or its push fails). In `"none"`, B prints "issue_10 not merged into main … To build it, merge their PR into main, then re-run" (flow.py:873-877), but no such PR exists. `holds={'11':'unmerged'}` and rc=3. The same input in `"stack"` gives `holds={'10':'unpushed'}`, "issue_11 skipped — prerequisite(s) not ready", and rc=1. The patch also skips flow.py:3146-3153 in `"none"` (the guard at flow.py:3131), which is the only place a failed publish gets recorded in `holds`. So in `"none"` a failed publish never shows up in the exit code. With independent bundles only, it exits 0. Fix: in the `wait_for_merge` branch, treat a patched prerequisite with no recorded PR (or, in-batch, one not in `pushed`) as `unmet`, or name it "publish it first". Keep the `"unpushed"` bookkeeping in `"none"` mode as well. No test covers this.

- NEEDS-HUMAN [human] — **A dependency chain exits 1 on every run except the last.** flow.py:804-806 and flow.py:928 (`… and not unmet`): with A→B→C in one `"none"` batch, B is held as `"unmerged"`, but C is "skipped — prerequisite(s) not ready (11)" with no hold of its own. So cli.py:755-757 returns **1** (probe: `holds={'11':'unmerged'}`, rc=1). This goes against the brief's Goal line: "A bundle whose prerequisite … has not merged into the bundle's own target base is **held** with a one-line reason and the way out". C's prerequisite has not merged, yet C is skipped. The builder documented this choice (docs/07-crosscutting.md, "a bundle that depends on a held one is skipped as not ready, so that run exits 1"), and it follows the #738 `"base"` precedent. But in `"none"`, chains are the normal case, not an error. A CI job reading the exit code would see "failed" on every run of a depth-3+ batch until the last two. Someone needs to decide whether C should be held too, so the run exits 3.

- NEEDS-HUMAN [human] — **A dependent on a different base can never be built in `"none"`.** flow.py:810 checks `merged_into(cfg, dep, repo, base)` against the dependent's base, and merged.py:109-116 rejects a merge into any other base. Concrete case: A targets `org/repo @ main`; B targets `org/repo @ release` and `Depends on: A`. After A's PR merges into main, the re-run still holds B, logging "merged, but into org/repo @ main; treating as not merged into org/repo @ release" and telling the user to "merge their PR into release". That is impossible, because A's PR targets main. The same input in `"stack"` builds B (rc 0). The brief does say "the bundle's own target base", so the code follows the brief. But this outcome (held forever, with advice that cannot be followed) is probably not what the brief meant. A cross-repo prerequisite gets the same dead end. A human should decide: accept a merge into the prerequisite's own base, refuse such a batch up front, or at least change the message.

- NEEDS-HUMAN [human] — **`--rehearse` (offline dry-run) in `"none"` stops after wave 0.** flow.py:2954 sets `wait_for_merge = do_publish and cfg.wave_mode == "none"`, with no `publisher.mode != "stub"` exclusion. `hold_unmerged` has that exclusion (flow.py:2946-2947), with the comment "not in a dry-run, which asks no host and holds nothing". The stub publisher records no PR, so every dependent is held. Probe: stub publisher, `"none"` gives rc=3 with 11 held; `"stack"` gives rc=0 with 11 built. A rehearse can never merge anything, so it can never exercise wave 1+ of a `"none"` batch. If a real PR was left in `publish.json` by an earlier run, the dry-run also calls `gh pr view`. This may be the intended "faithful rehearsal", but neither the brief nor the docs say so.

- NEEDS-HUMAN [human] — **A fetch failure is recorded as `"unmerged"` and exits 3.** flow.py:928-929 puts the dependent in `waiting` whenever it is not runnable and has no `unmet` entry. That includes `off_base` with `known=False`, meaning the checkout could not be fetched. Probe: A's PR merged, then origin made unreachable; the re-run gives `holds={'11':'unmerged'}`, rc=3. The PR did merge, so the label is wrong, and an environment fault is reported as a normal hold rather than a failure. In `"stack"` the same `off_base` hold records nothing and exits 1. The patch's docs state this on purpose ("a checkout that cannot be fetched, holds the bundle as well … the run exits **3**"), but the brief's leg (b2) only asked for "still held", not for exit 3.

**Other things I tried and could not break:**
- Stale `stack-base` records are still cleared in `"none"`, because `own_bases` is False so `_point_at_integration` runs with an empty `integ` (flow.py:3067).
- `Conflicts with` partner holds cannot fire in `"none"`: `held_unpushed`, `held_conflict` and `held_base` stay empty, so `conflicts` is None.
- `Depends on (merged)` goes through the same branch, since `waves.declared_deps` returns all three edge kinds (waves.py:53). It has no test of its own.
- Out-of-batch prerequisites on a re-run are covered by legs (b)/(b2).
- Config validation with non-string values (lists, whitespace, wrong case) falls back to `"stack"` with a note.

`"none"` turns off the carry, the fold/merge branch and per-bundle bases

The findings below are edge cases and test gaps, not blockers.

- NEEDS-HUMAN [impl] — template/src/pdca_harness/flow.py:2954 — `wait_for_merge = do_publish and cfg.wave_mode == "none"` does not exclude the stub publisher. `hold_unmerged`, two lines up (flow.py:2946-2947), and the carry (flow.py:1530, "dry-run: ask no host, hold nothing") both do. An in-batch prerequisite published by the stub has no `pr_url`, so every dependent is held as `"unmerged"` and the dry-run exits 3, with stderr telling the user to "merge their PR" when no PR exists. Either add `and cfg.publisher.mode != "stub"`, or decide on purpose that a dry-run rehearses the hold, and add a test for whichever is chosen.
- NEEDS-HUMAN [impl] — template/src/pdca_harness/flow.py:810-815, :873-877 — an in-batch prerequisite that was accepted but whose publish failed this run (texts not ready, or `_publish_bundle` false at flow.py:3114) has no `pr_url`, so `merged_into` returns False and its dependent is recorded as `"unmerged"` (exit 3). Consider checking `pushed` / a missing publish record first and giving the "publish it first" advice, or at least not claiming a PR exists.
- NEEDS-HUMAN [human] — docs/07-crosscutting.md:931-932 and flow.py:928 — in a three-bundle chain A→B→C under `"none"`, the first run builds A, holds B (`"unmerged"`) and skips C as "not ready" because B is not COMPLETE. C gets no hold, so `_results_rc` returns **1**, a failure, on a run where nothing went wrong and every step is waiting on a human merge. The docs state this on purpose, but it means any `"none"` batch with a chain deeper than one edge always reads as failed to CI. One option is to also add C to `waiting` when every unmet prerequisite is itself in `waiting`. This is a scope and exit-code decision.
- NEEDS-HUMAN [human] — template/src/pdca_harness/flow.py:3131 — in `"none"`, a `Conflicts with` pair is still put into separate waves by the scheduler, but the later one is now built on the plain base without its partner's work, with no hold and no message. Both PRs then open against main and the conflict shows up only at merge time. This may be the intended "waves still decide build order" behaviour, but neither the brief nor the new docs paragraph (docs/07-crosscutting.md:914-946) says what happens to `Conflicts with` in this mode. Confirm, and document it if it is intended.
- NEEDS-HUMAN [impl] — template/tests/test_flow_wave_mode_none.py:614-691 — the docs (docs/07-crosscutting.md:928-929) and the `_runnable` docstring (flow.py:761-764) promise the hold for every edge kind, in batch or not. Nothing exercises `Depends on (merged)`, an out-of-batch prerequisite (the path that used to go through the #647 branch), the untargeted-dependent fallback (flow.py:813-814, `unmet` rather than `unlanded`), or `--no-publish` in `"none"`. One case each for out-of-batch and `Depends on (merged)` would pin the "every edge" claim.
- flow.py:816-822 copies the `lacks` cache-and-check block at flow.py:851-856 line for line (same key shape, same `_base_lacks_merge` call, same `off_base.append`). A small local helper such as `_check_base(p, dep)` would remove the duplication. This is cleanup only; behaviour is the same.
- publish.py:240 — the extra `and cfg.wave_mode != "none"` is needed, because otherwise a `Stacks on` bundle returns 1 now that `_stacks_on_branch` gives None (publish.py:770). Correct, but the mode check now lives in two places for one rule. Optional: leave a short comment at :240 pointing to :770 so the two stay in step.

No resource leaks, off-by-one errors or API misuse found in the diff. `_UNBUILT_HOLDS` (cli.py:709) is used correctly in `_results_rc` (cli.py:755). The config fallback (config.py:744-747) has the same shape as the existing `merge_requires` check.
