- **Slug:** merge-mode-resume-or-hold-out-of-batch-prerequisite
- **Kind:** bug + enhancement
- **Tracker:** eduralph/pdca-harness#839 (child of #547)
- **Defect / goal:** In merge mode, a dependent whose prerequisite is COMPLETE, published by an earlier run, and still unmerged is handled wrongly. (a) **Bug:** with a plain `Depends on`, the prerequisite is neither merged nor held — `hold_unmerged` is off in merge mode (`template/src/pdca_harness/flow.py:2901-2902`), so `flow._runnable` (`flow.py:786-841`) builds the dependent on a base without the prerequisite's change. The same happens when the prerequisite is NAMED in the command (`pdca flow P D` with P COMPLETE): `_carry_finished` is skipped in merge mode (`flow.py:2888`), `held_finished` stays empty, and a named id is never a hold candidate (`flow.py:795-797`), so D builds without P. (b) **Gap:** with `Depends on (merged)`, the dependent is held "until their PR merges" (`flow.py:836-841`), but no step ever merges it, so the chain is dead until a human merges by hand — and the stack-mode hold text ("name X in the same `pdca flow <ids>` command so the run's line carries them", `flow.py:836-837`) is wrong advice in merge mode, where there is no line. Goal: a prerequisite PR that a merge-mode run opened as a non-final wave is merged through `merge._merge_one`'s gates before the dependent builds; anything else that is unmerged holds the dependent, with the reason and a merge-mode way out.
- **Design (binding):**
  - **Where the merge runs:** a pre-wave step in `flow._drive_and_act`, the merge-mode analogue of `_carry_finished` (`flow.py:2887-2891`): before wave 0, for every COMPLETE prerequisite (out of batch, or a finished named id — `_finished_named`, `flow.py:1270-1280`) of a drive-set bundle, in dependency order. Not inside `flow._runnable`, which only reads state and prints holds and runs for every wave before the pass-budget check (`flow.py:2931`, `:2950`); a `_merge_one` can wait up to `merge_wait_secs` and mutates the host. `_runnable` then judges each prerequisite with `merged.merged_into` exactly as it does for a plain `Depends on` under `hold_unmerged` (`flow.py:794-798`) — the dependent is released only when `merged_into` says the work is on ITS target base, never on `_merge_one`'s `rc == 0` (`is_merged` answers True for a merge into any base, `merge.py:573-574`, `merged.py:76-83`).
  - **Two flags, not one:** `hold_unmerged` is turned on for merge mode (publishing on, not a dry run); `own_bases` stays `False` in merge mode. Today `own_bases = hold_unmerged` (`flow.py:2905`) and that flag also gates `_base_plans` / `_bundle_bases` (`flow.py:2924-2927`, `:2994-3000`), which belong to the stack path only ("where the line folds for real", `flow.py:2903-2904`). Separate them.
  - **The marker:** `publish.json["merge_eligible"] = true`, written by `_merge_one` when it runs from `merge_wave` for a non-final wave (`flow.py:3078-3081`), BEFORE its first `gh pr ready` of that PR — so a PR refused at the ready-mark, the rollup or the merge is marked too. Publish writes no marker (`_publish_bundle` has no wave information, `flow.py:3064`). Lifetime: it lives in `publish.json` and survives an iterate the way the record does (`integrate.py:260`); a re-publish of the bundle (a rebuilt attempt, or a manual `pdca publish <id>`) writes a fresh record WITHOUT it, so that PR holds its dependents until a merge-mode run marks it again or a human merges it — the safe default. Meaning: "a merge-mode run opened this PR as a non-final wave and a later merge-mode run may ready and merge it unattended once its gates pass". A refused PR returned to draft (`merge.py:460-482`) keeps the marker and IS re-readied by a later run; a human who wants the PR left alone merges or closes it by hand, or removes the key (the docs say so).
  - **Which prerequisites are merged:** a marked, unmerged, COMPLETE prerequisite whose own declared prerequisites (every edge kind) are each `merged_into` the same base — else it is not merged and the dependent is held naming the prerequisite AND its unmerged prerequisite (P→Q). A close/no-fix prerequisite (no patch) needs no merge (`merged_into` answers True, `merged.py:93-95`). An unmarked PR is never readied or merged (criterion 3b).
  - **Refusal outcome:** a refusal by `_merge_one` holds only the dependent (and, through `_runnable`, its dependents) with a hold reason; the run continues with the rest. `_merge_one`'s messages end in "STOP: later waves are NOT run" (`merge.py:549`, `:559-566`, `:591-594`, `:684-692`, `:718-725`, `_refuse` :475-482), which is false on this path: the trailing instruction becomes a parameter (Do's shape) so this path prints "<dependent> is held; resolve at the PR, then re-run" and the wave-boundary caller keeps today's text byte for byte. The hold line itself names the prerequisite, says its PR did not pass the merge gates, and points at the `merge:` lines above for the reason — no reason plumbing beyond that.
  - **Hold text in merge mode:** names the prerequisite, the dependent's target base, and the way out: "let a merge-mode run merge it (it is marked), or merge the PR by hand, then re-run". Never "name X in the same `pdca flow <ids>` command" or "carries them" (there is no line).
  - **Dry run / `--no-publish`:** nothing is merged, nothing held, no `gh` call — as today (`test_flow_out_of_batch_prereq_hold.py:343-348`, `:358-364` stay green).
- **Success criterion:** Over the `StackFoldGit` real-git fixture (`template/tests/test_integrate_stack_bases.py`) with `gh` stubbed, `wave_mode = "merge"`, runs driven through `flow.flow_ids`:
