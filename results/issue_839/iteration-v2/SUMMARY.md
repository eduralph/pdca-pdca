### Advisory — code-review

# Advisory code review — issue #839

I found three correctness problems and one small efficiency cleanup. I confirmed all three problems by running a throwaway subclass of the patch's own test fixture, with `gh` stubbed as in `test_merge_resume_stranded_prereq.py`. All gates in `check-gates.json` pass or are deferred (T4), and none of them covers these cases.

- NEEDS-HUMAN [impl] — `template/src/pdca_harness/flow.py:805`: merge mode still builds a dependent on a base that lacks an unmerged prerequisite when that prerequisite has a patch and a readable brief with no usable `Repo + branch target`. On a plain `Depends on`, `_fold_candidates` drops such a bundle (`integrate.py:347-350`), so `cand` is empty, `briefless` is False, and no hold happens. In the probe, D and U both built, P was not on `main`, and no line named D. This is the bug in leg (1), and it contradicts the brief ("anything else that is unmerged holds the dependent") and `docs/07-crosscutting.md:914`. The same prerequisite on a `Depends on (merged)` edge does hold, and a patched prerequisite with no brief holds too, so the plain edge is the odd one out. `_merge_way_out` already has the advice for this case (`flow.py:1479-1480`, "its brief does not target"). Fix: in merge mode, wait on any patched prerequisite, not only on a fold candidate, and add a test.

- NEEDS-HUMAN [impl] — `template/src/pdca_harness/flow.py:1526`: a prerequisite whose `patch.diff` is not valid UTF-8 ends the whole run with a `UnicodeDecodeError` before wave 0. `takes` calls `integrate._has_patch` (`integrate.py:196`), which decodes the file outside `_isolate`, and the walk has no other guard. `merged_into` (`merged.py:95`) and `_runnable` (`flow.py:804`, not probed) read the patch the same way, also outside `_isolate`. Before this patch, merge mode did not read a plain-edge prerequisite's patch at this point, so this crash path on that edge is new. In the probe, the exception came out of `flow_ids` and nothing built, not even the unrelated bundle U. It is the same kind of failure as the missing-brief crash that round 1 sent back. Caveat: I wrote the bad bytes by hand and did not check whether a real bundle can reach COMPLETE with such a patch. Fix: treat a patch that cannot be read as "not taken" and hold only that dependent, and add a test.

- NEEDS-HUMAN [impl] — `docs/07-crosscutting.md:913`: the docs say the walk "never merges a PR that could not release a dependent of the run", and that is false when a dependent has more than one prerequisite. With D depending on marked P and unmarked R, the probe readied and merged P, then held D on R. The same should happen when D is held for another reason, such as a `Conflicts with` hold, because `_merge_prereqs` (`flow.py:1495`) looks only at the path down each edge (I did not probe that case). The merge itself matches the brief ("for every COMPLETE prerequisite"), so the smallest fix is to reword that sentence to say the walk judges each edge on its own, and to pin the behaviour with a test. If the merge should instead wait until all of D's edges can clear, that is a scope change to raise at sign-off.

- `template/src/pdca_harness/flow.py:1548`: `seen` is reset for each drive-set bundle, so N dependents of one marked prerequisite repeat its `takes` check, and each repeat costs a `gh pr view` in `merged_into`. It is not a hot path, so this is only a cleanup: when `p.name` is already in `order` for the same target, the walk could add the dependent to `reach` for that prerequisite and its taken prerequisites, without asking `gh` again.
