# Advisory code review — issue 839

I found no crash or wrong-merge bug in the claim step this round added to `_merge_prereqs`. There are two behaviour questions for the human and two small cleanups. All four come from reading the code; I ran no probes. The frozen T3 log shows the suite passing (2945 tests, `OK (skipped=2)`).

- NEEDS-HUMAN [human] — `template/src/pdca_harness/merge.py:171-175`: one refusal leaves the rest of that wave's PRs unmarked. `merge_wave` returns on the first non-zero `_merge_one`, and only `_merge_one` writes the marker (`merge.py:826`). If a wave has PRs A, B and C and A is refused, B and C were opened by a merge-mode run as a non-final wave but never get `merge_eligible`. A later run then holds their dependents and says to merge by hand. This fails safe and matches the brief's literal rule (the marker is written when `_merge_one` runs) and `docs/07-crosscutting.md:969` ("pushes and then tries to merge"). But it misses the brief's goal, that a PR opened as a non-final wave is merged before the dependent builds. In a multi-PR wave, one red PR turns its siblings into manual merges. Decide whether to accept that, or to mark every pushed PR of the wave before the first merge attempt.
- NEEDS-HUMAN [human] — `template/src/pdca_harness/merged.py:250`: the marker's hash is tied to the local `patch.diff`, not to the PR's head commit. `marked_for_this_patch` catches a local rebuild that never reached the PR. It does not catch commits pushed to the PR branch on the host after the mark. A later run would ready and merge those commits unattended if the rollup is green; with `merge_requires = "required"`, the host's required checks are the only check. The wave path can do the same, but only in the short time within one run. The marker lets this happen days later, and `--match-head-commit` (`merge.py:987`) pins only the head the gates just read. The docs (`docs/07-crosscutting.md`, marker paragraph) describe the patch check accurately but do not mention this case. The sign-off asked for the patch hash and said to change nothing else, so this may be accepted. Decide whether to accept it, say so in the docs, or also record and compare the head commit.
- `template/src/pdca_harness/flow.py:1717` and `template/src/pdca_harness/flow.py:1594`: `takes` and `_merge_way_out` each keep their own list of the conditions for "may this PR be merged", so the hold advice can drift away from what the walk does. A single helper that returns a reason, or none, could serve both. Cleanup only; I found no case where they disagree today.
- `template/src/pdca_harness/merged.py:228`: `has_patch` is a safe copy of `integrate._has_patch` (`integrate.py:194`), which can still raise on a bad decode. In merge mode `_runnable` never reaches the old one, because `line` is `None`, so nothing breaks. `_has_patch` could call `merged.has_patch` so there is one definition, if the import direction allows it. Cleanup only.
