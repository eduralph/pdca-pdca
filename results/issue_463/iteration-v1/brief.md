## Motivation

`integrate.fold` puts every accepted bundle of a target on one run-scoped line, and the next wave's Do worktrees and PR branches are cut from it (`integrate.py:1-24`). Wave membership, not dependency, decides what a PR sits on. So a bundle with no relation to anything in an earlier wave still gets a PR whose branch carries all of that earlier work. Three costs:

- **The PR misrepresents what it is built on.** A reviewer sees unrelated bundles under it.
- **Closing a PR does not keep its work off the target** (#630). A wave>0 PR opens against the real base (`publish.py:282`) but is cut from the line, so merging it lands every earlier-wave bundle, including one whose own PR the human closed.
- **Every bundle is exposed to the line's failure modes** (re-fold staleness, overlap conflicts, getwyrd/wyrd#675/#676), whether or not it needs a stacked base.

The briefs already declare the relationships; the wave planner uses them to order bundles and the fold ignores them. Independent bundles are the common case, so most PRs should sit on the real base.

## Design

1. **Prerequisite closure.** For each runnable bundle `d` of a wave, its in-run closure is every bundle of this run's drive set, plus every finished id the #646 pre-wave carry carried this run (`_carry_finished`; such ids are by definition not in the drive set, `_finished_named`, `flow.py:956-958`), reachable from `d` by a plain `Depends on` edge, a legacy `Stacks on` edge, or a `Conflicts with` edge to a bundle in an earlier wave, followed transitively. Only accepted bundles whose branch the fold can carry count (`integrate._fold_candidates`); a held one already holds `d` (`_runnable`), and a patchless one (close disposition) contributes nothing. `Depends on (merged)` and out-of-batch prerequisites are not in it: their work is on the real base (#647 holds `d` until it is).
2. **Empty closure → the real base.** `clear_stack_base(d)`: Do, verify and publish all use the target base, as a single-bundle run does.
3. **Non-empty closure → a base of its own.** Fold exactly the closure (in wave, then name order) onto a branch on origin named for `d`, derived from the run's line name so it stays batch-scoped and injective (it must not be a path prefix of the run's line or another ref, since git refuses a branch `x` and `x/y` together; `integration_branch` + a fixed suffix carrying `d`'s id is enough). Record that branch and the tip the fold pushed with `write_stack_base(d, branch, tip)`. Everything downstream (worktree, `$PDCA_VERIFY_BASE`, the PR branch cut from the recorded tip, #593's late-publish refusal) reads the record, so needs no change. Each prerequisite's own branch was itself cut from its closure's base, so the closure's union is what the fold produces; merging a prerequisite already present is skipped by commit (`_merge_published`'s `_in_line` check).
4. **The run's line stays, as a check.** The wave fold onto `pdca-integration/<base>-r<key>` keeps running after each wave, so the re-gate of the combined work (`[driver].regate_between_waves`), #674 same-wave conflict holds, #633/#623 stops and the #646 carry keep their meaning. No bundle is cut from it any more.
5. **A per-bundle base is built once per build of `d`.** It is started fresh from the base as fetched when `d`'s wave is driven, and re-built only when `d` is built again (plain push on creation, force-push on a re-build; see Scope); nothing but `d` is ever cut from it.
6. **#655 judges the base `d` is actually built on.** Today `_runnable` is passed `lines` for every integrated target (`flow.py:2397-2398`) and holds `d` when an out-of-batch prerequisite merged into the base is not on the run's line (`flow.py:735-743`), because `d` would be cut from that line. Under this design no bundle is cut from the run's line, and every base `d` gets (the real base, or its own base started fresh from the fetched base) follows the base. So `_runnable` judges such a prerequisite as for a target with no line (`merged.merged_into` alone) for every `d`; the #655 hold no longer arises in stack mode. Criterion (7) pins it; the #655 tests that expected the hold flip, per criterion (5).

## Alternatives considered

- **Cut a single-prerequisite bundle straight from its prerequisite's published branch** (the old `Stacks on`), and build a merged base only for several prerequisites. Fewer refs, but two code paths, and a branch rewritten after the prerequisite's publish would be cut from unchecked. Rejected for one uniform path through `fold` and its safeguards; noted as an optimisation for later.
- **One base per dependency chain** (connected component) instead of per bundle. Fewer refs, but a component joins bundles that only share a descendant, so `B` would still carry a sibling prerequisite's unrelated work. Rejected: it does not meet the Invariant.
- **Drop the run's line entirely.** Removes the re-gate's subject and the #674 conflict detection between independent bundles, which the human still has to merge. Rejected for now (Open question 2).

## Impact & compatibility

- Most PRs in a batch move to the real base; their diffs and their merge order become independent. The human's "merge the stack bottom-up" now applies per dependency chain, not per run.
- More branches on origin: one per bundle with a non-empty closure, under `pdca-integration/*` (the namespace the docs already ask hosts to allow force-pushes on).
- `docs/07-crosscutting.md`, the `integrate.py` docstring and `09-parallel-lanes.md` change their stated rule ("a later wave's PR carries every earlier-wave branch on the line") to the dependency-scoped one. The vendored-spec change is a human-only Check item (INTEGRATION §4).
- Existing tests that assert a wave>0 bundle is built on the run's line (`test_flow_same_wave_conflict.py` `_built_on_line`, `:169-179`; `test_flow_resume_stack_prereqs.py` `_built`) need the base they assert re-stated in terms of the closure. Each such change is named in `build-notes.md`; none may be weakened to pass.
- No config or template-question change; nothing for `copier update` to migrate.
