# Plan advisory — plan-reviewer — issue 463 / dependency-scoped-stack-bases

The problem framing matches the thread. The issue body says "Wave membership, not dependency, decides what a PR sits on top of", and the #630 comment says "B's PR branch contains no commit of Z's branch … It is true on `main` today". The root cause sits where the brief says: `flow.py:890-910` `_point_at_integration` writes the one run line into every runnable bundle, and it is called at `flow.py:2442`. The cited `path:line`s resolve on the target: `gates.py:570`, `publish.py:647/663/679/690/740`, `integrate.py:99/127`, `waves.py:200-212`, `StackFoldGit` at `test_integrate_stack_bases.py:123`. All five `Depends on` ids exist (`dependency-state.json`: 672, 673, 693, 694, 695, all PLANNED), and the ordering note covers what happens if one ends un-accepted. The findings below are about how far the design reaches and gaps in the success criterion.

- NEEDS-HUMAN — **The design drops the #646 carry's dependents onto the real base, so they no longer get their prerequisite.** Design §1 defines the closure as "every bundle of this run's **drive set** reachable from `d`". But a finished named id is, by definition, *not* in the drive set: `_finished_named` returns ids that are "COMPLETE and not in the drive set" (`flow.py:956-958`). `_carry_finished` folds those ids onto the line before wave 0, so that "wave 0 is pointed at the line" (`flow.py:1045`, `:1118-1121`). Its dependents are exactly the bundles that need that base. Under the brief's rule, D (`Depends on: P`, P carried) has an empty closure, gets `clear_stack_base` (Design §2), and is built without P's work. That breaks #646. The brief puts "the #646 carry's judgment of finished ids" out of scope and parks the carry in Open question 3. It never says that carried finished ids must count as closure members. The planner should either add carried finished ids to the closure definition (Design §1 and the Invariant) or state how D gets P.
- NEEDS-HUMAN — **Criterion (5)'s exception lets the tests that would catch the regression above be rewritten.** (5) allows suites to change "only where they assert today's 'a later wave builds on the whole line'". But `test_flow_resume_stack_prereqs.py:176-186` asserts that a **wave-0** bundle is built on the line (`self.assertEqual(base, self._line(["P", "D"]))`), and so do `:188-204`, `:206-219` and `:303-310` (`self._built("E")[0] == self.line`). These are not "later wave builds on the whole line" assertions. Even so, a per-bundle base under a different branch name (Design §3: "`integration_branch` + a fixed suffix") makes them fail on the name alone. Do will have to edit them, and nothing stops the edit from weakening them. The criterion should require these tests to be re-stated as "D's base contains `fix/P`'s tip" rather than as a branch name. Better still, add a criterion (6): with a clean carried finished prerequisite, its wave-0 dependent's base contains it and excludes an unrelated carried id (the `:290-299` shape).
- NEEDS-HUMAN — **The #655 line check is a design decision handed to Do, and no test pins it.** `_runnable` takes `lines` — "a dependent of it is cut from that line, not from the freshly fetched base (#655) … an out-of-batch prerequisite judged merged into d's base above counts only when the line has its work. Else d is held" (`flow.py:735-743`). Today `lines` is passed for every integrated target (`flow.py:2397-2398`). Under the new model, a bundle with an empty closure is cut from the fresh base, so if `lines` stays as it is, `_runnable` will hold d for a merge its real base already has. Open question 3 only says "Do must keep both checks judging the base `d` is actually built on, and say how in `build-notes.md`". That is behaviour Plan should decide, and none of criteria (1)–(5) would show it going wrong. The planner should either decide it in the brief and add a test case (an out-of-batch merged prerequisite plus an empty closure: d is not held), or list it as an explicit non-goal.
- NEEDS-HUMAN — **"Build that base with the existing fold" hides a change to `integrate.fold`'s API.** `fold` always works out the line it writes from `integration_branch(cfg, base, batch)` (`integrate.py:335-338`). It has no parameter for a different destination. Its "fresh, force-push" versus append-only behaviour, its per-target `integ_lock`, its `carried` bookkeeping and its `{(repo, base): …}` return type (`integrate.py:300-333`) all assume one line per target. Folding a per-bundle closure needs a new destination or key, plus lock and worktree scoping per bundle. That is a second, non-trivial change hidden behind "every fold safeguard applies to it unchanged" (Scope). The brief should name the `fold` signature change and the lock and worktree scoping as part of Scope, so that Check reviews them and does not find them as a surprise. Separately, a re-run of the same batch force-pushes per-bundle bases (Design §5). The existing suite runs against `receive.denyNonFastForwards` (`test_flow_resume_stack_prereqs.py:198`), and the brief does not say how a refused force-push of a per-bundle base behaves.
- NEEDS-HUMAN — **Criterion (1) checks less than the issue's "Done when".** The issue says: "B's PR branch must not contain **any commit** of Z's branch". Criterion (1) checks only `_ancestor(_tip("fix/Z"), _tip("fix/B"))`. The two are equivalent only while Z is a single commit. Either assert on `git rev-list fix/B` against every commit in `base..fix/Z`, or have the test give Z ≥2 commits. Otherwise a partial-carry bug passes the test.
- NEEDS-HUMAN — **Line numbers will drift once the prerequisites land.** The brief is "Verified against … `d6057eb`. Every `path:line` below is on that commit". But it depends on five PLANNED bundles that "edit the fold, the carry or the end of `_drive_and_act`" (Ordering note). Every cited line in `flow.py`/`integrate.py` is likely to move before Do starts. Do should re-verify the citations on the stacked base, and Check should not treat a mismatch with `d6057eb` as a citation failure.
