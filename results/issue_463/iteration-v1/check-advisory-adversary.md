# Adversarial review: issue 463 (dependency-scoped stack bases)

**The evidence holds.** On the patched tree, `tests.test_flow_dependency_scoped_bases` passes 9/9. In the frozen C4 red leg (`gate-logs/C4-verify.log`, `src/` reverted), all 9 fail. Cases (1)–(4), (6), the in-batch `Depends on (merged)` case and the #633 case fail on content: Z's two commits are found on `fix/B`, `fix/C`, `fix/E` and `fix/G`, H's base is not cleared, and D's base holds X. They do not fail on an import. Only the two API tests (the `into` parameter and the `bundle_base` name) go red just because the symbol is missing. The test drives `flow._drive_and_act` through real `integrate.fold` pushes. Its `_publish_bundle` stub copies publish's cut-from-tip rule instead of calling it. The brief asked for exactly that, and the patch changes only comments in `publish.py`'s cut logic. `_built_on`/`_beyond` (`template/tests/test_integrate_stack_bases.py:219-228`) is not a tautology: any non-merge commit beyond `main` and the closure heads fails it.

**The fix: two inputs now stop runs that used to finish.** I reproduced both offline with the new test's own fixture (a subclass of `DependencyScopedBases`). I ran each against the patched `src/`, and against the pre-fix `src/` (from `git archive HEAD`) with the patched tests.

- NEEDS-HUMAN [human] — **An undeclared overlap between bundles in different waves now stops the whole run at the line fold.** `template/src/pdca_harness/integrate.py:1350` (`_held_by`) holds a bundle only if it merges cleanly onto `pre`, the line as its wave found it. Any other conflict reaches the raise at `integrate.py:662`, and `flow.py:2708` stops the run. Before #463, a later-wave bundle was built on that line, so it could not conflict with it. Now most later-wave bundles are built on the real base or a narrow base, so an undeclared file overlap with an unrelated earlier-wave bundle hits this path. Concrete case: `A` and `Z` in wave 0 (Z adds `shared.txt`), `Y` (`Depends on: A`, also adds `shared.txt`), `C` (`Depends on: Y`). **Pre-fix:** A, Z, Y and C all end COMPLETE. **Patched:** `flow: wave 1 did not integrate (issue_Y's branch origin/fix/Y does not merge cleanly onto pdca-integration/main-r… (conflicts in shared.txt) — an undeclared cross-wave overlap …); STOPPING`, and C stays PLANNED. The #674 hold exists for exactly this situation inside one wave. The new model makes it happen across waves too, and there it gets a whole-run stop. The brief's Impact section doesn't mention this. Criterion (5), "nothing else regresses", was only measured on existing suites, and none of them has this case. A human has to choose: extend the #674 hold to bundles that weren't built on the line (hold Y and its dependents, let the run go on), or accept the stop and say so in Impact. `template/PCDA/quality-cycle/09-parallel-lanes.md:69` keeps the old "undeclared overlap STOPs the run" wording, but that sentence now covers far more cases.

- NEEDS-HUMAN [human] — **A base that moves mid-run and clashes with a prerequisite now stops the run before the next wave, including bundles that have nothing to do with the clash.** Every bundle base starts fresh from the base as fetched (`integrate.py:555`, Design §6). `_bundle_bases` raises on the first conflict (`flow.py:934`), and `flow.py:2594-2603` leaves the wave loop. Concrete case: `A` adds `a.txt`, `Z` adds two files, `B` (`Depends on: A`), `W` (`Depends on: Z`). After the line's fold after wave 0, someone pushes a different `a.txt` to `main`. **Pre-fix:** all four COMPLETE (B is built on the line, which does not follow the base). **Patched:** `STOPPING — wave 1 and later waves not run`, and B and W both stay PLANNED, though W never touches `a.txt`. The brief says fold safeguards, conflicts included, apply to bundle bases, so stopping on B may be intended. But a long run on a busy `main` now has a new way to fail, and one base that can't be built takes the whole wave down with it. Decide whether such a base should hold only that bundle and its dependents.

- NEEDS-HUMAN [impl] — **The stop message for a bundle-base conflict gives the wrong fix.** `integrate.py:911-914`'s text, "an undeclared cross-wave overlap; declare the conflict / re-order, then re-run", is reused when a bundle base clashes with the moved base. From the case above: `could not build issue_B's base …-dB from issue_A: issue_A's branch origin/fix/A does not merge cleanly … (conflicts in a.txt) — an undeclared cross-wave overlap; declare the conflict / re-order`. There is no other bundle to declare a conflict with, and a re-run hits the same clash. When `into` is set, tell a clash with `<base_remote>/<base>` (fix: update or rebuild the prerequisite's branch on the new base) apart from a clash between two closure members.

- NEEDS-HUMAN [impl] — **Docs and comments outside the brief's list still state the old rule** ("the next wave builds on the integration branch" / "cuts each dependent off it"): `docs/05-check.md:813-815`, `docs/index.yml:65`, `template/src/pdca_harness/publish.py:42-44`, `gates.py:535-539`, `drift.py:58-62` (drift now reads the bundle's own base, which moves only when that bundle is rebuilt, not "the line as it is NOW"), and the `_adopt_split_children` docstring at `flow.py:1886-1887`. T2 passed because it checks form and links, not content.

- NEEDS-HUMAN [human] — **The vendored spec glossary is stale.** `template/PCDA/quality-cycle/08-glossary.md:286-295` still says stack mode "cuts each dependent off it" and that "a later wave's PR carries every earlier-wave branch on the line". Like the `09-parallel-lanes.md` change, editing it is a human-only item (INTEGRATION §4).

- NEEDS-HUMAN [human] — **A test input changed, not just an assertion.** `template/tests/test_flow_reissue_after_conflict_hold.py:248` makes bundle 21 `Depends on: 12, 10` instead of `12`. Criterion (5) only allows re-stating the checked base in terms of content. I re-ran the original input on the patched code. The run is fine, but 21 is no longer named beside 10, because 21 is no longer built on 10. So the edit keeps the test's premise ("21's change on top of 10's") rather than hiding a failure. Low risk; confirm that build-notes names it.

**Attempted to refute, could not:**
- Closure computation (`flow.py:843-880`): transitive `Depends on`, conflict edges oriented by wave, carried finished ids, patchless members, and members on another target. All behave as the brief says. Dependents of a split parent (`flow.py:1948-1952`) and `Conflicts with` naming a finished id (dropped by `waves.conflict_map`) are limits that predate this patch.
- Name injectivity (`integrate.py:154-164`): `_flatten_base` emits only `-h`/`-s`, so `-d`/`-r` can't collide, and `run_batch` is never None in the flow (`flow.py:2430`).
- #655 removal: every base is either the real base or built fresh from it, so a merged out-of-batch prerequisite is always on it.
- Push rule: a plain push for a new branch, otherwise a push leased on the fetched tip. The test exercises `receive.denyNonFastForwards`.
- #633 on bundle bases: the carried heads are checked and never written (`integrate.py:752`). Covered by a red→green test.
- `test_flow_conflict_partner_hold.py` stubs `_bundle_bases` only where `_fold_lines` is stubbed too (there is no git checkout in that fixture), so the stub hides no behaviour.
- Dry-run, merge mode and `--no-publish`: `build_bases` is False, so every bundle is cleared to the real base, as before.
