# Advisory code review — issue 463 (dependency-scoped stack bases)

Lens: bugs the patch adds, plus reuse / simplification / efficiency. Citations are on the patched target at `$PDCA_TARGET`. I found no logic bug in the closure walk (`_closure`) or the new `fold(into=…)` path. The edges, the wave filter on `Conflicts with`, the exclusion of held bundles, the fresh start from the fetched base, the plain-push-or-leased-force rule and the guard that keeps `carried` unwritten all match the brief. The gate logs agree: C4 passed (red without the fix, green with it), and T3 passed. The findings below are cleanups and one question about how far a failure reaches.

- NEEDS-HUMAN [human] — `template/src/pdca_harness/flow.py:2592-2603`: if `_bundle_bases` fails for any one bundle of a wave, the whole run stops, and that includes bundles in the same wave that need no base of their own. `_bundle_bases` raises on the first failure (`flow.py:913-936`). One case shows the wider reach: an origin fetch that fails for one dependent's base used to hold only that dependent (#655). It now stops the run. The test was flipped from "hold" to "STOPPING" to match (`template/tests/test_flow_merged_prereq_on_line.py:254`). The brief's Scope says a refused push "stops the run as for any fold error", so this may be what was intended. But a line fold fails *after* a wave, while this fails *before* one, for a reason that belongs to a single bundle. Someone should decide whether a per-bundle hold (put `d` in a held set, name it, and go on) is the better result for a fetch failure or a conflict between two of `d`'s prerequisites.
- NEEDS-HUMAN [impl] — `template/src/pdca_harness/merged.py:149` (`merge_and_head`) now has no callers. Its only user was `flow._line_lacks_merge`, which this patch deletes. The module docstring at `merged.py:24-26` still says it "answers the follow-up when the dependent is cut from the run's line", and `merged.py:188` still names it. Remove it, or at least correct the docstring, so the module stops describing #655 behaviour that is gone.
- NEEDS-HUMAN [impl] — `template/src/pdca_harness/flow.py:1886-1887` (`_adopt_split_children` docstring) still says adopted children "are pointed at this run's per-target integration branch by the ordinary `_point_at_integration` call". After #463 they get a base of their own from `_bundle_bases`, or the real base. That sentence states the rule this patch replaces. It is in a docstring the patch did not touch, but this patch is what made it false.
- `template/src/pdca_harness/flow.py:2512-2514`: `list(_carry_finished(...) or ())`. `_carry_finished` always returns a list (`flow.py:1258`). The `or ()` only exists for the test stub `lambda *a, **k: None` at `template/tests/test_flow_out_of_batch_prereq_hold.py:332`. Make that stub return `[]` and drop the guard from production code.
- `template/src/pdca_harness/flow.py:2524-2529`: `build_bases` is the same expression as `hold_unmerged` two lines above it (`do_publish and wave_mode != "merge" and publisher.mode != "stub"`). Name the condition once and use it for both, or set `build_bases = hold_unmerged` with a comment, so the two cannot drift apart.
- `template/src/pdca_harness/flow.py:817-840` (`_point_at_integration`): the flow now passes only name-keyed maps (`flow.py:2607`). The `(repo, base)` tuple-key fallback (`flow.py:835`) is kept only for the older direct tests (`template/tests/test_integrate.py:351`, `template/tests/test_integrate_stack_bases.py:1090`). That is harmless, but a mixed `str | tuple` key type is easy to misuse. Consider moving those tests to name keys and narrowing the signature.
- Efficiency, `template/src/pdca_harness/flow.py:913-936`: each runnable bundle with a non-empty closure gets its own full fold before the wave starts: fetch, worktree reset, merges and push, run one after another under the target lock. Two dependents with the same closure each get their own fold. This matches the brief's Design §3/§5 (one base per bundle), so it is not a defect. On a wide wave of dependents it adds serial git work before lanes fan out, which could be worth noting in the Open questions follow-up.
- `template/src/pdca_harness/integrate.py:729-731`: on a host with `receive.denyNonFastForwards`, a re-issued run of the same batch that drives again a dependent built in an earlier run needs a force-push. A fresh fold always makes new merge commits, so the run stops there. The brief's Scope says this is intended, and the error text gives the fix. I'm noting it because, for a dependent, it is the main difference from the line's carry path, which continues without force.
