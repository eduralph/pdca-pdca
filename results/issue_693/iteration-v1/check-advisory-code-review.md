# Advisory code review — issue 693 (flow run with holds exits 3)

Lenses: correctness bugs the patch adds, plus reuse/simplification. Grounded on `$PDCA_TARGET`.

I found no correctness bug in the production change. The hold collector is filled on every path that reaches the end of `_drive_and_act`, including the `break` paths after a failed fold, re-gate or merge (`template/src/pdca_harness/flow.py:2547-2567` all fall through to `:2582-2584`). Those runs leave later waves unbuilt, so they exit 1 anyway, and 1 still wins over 3 (`template/src/pdca_harness/cli.py:716-718`). The `os.execvpe` keep-awake re-exec (`cli.py:148`) passes the exit code through unchanged, so 3 reaches the shell. The return types of `_drive_and_act`, `flow_ids` and `flow_batch` are unchanged, as the brief pins. Gates C4 (red before the fix, green after) and T3 (2464 driver tests, OK) back this up.

Findings (all minor, none blocking):

- NEEDS-HUMAN [impl] — `template/tests/test_flow_hold_exit_code.py:198-200` (`test_the_single_id_shape_is_unchanged_with_no_hold`): the section header says "the single-id shape reads the same signal", but the test only covers a single id with no hold, so it exits 0 with or without the fix. Nothing tests that `_report_single` passes `holds` into `_results_rc` (`template/src/pdca_harness/cli.py:770`). A one-bundle run cannot hold, because there is no fold after a single wave, so a real-git case may not be reachable. Either rename the header and test so they don't claim more than they check, or add a small unit check that `_report_single` returns 3 when given a non-empty `holds`. (The brief says the test must import only modules, so a direct call to `cli._report_single` with an extra argument would only fail with a TypeError before the fix. That is acceptable for an extra check, but it should not stand in for the required cases.)
- `template/src/pdca_harness/flow.py:2583-2584`: the hold keys strip the prefix with `removeprefix("issue_")`, but the results map built two dozen lines up uses `d.name.replace("issue_", "")` (`flow.py:2570`). For any real id they give the same result, and the exit code only checks whether `holds` is empty, so nothing breaks today. But #695 is meant to reuse this signal by id, and a future id with `issue_` inside it would give keys that don't match. Consider using one spelling. Not filed as NEEDS-HUMAN; it's a nit.
- `template/src/pdca_harness/flow.py:2584`: `held_unpushed` is sorted before it goes in, `held_conflict` is not. `held_conflict` is a dict, so it keeps insertion (fold) order and the output is still deterministic. A bundle can't be in both, because the fold skips `held_unpushed` (`flow.py:2543`), so neither `update` overwrites the other. No action needed; noted only because the two lines look inconsistent.
- `template/tests/test_flow_single_driver.py:806`: changing the stub to `report(results, *rest)` and forwarding `*rest` is the smallest change that keeps that test working with the new `holds` argument. Fine as is.
- Reuse/simplification: nothing to flag. The rule stays in the one `_results_rc` function, the collector is passed straight through without being copied, and the new constant `_RC_HELD` is used in one place only. The new test copies the stubs from `test_flow_same_wave_conflict.py`, which the brief allows explicitly.
