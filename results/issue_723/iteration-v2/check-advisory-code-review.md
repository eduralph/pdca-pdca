# Advisory code review — issue_723 (fold-builds-a-per-bundle-base)

Lens: bugs the patch introduces, plus reuse/simplification. All gates in check-gates.json pass. C4's log shows all 14 new tests error before the fix (`AttributeError: … no attribute 'build_bundle_base'`) and pass after it. I found no bug that blocks the patch. Three of the findings below are small and one is a design trade-off for the human to note. None needs to go back to Do.

- `template/src/pdca_harness/integrate.py:917` — `_foreign_work` subtracts another bundle's head only when that head is an ancestor of the excluded head. This catches the P-cut-from-old-line red case, which the brief's literal `foreign_commit` rule would miss. The cost is a false refusal when an excluded bundle was stacked on a *middle* commit of a member. Example: C was cut from `fix/A` at `a1`, and A later reached `a2`, which the line took and recorded. Then `a1` counts as C's work, and building B from `[A]` refuses. The docstring (`:907`) says this is deliberate: a shared commit counts for both bundles, so the build refuses rather than let foreign work through. Git can't tell the two cases apart, so the trade-off holds. It does mean #724's caller may see refusals on stacked (`Onto branch`) bundles. This is a note for sign-off, not a defect.
- `template/src/pdca_harness/integrate.py:786` — `others` drops an excluded name only if it is in `refs`. `refs` holds only members with a patch and a target, so a no-patch member that the caller also lists in `excluded` is treated as excluded. The docstring says "A name that is also a member's is a member". Names are also compared raw, so `"Z"` and `"issue_Z"` don't match. The harm is small: a no-patch member adds no commits, and a wrong refusal fails safe. Comparing against `{m.name for m in members}`, with names normalized, would match the docstring.
- `template/src/pdca_harness/integrate.py:859-889` — `_member_clash` repeats most of `_held_by` (`:1495`): try the head onto `pre` alone, then each earlier member alone, and fall back to all of them. On a branch started fresh from `base_ref`, `_held_by(wt, branch, head, base_ref, merged_in)` gives the same answer: `None` means a clash with the base, otherwise it returns `(partners, paths)`. `_member_clash` could call it and keep only the message wording. That removes a second copy of the partner-finding rule that could drift from the first. It is a cleanup only; the behavior matches.
- `template/src/pdca_harness/integrate.py:881` — when a member clashes, `_member_clash` runs one trial merge onto the base, then one per earlier member. That is O(members) checkouts and merges, but only on the error path, so it costs nothing in normal use.
- `template/tests/test_integrate_bundle_base.py` (the refused-force-push test, diff lines ~172-183) — the test checks that origin's tip is unchanged and that the message names the branch and the remedy. It doesn't use `_refused`, so no git step is spied, but the unchanged tip is enough to show the push was refused. No action needed.

No correctness bug found in the push rule (`:816`, `:845-846`: plain push to create, `--force-with-lease` on the fetched tip to rebuild), the carried-rewrite check, the missing-excluded-head refusal, or the shared `_owners` factoring. `fold`'s behavior is unchanged by moving `_owners` out.
