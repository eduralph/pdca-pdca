- NEEDS-HUMAN — **Criterion (6) lets a legacy `Stacks on:` member through without checking it, even though the brief says the build never widens.** The brief defines the cut point as "its recorded `stack-base-tip` … when it has a `stack-base` record, and nothing extra otherwise". The fail-closed list only covers three cases: a `stack-base` with no tip, a tip that is not an ancestor of the head, and `Onto branch`. But publish has a fourth way to cut a branch with no `stack-base` record. A hand-declared `Stacks on:` bundle is cut from its parent's PR branch: `stack_branch = wave_base or _stacks_on_branch(cfg, d)` (`publish.py:238`), then `checkout_base = f"origin/{stack_branch}"` (`publish.py:265`). The comment at `publish.py:278` says "Only a hand-declared legacy `Stacks on:` parent (no stack-base) keeps the parent branch". For such a member, "nothing extra" means every commit of the parent's work counts as the member's own work. So building with that member and without its parent quietly brings the parent's work in. That breaks the brief's Invariant ("refused, never silently widened") and SUMMARY §9's "fail closed whenever ownership can't be proven". No test in (6)(a)–(h) covers this. Fix: add "the brief declares `Stacks on:` and the member has no `stack-base`" to the fail-closed list, with its own red test (e). Alternatively, use the parent's published head as the cut point. Either way the brief has to say which.

- NEEDS-HUMAN — **"Nothing extra otherwise" also trusts records that `flow._point_at_integration` deleted.** `flow.py:909-910` calls `publish.clear_stack_base(d)` on any runnable bundle whose target was not integrated this run. That function removes both `stack-base` and `stack-base-tip` (`publish.py:663-670`). A member published from a line in an earlier run, then re-stamped by a run that cleared its record, now looks like a wave-0 bundle. Its whole cut-from-line history then counts as its own work, which is the same fail-open as the finding above. The rule as written cannot tell "never stacked" apart from "stacked, record since cleared". The brief should either say why this cannot happen to a member that `build_bundle_base` is given, or add a cross-check: a member with no record must have `publish.json`'s `base` equal to the target base, or its head minus `<remote>/<base>` must not reach any commit on a `pdca-integration/*` line. A line-based check would clash with the "must not look at `pdca-integration/*` refs" constraint, so the human has to choose.

- NEEDS-HUMAN — **Fail-closed case "a `stack-base` but no tip" cannot be detected with the accessor the brief names.** The brief says the cut point is `publish.read_stack_base_tip` (`publish.py:690`). That function returns `""` both when there is no `stack-base` (`publish.py:695`) and when there is a `stack-base` with no tip. So code that uses only that function treats the fail-closed case as "nothing extra", which is the trusting branch. The brief should tell Do to also call `publish.read_stack_base` (`publish.py:679`) to tell the two apart. Test (6)(e) should use `publish.write_stack_base(d, LINE)` with no tip, the shape at `test_integrate_stack_bases.py:979` and `:1470`, so a version that only calls `read_stack_base_tip` goes red.
