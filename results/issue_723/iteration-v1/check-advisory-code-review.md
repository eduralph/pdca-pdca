# Advisory code review — issue_723 (`build_bundle_base`)

Lens: bugs the patch introduces, plus reuse and simplification. All gates in `check-gates.json` pass. The C4 log shows all 11 new tests red before the fix (`AttributeError`) and green after. Line numbers are on the patched tree at `$PDCA_TARGET`.

## Correctness

- NEEDS-HUMAN [impl] — `template/src/pdca_harness/integrate.py:879` — `_foreign_work` can wrongly refuse a valid build when a member has gained commits since an excluded bundle was cut. It only subtracts a member's head from an excluded bundle's work when that head is an ancestor of the excluded head. Example: excluded `C` is cut from the run's line after wave 0 (so it holds A's old head `a1`), and then `A` gets one more commit (head `a3`, which the fold takes per #593). Now `a3` is not an ancestor of `C`, so A's commits `a1…` count as "C's work". They are on the built branch, so building `B` from `[A]` raises "… is issue_C's work". This is the brief's must-not-raise case (6) with one extra push to A, and A gaining commits is a normal flow. The caller already passes the earlier heads the run recorded for members (`carried`), so a likely fix is to add them to the heads this check can subtract (a carried `a1` *is* an ancestor of `C`). Add a test for this case. I worked this out by reading the code; I did not run it.
- `template/src/pdca_harness/integrate.py:774` — the rewritten-member refusal (criterion 5) reuses `_carried_tips`. Its message (`integrate.py:928`) says that merging would put old and rewritten commits "on `pdca-integration/main-r…`" (the run's line) and tells the user to re-issue the run. In this function the branch being built is the bundle base, not the line. The check is right but the wording points at the wrong branch. You could pass the target branch name in, or catch the error and re-word it.
- `template/src/pdca_harness/integrate.py:806` — when no single member can be blamed, `by` is a comma-joined list of names (`:886-888`). Then `by in refs` is false and the message reads "`A, B`'s branch  brings it in … Rebuild A, B's branch". It has an empty branch slot and a double space. This only affects wording.
- `template/src/pdca_harness/integrate.py:758` — the docstring says a member "on another target than `d` … raises before any git step". But a member with **no** usable target is dropped without a word by `_targeted` (`integrate.py:329-337`, called through `_fold_candidates`). So `members=[A, T]`, where `T` has no target, builds a base without `T` and gives no error. That matches what `fold` does, but here the caller named an exact member set. The brief's rule is "refused, never silently widened", and its spirit suggests narrowing should be refused too. Consider raising for a member that has a patch but no target.
- `template/src/pdca_harness/integrate.py:835` and `:846` — two fallbacks in `_member_clash` return the original `_Conflict` unchanged. One is `head is None`, which can't happen, because `_merge_published` raises `_Conflict` only when a head exists. The other is when `took` is empty but the head still merges onto the base alone, which in practice means `_take_in_base` moved the branch. In that second case the message keeps `_merge_published`'s "declare the conflict / re-order" wording, which the brief's criterion (4) wants avoided when no other bundle is to blame. This is a rare edge case, not a blocker.

## Tests

- NEEDS-HUMAN [impl] — `template/tests/test_integrate_bundle_base.py:182` — the revert-check test only asserts that the bundle base and a fresh run fold hold the same files. In this setup neither path refuses anything: the revert sits below the cut point, which is the limit #673 documents. So the test would still pass if `build_bundle_base` skipped the #623/#673 revert check entirely. It does not show that "a member … which brings in a revert of earlier work raises as the run's fold does" (criterion 4). Either add a case where the check actually fires (for example, an earlier member changes a path and a later member's branch, updated from a base that reverted it, brings the revert in), or record in the build notes that this criterion is covered only by sharing `_merge_published`, not by a test that goes red.
- `template/tests/test_integrate_bundle_base.py:231` — the must-not-raise foreign-ancestry case uses A's head exactly as C saw it. It does not cover the "member moved on" variant described in the first finding, which is why that gap is not caught.

## Reuse / simplification

- Factoring `_owners` out of `fold` (`integrate.py:703-714`, used at `:581` and `:787`) is a straight move with no change in behaviour.
- `_foreign_work` (`integrate.py:855`) is new code rather than a reuse of `foreign_commit` (`integrate.py:265`). That is justified: the brief's literal rule (`--not <base> <member heads>`) would hide the red case, because P's head contains X. The function's docstring explains the change of rule. No duplication worth flagging.
- The push and lock flow matches `fold` (`integrate.py:776-781` and on). The new `--force-with-lease` on rebuild is tighter than `fold`'s bare `--force`, which is good.
