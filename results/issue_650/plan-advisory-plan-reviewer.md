# Plan advisory — issue 650 / merge-mode-reads-head-from-its-own-remote

I checked the root cause, the scope and the target against `$PDCA_TARGET`, and they hold up. `merge._fetch` fetches only `(cfg.base_remote, "origin")` (`merge.py:259`). `_publish_stacked` pushes to `<remote>` (`publish.py:484`) and records `base: "<remote>/<branch>"` (`publish.py:539-547`). The `Onto branch` return at `publish.py:225-228` does come before the #411 guard at `:293`. `integrate` imports only `merged, publish` (`integrate.py:59`), so calling `integrate._published_ref` from `merge` does not create an import cycle. The issue offers two fixes ("fix, one of"). The brief does both, and the human signed off on that, so it is not hidden scope. The faults are in the success criterion and the fixture:

- NEEDS-HUMAN — **The test fixture as written cannot turn green with the fix the brief prescribes.** The success criterion (1) and the repro instruction both give `publish.json` as `{"mode": "stacked", "base": "other/feat", "pr_url": …, "repo": …}`, with no `"branch"` key. The brief also tells Do to read the remote "exactly as `integrate._published_ref` does … reuse it rather than re-parse `publish.json`". But `_published_ref` returns `None` when there is no `branch` (`integrate.py:150-152`: `if not branch or not isinstance(branch, str): return None`). So with this fixture the reused helper finds no remote, `other` is never fetched, and criterion (1) stays RED even with a correct patch. Real records do carry `"branch": branch` (`publish.py:541`). The brief should add `"branch": "feat"` to the fixture in both places.
- NEEDS-HUMAN — **The RED depends on a call shape that the fix has to change.** The repro and criterion (1) call `merge._base_read(cfg, primary, url)`, and the criterion also uses `_wait_for_update`. Neither function can see the bundle or its record today: `_base_read(cfg, repo, pr_url)` (`merge.py:276`), `_wait_for_update(cfg, repo, pr_url, stale, tip, wait_secs)` (`merge.py:303`), and `_fetch(cfg, repo)` (`merge.py:256`). To fetch "the remote the record names", Do has to pass that remote (or `d`) through all three, which changes their signatures. The C4 gate keeps the new test and reverts the production code. On that revert, a test that calls the new signature fails with `TypeError`, not with the "git failed … exited 128" RED the brief promises (brief line "Pre-fix, (1) returns `behind=None` with "git failed""). The brief should do one of two things. Either fix the new parameter shape in advance, for example an optional keyword like `remotes=()` that defaults to today's behaviour so the pre-fix call still runs, or drive the RED through `_merge_one(cfg, d, …)`, whose signature does not change. Otherwise the falsifiability claim cannot be checked.
- NEEDS-HUMAN — **The brief does not say what happens when a `"stacked"` record names no remote.** `_published_ref` returns `None` for a stacked record whose `base` does not end in `/<branch>` (`integrate.py:153-157`). It also returns `None` for an older record with no `branch`. The brief says to keep every read fail-closed (`merge.py:259-262`) but does not say whether this case should quietly fall back to `base_remote`+`origin` (today's behaviour, which then ends in the criterion-(2) message) or refuse up front. The two choices behave differently. If the brief does not decide, Do will choose without telling anyone. The planner should pick one and add a criterion for it.
- NEEDS-HUMAN — **Criterion (3) may not be checkable by the existing tests.** "a `new-pr` / `stacked-pr` record … fetches exactly what it fetches today" is what keeps behaviour unchanged for the common path. But `test_merge.py`'s `_gh` stub makes every `git` call succeed (`test_merge.py:85-99`), and none of the `_base_read`/`_fetch` call sites in that file are named in the brief. "Every existing test still passes" therefore may not prove that the fetch list is unchanged. The brief should require a test that asserts the `git fetch` argv list for a `new-pr` record (`origin` + base remote only, in today's order), or name the existing test that already does.
