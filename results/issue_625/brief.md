## Motivation

The #593 rework (PR #619) was verified with real git against a local bare origin and a stubbed `gh`. Two things were never seen on a real host: what a dependent PR shows after its prerequisites merge (before and after "Update branch"), and the real `gh pr view` answer after a merge and branch delete, which `merged.merged_head` / `merge_and_head` read. Every later stack-mode fix (#647, #655, #729, and now #626) builds on the stub's idea of that answer. A tool answers it again whenever GitHub or the driver changes. The human accepted that scope (a tool rather than a one-off manual run) in this re-plan.

## Design

**Where it runs.** On the existing private repo `eduralph/pdca-stack-sandbox` (default for `--repo`), with the token read from `--token-file` (default `~/.config/pdca/sandbox-gh-token`). Every `gh` and `git` subprocess the tool or the driver starts gets `GH_TOKEN` set to that token, and an ambient `GH_TOKEN`/`GITHUB_TOKEN` or a stored `gh` login is never used. `git` pushes through `gh auth git-credential`, set as the credential helper in the tool's own clone only, so the token is never written into a remote URL, a file in the work dir, or any output. `main` is never pushed to: each run works on its own base branch `live-<UTC stamp>`, created from `main` by `setup`.

**Repo guard (`preflight`, run first by `setup`, `run` and `teardown`).** Refuse, before any network call, a token file that is missing or empty, and a `--repo` whose name is not `pdca-stack-sandbox` and does not contain `sandbox`. Explicitly refuse `eduralph/pdca-harness`. Then `gh api repos/<repo>` must report `private: true` and push permission. From the same response, `allow_merge_commit` and `allow_squash_merge` must both be `true` (the scenario uses both); if either is `false`, refuse before `setup` creates anything. If a field is absent from the response (GitHub may hide merge settings from a token without admin rights), print a warning naming it and continue: a refused merge later is then INCOMPLETE. The guard is what makes the merges below allowed under the STOP exception, so every subcommand that writes to GitHub goes through it.

**Scenario** (all patches fixed and tiny, each on its own file unless stated; every bundle's Slug carries the run stamp so its branch names are unique per run, and a `--keep` run never collides with the next):
- Run 1: `A` and `C` independent (wave 0), `B` `Depends on: A, C` (wave 1). All are accepted and published; the fold builds the line; every PR opens against the run base.
- On GitHub: merge A and C with **merge commits**, then delete their branches (the sandbox does not auto-delete). Record B's PR files. Run `gh pr update-branch` on B and record its files again.
- Record `gh pr view <A> --json state,headRefOid,mergeCommit` after the delete.
- Run 2: `pdca flow A B C D`, naming all four ids, with `D` (`Depends on: B`) added. A, B and C are finished named ids, so the pre-wave carry (`flow._carry_finished`, `template/src/pdca_harness/flow.py:1425`, #646) judges every finished id of the target that can be carried, because D's `Depends on` names B. Its fold reaches A's and C's deleted branches through `integrate._merge_published` → `integrate._gone_branch` (`integrate.py:1350`, :1406). Naming only `D` would not reach that path: B would be out of the batch, and `_runnable` would hold D until B merges (#647). Record run 2's exit code, holds, per-bundle results and stderr, and whether D was built on a line that holds A's and C's work.
- Run 3 (plain-chain control): `P` (wave 0) and `Q` (`Depends on: P`, wave 1) in their own run, with the run base not moved between P's publish and the fold. Merge P with a merge commit, delete its branch, and record Q's PR files WITHOUT "Update branch".
- After the checks above, merge B with a merge commit and record whether A's, B's and C's changes are all on the run base.
- `S` (independent, in run 1 or its own run): **squash**-merged, branch deleted; record `gh pr view <S> --json state,headRefOid,mergeCommit` and whether each oid is on the run base.

**Checks** (`judge`; ids are stable so reports compare across runs):
- `E0` — every PR the runs opened has `baseRefName` equal to the run base (not the integration line, not `main`).
- `E1` — after "Update branch", B's PR files are exactly B's own files. The before-state is recorded and reported, not judged: run 1's line joins two wave-0 branches, so it is not a plain chain, and the docs say it can show more (`docs/07-crosscutting.md:655-661`).
- `E1b` — plain-chain control: after P merges, Q's PR files are exactly Q's own, without "Update branch" (the docs' plain-chain claim, `docs/07-crosscutting.md:654-657`). Together, `E1` and `E1b` judge both halves of the docs' "Files changed" claim.
- `E2` — A after merge + delete: `state` MERGED, `headRefOid` equals the head the run pushed for A, `mergeCommit.oid` present and on the run base.
- `E3` — run 2: exit 0, no holds, D `COMPLETE`; for each of A's and C's branches, stderr holds one of `_gone_branch`'s two SUCCESS messages; D was built on a line that holds A's and C's merged work. The expected one here is "… is gone and its PR merged at … — <line> already carries that commit; skipped." (`integrate.py:1434-1436`): run 2 asks for a different id set, so its line is new, starts fresh off the run base (`integrate.py:596-614`), and the run base already holds A's and C's merge commits. The other success message, "… the merged work reaches <line> through <base>." (`:1509-1511`), is also correct behaviour; record which one appeared. Do not match the bare shared prefix "is gone and its PR merged", which also starts the error messages at :1443, :1449, :1491 and :1503.
- `E4` — S after squash + delete: `mergeCommit.oid` on the run base, `headRefOid` NOT on the run base (the shape #626 assumes).
- `E5` — after B merges, A's, B's and C's changes are all on the run base.

**PASS / FAIL / INCOMPLETE.** A check is INCOMPLETE, never FAIL, when what it needs was not observed. That covers: a missing PR, an unconfirmed branch delete, an `update-branch` or merge refused by GitHub (a token-permission or repo-setting problem, not a driver bug), or a `git merge-base --is-ancestor` that exited with anything but 0 or 1 (0 → on base, 1 → not on base, other → unknown). `run` exits non-zero if anything is incomplete, and `judge` reports it. A FAIL means the observation was complete and disagreed with the expectation, and only a FAIL is filed as a bug. **A driver run is an observation, not a precondition:** once a run's preconditions were observed (for run 2: A and C merged, both deletes confirmed), a non-zero exit or an exception from the driver is the result, and the checks that run feeds (`E3`) are FAIL, with exit code, exception and stderr tail recorded. That is how a driver/host mismatch (for example `merged.merged_head` returning `None` because real GitHub gives no usable `headRefOid`, `merged.py:145-148`, so `_gone_branch` raises at `integrate.py:1428-1432`) is filed as a bug instead of blocking accept. If the human thinks a FAIL was a passing network error, they re-run; that is their call, not the tool's.

**Lessons from earlier builds (must still hold; see `iteration-v1`…`v4`).** Confirm each branch delete (a 422 "Reference does not exist" counts as gone) and record it. Read a PR's file list by polling until two reads in a row agree, recording the read count. Never poll until the list matches the expected value, which would hide a real FAIL. Write `state.json` as soon as `setup` creates the run base branch, before anything else can fail, so `teardown` can always clean up; if `setup` fails later, print the exact `teardown` command. Do may start from `iteration-v4/patch.diff`, but must replace its repo create/delete logic with the sandbox, run-base and token design above.

**Teardown.** Close every still-open PR whose head is a run branch. Delete the run's branches as listed under Citations expected. Leave `main`, the repo and its settings alone. Merged and closed PRs stay in the sandbox's history; GitHub cannot delete them, and they do no harm. Remove the local work dir unless `--keep`.

**Separation.** `run` only records raw data and `judge` only reads it. That keeps the network part thin and makes every expectation testable offline.

**Source of the scenario.** It follows the round-1 reviewer's recipe for #593 (`results/issue_593/iteration-v1/check-review.md:37` in pdca-pdca): A and C in wave 0, B on both; every PR base is the real base (`E0`); merge A and C with merge commits and inspect B's files (`E1`); merge B and confirm all three changes land (`E5`); a merged prerequisite whose branch was deleted, read through the real `gh pr view` (`E2`, `E3`). It adds the plain-chain control (`E1b`) and the squash shape #626 assumes (`E4`). The only change from the recipe is that "the real base" is the run's own `live-<stamp>` branch, so the sandbox's `main` stays clean across runs.

## Alternatives considered

- **Manual run, recorded in a comment** (the issue as written). Answers the question once; nothing reruns it when the driver or GitHub changes.
- **A fresh disposable repo per run** (iterations 1–4). Rejected in this re-plan: the assigned fine-grained token cannot create repos ("Resource not accessible by personal access token" on `createRepository`), and a token that can create and delete repos is more power than this check needs.
- **PRs against the sandbox's `main`**, with unique file names per run. Rejected: `main` grows with every run, and a failed run can leave it in a state the next run trips over.
- **A live test in the suite, skipped without a token.** A skipped test still counts as "ran" for the gate, so it would pass vacuously in CI and on the C4 red leg.
- **Splitting `judge` from the live half.** The human chose not to: slice one alone closes nothing, and the live half would keep the same coverage.

## Impact & compatibility

- New files plus two short doc sections; no driver behaviour changes; nothing reaches rendered instances.
- A live run opens about 7 PRs and a few branches on the private sandbox, then removes the branches; it makes no model calls and creates no repo.

## STOP discipline

Draft only until Check sign-off. Pushing to a feature/draft branch and opening a draft PR MAY happen during the cycle (useful for CI feedback). The PR MUST NOT be marked ready before sign-off accepts.

The tool's own `gh pr ready` / `gh pr merge` calls act only on the private sandbox repo, behind the repo guard, and are started by a human at sign-off. **Do must NOT run `setup`, `run` or `teardown` against GitHub.** Do proves the tool with the offline test only.
