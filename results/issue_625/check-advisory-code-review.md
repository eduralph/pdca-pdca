# Advisory code review — issue 625 / stack-mode-live-github-check-tool (iteration 7)

Lens: bugs the patch introduces, plus reuse / simplification / efficiency. I read the patch against the target at `$PDCA_TARGET` and checked the gate logs. C4 is red without the fix and green with it (22 tests). T3 is green: 2630 tests, 2 skipped.

**Result: no correctness bug found that the builder needs to fix.** This round's change is the separate settle rule for reads taken with no push to the PR. It is consistent between `run` and `judge`, because both call the same `read_off`. The new offline cases cover it from both sides. The notes below are advisory only. None is NEEDS-HUMAN.

- `tools/live/stack_mode_live.py:751-753` and `:1118-1119`: the poll's stop rule and `judge`'s re-check share `read_off` and the `NO_PUSH` set (`:119`). So the live stop rule and the offline verdict cannot drift apart. `judge` re-checks both of the last two reads and does not trust `synced` alone (`:1129`). That closes the iteration-5 gap of a stale read just before the last one.
- `tools/live/stack_mode_live.py:1071-1083`: the no-push rule uses two GraphQL fields, `mergeable` and `potentialMergeCommit.parents`, that no live run has recorded yet. The previous live run recorded REST `mergeable_state`, not these fields. B and Q are still drafts when they are polled. If GitHub does not fill in `potentialMergeCommit` for a draft PR, E1b would end INCOMPLETE again, for a new reason. The offline test cannot show this. Only the sign-off live run can. This is not a defect in the patch. It is a reason to read the first live report's `last read` field closely. If it comes back that way, the fix is to settle on `mergeable` plus head unchanged alone. I did not tag this NEEDS-HUMAN: the live run is already a hard sign-off item.
- `tools/live/stack_mode_live.py:1062-1064`: `read_off` treats an empty file list as "has no file list", which makes the check INCOMPLETE. No PR in this scenario can have an empty diff, so nothing in this run can hit it. I mention it only because a future scenario where a PR's change is already on the base would read INCOMPLETE, not FAIL.
- `tools/live/stack_mode_live.py:760`: `synced` comes from the last read only, while the loop stops on the last two. `judge` re-checks both reads anyway, so the result is right. The field only says more than it proves. Leave it as is, because the iteration-5 carry-forward asks for the flag.
- `tests/test_stack_mode_live_tool.py:171-172`: the passing `_good()` fixture has Q's file list change to `q.txt` while `baseRefOid` stays on the old commit. The sandbox has never shown that shape (it kept the old list). The fixture is meant to show the docs' expected outcome, so this is fine. The realistic shape is covered as a FAIL at `:276-286`.
- `tests/test_stack_mode_live_tool.py:355-457`: the INCOMPLETE cases for the new rule are specific and each one asserts the reason text: stale test merge, `UNKNOWN` mergeability, a stale read before the last one, head moved, a test merge for another head, an observations file from before this rule, and not synced. There is also a negative control (`:367-373`) showing that a test merge on the tip does not replace `baseRefOid` after a push. Both sides of the rule are tested.
- Efficiency: `_compare` (`:792-812`) makes one extra `gh api` call per polled list, about 7 per run, outside the poll loop. That cost is fine.
- Reuse: the tool imports the driver's own helpers instead of copying them: `publish._branch_name`, `integrate.integration_branch`, `cli._results_rc` and `flow.flow_ids`. I found no duplicated logic that an existing helper already covers.
