# Design proposal — issue 625 / stack-mode-live-github-check-tool

> Plan artifact. #625 asks for the #593 stack-mode workflow to be checked once on a real
> GitHub repo. Instead of a one-off manual run, this bundle builds a reusable tool that
> (a) sets up a disposable GitHub repo and the scenario, and (b) checks that stack mode
> behaves as the code and docs say, and writes a report. The live run itself happens at
> Check (Validation), and its report is what closes #625. Do reads ONLY this file.

- **Slug:** stack-mode-live-github-check-tool
- **Kind:** enhancement (design proposal)
- **Goal:** A standalone tool in pdca-harness, `tools/live/stack_mode_live.py` (stdlib only), with three steps: `setup` creates a private disposable GitHub repo (merge commits and squash allowed), pushes a base commit, and prepares a local checkout and bundle root with the scenario's briefs; `run` drives the scenario through the real driver code with the model leaves replaced by fixed patches (no model calls), real `git`, and real `gh`, merges PRs on GitHub, and records every observation as raw data in `observations.json`; `judge` reads `observations.json`, evaluates each named expectation, writes `report.md` + `report.json` (one line per check: id, PASS/FAIL, expected, observed), and exits 0 only if every check passes. `teardown` deletes the repo (`--keep` skips it). `judge` needs no network, so it can be tested offline and re-run on a saved `observations.json`.
- **Success criterion:** Binding (offline, C4): `tests/test_stack_mode_live_tool.py` runs `tools/live/stack_mode_live.py judge` as a subprocess on observation files it writes to a temp dir, and asserts: (1) observations matching every expectation below → exit 0 and `report.json` lists every check id as PASS; (2) observations where A's `gh pr view` after merge + branch delete has no `headRefOid` → non-zero exit and `report.json` marks check `E2` FAIL with the observed value; (3) observations where B's "Files changed" after "Update branch" still lists a file of A's → non-zero exit, `E1` FAIL; (4) a squash-merged S whose `headRefOid` is reported on the base → `E4` FAIL; (5) a PR whose `baseRefName` is the integration line → `E0` FAIL; (6) Q's files after P's merge listing a file of P's → `E1b` FAIL. **Hard sign-off condition (Validation, not optional):** before accept, the human runs `setup`, `run`, `judge`, `teardown` once against GitHub (e.g. from `pdca-pdca try 625`) and attaches `report.md` to the bundle and posts it on #625. This is what #625's "Done when" asks for, and it is the only check of `setup`/`run`/`teardown`. Sign-off records it as a §6 NEEDS-HUMAN item, open until the report is attached. A `run` that cannot drive the flow blocks accept. A FAIL in the report does not block accept: each FAIL is filed as its own bug, and with none, #625 closes.
- **Falsifiability:** The binding criterion goes RED on the C4 gate as it stands: the test calls the tool by path through `subprocess`, never imports it, so with the production change reverted the file is missing, the subprocess exits non-zero, and the test's assertions fail — a test that ran and failed, not an import error (which the gate treats as UNVERIFIABLE, `template/engine/scripts/run-verify.sh`, as `tests/run_root_suite.py:14` cites it). The tool lives outside `tests/` on purpose: the gate counts every `tests/*.py` path (subdirectories included) as a test, so a tool under `tests/` would leave no production change to revert and the gate would exit 77. The live expectations can only go red on real GitHub; that is the Validation run, not C4.

## Motivation

The #593 rework (PR #619) was verified with real git against a local bare origin and a stubbed `gh`. Two things were never seen on a real host: what a dependent PR shows after its prerequisites merge (and after "Update branch"), and the real `gh pr view` answer after a merge and branch delete, which `merged.merged_head` / `merge_and_head` read. Every later stack-mode fix (#647, #655, #729, #626 now) builds on the stub's idea of that answer. A one-off manual check would answer it once; a tool answers it again whenever GitHub or the driver changes.

## Design

**Scenario** (all patches fixed, tiny, on separate files unless stated):
- Run 1: `A` and `C` independent (wave 0), `B` `Depends on: A, C` (wave 1). All accepted and published; the fold builds the line; B's PR is opened against the base.
- On GitHub: merge A and C with **merge commits**, deleting their branches. Record B's PR files. Run `gh pr update-branch` on B; record its files again.
- Record `gh pr view <A> --json state,headRefOid,mergeCommit` after the delete.
- Run 2: `pdca flow A B C D` — all four ids named — with `D` (`Depends on: B`) added. A, B and C are finished named ids, so the pre-wave carry (`flow._carry_finished`, `template/src/pdca_harness/flow.py:1425`, #646) judges every carryable finished id of the target because D's plain `Depends on` names B. Its fold reaches A's and C's deleted branches through `integrate._merge_published` → `integrate._gone_branch` (`integrate.py:1350`, :1406). Naming only `D` would not reach that path: B would be out of batch, and `_runnable` would hold D until B merges (#647). Record its stderr and whether D was built on a line holding A's and C's work.
- Run 3 (plain-chain control): `P` (wave 0) and `Q` (`Depends on: P`, wave 1) in their own run, with the base not moved between P's publish and the fold. Merge P with a merge commit, delete its branch, and record Q's PR files WITHOUT "Update branch".
- After the checks above, merge B with a merge commit and record whether A's, B's and C's changes are all on the base.
- `S` (independent, separate run or same run 1): **squash**-merged, branch deleted; record `gh pr view <S> --json state,headRefOid,mergeCommit` and whether each oid is on the base.

**Checks** (`judge`; ids are stable, so reports compare across runs):
- `E0` — every PR the runs opened has `baseRefName` equal to the real base (no PR against the integration line).
- `E1` — after "Update branch", B's PR files are exactly B's own files. (Before it: recorded, informational — run 1's line has two wave-0 branches, so it is not a plain chain, and the docs say it can show more, docs/07-crosscutting.md:655-661.)
- `E1b` — the plain-chain control: after P merges, Q's PR files are exactly Q's own, with no "Update branch" (the docs' plain-chain claim, docs/07-crosscutting.md:654-657).
- `E2` — A after merge + delete: `state` MERGED, `headRefOid` equals the head the run pushed for A, `mergeCommit.oid` present and on the base.
- `E3` — run 2: the deleted branches were taken through the base (stderr names A's branch as gone and merged), no stop, D built on a line that holds A's and C's merged work.
- `E5` — after B merges, A's, B's and C's changes are all on the base.
- `E4` — S after squash + delete: `mergeCommit.oid` on the base, `headRefOid` NOT on the base (the shape #626 assumes).

**Separation.** `run` only records raw data; `judge` only reads it. That keeps the network part thin and makes every expectation testable offline.

**Safety.** `setup` creates a private repo named `pdca-live-stack-<UTC timestamp>` under the authenticated user unless `--owner` / `--repo` is given, refuses to reuse an existing repo unless `--reuse` is passed, and `teardown` deletes only a repo whose name has that prefix.

**Source of the scenario.** It follows the round-1 reviewer's recipe for #593 (`results/issue_593/iteration-v1/check-review.md:37` in pdca-pdca): A and C in wave 0, B on both; all PR bases are the real base (`E0`); merge A and C with merge commits and inspect B's files (`E1`); merge B and confirm all three changes land (`E5`); a merged prerequisite whose branch was deleted, read through the real `gh pr view --json state` (`E2`, `E3`). It adds the plain-chain control (`E1b`) and the squash shape #626 assumes (`E4`).

## Alternatives considered

- **Manual run, recorded in a comment** (the issue as written). Answers the question once; nothing reruns it when the driver or GitHub changes.
- **A live test in the suite, skipped without a token.** A skipped test still counts as "ran" for the gate, so it would pass vacuously in CI and on the C4 red leg; and the root suite should not create GitHub repos.

## Impact & compatibility

- New files only; no driver behaviour changes; nothing reaches rendered instances.
- A live run creates and deletes one private repo and opens ~5 PRs; it makes no model calls.
