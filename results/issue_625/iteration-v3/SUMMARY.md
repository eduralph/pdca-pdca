- Defect / goal: A standalone tool in pdca-harness, `tools/live/stack_mode_live.py` (stdlib only), with three steps: `setup` creates a private disposable GitHub repo (merge commits and squash allowed), pushes a base commit, and prepares a local checkout and bundle root with the scenario's briefs; `run` drives the scenario through the real driver code with the model leaves replaced by fixed patches (no model calls), real `git`, and real `gh`, merges PRs on GitHub, and records every observation as raw data in `observations.json`; `judge` reads `observations.json`, evaluates each named expectation, writes `report.md` + `report.json` (one line per check: id, PASS/FAIL, expected, observed), and exits 0 only if every check passes. `teardown` deletes the repo (`--keep` skips it). `judge` needs no network, so it can be tested offline and re-run on a saved `observations.json`.

# Advisory code review — issue 625 (stack-mode live GitHub check tool)

Lens: bugs the patch introduces, plus reuse / simplification / efficiency. Advisory only.

Overall: the round-2 fixes are in and look right. `state.json` is now written before any step that can fail (`tools/live/stack_mode_live.py:180-188`). The tri-state `_is_ancestor` (`:269-276`) keeps E4 from passing on a commit git could not judge. Branch deletes are checked and confirmed with `ls-remote` (`:409-431`). E3 now requires rc 0, no holds and D COMPLETE (`:679-684`), and its regexes match the exact success lines at `template/src/pdca_harness/integrate.py:1434-1436` and `:1509-1511` (the `origin/<branch>` ref form comes from `integrate.py:241`). The six offline cases the brief requires are present in `tests/test_stack_mode_live_tool.py:145-187`. I found no blocking correctness bug. Findings:

- NEEDS-HUMAN [impl] — `tools/live/stack_mode_live.py:314-317`: `_files` sleeps a fixed `--settle` (15 s by default) and then reads the PR's file list once. E1 (`:645`) and E1b (`:652`) are judged on that single read. If GitHub has not finished recomputing the diff when the read happens, a stale list containing A's or P's file turns into a FAIL. The brief says each FAIL gets filed as its own driver bug (brief "Success criterion"), so a slow GitHub could produce a false stack-mode bug, most likely on E1b, where there is no "Update branch" step to wait on. Fix: poll a few times until two reads in a row agree (or until the list changes from the pre-merge read), and record the read count or elapsed time in the observations. Do not poll until the list matches the expected value, because that would hide a real FAIL.
- `tools/live/stack_mode_live.py:420-429`: the confirm loop sleeps after its fifth and last failed `ls-remote`, then gives up. That adds up to 10 s of dead wait before the `Incomplete` raise. Minor: skip the sleep on the last attempt (same pattern as `_merge` at `:398-399`).
- NEEDS-HUMAN [human] — `tools/live/stack_mode_live.py:391` and `:395`: `run` calls `gh pr ready` and `gh pr merge`. The repo's `AGENTS.md` ("STOP discipline") forbids an agent from doing either "no path, regardless". These calls only touch the disposable `pdca-live-stack-*` repo, and the brief has a human run the tool, so this is not a real breach. Still, if an agent ever runs the tool (for example from `pdca-pdca try 625`), it would break that rule as written. The maintainer should decide whether `AGENTS.md` (or the CONTRIBUTING section this patch adds) needs a line saying the rule covers the project's own PRs and not this tool's throwaway repo, or that only a human may run `run`.

No duplicated logic: the tool uses the driver's own `cli._results_rc`, `publish._publish_record`, `publish.read_stack_base_tip` and `signoff.record` instead of copying them, and keeps the test fixture out as the brief asks. `run`/`setup`/`teardown` are not covered offline beyond the setup/teardown failure paths. The brief expects that (the live run is the sign-off condition), so I am not filing it as a defect.
