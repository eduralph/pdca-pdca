# Advisory code review — issue 625 / stack-mode-live-github-check-tool

Scope: `patch.diff` (new `tools/live/stack_mode_live.py`, new `tests/test_stack_mode_live_tool.py`, a `CONTRIBUTING.md` section). I checked the driver calls the tool makes against the target source (`flow.flow_ids` at `template/src/pdca_harness/flow.py:3370`, `cli._results_rc` at `cli.py:707`, `publish._publish_record` / `read_stack_base_tip` / `COMMIT_MSG` / `PR_BODY` at `publish.py:644,698,40-41`, the `Config` required fields at `config.py:109-119`, and the `integrate:` lines the judge matches at `integrate.py:1434-1436,1509-1511`). The names, signatures and message wording all match. The round-1 findings are addressed: `_is_ancestor` returns None for exit codes other than 0/1, the branch delete is checked and recorded, and E3 now checks rc, holds and D's COMPLETE. The C4 log shows red without the tool and green with it, and the T3 log shows all 12 new tests passing. I could not run `setup`/`run`/`teardown` here (they need the network). That is the brief's sign-off Validation step.

- NEEDS-HUMAN [impl] — `tools/live/stack_mode_live.py:128-162`: `setup` can leave a repo behind. It creates the GitHub repo at :129, but writes `state.json` only at :160, after the `gh api` PATCH, the local `git` steps and the `git push` at :151. If any of those fail (the most likely one is the push, through the gh credential helper), the private repo already exists but no `state.json` records it. `teardown` then exits at `_state` (:92). Re-running `setup` in the same workdir is refused (:110), and a fresh workdir creates a new timestamped repo, so the first one is orphaned and has to be deleted by hand. Fix: write `state.json` (or at least `repo`) right after the create, before anything that can fail. Or wrap the rest of `setup` so a failure prints the repo name and the `gh repo delete` command.
- NEEDS-HUMAN [human] — `tools/live/stack_mode_live.py:328,331`: the tool runs `gh pr ready` and `gh pr merge`. `AGENTS.md` ("STOP discipline") says an agent must never merge a PR or mark one ready, "no path". The brief makes merging on the disposable repo part of the design and has the human run the tool. But the brief also suggests running it from `pdca-pdca try 625`, so an agent might start it. The maintainer should decide whether that counts as an allowed exception (disposable `pdca-live-stack-*` repo only) and, if so, say it in `CONTRIBUTING.md` or `AGENTS.md`. Otherwise the tool should refuse to run unless a human starts it.
- `tools/live/stack_mode_live.py:330-334`: when the merge is still refused after the 6th try, the loop sleeps 30 s before giving up. A small waste: skip the sleep on the last attempt. Not worth a NEEDS-HUMAN.
- `tests/test_stack_mode_live_tool.py:132-147` (`_fails`): it checks `passed` is false but never checks that `result` is `"FAIL"` rather than `"INCOMPLETE"` for a finished run. A bug that sent every failing run to INCOMPLETE would still pass these cases. One `assertEqual(data["result"], "FAIL")` in the finished-run cases would close that gap. There is also no case where run 2's stderr has neither "gone and merged" line, which is the plain path for `_gone_and_merged` returning None (:524-542). The refused-carry case covers that path only indirectly. Minor, so no tag.

Reuse/simplification: no problems. `_run_problems` is shared between `_require` (run time) and `_run_ok` (judge), so the run-time stop rule and the judge's "not observed" rule cannot drift apart. The tool reuses the driver's own readers (`publish._publish_record`, `read_stack_base_tip`, `cli._results_rc`) and does not copy them.
