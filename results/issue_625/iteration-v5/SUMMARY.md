# Result — issue 625 / stack-mode-live-github-check-tool

## 1. Spec (from brief.md)              ← Check verifies against THIS
- Defect / goal: A standalone tool in pdca-harness, `tools/live/stack_mode_live.py` (stdlib only), with five subcommands. `preflight` checks the token file, the repo guard, that the repo is private and pushable, and that merge commits and squash merges are both allowed, and writes nothing. `setup` runs `preflight`, then creates a run-scoped base branch `live-<UTC stamp>` from the sandbox's `main`, and prepares a local clone and bundle root holding the scenario's briefs. `run` drives the scenario through the real driver code, with the model leaves replaced by fixed patches (no model calls), real `git` and real `gh`. It exits 0 only if every check passes. `teardown` closes the run's open PRs and deletes the run's branches on the sandbox (`--keep` skips this). It never deletes the repo, never touches `main`, and never changes repo settings. `judge` needs no network, so it can be tested offline and re-run on a saved `observations.json`. **Departure from #625's wording:** #625 asks for "a disposable GitHub repo". This brief uses a persistent private sandbox instead, with a fresh `live-<stamp>` base branch per run as the disposable part (the token cannot create repos; see Alternatives). # Advisory code review — issue 625 / stack-mode-live-github-check-tool

Lens: bugs the patch adds, plus reuse and simplification. I read the new tool `tools/live/stack_mode_live.py`, the new test `tests/test_stack_mode_live_tool.py` and the two doc edits against `$PDCA_TARGET`. I also checked the driver functions the tool calls (`flow.flow_ids`, `cli._results_rc`, `publish._branch_name` / `_resolve_target` / `_publish_record` / `read_stack_base_tip`, `integrate.integration_branch`, `signoff.record`, `state.state`). Their signatures match how the tool calls them. The two `_gone_branch` success messages the E3 regex matches (`tools/live/stack_mode_live.py:1012-1016`) match `template/src/pdca_harness/integrate.py:1434-1436` and `:1509-1511` word for word, em dash included. The offline gates are green (C4 red→green, T3 suite OK). One finding needs the builder to change code; the rest are small cleanups.

- NEEDS-HUMAN [impl] — `judge` ignores the `synced` flag that `run` records, so a stale file list counts as settled. `Live._files` stops polling only when two reads agree **and** both show the PR on the base tip just fetched and on the expected head, or when `--settle-max` runs out (`tools/live/stack_mode_live.py:741-748`). It records `synced: false` when it stopped on the timeout. `settled_files` checks only that the last two reads agree (`tools/live/stack_mode_live.py:985-989`). It copies `synced` into `seen` but never uses it. So if GitHub keeps returning its pre-merge or pre-update answer for the whole window (two equal reads at the old `baseRefOid`/`headRefOid`), E1 or E1b is judged on stale data. That most likely means a false FAIL, which the brief says gets filed as a driver bug, when it should be INCOMPLETE. The module docstring itself lists "a file list that never settled" as INCOMPLETE (`:44-46`). Fix: in `settled_files`, return INCOMPLETE when `rec.get("synced") is not True` (or check `baseRefOid`/`headRefOid` of the last two reads against `rec["expect"]`). The test cannot catch this today because `_reads` always writes `"synced": True` (`tests/test_stack_mode_live_tool.py:68-71`). Add a case to criterion (7) where the reads agree but `synced` is false, expecting E1 or E1b INCOMPLETE.
- Reuse: `cmd_teardown` re-implements the delete-a-branch-and-treat-422-as-gone logic (`tools/live/stack_mode_live.py:1373-1382`) that `Live._delete_branch` already has (`:669-679`). The two can drift: `run`'s copy retries three times, teardown's copy does not retry. A small module-level `delete_ref(repo, branch) -> (ok, how)` used by both would remove the duplicate. Not a bug.
- Simplification: in `guard`, `name.lower() != SANDBOX_NAME and "sandbox" not in name.lower()` (`tools/live/stack_mode_live.py:122`) reduces to `"sandbox" not in name.lower()`, because `SANDBOX_NAME` contains "sandbox". The first clause is dead. Cosmetic.
- Minor robustness: in `cmd_run`, `Live(...)` is built outside the `try` (`tools/live/stack_mode_live.py:892`). An import failure in `_driver()` or a `make_config` error therefore exits with a raw traceback and writes no `observations.json`. Nothing on GitHub has been touched by then, so this is harmless. It is just less clear than the "did not finish … teardown with" message `setup` prints (`:356-360`).
- Minor efficiency: `_said(r)` runs up to three times on the same result in `Live._delete_branch` (`tools/live/stack_mode_live.py:671-679`). `settled_files` re-sorts lists that `_files` already sorted (`:986`, `:989` vs `:735`). Negligible cost. Listed only as simplification.

Not filed: `setup` / `run` / `teardown` against real GitHub have no offline coverage beyond the guard and the teardown argv. That is by design: the brief makes the live run a separate sign-off item, so I don't repeat it here.
